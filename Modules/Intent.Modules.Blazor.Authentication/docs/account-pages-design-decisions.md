# Account Pages, Blazor Styling, And AI Tasks

This note records the current working understanding from the Blazor authentication, standard Blazor, MudBlazor, and AI task investigation.

The Intent MCP transport was unavailable during the latest update, so this is based on local source inspection rather than live designer state.

## Account Page Styling Decision

The account pages should be generated in two design-system-specific variants:

- **Standard Blazor variant** - emitted when `Intent.Blazor.Components.MudBlazor` is not installed.
- **MudBlazor variant** - emitted when `Intent.Blazor.Components.MudBlazor` is installed.

The reason for the split is visual consistency. A generated application that has the MudBlazor module installed is expected to look like a MudBlazor application. Standard account-page markup can compile and function inside that application, but it is not safe to assume that it will visually match the rest of the MudBlazor UI without MudBlazor-specific markup and styling.

For standard Blazor, Bootstrap-compatible classes and selectors are acceptable because the base Blazor server template links Bootstrap. The standard AI skill should not forbid Bootstrap outright. It should instead avoid MudBlazor selectors, MudBlazor CSS variables, and MudBlazor component assumptions.

For MudBlazor, the account pages should use MudBlazor components and the MudBlazor CSS bridge/overrides generated by the MudBlazor module.

## CSS And Theme Ownership

The base Blazor module owns the standard Blazor theme skill:

- `Intent.Blazor.Templates.AI.BlazorUxThemeSyncSkillTemplate`
- role `AI.Context.Skills`
- intended for generated Blazor applications without MudBlazor installed
- guarded so it does not apply when `Intent.Blazor.Components.MudBlazor` is installed

The MudBlazor module owns the MudBlazor theme and implementation skills:

- MudBlazor general AI instructions
- MudBlazor theme sync skill
- MudBlazor page/dialog implementation skills
- MudBlazor sample files used by those skills

The recent module move places the MudBlazor page/dialog skills and sample static content under `Intent.Blazor.Components.MudBlazor` instead of the base `Intent.Blazor` module. That keeps MudBlazor-specific AI context out of a standard Blazor-only installation.

## AI Task Creation Paths

There are two different AI task mechanisms in play:

1. `Intent.AI.Blazor` adds a designer context-menu action named `Generate Component`. Its script calls `createAICodingTask(...)` for the selected UI component and includes the component's associated files. This is a manual designer action.
2. `AITasksFactoryExtension` registers an `IAITaskProvider` with `application.AITaskManager` during Software Factory execution. That provider inspects generated changes and creates automatic AI tasks for newly created or overwritten Blazor component code-behind templates.

Those mechanisms are complementary, not duplicates. `Intent.AI.Blazor` can create a manual task from the designer without the Software Factory task provider. The Software Factory task provider can create automatic follow-up tasks without the user using the designer context menu.

`TemplateAITask` is the small helper implementation of `IAITask` used by the Software Factory task provider. It records the owning template, related templates, files to include, title, instructions, and applicability-to-change logic.

## Current Task-Provider Ownership Question

The base `Intent.Blazor` module currently still contains:

- `FactoryExtensions/AITasksFactoryExtension.cs`
- `FactoryExtensions/TemplateAITask.cs`
- the `Intent.Blazor.AITasksFactoryExtension` imodspec registration

This means any application with `Intent.Blazor` installed can register automatic "Implement Blazor Component" tasks during Software Factory execution.

That placement only remains clean if the automatic task is truly design-system-neutral, or if the base Blazor module also owns enough standard Blazor implementation skills for the task to be useful in a non-MudBlazor application.

After moving the MudBlazor implementation skills into `Intent.Blazor.Components.MudBlazor`, the base module has standard theme-sync context but does not yet have standard page/dialog implementation skills equivalent to the MudBlazor ones. That makes the current base task provider potentially too broad: it can ask the AI to implement a component using "appropriate skill(s)" even when the only available base skill is theme synchronization.

Moving the task provider into `Intent.Blazor.Components.MudBlazor` would make automatic component implementation tasks appear only when the MudBlazor-specific implementation skills are also installed. This is a containment fix, not a fundamental requirement.

An alternative is to keep the task provider in `Intent.Blazor`, but then the base module should also provide standard Blazor page/dialog implementation skills and should keep the task prompt explicitly design-system-neutral. In that model, MudBlazor contributes additional MudBlazor-specific skills and instructions, while the common task provider remains in base Blazor.

The key rule is: an `AI.Context.Skills` template supplies instructions, but it does not itself create AI tasks. Some module still needs either a designer script like `Intent.AI.Blazor` or an `IAITaskProvider` factory extension if tasks should be created automatically.

## Working Recommendation

Do not move `AITasksFactoryExtension` and `TemplateAITask` just because MudBlazor skills moved.

Move them only if the desired behavior is:

- automatic component implementation tasks should exist only for MudBlazor applications for now
- standard Blazor applications should not receive automatic component implementation tasks until standard page/dialog implementation skills exist

Keep them in `Intent.Blazor` if the desired behavior is:

- all Blazor applications should receive automatic component implementation tasks
- standard Blazor implementation skills will be added alongside the standard theme skill
- MudBlazor remains an additive provider of MudBlazor-specific skills and instructions

`Intent.AI.Blazor` does not remove the need for `AITasksFactoryExtension` if automatic Software Factory-created tasks are required. It provides a manual designer action. `Intent.Blazor.Components.MudBlazor` does not remove the need either unless it also registers its own `IAITaskProvider` or relies only on manual task creation.
