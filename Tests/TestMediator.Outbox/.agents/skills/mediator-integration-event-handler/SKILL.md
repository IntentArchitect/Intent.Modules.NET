# Mediator Integration Event Handler

Integration event handlers are generated by Eventing.Contracts, not by the Mediator module. Their handler class implements `IIntegrationEventHandler<TMessage>` and has a `HandleAsync(TMessage message, CancellationToken cancellationToken = default)` method for each subscription. Eventing.Contracts writes the body only for the actions it understands, and it stops short for three kinds of handler. You finish those.

## What the generator does and does not do

For each action modelled under a subscription on the handler:

- Publish Integration Event and Send Integration Command: generated as `_messageBus.Publish(...)` / `_messageBus.Send(...)`. The message is only populated when the action has field mappings. Without mappings the generator emits `new MessageName { }` with an empty initializer: it compiles and silently sends an empty message.
- Invoke (a modelled command): skipped silently. Nothing is generated for it.
- As soon as the generator writes anything, it marks `HandleAsync` with `[IntentManaged(Mode.Fully, Body = Mode.Fully)]`, so every later regeneration overwrites the body.
- A handler with no generated action stays a stub that throws `NotImplementedException`.

## The three cases you finish

1. Invoke only: the body is a stub. Nothing was generated.
2. Mixed: the body holds a generated Publish or Send, plus an Invoke the generator skipped.
3. Unmapped Publish or Send: the generated message is an empty initializer.

In all three cases, take the whole body over. Do not patch around the generated lines.

## Finding the handlers to finish

Nothing raises a task or a reminder. A handler needs finishing when either of these holds for any of its `HandleAsync` methods:

- the body still throws `NotImplementedException`; or
- the method is not marked `Body = Mode.Ignore`, and the subscription behind it has an Invoke, or a Publish or Send without field mappings. Check the subscription's actions and their mappings with `getElementDetails`.

Check every handler under `IntegrationEvents/EventHandlers` this way after a Software Factory run that touched integration event handlers, and check a handler whenever you change its subscriptions or actions in the designer. Adding an Invoke changes no generated file, so the file alone will not show it.

## Core rules

- ALWAYS put `[IntentManaged(Mode.Fully, Body = Mode.Ignore)]` on the `HandleAsync` method you are finishing. Without it the next Software Factory run overwrites your work.
- Write the WHOLE body of `HandleAsync`, including the actions the generator did produce. Rewrite them in your own body so one method holds the complete flow in model order.
- NEVER change the name, return type or parameters of `HandleAsync`. They are generated.
- Keep the actions in the order the model lists them.
- Inject only dependencies from the Domain or Application layers. Add them to the handler constructor (the constructor is `Mode.Merge`, so your additions are kept).
- Never introduce infrastructure packages or types into the handler.
- Thread the `cancellationToken` through every async call.

## Read the model first

1. Load the `exploring-the-model` skill.
2. Call `run_designer_query` with `getElementDetails` on the Integration Event Handler in the Services designer.
3. For each subscription on the handler, list the actions under it in the order the designer shows them. A handler with several subscriptions has one `HandleAsync` per subscription, each with its own actions.

Field mappings are not modelled for the interactions you finish. Decide which property of the outgoing message or command comes from which property of the incoming message by name and meaning, and by searching existing code that does the same.

## Writing the body

- Invoke a command: inject `Mediator.ISender`, then dispatch the command with `await _sender.Send(new TheCommand(...), cancellationToken);`. Build the command from the incoming `message`. The command goes through the full Mediator pipeline, so it is validated and saved by its own handler. Do not call its handler directly.
- Publish Integration Event: `_messageBus.Publish(new TheEvent { ... });` with every property populated from the incoming message, a value returned by an earlier step, or a clearly derived value.
- Send Integration Command: `_messageBus.Send(new TheCommand { ... });` populated the same way.
- Use the message bus interface that is already injected into the handler. If you rewrite the body, keep that field and use it. If it is not there, find the application's message bus interface by searching the code (usually `IMessageBus`) and inject it.
- NEVER flush or dispatch the bus yourself. The Mediator pipeline flushes buffered messages after the unit of work. Only call `Publish` or `Send`.
- An invoked command that itself publishes messages is fine. The messages are flushed once, after the command's unit of work.
- Do not call `SaveChangesAsync` in the handler for any of this. The invoked command saves its own work.

Example shape for a handler that invokes a command and then publishes an event:

```csharp
[IntentManaged(Mode.Fully, Body = Mode.Ignore)]
public async Task HandleAsync(OrderCreatedEvent message, CancellationToken cancellationToken = default)
{
    await _sender.Send(new RequestShipmentCommand(orderId: message.OrderId), cancellationToken);

    _messageBus.Publish(new OrderAcknowledgedEvent
    {
        OrderId = message.OrderId
    });
}
```

## Keep the handler in step with the model

Once you have taken the body over, Publish and Send changes on this handler no longer regenerate. Nothing will tell you the model moved. Whenever you implement OR revisit this handler for any reason, re-read its subscriptions and actions with `getElementDetails`. If the model changed since the body was written (an action added, removed, reordered or retargeted), update the body in the same piece of work.

## Workflow

1. Open the handler file and find its `HandleAsync` method or methods.
2. Read the model as described above.
3. Search for code usages of similar integration event handlers, the target command, and the message types.
4. Add constructor dependencies (`ISender`, the message bus) if they are missing.
5. Write the whole body, in model order, and mark `HandleAsync` with `[IntentManaged(Mode.Fully, Body = Mode.Ignore)]`.
6. Verify every property of every outgoing message is populated, and nothing is an empty initializer.

## Output expectations

Produce a concrete code update that:

- implements every modelled action on every subscription, in model order
- takes `HandleAsync` over with `[IntentManaged(Mode.Fully, Body = Mode.Ignore)]`
- sends invoked commands through `ISender`
- populates every outgoing message from the incoming message
- keeps unrelated refactors out of scope

## Review checklist

Before finishing, check that:

- `HandleAsync` carries `Body = Mode.Ignore` and no `NotImplementedException` remains
- every Invoke is implemented and goes through `ISender`
- no Publish or Send is sent with an empty initializer
- the bus is never flushed from the handler
- the actions follow the model's order
- the code path is cancellation-aware and async-safe
