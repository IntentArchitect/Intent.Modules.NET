# CONTEXT — Intent.Modules.NetTopologySuite

## Multi-host safety (converted)

This module previously broke any application with more than one ASP.NET Core host project (see `Intent.Modules.AspNetCore/CONTEXT.md` for the general invariant and the host-scoping overload matrix). A second host made every host-scoped template lookup in this module throw `More than one instance of template X was found` instead of generating, because each site used a singular `FindTemplateInstance(...)` — or, worse, the `TemplateDependency.OnTemplate(...)` form, which looks host-scoped but silently degrades to an unscoped `SingleOrDefault()` (see the "Never reach for the `TemplateDependency` overloads" trap documented in `AspNetCore/CONTEXT.md`).

Four sites were converted, all following the canonical pattern (`FindTemplateInstances<T>(...)` + `foreach`, filtered where needed by `OutputTarget.GetProject().HasMicrosoftNetSdkWeb()`):

1. **`FactoryExtensions/StartupExtension.cs`** — iterates `IAppStartupTemplate` instances, filtered to web hosts. Also gained a `configure-services-controllers-generic` guard (the same one `AspNetCore.Controllers/JsonOptionsExtension.cs` uses) so a web host with no controllers configured doesn't get an `.AddJsonOptions()` call injected against a statement that was never emitted.
2. **`FactoryExtensions/SwaggerConfigExtension.cs`** — iterates `Distribution.SwashbuckleConfiguration` instances via the **string** overload. No host filter needed: only hosts that actually have a Swashbuckle configuration instance exist to iterate.
3. **`FactoryExtensions/SerilogStartupConfigurationExtension.cs`** — iterates `App.Program` instances, with a per-host existence check (`OutputTarget.FindTemplateInstance(GeoDestructureSerilogPolicyTemplate.TemplateId) is null`) before referencing the destructuring policy type, so a host whose project never received the policy class (see `GeoDestructureSerilogPolicyTemplate.CanRunTemplate` — gated on the Serilog module being installed, not on being a web host) doesn't get a `Destructure.With(...)` call referencing a type that doesn't exist in that project.
4. **`Templates/GeoJsonSchemaSwaggerFilter/GeoJsonSchemaSwaggerFilterTemplatePartial.cs`** — `CanRunTemplate()` changed from `ExecutionContext.FindTemplateInstance(TemplateDependency.OnTemplate(...)) != null` to `OutputTarget.FindTemplateInstance<T>("Distribution.SwashbuckleConfiguration") != null`. This was the one site using both anti-patterns at once (singular lookup + the `TemplateDependency` trap). Fixing it also means the filter is now generated only into projects that actually configure Swashbuckle, rather than into every host regardless.

Cross-template type name resolution (`template.GetGeoJsonSchemaSwaggerFilterName()`, `template.GetGeoDestructureSerilogPolicyName()`, both in `Templates/TemplateExtensions.cs`) needed no changes — `GetTypeName`/`UseType` already resolve via `GetTemplate`, which tries `accessibleTo: OutputTarget` first (see `AspNetCore/CONTEXT.md` — "Cross-template type references are already host-correct").

Reproduced and confirmed fixed: installing this module into a WebAndWorker-shaped application (multiple ASP.NET Core hosts sharing one Domain package) threw `More than one instance of template X was found` before the fix and completes Software Factory generation cleanly after it.

## SDK package floor — `HasMicrosoftNetSdkWeb()` requires a newer `Intent.Modules.Common.CSharp`

The `HasMicrosoftNetSdkWeb()` extension (from `Intent.Modules.VisualStudio.Projects.Api`, used by `StartupExtension`) did not bind against this module's previous `Intent.Modules.Common` 3.7.2 / `Intent.Modules.Common.CSharp` 3.8.1 package floors — `ICSharpProject` did not expose it, even though the `Intent.Modules.VisualStudio.Projects` package version (3.7.1) was already high enough and already referenced. Bumped both floors to match `Intent.Modules.AspNetCore.Logging.Serilog`'s already-working combination: `Intent.Modules.Common` 3.11.0, `Intent.Modules.Common.CSharp` 3.10.10, `Intent.SoftwareFactory.SDK` 3.14.0 (the SDK bump was needed to restore a consistent build; not confirmed as the load-bearing one). The `.imodspec` `<dependency>` floors for `Intent.Common` / `Intent.Common.CSharp` were raised to match — see the "Dependency Floors" rule in `EntityFrameworkCore/CONTEXT.md` for why an API-surface change requires the floor to move with it.

The `Intent.SoftwareFactory.SDK` bump raised the module's minimum required Intent Architect client version — the Software Factory's own regeneration refused to run (`FriendlyException`) until `<supportedClientVersions>`'s lower bound was raised from `4.4.0-a` to `5.0.0-a` to match. The regeneration failure stated the required minimum outright; no external lookup was needed.

## Close-out — version 1.0.5-pre.0

Version bumped via the Module Builder designer (`Module Settings` → `Version`) and regenerated through the Software Factory, not hand-edited — `1.0.4` → `1.0.5-pre.0`. No module in this repo depends on `Intent.NetTopologySuite` (`grep -r 'dependency id="Intent.NetTopologySuite"'` across `Modules/` returns nothing) — nothing to propagate.

`Intent.Modules.EntityFrameworkCore` was initially bumped alongside it for the `ConfigureNetTopologySuite` gate change below, then reverted back to its unmodified version once that change was itself reverted — see the next section for why. It carries no functional change in this line of work.

## Per-DbContext geometry detection — tried, fixed, then reverted (decision, not a bug)

`Intent.Modules.EntityFrameworkCore/FactoryExtensions/DependencyInjectionExtension.ConfigureNetTopologySuite` originally gated `.UseNetTopologySuite()` purely on `dbContextInstance.IsApplicationDbContext` — always on for the primary DbContext when this module is installed, never on for a secondary DbContext even if _that_ one is the one mapping geometry.

A fix was attempted: add `NetTopologySuiteHelper.MapsGeometryTypes`, matching `AttributeModel.TypeReference.Element.Name` against a hardcoded `"Point"`/`"MultiPolygon"` set, and gate on `IsInstalled && MapsGeometryTypes` instead. That surfaced a real bug along the way — the first version iterated `dbContextInstance.DomainPackageModel.Classes`, which (confirmed by decompiling `Intent.Modules.Modelers.Domain.dll`) calls `GetElementsOfType(..., recursiveSearch: false)` and never descends into `Folder` elements, so a geometry entity organised into a folder (the normal case) was invisible to it — fixed by going through `executionContext.MetadataManager.Domain(...).GetClassModels()` filtered by package instead, the same recursive pattern used elsewhere in this module (`LazyLoadingProxyFactoryExtension.cs`, `EntityTypeConfigurationTemplateRegistration.cs`). **Lesson kept for next time: never use `DomainPackageModel.Classes`/`.Types`/etc. to mean "every X in this package" — those are shallow.**

Even fixed, the approach was rejected on a different ground: `MapsGeometryTypes`' hardcoded name list only recognizes the two Type-Definitions this module ships. A DbContext using some other NetTopologySuite geometry type this module doesn't model (`LineString`, `Polygon`, `MultiPoint`, `GeometryCollection`, ...) would silently lose `.UseNetTopologySuite()` on the primary DbContext — a regression versus the always-on-for-primary behaviour that shipped before. Explicit decision: **stick to `IsApplicationDbContext` only** — accept that a secondary DbContext mapping geometry won't get NTS support — until there's a concrete, reported case that needs it. `NetTopologySuiteHelper` is back to just `IsInstalled`; `MapsGeometryTypes` was removed rather than left unused.
