# Context: Intent.Domain.Guardrails.Contracts

## Purpose

Guards a brownfield codebase's domain layer. Each Domain designer element that was imported from existing code is merged back into its existing file, so every modelled type and member keeps existing. The module must never implement behaviour or rewrite a developer's code.

## Architectural Decisions

- **Merge directives: plain `Mode.Merge` plus a constructor/method default (user decision).** Every contract file carries exactly these two lines, written by `ContractBuilderExtensions.IntentManagedContractMerge()` (shared by all seven C# templates; the Services module has an identical helper):
  ```csharp
  [assembly: DefaultIntentManaged(Mode.Merge)]
  [assembly: DefaultIntentManaged(Mode.Merge, Signature = Mode.Fully, Attributes = Mode.Merge, Comments = Mode.Merge, Targets = Targets.Constructors | Targets.Methods)]
  ```
  - **How:** the first line is `CSharpFile.IntentManagedMerge()`, which the builder always writes first. The second is `AddAssemblyAttribute(CSharpDefaultIntentManagedAttribute.Merge().WithSignatureFully()...)`, because the typed helper has no `Attributes`/`Comments` methods and its `WithAccessTargets*` can only set one target. Probed: the rendered header matches the two lines exactly, also after `GlobalNamespaceOutput` unwraps a No Namespace file (it keeps everything above the namespace byte for byte).
  - **Why it's valid:** RoslynWeaver's `ManagedModeManager` allows one untargeted default plus targeted ones; only two _untargeted_ defaults throw. `Intent.RoslynWeaver.Attributes` 3.0.0's `DefaultIntentManagedAttribute` has the `Signature`, `Body`, `Comments`, `Attributes` and `Targets` properties used here.
  - **Effect:** types, properties and everything else stay under plain Merge. Constructors and methods have fully managed signatures (the model's signature replaces the existing one), merged bodies (Body isn't set, so it follows `Mode.Merge`), and merged attributes and XML comments. Only the attribute's own wording is relied on here; RoslynWeaver's per-mode behaviour for Attributes and Comments wasn't re-probed.
  - **Earlier state:** plain `Mode.Merge` only. From decompiled RoslynWeaver 5.0.1, `MergeSignature` already brought matched members' modifiers (except `virtual`/`partial`), return types and parameters in line with the model, missing members were inserted whole, and existing bodies were merged (`ManageStatementBlock(..., Mode.Merge)`), which is why generated bodies are always empty (next entry). Those points still hold for everything except the signature mode of constructors and methods.
  - **Properties under plain Merge** (read from the RoslynWeaver 5.0.2-pre.6 source, `TreeMerger.PropertyDeclarationSyntax.cs` `MergeSignature`; confirmed in TestReverse, whose `{ get; init; }` record DTOs merged with only the file header added): an existing property's accessor list, accessor modifiers, accessor bodies and initializer are never touched, so `init`, `private set`, `protected set` and get-only `{ get; }` survive. Only a newly inserted property gets the template's `{ get; set; }`. The type is replaced unless equivalent, missing template attributes are added, and the property's own modifiers follow the template. On the first merge (no previous output) every modifier except `virtual`/`partial` is replaced, so an existing `required` is dropped unless it is modelled (Property Configuration, below).
  - **Accessor setting and stereotype: proposed, then dropped by the user (2026-10-14).** A Default Record Property Setter setting plus a property-level stereotype (set, init, private set, …) was proposed for records that use `init`. Because Merge keeps existing accessors, it would only have affected newly added properties. A Required checkbox, to stop the first-merge loss of `required`, was offered too and deferred; it was added the next day as the Property Configuration stereotype (its own entry below).
- **Body/Signature Ignore defaults: considered, then removed by the user.** The rejected design added a second, _targeted_ `[assembly: DefaultIntentManaged(Mode.Merge, Body = Mode.Ignore, Signature = Mode.Ignore, Targets = Targets.Methods | Targets.Constructors | Targets.Properties)]` so existing bodies and signatures were never touched. If it is ever reinstated, it must stay targeted:
  - An _untargeted_ `Body = Mode.Ignore` also applies to the type node, and `TreeMerger.VisitBasedOnMode` never runs `AddMissingMembers` under Body=Ignore, so missing members would never be added.
  - A template-level `WithDefaultBodyMode(Mode.Ignore)` in `GetTemplateFileConfig` is folded into the untargeted default by `ManagedModeManager.ApplySettingsDefaults`, with the same failure.
  - The builder can't put `Body =` on its own `DefaultIntentManaged` line, and a second untargeted attribute makes RoslynWeaver throw.
- **Constructors and methods always have empty bodies: no statements, no `NotImplementedException`, no TODO (user decision).** Under `Mode.Merge` the generated body is merged with the one on disk, so an empty body leaves existing implementations untouched. A `throw` stub risked being merged into real code. The cost: a newly added method that returns a value won't compile until someone writes its body, and new async methods raise CS1998. This deliberately departs from the repo's file-builder-expert stub convention; don't reintroduce a statement.
- **Async: name convention plus an explicit Async Configuration stereotype (user decision).** An operation is async when its name ends in `Async`. This module's own **Async Configuration** stereotype on operations overrides that either way. Async operations emit the `async` keyword, a `Task`/`Task<T>` return type and `CancellationToken cancellationToken = default`. The return type is never double-wrapped, and `method.Async()` (probed) leaves an existing `Task` alone. Abstract operations never get `async`, because C# forbids it without a body.
  - Why the keyword is emitted: under plain `Mode.Merge`, RoslynWeaver replaces an existing method's modifiers with the template's. Omitting `async` stripped it from async/await implementations and broke the consumer build.
  - Cost: new stubs raise CS1998, and the model can't tell the code's styles apart from the name alone, so whoever models the code (by hand or with the C# importer) must apply the stereotype wherever code and name disagree.
  - **Stereotype shape (user decisions, 2026-10-15):** Async Mode (`async` default / `no async keyword` / `sync`), Task Type (`Task` / `ValueTask`), Include Cancellation Token, Cancellation Token Name and Cancellation Token Default. All of it is computed in `ContractAsync` (`For`, `GetReturnType`, `AddCancellationTokenParameter`, `ApplyAsyncKeyword`), identical in both modules apart from namespaces.
    - **Async Mode replaced the Is Async checkbox,** because Is Async = false (the old workaround) also unwrapped the Task return type, so a method that returns its task directly (`Task<T> FindAsync(…) => _set.FindAsync(…)`) couldn't keep its token. `no async keyword` keeps the return type and token and omits only the modifier. Rejected: a separate Async Keyword checkbox (the user preferred one select).
    - **No migration (user decision):** both modules are unpublished (1.0.0-pre.0, only in the local `D:\Dev\.intent-modules`), so only the user's test models had Is Async. An empty Async Mode reads as `async`, the default, which is what Is Async ticked did. An operation where Is Async was unticked must be set to `sync` by hand. Rejected: reading the stored legacy value in code, and bumping to 1.0.0-pre.1 with a Version Migration.
    - **Task Type:** empty keeps the earlier rule (Task, or ValueTask when the return type is modelled as one). An explicit value converts a modelled Task/ValueTask; `Async(asValueTask)` would also convert, but the no-keyword path can't call it, so `GetReturnType` does the conversion itself. `CSharpType.IsTask()` also matches `IAsyncEnumerable<T>`, so the Task-only checks on `CSharpTypeName`/`CSharpTypeGeneric` are used, and an `IAsyncEnumerable<T>` return type is left unwrapped (before this, the Domain module wrapped it in `Task<…>`). Rejected: a Use ValueTask checkbox.
    - **Cancellation Token Default** (checkbox, default ticked) is read raw by name, not through the typed accessor, so a stereotype applied before the property existed (nothing stored) keeps `= default` instead of reading as false. Rejected: a select that also offered the `= default(CancellationToken)` spelling.
    - **Cancellation Token Name** (user-requested extra): method signatures are fully managed, so a token named `ct` was renamed to `cancellationToken`, breaking bodies that use it. The name is validated as a C# identifier and must not repeat a modelled parameter's name (`ElementException`).
    - **Probed** with reflection against the built module (`GetReturnType` over every mode, Task Type and modelled type; rendered declarations for `async`, `no async keyword` with `ct` and no default, ValueTask, and `sync`). Not verified in a consumer; the user is testing it.
    - **Plain-value core (2026-10-16, in step with Services' service proxies).** `For` now has the typed-accessor overload and an `IStereotype` overload that reads a filter-targeted Async Configuration by property name; both build the same private `Settings` record. `AddCancellationTokenParameter` gained a `CSharpInterfaceMethod` overload. Both overloads are unused here and kept only so the two copies stay identical. The option comparisons are the same ordinal strings as the generated `Is*()` accessors (checked in both modules' `OperationModelStereotypeExtensions`), so Domain output is unchanged.
  - Rejected: reading Intent.Application.Contracts' Asynchronous/Synchronous stereotypes (a foreign module, not a dependency); dropping the automatic CancellationToken (the user kept it, overridable per operation); a targeted `Signature = Mode.Ignore` for methods (offered, not chosen).
  - The Async Configuration accessor is generated against `Intent.Modules.Common.Types.Api.OperationModel`, so the helper bridges from the Domain `OperationModel` through `InternalElement`.
- **Names are verbatim, and contracts are always concrete types.** RepositoryContract emits the concrete repository class with stubbed operations; no interface is generated (user decision). Everything except EnumContract is a `class` by default.
- **Type Configuration stereotype selects class or record.** Defined in this module's package and installed into the Domain designer ("Include in Module" + "Reference in Designer" = Domain). Applies to Class, Value Object, Repository, Data Contract and Domain Service. Empty or absent means class. `ContractTypeKind.cs` reads it through the typed `TryGetTypeConfiguration` accessors (never `AsEnum()`, which throws on an empty value), and `AddContractType` is the single dispatch to `AddClass` / `AddRecord`. A record/class inheritance mismatch with the base type raises an `ElementException`.
  - **Struct was requested and then dropped by the user.** `Intent.Modules.Common.CSharp` (up to 3.10.11) can only declare a class or a record. Rejected workarounds: raising an error for struct (offers an option that always fails), and rewriting `class` to `struct` in the output text (breaks the file-builder rules). Revisit when the builder supports structs.
  - RoslynWeaver matches type declarations with `kindsMustMatch: true`, so the configured kind must match the existing type on disk. A mismatch adds a second declaration with the same name.
  - **Positional records and primary constructors (user requests, 2026-10-13; two separate features).**
    - **Positional record:** a third Type option, `positional record`, on the typed Type Configuration and the Domain Events one. `ContractTypeKind.PositionalRecord` builds a record whose attributes (Domain Event properties) are its primary constructor's parameters in model order, typed as the properties they declare, Values as defaults (`AddContractAttributes` / `AddDomainEventFields`). It applies to Class, Value Object, Data Contract and Domain Event; Repository and Domain Service raise an `ElementException`. A Class keeps navigation properties, constructors and operations in the body.
    - **Primary Constructor stereotype** (marker, no properties, on Class Constructor; only Class has constructors in the Domain designer). The marked constructor is emitted with `AddPrimaryConstructor` (same parameter rules as `AddStubbedConstructors`, which now skips it). On a record, attributes named like its parameters aren't declared again (they're the positional properties); on a class every attribute stays a property. More than one marked constructor, or one on a positional record, is an `ElementException`.
    - **Inheritance:** record-ness is compared, so record and positional record can derive from each other. When both a type and its base declare parameters on the type, the base's are passed by name (`PassBasePrimaryParameters` → `CallsBase`) and must be among the type's own, else `ElementException`. A Class without its own primary parameters writes no base arguments, because it can call the base from an ordinary constructor; Value Objects, Data Contracts and Domain Events have no constructors, so they must be positional too.
    - **Not verified in a consumer:** how RoslynWeaver merges a type's parameter list into existing code (unchanged, added or changed parameters, base arguments, and an existing primary constructor that isn't modelled). The user is testing it.
- **Type resolution uses role strings, not template ids.** Each template registers all six Domain roles (`GuardrailsContractsDomainRoles`) as type sources, with an `ICollection<T>` formatter. Role strings let the Services contract module resolve Domain types without an assembly reference to this module.
- **Shapes mirror reference templates without their behaviour.** EntityContract follows `Intent.Modules.Entities` DomainEntity (base class, generics, navigations, ctors, operations), with no private setters, backing fields or domain-event plumbing. ValueObject has no equality members. DataContract uses `BaseDataContract`, because `BaseType` is obsolete.

- **File Config stereotype: renamed files, non-folder namespaces and multi-type files (user decision).** Applies to Class, Value Object, Repository, Data Contract, Domain Service and Enum (the Enum accessor extends `Intent.Modules.Common.Types.Api.EnumModel`). Both properties are optional and only applied where set. Ported from `Intent.Services.Guardrails.Contracts` (see its CONTEXT.md entry of the same name); the shape is the same on purpose:
  - **Builders:** each kind's type is built in `ContractTypeBuilders` (`AddEntity`, `AddEnum`, `AddValueObject`, `AddRepository`, `AddDataContract`, `AddDomainService`), with `AddContract` dispatching on the element type. The member helpers take `ICSharpTemplate`, always the template whose file is being built, so a file owner can build another element's type. Type resolution is identical either way, because all six templates register the same six roles and the same `ICollection<T>` formatter.
  - **Filename:** `.cs` is stripped, then `CSharpFile.WithFileName`. With `.cs` the name is taken verbatim apart from whitespace after `.cs`; without it, it is trimmed (user decision, 2026-10-14). That lets a file such as `abc .cs` be targeted, which a trimmed `abc ` couldn't. Nothing downstream trims: `CSharpFile`, `TemplateFileConfig` and the Software Factory host pass the name through, and `Path.GetFullPath` only strips trailing spaces from the whole path, which ends in `.cs` (probed with reflection: `abc .cs` gives `abc `, ` abc.cs` gives ` abc`, `abc ` gives `abc`). File name only; a path separator or invalid character raises an `ElementException`. Type resolution reads the class name from config metadata, so references still resolve (probed: `orderLines.cs` gives file `orderLines`, class `orderLine`).
  - **Namespace:** `ContractFileGroups.GetContractNamespace` replaces `this.GetNamespace()` in `new CSharpFile(...)`. The value is used verbatim (only trimmed), so it is validated rather than corrected: dotted identifiers, and `ToCSharpNamespace()` (applied by `CSharpFile` and the template's `Namespace`) must leave it unchanged apart from @-escaping keywords. Anything it would rewrite raises an `ElementException`.
  - **Multi-type files:** templates whose `FileMetadata` file name and `GetFilePath()` are equal (OrdinalIgnoreCase) form a group. The owner is the member named like the file (ordinal, then case-insensitive), else the first by ordinal name then id. It adds the others at OnBuild priority 0; non-owners return false from `CanRunTemplate()` (hand-written `*Template.FileGroup.cs` partials with the `IDomainContractTemplate` marker) but stay discoverable. Members with different namespaces raise an `ElementException` asking for the same File Config Namespace on every type in the file, or none.
  - **Domain specifics:** grouping is by real output path, so an entity and a repository only share a file when both templates' Output Anchors put them in the same folder. With the usual Repository anchor on Infrastructure they never group. Groups can span output targets; their derived namespaces can then differ, which the namespace check reports.
  - **`CSharpFile` is now created with the template (`new CSharpFile(ns, folder, this)`)**, as in Services, so builder features that need `File.Template` work. Together with that, an async operation modelled as `ValueTask`/`ValueTask<T>` now calls `method.Async(asValueTask: true)`; plain `Async()` silently converted ValueTask to Task.

- **Ships the `reverse-engineer-domain` AI skill (user decision).** `ReverseEngineerDomainSkill` is a Single File, Markdown File Builder template with role `AI.Context.Skills`, emitting `skills/reverse-engineer-domain/SKILL.md`. It replaces the removed entry module's `reverse-engineer-designers` skill, with one skill per contract module. The content was supplied by the user and is embedded in a non-interpolated raw string, so its braces and quotes need no escaping. It is verbatim except for user-requested additions: guidance on File Config, Collection Type, Parameter Modifier and multi-location Template Outputs (Registration Filter); the §4a key-mode guidance (switch `Key Creation Mode` to `Manually add PKs and FKs` when the code doesn't follow one surrogate key per entity) and the matching key evidence in §1. No `name:` or `template-id:` front-matter is added. The skill describes this module's template behaviour (async rule, Async Configuration, repository output, merge directive), so a template behaviour change must update the skill in the same change.
  - **Type spelling, nullability and never dropping members (user decisions, from a Basislink adoption).** An agent deleted 9 DTO fields and an operation from the model because the template spelled their types differently from the code: `Nullable<DateTime>` vs `DateTime?`, `string?` (nullable reference types off) vs `string`, `DTO.Logging.LogDTO` vs `LogDTO`. It had generalised the skills' "leave unmodelled and report" rules. Both skills now:
    - extract types as spelled, plus each project's and file's nullable context (§1);
    - model `Nullable<T>` exactly like `T?`, and treat `string?` with nullable reference types off as a code defect (warning CS8632) that the template's `string` fixes;
    - share one "Equivalent type rewrites — ask, never drop" step (§6 here, §7 in the Services skill), worded identically. It forbids dropping or omitting members to keep a diff header-only, and asks the user once: accept the rewrites (recommended), leave the members out with a comment, or model them but don't adopt the files yet;
    - qualify every "leave it unmodelled" and "remove the operation" rule as covering only shapes the model can't express.

    The user said "fields"; the rule was applied to every member kind (properties, fields, parameters, operations) because the operation was dropped for the same reason.
  - **Formatting changes are accepted, and Auto Format is never turned off (user decision, 2026-10-09, from the Basislink adoption).** The skills used to require header-only adoption diffs. RoslynWeaver's Auto Format also re-lays-out whitespace inside hand-written method bodies (e.g. `GetFileName(x): null` → `GetFileName(x) : null`, across hundreds of lines), so an agent turned the `Auto Format by Default` setting off to get header-only diffs. That hid harmless fixes, and with formatting off the members the SF rewrites (declarations with attributes) lost their indentation: 23 controllers ended up with flush-left declarations. The user's rule: a change that is purely formatting, with no change in meaning, is acceptable, since it improves readability and alignment with coding standards. Both skills now:
    - allow the Intent headers plus formatting in an adoption diff (the Goal line, §6 steps 1, 2 and 6 here, §7 steps 1, 2 and 6 in the Services skill);
    - share one "Formatting changes — accept, never suppress" step (§6 step 5 here, §7 step 5 in the Services skill), worded identically. It defines formatting as the same tokens in the same order with only whitespace changed (string and comment text untouched), applies it without asking, forbids disabling or suppressing Auto Format, asks the user before turning it back on if it is already off, and reports how many files were reformatted;
    - reword the two "header-only" phrases in the shared "Equivalent type rewrites" step, so they no longer imply formatting must be avoided.
  - **Editing gotcha:** edit the skill text with a plain-text editor. Intent's `patch_file`/`write_file` run a C# formatter that re-indents the whole raw string to the same depth. That flattens nested markdown lists, indented tables and code fences, which changes the rendered SKILL.md, although it still compiles.

- **Collection Type stereotype (user decision).** The template defaults are `ICollection<T>` for properties and `IEnumerable<T>` for operation and constructor parameters and return types. Under plain Merge, a mismatch rewrites the existing signature, so `Collection Type` (on Attribute, Parameter, Operation for its return type, and Association Target/Source End) chooses IEnumerable, ICollection, IList, IReadOnlyCollection, IReadOnlyList, List, HashSet, ISet, IQueryable, Array (`{0}[]`) or Custom (`Custom Format` with `{0}`).
  - The option mapping lives in `ContractCollectionTypes`; it uses the typed `IsX()` helpers only, so an empty Type keeps the default.
  - A Custom Format must contain `{0}` and have balanced brackets, because `CSharpCollectionFormatter` would otherwise emit `MyList<{0}` as-is.
  - The stereotype is ignored for non-collections, and applied before the async Task wrapping.
  - Parameter and Operation accessors are generated against Common.Types models, bridged via `InternalElement`.
  - The Services module has the same stereotype and option list; keep them in step.
- **No Namespace on File Config (user decision).** Same design as Services (see its CONTEXT.md):
  - `GetContractNamespace` returns `""`;
  - the hand-written partials override `Namespace` to `""`, because otherwise `CSharpTemplateBase.Namespace` falls back to `OutputTarget.Name` and other files get `<Project>.Type` plus a bogus `using`;
  - `RunTemplate()` unwraps the builder's `namespace { }` block via `GlobalNamespaceOutput.UnwrapGlobalNamespace`, which is a copy of the Services helper. It is the documented exception to "no raw structural strings", and throws on any unexpected shape.
  - Setting No Namespace together with Namespace raises an `ElementException`. Members of a multi-type file must agree.

- **Parameter Modifier stereotype (user decision).** `Modifier`: `ref`, `out`, `in`, `ref readonly` or `params`, on parameters, so Merge mode keeps the code's modifiers instead of dropping them. Implemented in `ContractParameterModifiers`. The builder emits `ref`, `out` and `params` on method parameters (`WithRef/Out/ParamsParameterModifier`). Its `WithInParameterModifier()` sets an empty modifier (a builder bug), constructor parameters have no modifier API, and there is nothing for `ref readonly`. In those cases the modifier is written as a prefix of the parameter's type text, which was probed and renders correctly. `this` (extension methods) is deliberately not offered: it needs a static class, which the contract templates can't model.
- **Property Configuration stereotype → Required (user decision, 2026-10-15).** Merge replaces a matched property's own modifiers with the template's on its first merge (see "Properties under plain Merge"), so an unmodelled `required` was dropped. Ticking Required emits it (`CSharpProperty.Required()`, in `ContractBuilderExtensions.WithContractRequired`), so the first merge keeps it.
  - **Targets:** a typed definition on Attribute and both association ends (navigation properties), read through the generated `GetPropertyConfiguration()` accessors (association ends via `IsContractRequired`, which switches on the concrete end model, as `GetCollectionFormat` does). A filter-targeted definition in the "Domain Events" folder covers the Domain Event Property, read raw by definition id in `DomainEventsMetadata.IsRequiredDomainEventProperty`.
  - **Shape (user decision):** a Property Configuration stereotype with a Required checkbox (default unticked), leaving room for other property options. Rejected: a marker stereotype named Required Member or Required.
  - **Positional records (user decision):** their fields are primary-constructor parameters, which C# can't make `required`, so the stereotype is ignored silently there (the positional builders never read it). The same applies to a record's attributes that a Primary Constructor already declares. Rejected: an `ElementException`.
  - **Accessors are deliberately not modelled:** Merge keeps existing ones (see "Properties under plain Merge"), so the template still emits `{ get; set; }`.
  - **Not verified in a consumer:** built and the module SF rerun cleanly; the user is testing it. Expected: Required on a property gives `public required T X { get; set; }` for a new property, and an existing `public required T X { get; init; }` is unchanged.
- **Operation Configuration and Constructor Configuration (user decisions, 2026-10-15).** Method and constructor signatures are fully managed (`Signature = Mode.Fully`), so every operation used to be rewritten to `public` (plus `async`), and every constructor to `public`.
  - **Operation Configuration** on Operation: an Access Modifier select (`public` default, `protected`, `internal`, `private`, `protected internal`, `none`) plus Virtual, Override, Sealed and New checkboxes. `static` and `abstract` stay on the Domain Operation's own Is Static and Is Abstract; `async` stays on Async Configuration. Rejected: a validated Modifiers text box like Type Configuration's (the user preferred a select plus checkboxes).
  - **Constructor Configuration** on Class Constructor (user-accepted extra): Access Modifier only, because EF Core entities commonly have `protected` or `private` constructors. There is no `none`: `CSharpConstructor` has no way to omit the access modifier, so implicitly private code is modelled as `private` and written out. It is ignored on a Primary Constructor, which has no access modifier of its own.
  - **No access modifier (user decision: "nothing, as written"):** expressed by `none`, which calls `WithoutAccessModifier()`. An empty value falls back to `public`, the stereotype's default (my assumption, stated to the user), so a cleared or unstored value never silently makes every method private.
  - **Validation:** the builder's modifier methods silently clear the ones C# forbids alongside them (last call wins), so `ContractMemberModifiers.Validate` raises an `ElementException` for every rejected combination first: static with virtual/override/sealed/abstract, virtual with override or abstract, sealed without override or with abstract, new with override, and virtual/abstract/override on private or `none`. Is Static plus Is Abstract, which used to give a silent abstract-only method, is now one of those errors. `private protected` isn't offered, because the builder has no method for it.
  - **Shared code:** `ContractMemberModifiers` (`ApplyContractModifiers` for methods, `ApplyContractAccessModifier` for constructors) is identical in both modules apart from namespaces. The Domain Operation Configuration accessor is generated against the Common.Types operation model, bridged through `InternalElement` like Async Configuration.
  - **Probed** with reflection against the built module: every valid combination rendered as written (e.g. `protected override`, `public sealed override`, `public new virtual`, `public abstract override`, and no modifier for `none`), each invalid one threw from `Validate`, and all five constructor options rendered. Not verified in a consumer; the user is testing it.

- **Minimum Visual Studio module version (user decision).** The `.imodspec` declares, in a hand-maintained `<interoperability>` / `<!-- Minimum Compatible Versions -->` block (the same convention as Intent.Application.FluentValidation and 11 other modules), that a detected `Intent.VisualStudio.Projects` must be at least `4.1.11-pre.1` (raised from `4.1.11-pre.0` on 2026-10-17, user request: latest pre-releases). The Module Builder doesn't model interoperability, and the Software Factory preserves the block on regeneration (verified). `4.1.11-pre.1` is on the public feed and in `D:\Dev\.intent-modules`.
- **Minimum Codebase Structure version and client range (user decision, 2026-10-17).** The same block requires a detected `Intent.Modelers.CodebaseStructure` of at least `1.2.0-pre.1`, because the skill's §2 edits consumers' Template Outputs, and 1.2.0 lets File Classification apply to them (it stamps a `**/*` entry on install and migrates Output Classification). The user chose an interoperability minimum over a dependency, the same as Services. 1.2.0-pre.1 needs Intent Architect 5.4.0-beta.6, so `supportedClientVersions` is raised by hand from `[5.1.0-a,6.0.0)` to `[5.4.0-beta.6,6.0.0)`. Without that, a consumer on an older client that has Codebase Structure installed would fail to install it. The Software Factory keeps the hand-set range (verified: the rerun staged nothing).

- **Domain Events: no dependency on Intent.Modelers.Domain.Events (user decision).** The reverse-engineering skill installs the Domain Events modeler only when the code has domain events, so `DomainEventContract` must work without it.
  - **Model type:** a custom model type (`Intent.Metadata.Models.IElement`, fully qualified so the generated `TemplateExtensions.cs` gets its `using`).
  - **Raw-id access:** all raw-id access lives in `DomainEventsMetadata`. Elements come from `GetElementsOfType` (an unknown id returns empty, verified in the engine), properties from `ChildElements` by type id, and the base event from the Domain Event Generalization association.
  - **Pinned ids:** the ids are pinned to Domain.Events 4.4.7. If that modeler ever changes them, the contracts silently generate nothing.
  - **Stereotypes:** the Domain Event stereotypes (File Config, Type Configuration, and Collection Type and Property Configuration on its Property) are separate definitions in the "Domain Events" folder, targeted by filter function on `element.specializationId`. Typed targeting would make the Module Builder reference, and so depend on, that package. Because they have no typed accessors, they are read by definition id and property name; renaming a property in the designer would silently make it read empty.
  - **Folders:** `IElement` isn't `IHasFolder`, so the built-in `GetFolderPath()` / `GetNamespace()` ignore designer folders. `GetElementFolderPath` / `GetElementNamespace` rebuild the same folder chain and Folder Options rule.
  - **Output and scope:** the type is emitted through the shared builders, joins multi-type groups and is a `DomainEvent` role type source. Only Domain-designer events are generated, and publishing associations generate nothing.

- **Type modifiers: Type Configuration → Modifiers plus a Default Type Modifiers module setting (user decision).** Plain Merge replaces an existing declaration's modifiers with the generated ones, so `internal sealed` code was rewritten to `public`.
  - **Where:** `ContractTypeModifiers.ApplyContractModifiers`, called last in each builder's configure callback, because `abstract` also comes from Is Abstract and from abstract operations (`AddStubbedMethods`).
  - **Precedence:** a non-empty Modifiers on the element, then the setting, then `public`. The setting is "Default Type Modifiers" in the group "Domain Guardrails Contracts Settings" (`Settings/ModuleSettingsExtensions.cs`, generated). It is a Select whose options are `public` or `internal`, each with nothing, `sealed`, `partial` or `sealed partial`, plus `none`, `sealed`, `partial` and `sealed partial` with no access modifier; the default is `public`, which keeps the earlier output, and an empty value still falls back to `public`.
  - **Modifiers is a validated text box.** It takes at most one of `public`/`internal`, plus any of `sealed`, `abstract`, `static`, `partial`, with at most one of `sealed`/`abstract`/`static`; or `none` on its own. **The access modifier is optional:** without one the type is declared without one (`CSharpClass.WithoutAccessModifier()`, Common.CSharp 3.10.12-pre.0), so `sealed` gives `sealed class X` and Merge leaves code that omits it alone. The builder offers only `Public/Internal/Sealed/Abstract/Static/Partial` for top-level types, so `file` and `unsafe` are rejected.
  - **`none` means no modifiers at all, and must stand alone (user decision).** A keyword is needed because an empty Modifiers already means "use the setting", which every element that sets only Type relies on. `none` reads plainly in the text box, in the setting's dropdown and in the generated option accessors. Rejected: a separate Omit Access Modifier checkbox (two properties that can contradict each other, and the setting would still need new options), and reusing `internal` to mean "omit it" (it would rewrite code that does say `internal`).
  - **Superseded: an access modifier used to be required,** because `CSharpClass` in Common.CSharp 3.10.5 always wrote one, so implicitly internal code was modelled as `internal`. Elements modelled that way still generate `internal`: it compiles and means the same, but Merge keeps adding the keyword to code that lacks it. Old values stay valid, so this isn't a breaking change; the reverse-engineer skill now says to model the declaration exactly as written.
  - **Setting vs element:** the setting is a convention for every type, so its `sealed` is dropped for abstract types and for types another modelled type inherits from (Class through `ParentClassTypeReference`, Data Contract through `BaseDataContract`, Domain Event through its generalization). `abstract` and `static` aren't offered as defaults; a hand-edited value containing them is a `FriendlyException`. Element Modifiers are used as given: `sealed`/`static` on an abstract or inherited type, and `static` on a record, raise an `ElementException`.
  - **Rejected:** a Select for Modifiers (16+ combinations, and still missing `static`/`abstract partial` cases), and a free-text setting (a closed list is safer for the bulk convention).
  - **Enums (user decision: a separate stereotype):** an **Enum Configuration** stereotype on Enum has an `Access Modifier` select (`public` / `internal` / `none`). When it is empty, the enum takes the access modifier of Default Type Modifiers, so `internal sealed` gives `internal enum`, and a setting without one (`none`, `sealed`, …) gives `enum S`. An enum can't be sealed or partial, so the rest of the setting doesn't apply. Implemented in `ContractTypeModifiers.ApplyContractAccessModifier` (`CSharpEnum.Public()/Internal()/WithoutAccessModifier()`), and it shares `GetDefaultModifiers` with the class path. Rejected: adding Enum to Type Configuration with `Type` hidden on enums, which mixes a class/record setting into enums. Probed: no setting gives `public enum`, `internal sealed` gives `internal enum`, an element value wins either way, and an unexpected stored value is an `ElementException`.
  - The Domain Event Type Configuration has the same property, read by name in `DomainEventsMetadata.GetDomainEventModifiers` (the same raw-access caveat as its other properties).

- **Short names for generic collections: a workaround for an arity-blind check in Intent.Modules.Common.CSharp.** Reported by the user: `public System.Collections.Generic.IEnumerable<BasisBuyBidDTO> CalculateBasisList(string oneId, ref System.Collections.Generic.IEnumerable<BasisBuyBidDTO> bidList)`, although the `using` was present.

Its known-types registry (`CSharpTypesCache.GetCommonKnownTypes`) holds every non-open-generic type of the loaded `System.*` assemblies, so it includes `System.Collections.IEnumerable`, but nothing records arity. `GenericCSharpTypeParser` passes only the bare name to the check. So when the usings include `System.Collections`, `IEnumerable<T>` counts as ambiguous and stays fully qualified, although C# tells the two apart by arity. The usings include the existing file on disk, and legacy files often import `System.Collections`, which is why merged contracts hit this more than greenfield templates.

It also adds the `using System.Collections.Generic`. `global::` forms and every other type are left alone (probed against the built module).

  - **Root-cause fix (not made; offered to the user):** make the check arity-aware in Intent.Modules.Common.CSharp. `GenericCSharpTypeParser` would pass the type-argument count, and the registry and conflict check would ignore entries whose arity differs. ## Invariants & Constraints

- **No casing changes, ever (user decision).** The designer is reverse-engineered from the code and is the authoritative view of it, so every generated name must be exactly the designer name: types, members, parameters, literals and namespaces. Always pass `element.Name` as a string to the builder. Its model overloads (e.g. `AddProperty(type, model)`) Pascal-case the name, so `lowerProp` becomes `LowerProp`. Under Merge that would add a second, renamed member beside the real one. The string overloads, `AddClass`/`AddRecord`/`AddEnum`/`AddLiteral` and `ToCSharpNamespace` were all probed (Common.CSharp 3.10.5) and keep names verbatim.
- The six role strings are a shared contract with `Intent.Services.Guardrails.Contracts`, which resolves four of them, and with the Output Anchors in consumer applications. Changing one means a synchronised version bump of both modules.
- Never call `RepresentsModel` on a `CSharpEnum` or `CSharpEnumLiteral`. In Intent.Modules.Common.CSharp 3.10.5 to 3.10.11 it throws, so EnumContract crashed the whole consumer Software Factory run. `AddEnum` never sets the enum's parent; setting it by hand still fails because `CSharpEnum` isn't `ICSharpReferenceable`, and literals report "not supported". Classes, records, properties, constructors, methods and parameters are all fine (probed).
- `Templates/TemplateExtensions.cs` is Fully managed. Shared builder logic lives in the hand-written `ContractBuilderExtensions.cs`, `ContractTypeKind.cs`, `ContractTypeBuilders.cs` and `ContractFileGroups.cs`, and the `*Template.FileGroup.cs` partials. A template's own type must be built only through `ContractTypeBuilders`, or a multi-type file owner would build it differently.
- Consumer projects need the `Intent.RoslynWeaver.Attributes` NuGet package for merged files to compile.
