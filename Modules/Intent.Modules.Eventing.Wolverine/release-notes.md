### Version 1.0.0

- Fixed: an application with Transactional Outbox = Durable failed to build on first generation (`CS0234`/`CS1061` for `Wolverine.EntityFrameworkCore`/`Wolverine.SqlServer`/`Wolverine.Postgresql`) because the `WolverineFx.EntityFrameworkCore` and `WolverineFx.SqlServer`/`WolverineFx.Postgresql` NuGet package references were never declared alongside the `using` statements and durability calls that need them. Existing golden samples masked this because their `.csproj` already had the packages hand-pinned from before the regression; any newly generated application hit it immediately.
- Breaking Change: `WolverineEventingConfiguration` is removed. This module now contributes a private `ConfigureEventing` method (and one call statement) directly into `Intent.Wolverine.Common`'s shared `WolverineConfiguration.Configure(WolverineOptions, IConfiguration)`, alongside `Intent.Application.Wolverine`'s `ConfigureCqrs` — one generated class per application instead of two, and no `ConfigureLocal`/`ConfigureRabbitMq`/`ConfigureAzureServiceBus`/`ConfigureAmazonSqs` method names leaking the transport choice into the public shape of generated code.
- New Feature: multi-tenancy is now envelope-native. `WolverineTenantHeaderStrategy` (a custom header, configurable via `Wolverine:TenantHeader`) is removed; a new `WolverineTenantStrategy : IMultiTenantStrategy` reads `Envelope.TenantId` directly and is registered into Finbuckle's own strategy chain (`WithStrategy<T>(ServiceLifetime.Scoped)`) alongside `WithHeaderStrategy`, matching how `Intent.Eventing.MassTransit` wires its own Finbuckle strategy. `WolverineTenantMiddleware` is now two lines (`BeforeAsync`, no `FinallyAsync`), and `WolverineMessageBus` builds `DeliveryOptions.TenantId` itself.
- New Feature: this module now conforms to the Composite Message Bus pattern. A new `AddWolverineEventingConfiguration(IServiceCollection, IConfiguration, MessageBrokerRegistry)` extension method (emitted only in applications that need a composite bus) registers `WolverineMessageBus` and maps it against every Wolverine-designated published message/sent command in the shared broker registry, so an application combining Wolverine with another eventing provider now routes Wolverine-addressed messages correctly instead of Wolverine being silently absent from the composite bus.
- Fixed: the RabbitMQ transport helper declared its return/parameter type as `IRabbitMqTransportExpression`, which does not exist in WolverineFx 5.39.5 (`CS0246`) - the real type is the concrete `Wolverine.RabbitMQ.Internal.RabbitMqTransportExpression`. Every RabbitMQ-transport application now builds.
- Fixed `Intent.Wolverine.Common` not being declared as an imodspec dependency, so installing this module now automatically brings it in instead of requiring a separate manual install. This module no longer bundles its own copy of that module's assembly either, so the two can't disagree about which copy the module loader binds to.
- Improvement: the `builder.Host.UseWolverine(...)` configuration this module contributes is now sequenced by an explicit factory-extension `Order` relative to the other Wolverine modules, rather than depending on arbitrary execution order. Generated output is unchanged.
- Consolidated the `Message Topology Settings` and `Command Distribution` stereotypes into the single `Wolverine Message` stereotype, which now carries both the `Topic Name` and `Destination Queue Name` overrides and applies to both Integration Events and Integration Commands. The publish/send name resolution reads them from there.
- Fixed Amazon SQS binding the `Region` configuration value to the transport's service endpoint URL (`ServiceURL`) instead of the AWS region. `Region` now selects the region via `RegionEndpoint.GetBySystemName`, and the optional `Wolverine:AmazonSqs:AccessKey`/`SecretKey` pair is applied as static credentials only when both are present - when either is absent the AWS default credential chain is used.
- Fixed Amazon SQS delivering a published Integration Event to a point-to-point SQS queue instead of fanning it out. An Integration Event's publish rule now targets an SNS topic (`ToSnsTopic`), SNS-to-SQS being AWS's fan-out primitive, and a subscribing application's queue is subscribed to that topic. Integration Commands are unchanged and remain point-to-point on an SQS queue. This adds a `WolverineFx.AmazonSns` package reference for applications using the Amazon SQS transport.
- Added an explicit Handler Type Registration per subscribed message's `IIntegrationEventHandler<T>` implementation, alongside the listener. Registrations are emitted per distinct handler type, so a handler carrying several subscriptions - or a message subscribed to more than once - still produces exactly one. Wolverine's conventional handler discovery remains enabled; verified against WolverineFx 5.39.5 that an explicitly registered type which conventional discovery also finds is not registered twice.
- Fixed the Durable Transactional Outbox adding the `WolverineFx.EntityFrameworkCore` and provider packages but emitting none of its five registrations. Message persistence for the modelled Database Provider, the `DbContext` integration, auto-apply-transactions, durable-outbox-on-all-sending-endpoints and durable-inbox-on-all-listeners are now all emitted.
- Fixed the outgoing multi-tenancy header being dead code: the generated message bus now passes `DeliveryOptions` carrying the current Tenant Identifier on every published Integration Event and sent Integration Command, and the header name is configurable via the `Wolverine:TenantHeader` appsetting, defaulting to `Tenant-Identifier`.
- Fixed the `Wolverine:AzureServiceBus:ConnectionString` and `Wolverine:AmazonSqs:Region` appsettings being registered with invented non-empty placeholder values, which meant the generated fail-fast guard for a missing connection setting could never fire. Keys with no real default are now registered as empty strings.
- Removed the `Broker Topology` module setting and its Auto-provision / Externally owned behaviour. The module now always declares the exchanges, topics and queues the application uses. An application whose credentials cannot declare a destination is no longer supported; the `Topic Name` and `Destination Queue Name` overrides still let you match an existing estate's names, but the declaration attempt cannot be suppressed. Applications that had this setting will silently fall back to the previous default (Auto-provision), which was already the behaviour for all but explicitly Externally-owned applications.
- `WolverineMessageBus` now declares the `Application.Eventing.MessageBusImplementation` template role, as every other eventing provider already did. This is how a broker module that adds a member to the `IMessageBus` interface finds each provider's bus and gives it a default implementation so it still compiles.
- Corrected the previous release note about `IMessageBus.Send<TMessage>(TMessage, Uri)`. That overload is contributed by `Intent.Eventing.MassTransit`, which also supplies a `NotSupportedException` implementation for every non-MassTransit provider. Wolverine no longer hand-writes its own copy: it was emitted even in applications whose `IMessageBus` never declared the overload, and it silently discarded the address instead of rejecting it. With the role above declared, the correct throwing implementation is now contributed automatically, and only where the interface actually declares the member.
- Fixed a `NullReferenceException` generating `WolverineMessageBus`/`WolverineTenantMiddleware` for any application that had never generated those files before, caused by resolving a foreign type before the file's first class existed.
- Fixed the generated `WolverineMessageBus`'s `Wolverine.IMessageBus` using-alias failing to compile (`CS0246`) once an application's own namespace no longer nested under a literal `Wolverine.*` segment.
- Fixed a missing `using Wolverine.ErrorHandling;` that broke the build whenever an Error Handling Policy other than `None` was selected.
- Fixed RabbitMQ's exchange-to-subscriber-queue binding calling `BindExchange` on the wrong object, which failed to compile.
- Fixed the generated message bus being registered as `Transient` instead of `Scoped`, inconsistent with every other eventing provider.
- Fixed the `Wolverine Message`, `Message Topology Settings` and `Command Distribution` stereotype definitions not being available to consumer applications: `Include in Module` was not set on the module's `Module Settings`, so the stereotype definitions never shipped in the packaged `.imod` even though they existed in the model.
- Documented uninstall behaviour, including the additive-only `appsettings.json` caveat and which keys to remove by hand.
- Added a MassTransit-to-Wolverine migration guide to `docs/README.md`: ordered migration steps, a setting-equivalence table, the artefacts a swap leaves behind, and a staged (side-by-side) migration path for large applications.
- Fixed the generated `WolverineMessageBus` not implementing `IMessageBus.Send<TMessage>(TMessage, Uri)`, causing a `CS0535` build error whenever Wolverine coexists with another provider (e.g. MassTransit) behind a Composite Message Bus. Wolverine has no explicit-address concept, so the overload ignores the address and delegates to the same buffered `SendAsync`, matching the interface's own documented contract for providers that don't support explicit addressing.
- Fixed `WolverineFinbuckleConfiguratorExtension` registering the (static) `WolverineTenantMiddleware` via `opts.Policies.AddMiddleware<T>()`, which fails to compile (`CS0718`) because C# forbids a static type as a generic type argument. Switched to the `Type`-based `opts.Policies.AddMiddleware(typeof(T))` overload, which Wolverine's own API provides for exactly this case.
- Fixed `WolverineTenantHeaderStrategy` never being registered in DI, so every request to a Finbuckle-enabled application threw `InvalidOperationException` the moment `WolverineMessageBus` was constructed - not just requests that publish.
- Fixed a `NullReferenceException` intermittently generating `WolverineTenantMiddleware` on a Finbuckle-enabled application, caused by resolving a foreign template's type name before that template had finished constructing in the same Software Factory pass.
- Fixed Local transport never registering subscribed handler types, so a Local-transport handler was silently never invoked - the app builds and starts cleanly, but Wolverine logs "found no handlers" and every message goes undelivered instead of reaching the handler.
- Fixed: publishing under Transactional Outbox = Durable silently discarded every message - the dispatch-layer flush is stripped once the outbox is Durable, but nothing spliced a replacement into `ApplicationDbContext.SaveChanges`/`SaveChangesAsync`, so messages buffered on the bus were dropped when the request scope disposed. The flush is now spliced directly into the DbContext, mirroring `Intent.Eventing.MassTransit`.
- Fixed: an application with Transactional Outbox = Durable and either dispatch stack's unit-of-work (Wolverine's `UnitOfWorkMiddleware` or MediatR's `UnitOfWorkBehaviour`) threw `InvalidOperationException: An ambient transaction has been detected` on every command, because Wolverine's Eager EF transactional middleware collided with the unit-of-work's own `TransactionScope`. Durable outbox now opts into `TransactionMiddlewareMode.Lightweight` when either unit-of-work is present.
- Fixed: an Azure Service Bus subscriber listened on a plain queue nothing was ever published to, instead of a subscription bound to the publisher's topic, so every subscribed Integration Event went undelivered. Subscribed events now bind `ListenToAzureServiceBusSubscription(...).FromTopic(...)` against the same topic name the publish side resolves.
- Fixed: an Amazon SQS/SNS subscriber's queue was declared via `SubscribeSqsQueue` on the publish side but never registered as a listener on the SQS transport, so the queue was never created and Wolverine's SNS subscription step failed permanently on startup. Subscribed events now also register `opts.ListenToSqsQueue(...)` for the same queue.
- Fixed: an Amazon SQS/SNS subscriber's queue name was derived from the subscribing application's display name, which can contain dots (e.g. `WolverineEventing.Transport.AmazonSqs`) - a character AWS SQS/SNS resource names don't allow, but RabbitMQ and Azure Service Bus do. The queue got created under a different, sanitized name than the one Wolverine's SNS transport looked it up by, so subscription creation failed with `QueueDoesNotExistException` on every startup. Queue names used for the Amazon SQS transport are now sanitized (`.` → `-`) before being passed to `SubscribeSqsQueue`/`ListenToSqsQueue`; RabbitMQ's and Azure Service Bus's names, where dots are valid, are unaffected.
- Fixed: an Amazon SNS-to-SQS subscription delivered the published payload wrapped in SNS's own JSON notification envelope, which Wolverine's SQS listener cannot parse as its own raw envelope format (`FormatException: The input is not a valid Base-64 string`), so every subscribed message failed to process. `SubscribeSqsQueue` now sets `RawMessageDelivery = true`, so the SQS side receives the same raw envelope a direct `ListenToSqsQueue` subscriber would. Verified end-to-end against a real AWS account.
- Fixed: `WolverineMessageBus.FlushAllAsync` now suppresses any ambient `TransactionScope` around its dispatch when Transactional Outbox = None, matching `Intent.Eventing.AzureServiceBus` and `Intent.Eventing.NServiceBus`. Azure Service Bus rejects a send made inside a `TransactionScope` that is not `Serializable` (`InvalidOperationException: The only supported IsolationLevel is Serializable`), and both dispatch stacks' unit of work opens theirs at `ReadCommitted` - verified against a real Azure Service Bus namespace, and it fails whether or not a database is enlisted. Generated code was not previously affected, because the flush seam is registered outside the unit of work in both stacks, but that was an implicit ordering guarantee rather than an explicit one. Not emitted for Transactional Outbox = Durable, where the flush runs inside `SaveChangesAsync` on purpose so outgoing envelopes commit atomically with the entity changes, and no broker call happens on that path.
- Fixed: a subscribe-only application (one that handles Integration Events but publishes none and sends no Integration Commands) with Transactional Outbox = Durable failed to start, throwing `Unable to resolve service for type 'IMessageBus' while attempting to activate 'ApplicationDbContext'` during DI validation. The transactional-outbox flush spliced into the DbContext injected the message bus, but a subscribe-only application deliberately gets no bus registration - and has no outgoing messages to flush in the first place. The splice is now skipped unless the application actually publishes a Message or sends an Integration Command.
- New Feature: the subscriber queue/subscription name is no longer fixed to the `{application-name}-{message-name}` convention. Apply the new `Wolverine Subscription` stereotype to a subscription (on the Integration Event Handler's association to the Message) and set **Subscriber Queue Name** to override it - used verbatim, not kebab-cased, same as `Wolverine Message`'s `Topic Name`/`Destination Queue Name`. Needed because the convention name scales with the application's own display name with no ceiling, while Azure Service Bus caps subscription names at 50 characters (confirmed live: a long application name pushed a convention name to 69 characters and crashed on startup) and AWS SQS/SNS names allow only alphanumerics, hyphens and underscores. Also the direct equivalent of MassTransit's `Endpoint Name` for anyone migrating.
