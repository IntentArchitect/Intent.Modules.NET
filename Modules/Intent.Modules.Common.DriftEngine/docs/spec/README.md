# Intent.Common.DriftEngine: phase 0 specification

Phase 0 of [the plan](../plan.md). It is done when it is signed off.

The specification gives the requirements, the interfaces between the five building blocks, and the scope model. Beside it is an acceptance suite that later phases must pass. The suite's cases are built from the 321 checks in [`check-classification.md`](../check-classification.md), the real codebases, and scope cases.

## Decisions taken in phase 0

User decisions are marked as such. The others follow from the plan's principles, and are open to change at sign-off.

| #  | Decision                                                                                                                                                                                                                                                                                | Source                                        |
| -- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| 1  | Scope lives on the **Codebase Structure** designer: a `Drift Scope` stereotype on the Root Folder, folders and projects, with rows of match, in or out, and reason.                                                                                                                     | User, 2026-11-12                              |
| 2  | The engine reads **Intent's model directly** (designers, elements, stereotypes, associations). There is no intermediate model format. The suite keeps its models as data: the test harness turns a fixture's model into Intent model objects, so only the tests carry that translation. | User, 2026-11-12                              |
| 3  | **Readers never build or run the code.** A framework reader reads committed files only, such as EF Core's migration `ModelSnapshot.cs` or a checked-in `openapi.json`.                                                                                                                  | User, 2026-11-12                              |
| 4  | **The model states a value only where the code states it explicitly.** A table name is modelled only when the code has a `ToTable`. Conventional values aren't modelled, so no rule re-derives a framework convention to make a modelled value pass.                                    | User, 2026-11-12                              |
| 5  | The suite is **JSON Schemas plus data fixtures**. Tests that check the fixtures pass now; tests that need the engine are skipped until phase 1 plugs it in.                                                                                                                             | User, 2026-11-12                              |
| 6  | Code-only explicit values the model doesn't state (a `ToTable` with no modelled table name) are not drift by default. They are an opt-in "must be modelled" rule (`unmodelled.value`).                                                                                                  | Principle 1, from decision 4                  |
| 7  | A modelled item missing from the code is a finding, never a pending Software Factory change.                                                                                                                                                                                            | Principles 2 and 4                            |
| 8  | Every claim with no rule is its own can't-verify finding, not one warning per kind.                                                                                                                                                                                                     | Principle 2                                   |
| 9  | Unnamed indexes are claims. Common.Drift left them out to avoid permanent can't-verify rows.                                                                                                                                                                                            | Principle 2                                   |
| 10 | Empty model values are not claims. Common.Drift stated them so code-only values were caught; that is now the opt-in rule in decision 6.                                                                                                                                                 | Principle 1                                   |
| 11 | Model-only rules (naming, a Layer needs a Path) are designer validation, not drift. The engine doesn't run them.                                                                                                                                                                        | Plan, "from module building: live validation" |
| 12 | Coverage inventories of code the model can't state are dropped.                                                                                                                                                                                                                         | Principle 1                                   |
| 13 | Rules are keyed by claim kind, not by the pack whose vocabulary stated the claim, and a kind may have several rules. The EF Core pack reads `relationship.onDelete` whichever pack's vocabulary stated it. See [rules.md](rules.md) and [packs.md](packs.md#who-ships-what).                | Principle 5                                   |
| 14 | When two packs give conventions for one element type, the pack that requires the other wins (house over stack over core). Two unrelated packs that disagree are a `config/conventionConflict` error.                                                                                    | Principle 5                                   |
| 15 | A type is located by name among every kind the language has, so a Class written as an `enum` is reported as the wrong kind, not as missing. `type.kind` verifies when the code's kind is one the conventions allow (`class` or `record` for a Class).                                     | Principles 2 and 6                            |
| 16 | Nullability is compared once, by `member.nullable` and `parameter.nullable`. The `type` comparer ignores it, so a `string?` modelled as `string` is one finding, not two.                                                                                                              | Principle 6                                   |
| 17 | An operation is the method of its name. Overloads are told apart by parameter names, then by parameter types, then by count. A single method of that name is the operation's method, so a wrong parameter list is a contradicted `operation.parameters`, not a missing operation. | Principle 6                                   |
| 18 | Vocabulary can follow element-valued stereotype properties, mappings and generic type arguments, and read association ends and whether a package is referenced. That is what the proxy, gRPC and generic-type checks need. See [vocabulary.md](vocabulary.md).                          | Decision 2, principle 5                       |
| 19 | A pack can add placeholders to another pack's vocabulary entry (`extends`), so a module's Backing Field stereotype makes `column.name` look at the field without redefining the entry.                                                                                                  | Principle 5                                   |
| 20 | `{Folder}` keeps Common.Drift's meaning, the nearest designer folder's name, so its checks map by name. Structure kinds use `{FolderPath}` for the full path.                                                                                                                         | Conversion                                    |
| 21 | The TypeScript reader (with Vue single-file components) and the Protobuf reader are specified now and built later, in the `intent.typescript` and `intent.protobuf` packs. Their cases fix what they must do. The JAV-FE and gRPC checks trace to them.                                     | Principle 5                                   |
| 22 | A project file that won't parse is a reader failure: one `engine/readerFailed` finding for the file, and `readerFailed` for every claim that needed its settings. A syntax error in a source file gets no finding of its own; claims read from the nodes it leaves incomplete are `readerFailed`. | Principles 2 and 3                            |
| 23 | Index columns are ordered. JAV-DOM-30 compared column sets; a reordered index is now contradicted.                                                                                                                                                                                      | Principle 3                                   |
| 24 | JPA states a user-supplied key only by silence (no `@GeneratedValue`), so a modelled "User supplied" Data source on JPA is contradicted as not stated. On JPA the model leaves Data source at its default.                                                                               | Decision 4                                    |
| 25 | Opt-in rules are policy: they are available from phase 1, and each has one default severity. eShopCustom's "note" level findings become errors unless the model overrides their severity.                                                                                               | Principle 1                                   |
| 26 | A pinned pack found at a different version is `config/packVersion`, separate from `config/packMissing`, and doesn't run. A module upgrade never silently changes what is checked.                                                                                                      | R52                                           |
| 27 | `Drift Scope` applies to the Root Folder and Folders only, not to project elements. Targeting the Visual Studio project types made the module depend on Intent.VisualStudio.Projects, which a Java codebase doesn't have; a row on the Root Folder or a folder covers any project by glob. | Phase 1 build; language-neutral core (plan)   |
| 28 | With no Drift Scope the hosted run only warns and adds no Area to the drift report. An error would stop Intent applying any of the run's changes, including the ones that set scope up. `scope/missing` stays an error in the run result. | Phase 1 build                                 |
| 29 | A nullability claim whose code is outside a nullable context isn't drift: it stays can't verify `unresolved` in the run result, has no finding of its own, and one `engine/notStated` info note lists them. The drift report says "Drift found" for any finding, so per-claim findings made a clean codebase report 753 errors. | Phase 1 build, basislink5 run |
| 30 | **The drift report holds only drift.** An AI reads it, so anything else is noise. What is out of scope isn't drift, so it is never listed there: the coverage listing (`scope/coverage`) and the `engine/notStated` note are info, written to the Software Factory log only. An Area appears only when it has a finding, and never shows a category as clean. | User, 2026-11-13 |

## Open questions for sign-off

1. **"Same results" in phase 6 means the same verdicts, apart from the listed semantic changes.** Decisions 4 and 6 to 10 change what Common.Drift reported. For example, a modelled table name with no `ToTable` passed in Common.Drift through `absent: {Entity}`, and now is contradicted. [conversion.md](conversion.md) lists each change, and phase 6's side-by-side run must explain every difference by one of them.
2. **Default severities.** The proposal is: every can't-verify outcome is an error, as contradicted is. A stale scope entry or exception is a warning. A missing reason on an Out entry is an error. See [claims-and-findings.md](claims-and-findings.md).
3. **Where a house pack lives.** The proposal is `drift/` in the folder that holds the application's `.application.config`, beside Common.Drift's `guardrails/`, committed with the code.

## Glossary

| Term        | Meaning                                                                                                                                   |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Claim       | One checkable statement the model makes about the code: a claim kind, the element that states it, the expected value and its placeholders |
| Claim kind  | A named kind of claim, such as `table.name` or `member.type`                                                                              |
| Vocabulary  | Pack data that turns model elements into claims (block 1)                                                                                 |
| Code graph  | What the code readers produce: files, types, members, statements, imports, calls, each with its location (block 2)                        |
| Rule        | How a claim's value is read from the code graph: the structure rule or a module's claim reader (block 4)                                  |
| Reading     | A rule's result for one claim: a value and where it came from, or why there is none                                                       |
| Outcome     | Verified, contradicted, or can't verify with a reason                                                                                     |
| Finding     | A row in the drift report: a claim that isn't verified, or a scope, configuration or opt-in rule finding                                  |
| Scope       | Which code is read: In and Out entries on the Codebase Structure designer                                                                 |
| Pack        | A bundle of vocabulary, rules, language profiles, conventions and plug-ins for one technology, or for one codebase's house style          |
| Opt-in rule | A "must be modelled" rule a team turns on; it reports in-scope code of a kind the model doesn't describe                                  |
| Silence     | A reading taken from `default` or `absent`: the code says nothing about the claim                                                         |
