# Context: Intent.AspNetCore.Controllers.Dispatch.Mediator

## Purpose

Makes the controllers generated by `Intent.AspNetCore.Controllers` for Commands and Queries dispatch through Mediator's
`ISender`. A satellite of `Intent.Application.Mediator` (plan: `intent/.plans/2026-10-13-mediator-dispatch-modules.mdx`,
decisions G1, G2, G5, G11). It is a port of `Intent.AspNetCore.Controllers.Dispatch.Wolverine`; only the injected type and
the call differ.

## Architectural Decisions

- **Ported from the Wolverine controller dispatch; the only changes are the type and the call.** The injected type is
  `Mediator.ISender` (field `_sender`), the call is `await _sender.Send(payload, cancellationToken)`. Mediator's `ICommand`,
  `ICommand<T>` and `IQuery<T>` all resolve through the same `Send` overloads, so the response type is inferred; the
  generated call has no type argument and the void and typed forms differ only by whether `var result =` is emitted.
- **The module replaces the `ControllerTemplate` registration for CQRS elements.** `ImplicitControllerTemplateRegistration`
  registers `ControllerTemplate.TemplateId` itself with `CqrsControllerModel`s (grouped by parent folder, one controller per
  group, `Default` for the package root). The extension only touches controllers whose model is a `CqrsControllerModel`.
- **Command and query types are resolved through the core's template ids as type sources.** The extension adds
  `Intent.Application.Mediator.CommandModels` and `Intent.Application.Mediator.QueryModels` (and the `Application.Contract.Dto`
  role) to the controller. Rejected: referencing the core's template classes. Seam and dispatch modules take string ids and no
  `ProjectReference` on the core (G11); the ids are listed in the plan's "Template ids other modules depend on".
- **`Intent.Modules.AspNetCore.Controllers` is referenced as a NuGet package**, not a project reference, for package-boundary
  integrity (as in the Wolverine module).
- **Priority 10 `OnBuild`.** The dispatch statement is added after the controller template has built its action methods; the
  parameter-to-payload statements are inserted from an `OnBuild` of the command and query templates at the same priority.

## Invariants & Constraints

- **Mutually exclusive with `Intent.AspNetCore.Controllers.Dispatch.Wolverine` and `.MediatR`.** All three register the controller
  template for the same Commands and Queries (same template id, same `CqrsControllerModel` shape), so installing more than one
  produces conflicting controllers. Documented in the README, not guarded by a `FriendlyException` (G3).
- **The template ids `Intent.Application.Mediator.CommandModels` / `QueryModels` are a contract with the core.** Renaming or moving
  those File Templates in the core's Module Builder makes this module find nothing, silently: no type source, no parameter
  assignments, and `GetMappedPayload` falls back to `new Type()`.
- **The generated action ends with `controllerTemplate.GetReturnStatement(...)`** from `Intent.AspNetCore.Controllers`; this module
  never emits the response itself.
- **The imodspec declares `Intent.Application.Mediator`** because the generated controller needs `Mediator.ISender`, the command and
  query contracts and the handlers it brings.

## Module Interactions

- **Intent.AspNetCore.Controllers** - supplies `ControllerTemplate`, `IControllerModel` and `FileTransferHelper`. Built against `7.1.10`.
- **Intent.Metadata.WebApi** - `4.6.4` declared (as the Wolverine counterpart); supplies the HTTP settings models.
- **Intent.Application.Mediator** - written against `1.0.0-pre.0`. Its imodspec interoperability installs this module when
  `Intent.AspNetCore.Controllers` is detected.
- **Intent.AspNetCore.Controllers.Dispatch.Wolverine / .MediatR** - siblings; mutually exclusive (above).
