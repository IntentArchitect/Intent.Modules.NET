# Intent.Bugsnag — Context

## Purpose

Adds Bugsnag error reporting to a .NET application: the NuGet package, configuration, ASP.NET Core middleware and, when `Intent.QuartzScheduler` is installed, a Quartz job listener that reports exceptions thrown by scheduled jobs.

## Module Interactions

- **Intent.QuartzScheduler: the job listener must match the Quartz major that module requests.** `BugSnagQuartzJobListenerTemplate` and `BugSnagQuartzJobListenerExtension` do not decide from the target framework. In `OnBuild` they look up the template with role `Distribution.DependencyInjection.Quartz` (QuartzScheduler's configuration template) and read the NuGet packages it requested: a `Quartz*` package at 4.x or later means Quartz 4 (`Templates/BugSnagQuartzJobListener/QuartzVersion.cs`). Decided 2026-11-18 after review.
  - Rejected: repeating QuartzScheduler's framework rule here. The first version did (`GetMaxNetAppVersion().Major >= 10`), and it had two faults. It had to change in step with QuartzScheduler's rule, which had just changed to "every target framework is net10+", and it decided for Bugsnag's own project, which need not be the project the Quartz configuration lands in. It also made Bugsnag depend on a minimum QuartzScheduler version: QuartzScheduler 1.1.0 requests Quartz 3 on `net10`.
  - The lookup is a lookup, so it runs in `OnBuild`, never the constructor. It relies on QuartzScheduler requesting its package in the configuration template's constructor (from 1.2.0). Build callbacks at the same order run sorted by template type name, so `Intent.Modules.Bugsnag…` runs before `Intent.Modules.QuartzScheduler…`, and a package requested in one of that template's callbacks is not there yet. The first 1.2.0-pre.0 build did exactly that, and the listener always came out in the Quartz 3 shape (found in review, 2026-11-18). QuartzScheduler 1.1.0 still requests during the build, which is harmless: an empty result means Quartz 3, and 1.1.0 is Quartz 3.
  - Quartz 3 → 4 (adapted in 1.0.10, 2026-11-13): `IJobListener` callbacks return `ValueTask`, and every member has a default implementation. Quartz 4 rejects a listener whose methods do not match at startup, with a `SchedulerConfigException` from `AddJobListener`. It is not a compile error. So on Quartz 4 the template emits only `ValueTask JobWasExecuted` and leaves the two no-op callbacks to the defaults. `GroupMatcher` moved from `Quartz.Impl.Matchers` to `Quartz`, so the extension adds that using only on Quartz 3.
  - Because the listener follows what QuartzScheduler requests, Bugsnag works with any QuartzScheduler version and has no `<interoperability>` entry for it. The reverse is needed: QuartzScheduler's `.imodspec` installs Bugsnag `1.0.10`, since an older Bugsnag emits a `Task` listener whatever Quartz the project gets. That detect version is hand-maintained.
  - On Quartz 4 the registration is `q.AddJobListener<T>(new IMatcher<JobKey>[] { GroupMatcher<JobKey>.AnyGroup() })`. Quartz 4 declares the matchers as a C# 13 `params IReadOnlyCollection<IMatcher<JobKey>>`, and under LangVersion 12 or lower (this repository's root `Directory.Build.props` pins 12.0, and any consumer may) a params collection is an ordinary parameter. So both a bare matcher (CS1503) and no argument (CS1501) fail to compile there. An explicit array binds under every language version and keeps the 3.x "every group" semantics. Found by building a scratch consumer, 2026-11-18.
  - `JobWasExecuted` uses `Async(asValueTask: usesQuartz4)`. `Async()` alone is `Async(asValueTask: false)`, which rewrites a `ValueTask` return type to `Task`, and the first 1.0.10-pre.0 build emitted a `Task` listener on Quartz 4 because of it.
  - Verified against a scratch consumer, 2026-11-18. On `net10` (worker and web), Quartz 4 accepts the listener at startup with no `SchedulerConfigException`, and `JobWasExecuted` is called with the job's exception. On `net9` and on a `net9.0;net10.0` multi-target, the output is unchanged from 1.0.9. Updating Bugsnag alone on `net10`, with QuartzScheduler still on 1.1.0, also left the output unchanged (Quartz 3 listener), and the app ran on Quartz 3.22.10. In the Tests solution, QuartzScheduler's detect moved both Bugsnag apps to 1.0.10-pre.0. `BugSnagTest.ServiceHost` (`net10`) got the Quartz 4 listener and starts on Quartz 4.7.3, and `BugSnagTest` (`net9`) regenerated with zero source diff.
