# SDD — Verify

You are running the **verify** step — the review pass after `/sdd-implement`. Check that what was built actually satisfies the spec and **record a per-requirement verdict** the flow can act on. This is **review, not repair**: your only write is the verdict — you do not change the model or code, and you raise no gate. When gaps remain, `/sdd-heal` fixes each failing requirement **in place**, one gap at a time, and never re-does the work that already passed; you just judge. Your gap descriptions **are** the healer's brief, so make them precise and actionable.

**Dispatched with only a slug** (as `/sdd-run` does): judge from the spec, the model and the code alone. Treat every earlier claim — a wave report, a heal summary, the previous verdict — as unverified until you have checked it yourself. Your final reply goes to the dispatcher, so end with the chat report from **Record the verdict, then report**.

## Honour the solution's governance

When the spec's framework declares governance documents — Spec Kit's `.specify/memory/constitution.md`, say — `read_spec` returns them as `governanceDocuments` and the Specs panel lists them. **Read them first and treat their rules as binding on what you produce.** They are the user's standing constraints, not background reading. If a requirement and a governance rule genuinely conflict, say so and ask rather than silently picking one.

## What to do

**First, resolve the slug — never guess it.** If you weren't handed an exact slug, call **`read_spec` with no `slug`**: it lists every spec in the solution with its `slug`, `phase` and progress. Match what the user named against that list. Specs live under `intent/.specs/` and are reachable **only** through `read_spec` — never glob or grep the workspace hunting for spec artifacts. If nothing there plausibly matches what they named, `ask_user_question` offering the closest specs as options rather than inventing a slug.

**Questions that cite requirements.** Pass the slug as `spec` on every `ask_user_question` that names a requirement id, so the card links each id to its requirement, and say in plain words what each cited requirement requires: the user may not remember what `R3.14` is.

1. Load the spec:
   - `read_spec(slug, artifact: "requirements")` — the EARS acceptance criteria (R1, R2, …), **and the framing sections above them**: the **Key User Journeys** (`UJ-N`) are what the criteria are trying to add up to, the **Glossary** is the vocabulary the model should speak, and **Non-Goals / out-of-MVP** is a boundary the implementation can violate just as easily as it can fall short of a criterion. An imported spec (e.g. a BMAD PRD) carries the same material under its own headings — `read_spec` returns the framework's own documents with `externallyOwned: true`, and they are **read-only** here: never write or normalize a `requirements.md` for such a spec. If the requirements themselves are wrong, say so and stop rather than fixing them in place.
   - `read_spec(slug, artifact: "design")` — the intended model changes + realization plan.
   - `read_spec(slug, artifact: "traceability")` — which tasks/elements/files were meant to satisfy each requirement. Compact per-requirement target summaries by default; `read_spec(slug, artifact: "traceability", requirementId: "R3")` for one requirement's full targets.
   - `read_spec(slug, artifact: "coverage")` — the covered/uncovered/stale/broken rollup: summary + one compact row per requirement (`id`/`title`/`status`/`linkCount`), **no** per-target arrays. Narrow to the failing ones with `status: "gap"` (or `uncovered`/`stale`/`broken`/`covered`), and drill into one requirement's full targets with `requirementId: "R3"`.
   - `read_spec(slug, artifact: "tests")` — the `testFiles` citing the spec, then each criterion that is not yet `tested` with its **test status** (`partly tested`, `stale`, `unconfirmed`, `mismatch`, `untested`, `judged` or `untestable`) and how many tests cite it, and any orphan citations. This decides how each criterion is judged (step 2, **Tests**). A criterion's numbered clauses and citing tests (`file:line title`, each marked with its degree or `unconfirmed`) come only with `requirementId`, which includes the tested criteria too: read them one requirement at a time, as you or a sceptic judge it, never for the whole spec. A test cites criteria in its title as `[spec:<slug> R1.4, R1.5]`.
   - `get_change_review(section: "traceability", specSlug: "<this spec>")` — the **change side** of the same question, and the one input here that is computed rather than judged. `coverage` walks from each requirement out to its links, so it can only ever see a requirement nobody linked; it is structurally blind to the opposite failure — a designer element or hand-written file that was changed for this feature and that **no requirement points at**. This is the deterministic review the Changes Review tab renders, over the merge-base → working tree range, so committed waves and the worktree are both in it. It returns a compact text report: the traced map (spec → requirement → the changes realizing it, `[stale]`-marked) followed by the `untraced elements` and `untraced custom files` lists. Read it before you judge anything: it tells you where to look as well as what is missing.
     - **Always pass `specSlug`** — it names the one spec whose requirements get expanded. Every other spec in range is reported as a name plus its requirement count, and omitting `specSlug` expands none of them. The untraced lists stay solution-wide either way, because they are the gate. It also decides what counts as traced there: this spec's links count even when recorded before the range, another spec's only when recorded inside it.
     - Rows are **rolled up into their parent**: a row ending `(+N child change(s))` is **N+1 changes**, not one — the parent plus N of its attributes / fields / operations that changed too. Read it as a group when you resolve it, and don't mistake it for a single finding.
     - Every list is capped (`maxRows`, default 200) and any overflow is stated in the output — if you see rows omitted, re-run that section with a higher `maxRows` before judging, rather than treating the visible rows as the whole set.
     - Check the range line in the feedback. When no base branch could be resolved (a solution sitting on its own trunk, a single-branch clone) the review falls back to a HEAD baseline and says so — that range covers **only the working tree**, so committed waves are invisible in it. Re-run with an explicit `refA` (the commit the spec's work started from) or `baseBranch` before you conclude that anything is untraced or missing. Whichever range you settle on is the one `record_spec_verdict` re-checks: it reuses the range of your last `get_change_review` call in this conversation, so you do not have to repeat it (you may still pass `refA` there to override). A range whose refs aren't a walk from an older baseline to a newer comparand — reversed, or two diverged branches — is also called out on that line; the diff is correct, but added work reads as deleted in a reversed one, so fix the range rather than judging from it.
     - When the spec already has a verdict, a defaulted range starts at the commit that verdict recorded, and the range line says "(last verify)". That verify resolved every untraced change before it. Pass an explicit `refA` only when you need the whole branch.
2. Verify, per requirement:
   - **Model**: `getDesignerValidationErrors()` is clean; the designed elements/associations exist (`searchElements()`, `getElementDetails()`).
   - **Coverage**: every requirement has ≥1 trace target, spanning **both** what realized it — every model change it drove (the designed elements/associations) **and** every custom-code file written for it must be linked. Flag `uncovered`, `stale` (a criterion was reworded since its tests were judged), and `broken` (a linked element/file no longer resolves against the saved model / disk — `read_spec(slug, artifact: "coverage")` now computes this, matching the Specs panel). A `broken` (or `uncovered`) requirement — including one whose model is linked but its custom code isn't, or vice versa — is a coverage gap: record it as a **`gap`** verdict whose `actual` names the missing/unresolved target, so `/sdd-heal` re-records the corrected link. Because `complete_spec_task` refuses to tick a `[model]`/`[code]` task while its designer is unsaved **or while any of that task's recorded links is broken**, and `record_spec_traceability` rejects a target that doesn't resolve rather than storing it, a wave that reached "all ticked" implies its links resolved at the time. So a `broken` link at verify time means it broke **after** the tick — a later rename or delete, or a hand-edited `traceability.json` — and an `uncovered` requirement usually means a rejected link was never re-recorded. Both are still gaps; the distinction is what the healer should go looking for.
   - **Untraced changes — the deterministic gate.** Every row under the change review's `untraced elements` / `untraced custom files` is a change that was made and that nothing claims. **Resolve each one, and say which way you resolved it** — leaving them unmentioned is the failure this step exists to prevent. There are exactly two allowed outcomes per untraced change: either it **realizes one of this spec's requirements** (the wave just never recorded the link) — record a **`gap`** on that requirement, naming the untraced element/file in `actual` and `location` so `/sdd-heal` records the missing link, attributing it via `design.md` / `tasks.md` — or it **belongs to other work** (a different spec, a manual fix, an unrelated refactor sharing the branch) — record no gap and name it in your chat report as out-of-spec work. The range is solution-wide, so the second outcome is normal, not a failure. Three things are deliberately **not** untraced findings and never appear in the lists: a deleted element (nothing is left to link), a `FullyManaged` file (generated output — its traceability belongs on the model element that produced it) and a test file (its title cites the criteria it asserts). Conversely, when the report warns that a designer's element diff failed, the element list is **incomplete** — say so rather than reading it as clean.
   - **Tests — the durable proof.** Judge each criterion by its test status from `read_spec(slug, artifact: "tests")`:
     - **tested** (a confirmed, current binding): run its citing tests narrowly, by the files they sit in (`read_spec(slug, artifact: "tests", requirementId: <its requirement>)` lists them; a full verify takes every `testFiles` entry at once), each joined to its `testRoot`: `npx jest <file> -t "spec:<slug> "` (never put the brackets in: `-t` is a regex), or `dotnet test <project> --filter "(FullyQualifiedName~<class>|…)&DisplayName~spec:<slug>" --logger "console;verbosity=normal"`, naming the classes those files declare (so passing tests are listed by name). Run each project once for everything you need from it. Then read each cited title's own result, because these select every test in those files citing the spec, and a cited test that didn't run counts as red: each criterion's `tests` count is how many results citing it must pass. A build or test command that fails before any test runs because a file it writes is locked or in use by another process (another agent is building) is no result: run it again once, and if it is still locked, report it as blocked rather than as a disagreement. Green is a pass for that criterion. Red is a **disagreement**. Don't re-read the code for it.
     - **stale** or **unconfirmed** (its wording or a citing test changed since it was confirmed, or it was never confirmed): run the citing tests, then have the **sceptic** below judge each test `read_spec` marks `unconfirmed`. A test marked with a degree (`full`, `partial 1,3/4`, `mismatch`) is already judged against this wording and body: never re-judge it. The sceptic records one binding per judged test.
     - **partly tested**: run its citing tests as for tested. The missing clauses are heal's work, not a gap.
     - **untestable**: judge it by reading the code (`read_file`), and only when `read_spec(slug, artifact: "verdict")` lists its requirement in `movedSinceVerdict`. Otherwise it holds as judged. A **judged** criterion (an earlier verify passed it by reading the code, as no test cites it) is handled the same way.
     - **mismatch** (a sceptic found a citing test asserting what the criterion doesn't say, and neither has changed since): it is still a disagreement. Read its requirement with `requirementId` for the mismatch's reason and its test's `file:line`, and record it as one again.
     - **untested**: report it. It is not a gap: heal writes its tests. In a **full** verify (a spec's first, an extraction's, or one the user asks for), judge its requirement by reading the code like any other: that audit is what catches defects no test covers. A targeted verify doesn't re-audit it. Passing a requirement judges its untested criteria, so give that result a `reason` naming where the code satisfies them (step 1 under **Record the verdict**). When your instructions say heal reported it untestable, give it to the sceptic with heal's reason. Only your sceptics record `untestable`, and only when they agree; otherwise it stays untested. Report every orphan citation (an id that is not one of the spec's criteria, such as a bare `[spec:<slug> R12]`) on the requirements you judge as an observation naming the test, and ask that it cite the criteria it asserts (`[spec:<slug> R12.1, R12.3]`). A citation that names no criterion tests none, so it can never stop a code change counting as out of date.
   - **Disagreements.** A failing citing test, or a sceptic finding that a test asserts something the criterion does not say, is a disagreement: neither side wins by default. Record it as a **`gap`** whose `reason` starts with `Disagreement:`, with `expected` = the criterion's wording, `actual` = what the test and code do, and `location` = the test's `file:line` plus the code it exercises. The Run asks the user once, for all of them, whether to fix the code, change the test or reword the criterion.
   - For a large area, you may dispatch `discovery` sub-agents (`create_sub_agent`) to map it read-only before judging. Emit them in a **single response** so they run concurrently, each with a slice of the requirements. Use **at most four** in all, because each one re-reads the same spec and code. Have each return, per requirement, its verdict and the `file:line` it rests on.

   **The sceptic.** Dispatch sceptic sub-agents for the stale and unconfirmed criteria still to judge, and the untested ones heal reported untestable, one per about twelve criteria, grouped by requirement and all in a single response. Use your host's own sub-agent tool when it has one (Claude Code's `Agent`), because those run in parallel; otherwise use `create_sub_agent` with `agentId: "discovery"`. Give each one the slug and the criterion ids to judge, plus heal's reason for any untestable claim. Have it read each criterion with `read_spec(slug, artifact: "tests", requirementId: <criterion id>)`: that gives its numbered `clauses` and every citing test with its body, the `unconfirmed` ones to judge marked, so it reads code only where a body calls a helper it needs to see. Don't read them yourself to paste them into the brief. Have it record its own judgements and return only the mismatches (`criterion · file:line · what it asserts that the criterion doesn't say`), each untestable claim it agreed or disagreed with, and any binding still refused. The brief, per unconfirmed test:

   > Judge this test against the criterion's numbered clauses, reading its other citing tests too: which clauses does it actually assert? It asserts a clause when it checks part of it and the criterion's tests together check all of it (R28.12), so a clause whose branches are split across tests is credited to each. A test that sets up a case but never checks the outcome asserts nothing. Return `full` when it asserts every clause, `partial` with the `covered` clause numbers (possibly none), or `mismatch` naming what it asserts that the criterion does not say. Return `untestable`, with the reason in a few words (e.g. `visual judgement`), only when no automated test could assert the criterion; for a claim heal made, say whether you agree.

   > Then record every judgement with `record_spec_verdict(slug, bindings)` and no `results`, one binding per judged test, naming the test as `read_spec` lists it (`test: "tests/A.test.ts:12"`): `{ criterion, test, degree: "full" }`, `{ criterion, test, degree: "partial", covered: [1, 3] }`, `{ criterion, test, degree: "mismatch", missing: "<what the test asserts that the criterion doesn't say>" }`, or `{ criterion, degree: "untestable", missing: "<reason>" }` for a heal claim you agree with. Fix and record again each binding it refuses, except one refused because you changed that test.

   The sceptics' bindings are the judgements: don't record them again. The criterion is tested once its tests' bindings together cover every clause. A `mismatch` is also a disagreement, recorded as a gap below.
3. **Then verify the journeys, not only the criteria.** Criteria pass one at a time; a user journey is what they are supposed to add up to, and a feature can satisfy every criterion and still have no working path through `UJ-2`. Walk each `UJ-N` beat by beat against what was built — entry state, each step of the path, the climax, the resolution, and its edge case — and check there is a real operation / endpoint / interaction behind each beat. A journey with a missing or dead beat is a **`gap`**, recorded against the requirement(s) that name it under `**Realizes:**` (or the nearest owning requirement when none does), with the broken beat in `actual`. While you're there, flag anything built that lands in **Non-Goals** or out-of-MVP scope — that's a gap too, and the healer's brief is to remove it, not to add more.

## As-built mode (extraction)

When `/sdd-extract` loads this skill, the spec documents code that already existed, so **the code is the truth**. That is a user decision, and these deltas apply:

- **Pass `refA: "HEAD"`** to `get_change_review`. The feature was committed long before the spec, so the branch range would list every unrelated change on it as untraced. With `HEAD`, the untraced gate covers only uncommitted work, which is what the extraction itself touched. Say in the report that the range is deliberately narrow.
- **A behavioural gap means the requirement misdescribes the code**, not that the code is wrong. Record it as normal: `expected` is the criterion as written and `actual` is what the code does. `/sdd-extract` rewords the criterion to match `actual` and verifies again. If the extra behaviour would push the criterion over the atomicity limit in **sdd-requirements**, it becomes a new criterion id instead. It does not heal.
- Code changes happen only through the suspected-bug questions `/sdd-extract` asks after the verdict, never from here.

## Re-verify mode (dispatched with requirement ids)

When you are told to re-verify only some ids (as `/sdd-run` does after a heal), the rest of the verdict stands as recorded. Judge only those ids, exactly as above, with these deltas:

- **Ids may be criteria** (`R3.14`): judge only those, and give one result for each requirement they belong to. Judge each by its test status exactly as above: a tested criterion's tests are run, never re-read.
- **Load only what they need.** Read `catalog`, `traceability` and `coverage` with `requirementId` for each id, `tests` once without it for the statuses and `testFiles`, and read only the journeys those ids name under **Realizes:**. A requirement's clauses and citing tests are the sceptic's to read, as above. You don't need the whole requirements document or the design.
- **Review only the new changes.** Leave `refA` unset. Given the spec, the change review starts at the commit the last verify recorded, because that verify resolved every untraced change before it, and its range line says "(last verify)". It falls back to the default range by itself when that commit is gone.
- **No reader fan-out.** Judge the ids yourself. Challenge the candidate gaps as below.
- **Traceability gaps only:** when told so, judge them from `coverage` and the change review alone. Read no code and dispatch nothing.
- **When told to run the tests citing other requirements**, run them once, by the files they sit in, with the commands under **Tests** above, together with the tests of the ids you judge. Record each failing test as a disagreement on the criteria its title cites, even on a requirement you were not given. When a test fails in its own setup before it asserts any behaviour (a script or module it never loads, a fixture that no longer matches the code's shape), say so in the gap's `actual` and recommend **change the test**. With no ids listed, judge nothing else.
- **Record with `merge: true`**, with one result for each listed id and each requirement a failing citing test gave a gap, and none for any other. Without `merge`, the requirements you didn't judge drop out of the verdict.
- **Problems outside the list are observations, not gaps.** If you notice that a requirement you weren't asked to judge looks wrong, or an untraced change realizes one, put it in your report under "Observations", with `file:line`. Do not record a result for it, even when `record_spec_verdict`'s feedback asks for a gap.

## Challenge every gap before you record it

A false `gap` is expensive: `/sdd-heal` turns each one into a repair task, so a mistaken gap sends the healer to change working code against a requirement it already satisfies. Before recording, **try to disprove each candidate gap** — passes need no challenge, only the gaps do.

Dispatch **one** `discovery` sub-agent for all the candidate gaps, not one each, briefed to argue the opposite case for every one. Split them across two sub-agents only when there are more than eight. For each candidate the brief is:

> Requirement `<id>` is claimed to be unsatisfied because `<candidate reason>`. Read the model and the code and try to show it IS satisfied — the behaviour exists somewhere the reviewer didn't look, the element is linked under a different id, the criterion is met by generated code rather than hand-written code, or the reviewer misread the criterion. Report `refuted` with the exact element id / `file:line` that satisfies it, or `confirmed` with precisely what is missing.

Then:

- **Refuted with evidence** — record it as a `pass` and cite that evidence in your report.
- **Confirmed** — record the `gap`, and fold the validator's specifics into `actual` / `location`; a challenged gap gives the healer a much sharper brief than an unchallenged one.
- **Inconclusive** — record the `gap`. When you genuinely cannot tell, a gap is the safe verdict; say in the report that it was inconclusive.

**Disagreements skip the challenge too**: a test either failed or the sceptic already argued the case, and the user settles them.

**Traceability gaps skip the challenge entirely** — both the `broken`/`uncovered` ones `read_spec(slug, artifact: "coverage")` computed and the untraced changes `get_change_review` computed. They are already machine-checked: a link either resolves or it doesn't, and a changed node either carries a requirement ref or it doesn't. There is nothing for a sceptic to refute, so dispatching one only burns a turn. Record them directly. The one judgement left on an untraced change is **attribution** — whether it belongs to this spec or to other work — and that is yours to make from `design.md` / `tasks.md`, not a validator's.

## Record the verdict, then report

1. **Record the machine-readable verdict.** `record_spec_verdict` is available in **every** session type — a panel-fired review, an in-app chat, or an external ACP harness — so recording the verdict is always the required output of this step, never something to skip because no panel is watching. Call `record_spec_verdict(slug, results)` with one result per requirement. In re-verify mode, give one result per listed id and pass `merge: true`. A **pass** is `{ requirementId, verdict: "pass" }`, plus a `reason` naming the `file:line` that satisfies its untested criteria when it has any: the tool records that reason as their `judged` binding, which holds until their wording or code moves. The sceptics already recorded the test bindings (step 2), so pass none; the tool hashes each criterion's wording and test body itself into the spec's `test-judgements.tsv`. A **gap** carries the healer's brief — `{ requirementId, verdict: "gap", reason, expected, actual, location }`:
   - `reason` — a one-line summary of what's missing or wrong.
   - `expected` — what the acceptance criterion requires (the target behaviour the fix must produce), starting with the ids of the criteria it fails (`R1.4, R1.10 — …`): heal writes tests only for those.
   - `actual` — what is actually there now: the specific deficiency (missing, wrong, or a broken/absent element).
   - `location` — where to fix it: the file(s) and/or model element(s)/operation(s) involved.

   Mark `gap` whenever the behaviour the criteria describe isn't genuinely there **and the challenge above didn't refute it**; when unsure, prefer `gap`. **`/sdd-heal` reads these fields straight from `verdict.json` as its brief** and turns each gap into one repair task — so `expected`/`actual`/`location` must be precise and actionable, not vague. A weak brief produces a weak fix; leaving them blank leaves the healer guessing.

   `record_spec_verdict` **re-runs the change review itself** and warns in its feedback when untraced changes remain after your verdict. It does not store that review: the untraced lists are solution-wide, so they describe the branch rather than this spec, and your chat report (step 2) is where they are accounted for. Treat the warning as a prompt to correct the verdict, not as noise.

   It re-runs over **the range you reviewed**, not a fresh default: the range of your last `get_change_review` call in this conversation, or `refA`/`refB`/`baseBranch` if you pass them there (which wins). If that range was narrowed, the feedback says so too — an empty untraced list over a working-tree-only baseline is a much weaker result than an empty one over the branch's merge-base, and if that is what you got, widen the range with `refA` and record again rather than reporting it as clean.

   `verdict.json` and `test-judgements.tsv` are committed with the spec. The judgements file merges line by line (`merge=union`), so two branches' bindings combine. When `verdict.json` conflicts on merge, re-run verify rather than merging it by hand.

2. **Report in chat too.** Summarise the per-requirement verdict for the user, each citing its evidence (an element id, a file, a test, or the missing piece), give the test status counts (tested, partly tested, mismatch, untested, judged, manual check), list the **disagreements** apart from the other gaps, note how many candidate gaps the challenge pass refuted, and list the concrete gaps — call out any traceability problems (uncovered, broken links, stale or mis-linked traces) alongside the behavioural gaps.

   State the **change review** result explicitly too, because it is the part the user cannot reconstruct from the verdict rows: the range reviewed, how many changed elements and code files it covered, how many requirements they realized, and — one line each — every untraced change with how you resolved it (which requirement's gap it became, or why it is out-of-spec work). If nothing was untraced, say so in a sentence; that is a real result and worth stating plainly.
3. **Stop.** The recorded verdict is the phase decision, and the lifecycle applies it: a clean verdict moves a spec at verification to **done**, whatever the gate cadence, and a verdict with gaps leaves a done spec at **done**, showing its gaps. `record_spec_verdict`'s feedback says when the phase moved. Change nothing else.
