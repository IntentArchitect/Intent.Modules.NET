# Context: Intent.Common.Drift

## Purpose

The drift check that compares a designer's model with hand-written code, and the always-on rule and skills that go with it, shared by every module that contributes a designer. It knows no designer: Intent.Domain.Guardrails.Contracts and Intent.Services.Guardrails.Contracts each contribute one (`DriftDesigner`), and a later module (a UI Guardrails module, or any other) contributes the same way.

## Architectural Decisions

- **The drift check is its own module (user request and decisions, 2026-10-29, plan `Modules/intent/.plans/2026-10-29-extract-drift-engine-module.mdx`).** The Domain and Services Guardrails modules each carried a full copy of the engine, the guidance and near-copies of the report template and the ValidateDriftRecipes task, about 5,300 lines kept identical by a test; every change was made twice, and a third designer would have meant a third copy. This reverses the Domain module's "the engine is copied, not shared" decision, which rejected a shared module because it meant a third module and a new dependency for consumers: both costs are now accepted. The user's decisions:
  - **Id and folder:** `Intent.Common.Drift`, in `Modules/Intent.Modules.Common.Drift`, an application of the Guardrails solution.
  - **Consumer paths and names don't change:** `guardrails/<designer>.drift.json`, `.cache/guardrails/<application>/` with `<Designer>DriftReport.mdx` and `<Designer>.model.json`, the skill names, both task ids and the report template ids stay, because Domain and Services 1.0.0-pre.2 were published with them. The guidance text stays byte-identical, "Guardrails application" included; wording for reuse beyond Guardrails is a later, separate change.
  - **Only the drift check moves.** The other duplicated Guardrails code (`ContractAsync`, `ContractMemberModifiers`, `ContractTypeModifiers`, `ContractDefaultValues`, `IntentManagedContractMerge`) stays copied, for a separate follow-up.
  - **The code index stays C# only:** the UI Guardrails module's language isn't decided, so the seam for a second index (Razor, TypeScript) behind the same `find` grammar is deferred rather than guessed. Regex read cases already work on any text file.
- **What is common and what each module supplies.** Core: the code index, the recipe engine and file format, the probe and wrong-element checks, ownership and exceptions, the structure comparer and `Modellable`, the baseline memory, report rendering, `DriftCheck.Run`, `RecipeValidation`, the report template's logic (`DriftReportRunner`), the module task's logic (`RecipeValidationTask`) and the five guidance templates. Each contributing module: its kinds of fact, its model reader (`DriftModel`), its contract templates, its text in the guidance (`DriftGuidance`), its technology guides and reverse-engineer skill, and a report template and module task that delegate to core with their ids unchanged.
- **The contribution contract.** `DriftDesigner(Name, DesignerId, Order, Kinds, ReadFacts, ReadElements, ValidateTaskId, Guidance)`.
  - **Discovered, not registered.** The guidance templates take every template instance of the run that implements `IDriftDesignerSource` (each module's drift report template does), one per designer name, ordered by `Order` (Domain 10, Services 20, so the text lists them as before). It is the find-the-template pattern (Wolverine's `FindTemplateInstance`), so there is no static registry to reset between runs. Discovery ignores `CanRunTemplate`: a report template turns itself off once its check finds nothing to report, and its designer still counts.
  - **Two readers, not one `ReadModel` (deviation from the plan's sketch, my call).** `ReadFacts` and `ReadElements` are the two `DriftModel` calls the report template already made; the module task reads only facts, so one combined reading would have made it read every element for nothing.
  - **`IDriftStructureSource : ICSharpFileBuilderTemplate`, naming its designer.** Each Guardrails module's contract marker interface (`IDomainContractTemplate`, `IServicesContractTemplate`) derives from it and implements `Designer` as a default interface member, so no contract template's file changed. The runner compares only the structure sources of its own designer.
  - **One contribution per designer.** A designer has one recipe file and one catalog; fact keys are already namespaced (`column.*`, `intent.*`), so merging two modules' kinds for one designer later is additive.
- **The report template takes the interface, so its signature is merged (my call, verified).** Module Builder generates a Markdown template's class with `[IntentManaged(Mode.Merge, Signature = Mode.Fully)]` and no `partial`, so `IDriftDesignerSource` can't be added in a sibling file the way the contract templates add their marker. Each module's `DriftReportTemplate` is marked `Signature = Mode.Merge`, as this repo's MediatR and ServiceImplementations templates are, and the Software Factory rerun kept the interface (it only added the template's own usings). Composition, not inheritance: the template holds a `DriftReportRunner`, takes its `ReportFile` as `MarkdownFile`, and answers `CanRunTemplate` from `CanRun`.
- **The guidance templates build their text in `AfterBuild`, and are written only once a designer is contributed.** Contributions are template lookups, which resolve only once every template is registered. `CanRunTemplate` is false with no contribution, so installing this module alone writes nothing (before the move, no Guardrails module meant no guidance either).
- **Each kind names its own element and describes its placeholders (plan step 4).** `FactKind` takes its placeholders as `FactPlaceholder(Name, Description)` and an explicit, required `Own` list (validated to be some of its placeholders), replacing the central `Describe` switch and the `OwnPlaceholders` name heuristic, which knew both designers' placeholder names. Each module's lists are set to what the heuristic chose, and `FactKindTests` pins them to it. The `Entity` and `Member` descriptions mention both designers' meanings and are repeated in both contributions, because the configure-drift-check skill used to describe a placeholder once for both and its text is kept as it was. The engine takes a designer's kinds as an input (`DriftCheckInput.Kinds`, `RecipeValidationInput.Kinds`, `RecipeFile.Parse(json, designer, kinds)`) instead of looking them up by name.
- **Public surface: only what a contributing module calls.** `DriftDesigner`, `DriftGuidance`, `IDriftDesignerSource`, `IDriftStructureSource`, `FactKind`, `FactPlaceholder`, `ModelFact`, `Modellable`, `DriftReportRunner` (with `ReportPath`) and `RecipeValidationTask`. The rest is internal, with `InternalsVisibleTo` for `Intent.Modules.Guardrails.Contracts.Tests`. `GeneratedFile` stays internal (the plan listed it as public): the runner builds them, and no module needs to.
- **`Modellable.MetadataKey` is `Drift.Modellable`, was `Guardrails.Modellable`.** It lives only in memory during one run, from the contract templates to the report template, and both sides use the constant.
- **Proof that the move changed nothing a consumer sees: golden renders captured before it.** `GoldenTests` renders the rule and the four skills for three installs (both designers, Domain only, Services only), each report template's report and log, and each task's JSON, against `Fixtures/Golden/`, which were captured on the pre-move code (and matched between two checkouts). After the move they match exactly; regenerate them with `GUARDRAILS_GOLDEN=update` only for an intended change. `FakeDesignerTests` contributes a third designer with one kind and runs it through the recipe parser, the check, the task and the guidance.
- **Package and dependency versions.** The csproj references `Intent.Modules.Common` 3.11.1, the lower of the two Guardrails modules' (Services 3.11.1, Domain 3.11.8): a higher one would fail the Services module's restore with NU1605 once it references this project. `Intent.Modules.Common.CSharp` 3.10.12-pre.2, SDK 3.14.0-pre.1 and compile-only Roslyn 4.14.0 match both. The `.imodspec` dependencies are hand-added to match (Intent.Common 3.11.1, Intent.Common.CSharp 3.10.12-pre.2) plus Intent.OutputManager.RoslynWeaver 5.0.3-pre.2, whose lib folder supplies Roslyn at run time; the module has no C# template, so the Software Factory doesn't add it. `supportedClientVersions` stays `[5.1.0-a,6.0.0)`: the SDK needs 5.0 and RoslynWeaver 5.1, and this module has none of the Guardrails modules' Codebase Structure interoperability that raised theirs to 5.4.0-beta.6.

## Engine and guidance decisions (moved from the Domain module, 2026-10-29)

- **Drift check: every Software Factory run compares the model with the code (user decisions, plan `2026-10-20-drift-check-compares-model-with-code`, built 2026-10-20).** The Basislink authority audit compared 1,588 facts and found 6 where the model and the code disagreed (two routes, three text types, one column type). The module-task check reported `No drift` for all 6, because it only compared each side with fingerprints taken at the last save, and the adoption's first save had accepted them. Its other findings: false alarms on things that agree (F-4, F-8), wrong labels (O-1, O-3), and blind spots for signatures and removed members (F-2, F-3). The design keeps the old one's generic idea, that the AI understands the technology once and the check is deterministic, but the AI now records how to read each kind of fact, not where each fact is, and there is no baseline and no save.
  - **Shape.** A `DriftReport` File Template (Markdown File Builder, Single File, no model, role `Default`) in each contributing module is where the check runs, through `DriftReportRunner`, and outputs the report into the solution's `.cache` folder (see "Reports in the solution's `.cache` folder" below). Every Wrong line is also one `Log.Failure`, so the run fails, and so does the CLI on CI. An exception inside the check is caught, logged as a failure, and written into the report, so the rest of the run still generates (though, being a failure, its changes then aren't applied by themselves).
  - **`Log.Failure`, not a thrown `FriendlyException` (user asked for one; rejected with evidence, 2026-10-20).** A `FriendlyException` thrown from a build callback is wrapped in a plain `Exception` by `FileBuilderHelper.PerformConfiguration` (Intent.Modules.Common; only `ElementException` passes through unwrapped), so it shows as a stack trace. Even unwrapped (re-checked in the Intent Architect source, 2026-10-21), `TaskTracker.StartTask` publishes the friendly message but rethrows it as a `HandledException`: its `_throwExceptions` is always true, since nothing calls `DoNotThrowExceptions()`. `SoftwareFactoryExecutionEnvironment.StartAsync` then ends the run before staging and sends Intent a problem report for any exception, `ElementException` included. Nothing would be staged, so a model-first change's output could never land and its drift could never clear. Instead the failure is logged, not thrown. **Logged as friendly and element errors (user, 2026-10-21):** the user had Intent Architect changed so that `Log.Failure(Exception)` publishes a `FriendlyErrorMessage` for a `FriendlyException` and an `ElementErrorMessage` for an `ElementException`, without ending the run (handover `handover-log-failure-friendly-exceptions.md`). **One error, an element error when it can be (user decision, 2026-10-22, replacing a friendly error plus up to five element errors):** `LogFailures` logs exactly one failure, `FailureMessage`: "The Domain model and the code have drifted: N drifts detected and listed in the drift report (path)", plain text, the path with forward slashes because the card's Markdown ate a backslash path's underscore. It is an `ElementException` on the first row's innermost model element that `DriftModel.ElementsById` resolves (`DriftReport.FailureElementIds`, in the report's order, so a contradiction's element first), because Intent offers **Try fix with AI** on an element error: a developer who ran the Software Factory by hand gets a clear call to action that hands the whole report to the AI. With no resolvable element it is a `FriendlyException` with the same message. On CI no report is written, so it is a `FriendlyException` listing the lines. **Rejected (the earlier design):** a friendly error naming the report plus an element error per row when no more than five rows had an element; it gave no single AI entry point, and per-row errors invited fixing rows one by one. On a client without that change each shows as a plain error prefixed with the exception type; the exceptions are never thrown, so there's no stack trace. `supportedClientVersions` isn't raised until the release that has the change is known.
  - **Off until the recipe file exists (user decision, 2026-10-20, after the first Basislink install; supersedes the plan's "a missing recipe file is one Wrong line").** A `Log.Failure` stops Intent applying the run: the client unticks every staged change when a run has errors (`SoftwareFactoryRunHost.ts`, `performChange = false`), and the AI's `run_software_factory` only auto-applies a run without errors (`RunSoftwareFactoryTool.cs`). The first run after installing failed (the missing recipe file, plus 26 structure lines in Services), so the configure-drift-check skill that run generated was never applied: the check blocked its own set-up. Now `BuildAndCheck` looks for `guardrails/<designer>.drift.json` first; without it, nothing is read or rendered, the report says the check is off and how to set it up, and the run gets one `Log.Warning`, which doesn't untick anything. `DriftCheck.Run` treats a null recipe the same way (`DriftReport.Off`). The structure check is off too, as the user asked ("not do checks"): it is part of the same opt-in. Writing the file, even as `{}`, turns everything on.
  - **After-build, not OnBuild (deviation from the plan, my decision).** The plan said `MarkdownFile.OnBuild(…, int.MaxValue)`. `CSharpFile.ToString()` throws until `FileBuilderHelper` marks the whole build step done, so the contract templates' output can't be read during it. The check is registered with `AfterBuild(…, int.MaxValue)` instead. `FileBuilderFactoryExtension` runs the build step at After Template Registrations and the after-build step at Before Template Execution, both before the Software Factory calls each template's `CanRunTemplate()` to run it (read in `D:\Dev\Intent`'s `SoftwareFactoryProcessOrchestrator.ExecuteTemplates`).
  - **CI (plan callout, implemented as decided).** `FileBuilderHelper.PerformConfiguration` only builds templates whose `CanRunTemplate()` is true, at the start of each step. `CanRunTemplate()` is therefore true until the check has run, and false afterwards when `TF_BUILD` is set, so the check runs on CI and fails the run, but the report isn't written (nor is the last one deleted).
  - **The fact catalogue (each contributing module's kinds: `DomainDrift`, `ServicesDrift`; `Drift/FactKinds.cs` until 2026-10-29)** is the list of facts each designer states: key, report label, placeholders, model values and source. The engine validates recipes against it, each designer's reader uses it, and the configure-drift-check skill's fact tables are generated from it, so the skill can't drift from the code. Each module carries only its own designer's facts; until 2026-10-29 both modules carried both designers' facts, because whichever module wrote the skill documented both.
  - **Recipe engine (`Engine/RecipeEngine.cs`), no technology knowledge.** `guardrails/<designer>.drift.json` beside the `.application.config`; JSON with `//` comments allowed. Per fact kind: `find` (a path, or alternatives tried in order), `read` cases (first match wins; `value`, `case`, `part`, `in`), `default`, `absent`, `inherit`, `replace`, `case`, `files`; plus `own` and `exceptions`. Decisions taken while building it:
    - **Code is read as canonical text:** tokens joined with no whitespace except one space between two words, comments and disabled code dropped, string contents verbatim. Regular expressions then don't depend on layout. Anchors (`statement:…`, `chain:…`) are tokenised with Roslyn's lexer and joined the same way, so `Property(e => e.Name)` matches however it is laid out. Non-C# files collapse whitespace the same way.
    - **Find steps:** `class`, `method`, `property`, `parameter` by name; `statement` and `chain` by contained text; `file` by pattern; any kind `with <regex>`; or a bare kind. Text and regex steps return the smallest node of the kind around each match; `chain` returns the whole fluent call chain. A fact's find must end at one node, or the parts of one partial type; several is unverifiable. Overloads of a Service operation are chosen by the model's parameter names (model knowledge, not technology).
    - **`part` (declaration or body) and `in` (an enclosing kind) were added beyond the plan.** Without `part`, `inherit: class` would find a method's `[Authorize]` inside the class's text; without `in`, a parameter's binding couldn't be inferred from its method's route template (the plan's tests require inferred binding).
    - **`absent` was added beyond the plan:** the value when find finds no code. Code states some facts by saying nothing (an unconfigured string column is `DEFAULT` with no max length); without it every unconfigured column would be unverifiable. `default` stays the value when the code is found and no case matches. Both are used as written; only read values pass through `replace` and `case`.
    - **Placeholders with filters** (`{Service|trimEnd:Controller}`, `lower`, `upper`, `camel`, `pascal`, `trimStart`): ASP.NET's `[controller]` token can't be compared without them. Inside a regular expression a placeholder is escaped; `\{` is never one. An unknown placeholder is a recipe error.
    - **Every problem is collected, never thrown:** invalid JSON, an unknown fact key or property (typos), a bad find path, regex or placeholder are each a Wrong line, and a broken recipe's facts aren't then reported one by one. A fact kind with no recipe is one line with its count. A missing recipe file turns the check off (above).
    - **Ownership:** code an `own` entry finds is modelled when some fact's find located it, or code inside it, or (since 2026-10-21) it is a generated type or a type in a file a template writes. Exceptions are a file pattern (a `/`, `*`, `?` or `.cs`), a type, a `Type.Member` or an ownership name, optionally `{ "match", "reason" }`, and cover only unmodelled code. A type or `Type.Member` covers only declarations, never code a convention finds inside a member (since the re-test fixes, C8b). The report lists each with its count; one that matches nothing is a warning (since 2026-10-21; it was an informational list of every exception and its count).
  - **Structure (`Engine/StructureComparer.cs`).** Each runnable contract template (an `IDriftStructureSource` of the designer, such as `IDomainContractTemplate`; file-group owners only) is rendered with `CSharpFile.ToString()`, parsed with Roslyn and compared with its file on disk (`GetMetadata().GetFilePath()`): kind, type modifiers, type parameters, a record's or primary constructor's parameters, base types (the model's must all be there; extra code bases are fine, as Merge keeps them), and members by name and, for methods and constructors, parameter types. Method modifiers are compared except `partial`; property modifiers except `virtual` and `partial`, which Merge doesn't change. Type spellings are compared by meaning (`TypeKey`: `Nullable<T>` is `T?`, `Int32` is `int`, a qualified name is its last part). An unmodelled method, property or constructor is reported only when it is public (since 2026-10-28, see below); constructors count only in a type with a modelled constructor; enum literals always. An unmodelled member found by both an `own` entry and the structure check is reported once.
  - **Only unmodelled public members are reported (user decision, 2026-10-28).** This supersedes "the access levels in play": public, plus every access level any generated method, property or constructor used, pooled across the whole run.
    - **Why.** In Basislink, a Service operation modelled `private` made every unmodelled private method in the run a row, on every generated type, Service Proxies included, although a proxy operation couldn't be private then. The agent wrote exceptions for 9 private methods it couldn't or shouldn't model. The pooling also rewarded the reverse-engineer skills' "every method … with its modifiers as written": one private member modelled made all of them mandatory.
    - **The rule.** The user: modelling a protected, internal or private member is a judgement call the AI makes (typically not, sometimes yes), so one left out is never drift. `StructureComparer.CompareMembers` reports an unmodelled member only when `CodeLocator.AccessOf` gives `public` (an interface member without a modifier counts as public). A modelled non-public member is still compared (signature, modifiers, removal). Both reverse-engineer skills now say which members to model: each type's public members, and a non-public one only when it's part of the design.
    - **Rejected:** working out the access levels per element type, with `Modellable` recording which levels and `static` each can express (my first proposal). It would still make one modelled private member oblige every other, and the per-type limits were gaps in the Services module, not the designer's, now fixed (Service Proxy Operation Configuration and Parameter Modifier, see the Services CONTEXT.md). Also rejected by the user: steering that tells the AI to report a row it can't model as a module gap.
  - **Only what the element can state is compared (user decision, 2026-10-23).** In eShop3 (the dotnet eShop, onboarded with both modules) the Services check failed every run on 30 `parameters: model (none), code (…)` rows: primary constructors holding injected dependencies on handlers, Services, proxies and `OrderQueries`, which no Services element can state. Another 40 "isn't modelled" rows (handlers' `Handle`, DTOs' `ToString()` and `FromOrder`, a Service's properties) needed 34 exceptions. Emptying `services.drift.json` to `{}` left the 30, so no recipe made them and no exception could cover them (exceptions only cover "isn't modelled"). The user: the drift system keeps "the non-deterministic aspects OF WHAT IS MODELLED" in sync; "if it can't be modelled", it isn't checked, and nothing should need configuring around it. What each element can state is in each contributing module's CONTEXT.md.
    - **Mechanism.** Each builder records a `Modellable` on the type it builds (metadata key `Drift.Modellable`, `Guardrails.Modellable` until 2026-10-29): the kinds it can be declared as, and whether it can state generic parameters, parameters on the type, properties, methods and constructors. `DriftReportRunner.ModellableTypes` passes it to the engine as `GeneratedFile.ModellableTypes`. `StructureComparer` compares a kind only when the code's is one the element can be declared as, generic parameters and the type's parameter list only when the element can state them (what the model does state is always compared), and reports an unmodelled member only in a group the element can model. Modifiers and the base types the model names are always compared.
    - **Fields, events and indexers are never reported** (no designer models one; this removed `StructureTests`' public-field row). A code field that stands for a modelled property is still reported, because that row is about the property.
    - **A type with no `Modellable` is compared on everything**, the earlier behaviour: a builder that forgets to record one over-reports rather than hides drift.
    - **The baseline's fingerprints are unchanged.** They still read the whole declaration. So a code change to something the model can't state, such as a new injected dependency, still counts as the code changing: the Software Factory still doesn't delete a removed type's file over it, and a model change to the same declaration is still reported as changed on both sides.
    - **Rejected:** fixing it with recipes or exceptions (needing configuration for what can't be modelled is the defect); comparing a type's parameters only when the model generates some (it would hide a Class's unmodelled primary constructor, which the model can state).
    - **Skills.** sync-model's How the check works and configure-drift-check's Recipe files say that structure rows come from the templates' output, not the recipe file, and that nothing unmodellable is reported. Exceptions are for code the developer chooses not to model. A gotcha says to tell the developer about a row that asks for something the designer can't express, rather than configure around it.
    - **Tests:** `ModellableTests` (each element shape on the engine, and the real Services and Domain builders end to end through the engine, each module's own copy until 2026-10-29). All 132 pass with 0 warnings. Both modules were rebuilt and published to `D:\Dev\.intent-modules` on 2026-10-23 (DLL md5s: Domain `7e66ab447bbc3133975f32119fb6ceba`, Services `2a6a858037c18a04915d4fd320c2875d`). They were rebuilt and published again on 2026-10-26 for the interop minimums (Codebase Structure 1.3.0-pre.0, WebApi 4.7.22-pre.1) and the skill's WebApi wording: 132 pass, Domain's DLL is unchanged, and Services' is `6f9705de33a8ee78a45d3037b3c40299`. Before the user was ready to rebuild, they first ran with all build output in a temp folder (`--artifacts-path`, plus `IntentModuleOutputPath` for the `.imod`). That works, except `SharedCodeTests` (deleted 2026-10-29), which finds the sources by walking up from the output folder.
    - **Not yet verified in eShop3:** that needs a rebuild and reinstall. Expected: the 30 rows go, and most of the 34 exceptions show as stale. The exceptions for members their element can model, such as a proxy's methods, stay.
  - **A model-first change is left to the Software Factory until applied (user decision, 2026-10-21; replaced "no baseline, and a model-first change fails one run").** The structure check compares what the templates will write with the code on disk, so on its own it can't tell a property the model just added (the template is about to add it) from one the code just deleted (drift). The user found the failing run noise ("expected behaviour: the template will add that line"). Now `ModelBaseline` (`.cache/guardrails/<application>/<Designer>.model.json`, per machine, written directly after each check, never on CI) keeps, per generated type (`Order`) and member (`Order.Total(bool)`), the fingerprints of the model's and the code's versions when they last agreed (`Model`, `Code`). A difference is skipped only when the model moved and the code is exactly as it was then (for an aspect new since the baseline, still absent); anything else is reported, including an aspect that never agreed (it already differed when the check first saw it). **Both sides changed is drift (user decision, 2026-10-21, replacing the same day's model-only baseline):** the first version kept only the model's fingerprint, so a member changed both in the model and by hand was skipped, and the Software Factory's change silently overwrote the hand edit. The user: in a brownfield the point is to detect when they are out of sync, not to overwrite code. Such a row is now reported and ends "(the model and the code have both changed since they last agreed)"; drift fails the run, so the overwrite stays unticked. Rejected: dropping the baseline (every model-first change fails a run again) and using git to spot hand edits (the Software Factory's applied output is an uncommitted change too, and CI has no signal). The code's side is looked up by the code member's own key first, so a method whose parameters the model changed still finds its old entry. A first-version baseline (no code side) fails to parse (`UnmappedMemberHandling.Disallow`) and counts as none. The code's declaration fingerprint takes the union of the code's base types, so an interface added in code alongside a model change to that type's declaration reports it as both changed: conservative on purpose. **Until applied, not one run (user's choice over "one run" and "keep reporting"):** a pending aspect stays skipped however many runs pass, because the Software Factory keeps proposing it. That is by design (user, 2026-10-21): a change the Software Factory is proposing is already in front of the developer in the Changes pane, and the drift report is for changes nobody has seen. Without a baseline (a machine's first run, a fresh clone, CI) nothing is skipped. Only structure is baselined: facts are never written by the templates, so a model-only fact change is always drift. Ownership lines on the same node as a skipped structure line are skipped too, and so are those on a whole type the model removed (its file being deleted) if its code is as it was when they last agreed (`StructureComparer.CodeFingerprints`); its entries stay in the baseline while the code has it. **Accepted cost:** a mistaken model edit to a member (C0 M5, a field's type; M6, a field deleted) is no longer a drift error; it shows as a staged code change. The fingerprint is everything the comparison reads (kind, access, type, parameters, type parameters, modifiers, value; for a type, kind, modifiers, type parameters, parameters and base types), so it changes exactly when the template's output for that aspect does.
  - **A type or member the code lacks is never a row (user decision, 2026-10-28; narrows the entry above and supersedes MEM9b).** In eShop8 the user added `Test` to `Order`, removed it (the Software Factory's removal applied), then added it back, and the report said "`Order.Test` (property) is modelled, but not in the code". Two causes, both in the old "code doesn't have it" branch of `ApplyBaseline`: the memory carried the old agreed entry through the pending removal, so the re-add looked like the code deleting a member both had; and MEM9b's date check compared the file's write time with the memory's, but the memory is saved during the run and the Software Factory writes the applied files afterwards, so any model-first addition to a file the previous apply touched was reported. The user: the drift report is secondary, and the Software Factory already shows anything it will write, applied or not, so it needn't worry about it. Now every `Missing` difference is a pending addition: with or without a memory (first run, CI), whether the model added it or the code deleted it, and whether the model changed it too. Facts about it are still read through the accepted view, so its gaps (no `IsRequired()`) are reported on the same run. The date check (`BaselineSavedAt`, `CodeFile.LastWriteTime`) is gone. **Accepted cost:** a member deleted by hand is no longer reported; the Software Factory proposes it back as a stub, and the sync-model gotcha says not to apply that unless it should come back. **Rejected:** a `Removed` flag on the carried entry plus an `AfterCommitChanges` factory extension re-dating the memory after apply (fixes both causes but keeps a check the user doesn't want).
  - **Facts about pending changes are read as if the changes were applied (user decision, plan `2026-10-21-check-new-element-facts-on-first-run`, replacing the same day's "facts about an added element wait", see the Domain module's Superseded).** Adding `test` to `basisCalcLog` failed the staging run on its `column.required` fact; the first fix held such facts back until the property was on disk, so the gap took two runs to show. ## Invariants & Constraints

- **Exactly one copy of this assembly loads.** A contributing module references this project with `Private="false"` (compiled against, never copied to its output) and declares `<dependency id="Intent.Common.Drift" …/>` in its `.imodspec`; the installed drift module supplies the DLL. If a contributing module's `.imod` carried its own copy, the loader would bind whichever loaded first, `OfType<IDriftDesignerSource>` would find nothing, and the guidance would list no designer. `Intent.Modules.Application.Wolverine.csproj` records the same trap. Checked on 2026-10-29: each `.imod`'s `lib` holds only its own DLL.
- **Guidance text is edited with a plain-text editor.** Intent's `write_file` / `patch_file` re-indent raw strings. A raw string's line breaks are the source file's, so a file saved with LF and one with CRLF render differently until git normalises them; the golden tests compare with line breaks normalised.
- **The recipe format, the fact keys and their vocabulary are a contract with consumers' committed recipe files** (see the Domain module's Invariants), and so are the consumer paths above.
