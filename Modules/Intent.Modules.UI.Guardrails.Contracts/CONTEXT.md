# Context: Intent.UI.Guardrails.Contracts

## Purpose

Keeps the User Interface designer authoritative for a brownfield UI in any technology. It writes no UI code: the `reverse-engineer-ui` skill models the UI at the level of what each part is and what it calls, and the module contributes the designer to the shared drift check (Intent.Common.Drift), which fails the Software Factory run when the model and the code disagree. Built from plan `Modules/intent/.plans/2026-11-01-ui-guardrails-module.mdx` (in the `feature/guard-rails-contracts` worktree), 2026-11-01.

## Architectural Decisions

- **Model and drift check only, no UI code written (user decision).** No template writes or merges UI code. Intent's own Blazor modules write `.razor` files once and never merge them afterwards, and the drift check reads any technology through recipes. Rejected: C# templates guarding Blazor code-behind (Blazor only, only where code-behind is used, and tied to today's element shapes).
- **The family name is kept (user decision):** `Intent.UI.Guardrails.Contracts`, although it guards no code contracts, so it still fits if code-behind guarding is added later. The drift check names the designer `UI`: recipe file `guardrails/ui.drift.json`, report `UIDriftReport.mdx`, order 30 after Domain (10) and Services (20).
- **What the check covers (user decision):** every page, dialog, component and layout (`component.kind`), each page's route, security with roles and policies, and each backend call, navigation, dialog opened and child rendered. "The page invokes `CreateCustomer`, it doesn't matter where": the level is what each part calls, never how. Widgets, Component Operations, Properties (route and query parameters included: the route carries them), Event Emitters, Model Definitions and mappings are never modelled; they can become new fact kinds later.
- **One reader and one reference per designer version (plan).** The User Interface designer is being overhauled. Everything specific to today's designer is in `Drift/UserInterfaceDesigner1.cs` (type ids, reading into the neutral `UiModel`, each fact's source text, the designer's terms in the rule and the intent-drift reference) and in the skill's `references/user-interface-designer-1.md`. `UiDrift` (fact keys, placeholders, values, building facts), `UiModel`, the recipe guides and SKILL.md are version-neutral. For the next designer: add `UserInterfaceDesigner2.cs` and `user-interface-designer-2.md`, choose the reader by the element types the designer has, and add a row to SKILL.md's "Model it" table. Not built now: version detection, with one version there is nothing to choose between.
- **Raw element reads, no Intent.Modules.Modelers.UI NuGet reference (plan).** Elements are read by type id, stereotypes by name, as the siblings' drift readers do, so nothing compiles against an API the overhaul replaces. The ids are Intent.Modelers.UI 1.1.6's and Intent.Modelers.UI.Core 1.0.4's; `UiModelFactTests` hard-codes them as a pin. Only Components and Layouts, and what is inside them, are read: the Component Operation shares its type id with the Services designer's Operation.
- **`Show Dialog` comes from Intent.Modelers.UI.Core, so it is a dependency too (my call; the plan listed three dependencies).** The plan put `Show Dialog` in the designer, but in 1.1.6 it is defined by Intent.Modelers.UI.Core 1.0.4, as is the `Dialog` target trait. Without it the user's chosen `intent.opens` fact couldn't be modelled. Rejected: telling the agent to install it when needed (a missing modelling capability is the module's gap to close).
- **Where an interaction is modelled doesn't matter (user: "it doesn't really matter where it happens").** An association on anything inside a Component or Layout (a Component Operation, a Layout Header) counts as its own, as older models and Intent's samples put them. The skill models them on the Component only, which is also the designer's own AI rule. For the same reason (my call): a `Display Component` in a view counts as a component rendered (`intent.uses`), as eShop.Web's model has its composition; and a Component a `Show Dialog` opens is a dialog with or without the `Dialog` stereotype, which models before Intent.Modelers.UI 1.1.3 lack (the Angular sample's dialogs).
- **A two-way Navigation leads both ways (my call).** The designer's rule models a pair of pages that navigate to each other as one bidirectional association; the reader takes the target end, and a navigable source end, so each page gets its fact.
- **Placeholders (my calls beyond the plan's table).** Every kind has `{Folder}` (the component's folder name), as Services does, so a recipe can tell two `Index.razor` files apart. `page.route` and `{Route}` are the route without its leading `/`: Intent's models write `/customer/add` and the skill models `customer/add`, and the code's leading slash isn't significant to any router. `{RouteStart}` is the route before its first parameter (a segment containing `{`, or starting `:` or `*`) with no trailing `/`, so recipes add the separator their technology uses.
- **`security` is stated for every page (plan), not only once the designer uses `Secured`** (Services' rule). A UI with no security therefore needs a `security` recipe, which every guide has with `default: None`. In exchange a page that gains `[Authorize]` in code is reported.
- **Navigation is read from routes, not page names (user-accepted).** Code navigates by URL. A route built by a helper or a constant is marked `unreadable` by the guides' advice, not guessed.
- **A component modelled before its code exists fails the run (user decision).** Nothing generates UI code, so its facts can't be found until the code is written; Services treats an interaction modelled first the same way. Rejected: a "not built yet" warning (an engine change, and with no baseline, as on CI, a page deleted from the code would only warn).
- **Recipe guides for Blazor, Angular and React (user decision), each tested against fixtures (`UiGuideTests`).** Blazor: trimmed from NewSolution156's eShop.Web.Client and Blazor Server sample. Angular: trimmed from its Angular sample, with a guarded route (with roles) and a child component added, since the sample has neither. React: hand-written in React Router's style (no React sample exists). Planted changes cover route, security, roles, a call, a navigation, a dialog, a child and an unmodelled page or component per technology.
- **How the guides read each technology (my calls, each forced by the tests):**
  - A component's files are one find (`file:**/{Component}.razor*`, `file:**/{Component|kebab}.component.*`, `file:**/{Component}.?sx`), relying on the engine's one-unit rule.
  - Angular and React pages are routed elsewhere, so `component.kind` reads layouts and dialogs from the component's own files and `inherit`s the routes file for `Page`. Their dialog cases are narrow (`MatDialogRef<`, a root `<Dialog>`/`<Modal>`) because own-file cases win before the inherited routes file is read.
  - Angular navigates with segment arrays (`navigate(['/customer', 'edit', id])`): the engine's `replace:<text>:<with>` filter writes a route as one (`{RouteStart|replace:/:','}`).
  - Route-file cases stay inside one route object with `(?:[^{}]|\{[^{}]*\})*?`, and fixed-value cases match the token that states the fact (`canActivate`, a guard's name) with lookarounds for context, so the recipe probe changes that token.
  - Blazor's `own` entries split `page` (`@page`) from `component` (any other `.razor` with markup, leaving out the router, the host page and `_Imports.razor`), so no exceptions are needed for framework files. Angular and React name unmodelled components by class or function (`"name": "$1"`); Blazor's are named by file path, the only name a `.razor` file states.
- **Template class comments.** The guide, skill and reference templates have fully managed signatures, so the Software Factory removes comments on their classes; the note that their text is edited with a plain-text editor lives on `DriftRecipeGuides` instead.

## Invariants & Constraints

- **The fact keys, labels, placeholders and value vocabulary are a contract with consumers' recipe files** and must survive the designer's overhaul. `FactKindTests.The_UI_kinds_are_the_contract_the_recipe_files_were_written_against` pins them.
- **Exactly one copy of Intent.Common.Drift loads.** The project references it with `Private="false"` and the `.imodspec` depends on it; the `.imod`'s `lib` holds only this module's DLL (checked 2026-11-01).
- **Guide, skill and reference text is edited with a plain-text editor.** Intent's file tools re-indent raw strings. The fixtures are read with `\n` line breaks whatever git checks out (`UiGuideTests.FixtureFolder`).
- **No UI code generator on a consuming application.** The skill tells the agent never to install Intent.Blazor, Intent.Angular or the like; they would generate pages over the hand-written ones.

## Module Interactions

- **Intent.Common.Drift 1.0.0-pre.1.** This module contributes `UiDrift.Designer` from its `UiDriftReporter` factory extension (Intent.Common.Drift's `DesignerDriftReporter`, marked `[IntentManaged(Mode.Merge)]` so the Module Builder keeps its base class; user decision 2026-11-10, it replaced the DriftReport template), which reports with `DriftCheckRunner`: its findings are the UI Area of the application's drift report. It references the hub as the `Intent.Modules.Common.DriftReporting` package and depends on Intent.Common.DriftReporting 1.0.0-pre.0 (Intent.Common.Drift from 1.0.0-pre.2), and its `ValidateDriftRecipes` task; the rule and skills come from the drift module. The floor is 1.0.0-pre.1 because the guides need its `kebab` and `replace` filters, its reading of a component's files as one place, and interpolated C# strings read as written (all added for this module; 1.0.0-pre.0 was already published).
- **Intent.Modelers.UI 1.1.6 and Intent.Modelers.UI.Core 1.0.4** are installed with this module. 1.1.6 is the version where a diagram a script creates keeps its name and the duplicate Component Operation check is fixed.
- **The Services designer** holds the calls' targets. The reader names an Operation's owner (`{InvokedOwner}`) from its parent element by name, as Services' own reader does; the skill requires the backend modelled first (reverse-engineer-services, or a referenced Services package).
- **Not verified in a consumer.** The end-to-end run in a brownfield UI application (install, `/reverse-engineer-ui`, configure the check, a clean run) needs that solution open in Intent Architect. Open there: whether creating a `Call Service Operation Action` by script opens a mapping dialog; the reference tells the agent to close it with `resolve_designer_dialog` and leave the mapping empty.
