# Context: Intent.Services.Guardrails.Contracts

## Purpose

Guards a brownfield codebase's application layer. Each Services designer element that was imported from existing code (services, commands, queries, DTOs, enums, and, when their optional modelers are installed, domain event handlers, integration events, integration commands, eventing DTOs and integration event handlers) is merged back into its existing file, so every modelled type and member keeps existing.

## Architectural Decisions

- **Merge directives: plain `Mode.Merge` plus a constructor/method default (user decision).** Every contract file carries `[assembly: DefaultIntentManaged(Mode.Merge)]` and `[assembly: DefaultIntentManaged(Mode.Merge, Signature = Mode.Fully, Attributes = Mode.Merge, Comments = Mode.Merge, Targets = Targets.Constructors | Targets.Methods)]`, written by `ContractBuilderExtensions.IntentManagedContractMerge()` in all six C# templates. It is identical to the Domain module's helper; keep the two in step. The Domain module's CONTEXT.md records how it is built, why RoslynWeaver accepts it, the probe, and the earlier plain-Merge behaviour that still applies outside constructor and method signatures. Existing bodies are still merged (`ManageStatementBlock(..., Mode.Merge)`), which is why generated bodies are always empty.
- **Every contract is a concrete type.** Services are emitted as a class (or record), never an interface. Brownfield application services are matched by their concrete class name, which is used verbatim. The rejected option was mirroring `Intent.Modules.Application.Contracts`' `IXService` interface, which would never merge onto the existing class.
- **Type Configuration stereotype selects class or record.** Defined in this module's package and installed into the Services designer ("Include in Module" + "Reference in Designer" = Services). Applies to Service, Command, Query and DTO. Empty or absent means class. `ContractTypeKind.cs` reads it through the typed accessors, and `AddContractType` is the single dispatch to `AddClass` / `AddRecord`. A DTO whose kind differs from its parent DTO's raises an `ElementException`. The parent is read through `ParentDtoTypeReference`, because `ParentDto` throws when there are multiple generalizations.
  - **Struct was requested and then dropped by the user**, because `Intent.Modules.Common.CSharp` (up to 3.10.11) can't declare a struct. Revisit when the builder supports it.
  - RoslynWeaver matches type declarations with `kindsMustMatch: true`, so the configured kind must match the existing type on disk. A mismatch adds a second declaration with the same name.
- **Commands and queries are plain property types** with no `IRequest` or MediatR interfaces. Adding interfaces would be implementation, and would assume a mediator library the codebase may not use.
- **Async: name convention plus an explicit Async Configuration stereotype (user decision).** This is the same rule as the Domain module, whose CONTEXT.md records the reasoning and rejected options. In short: a name ending in `Async` means async, and this module's own Async Configuration stereotype on Service operations (Is Async, Include Cancellation Token) overrides it. Async operations emit the `async` keyword, because plain `Mode.Merge` otherwise strips it from existing async/await methods. The earlier by-id reads of Intent.Application.Contracts' Asynchronous/Synchronous stereotypes were removed. Keep this stereotype identical to the Domain module's. A modelled `ValueTask` return type uses `method.Async(asValueTask: true)`, because plain `Async()` rewrites `ValueTask` to `Task`.
- **Methods always have empty bodies: no statements, no `NotImplementedException` (user decision).** The empty body merges with whatever is on disk and leaves it untouched. The cost is that a new value-returning method won't compile until implemented. Same rule as the Domain module; don't reintroduce a statement.
- **Type resolution uses role strings.** The module registers eight of its own roles as type sources (Service, Command, Query, Dto, Enum, IntegrationEvent, IntegrationCommand, EventingDto) plus the Domain module's Entity, Enum, ValueObject and DataContract roles (`GuardrailsContractsServicesRoles.TypeSources`), with a `List<T>` formatter. That way DTO and command fields typed as Domain types resolve without an assembly reference to the Domain contract module, and message properties typed as Eventing DTOs resolve to the eventing contracts. The handler roles are not type sources: nothing references a handler as a type.

- **Ships the `reverse-engineer-services` AI skill (user decision).** `ReverseEngineerServicesSkill` is a Single File, Markdown File Builder template with role `AI.Context.Skills`, emitting `skills/reverse-engineer-services/SKILL.md`. Its content is the user's, embedded in a non-interpolated raw string, verbatim except for user-requested changes: its two `struct` mentions were removed (the C# builder can't emit structs), and guidance was added for File Config, Collection Type, Parameter Modifier and multi-location Template Outputs (Registration Filter). It points agents at `reverse-engineer-domain` (from the Domain module) first, and describes this module's template behaviour, so a template behaviour change must update the skill in the same change.
  - **Type spelling, nullability and never dropping members (user decisions).** Same change as the Domain skill; its CONTEXT.md records why and what. Here the nullability guidance is under §3 item 3, and the shared "Equivalent type rewrites — ask, never drop" block is §7 step 4. Keep that block worded identically in both skills.
  - **Formatting changes are accepted, and Auto Format is never turned off (user decision, 2026-10-09).** Same change as the Domain skill; its CONTEXT.md records why (an agent disabled Auto Format to get header-only diffs, and 23 controllers lost their indentation). Here the shared "Formatting changes — accept, never suppress" block is §7 step 5, with a matching Gotchas line. Keep that block worded identically in both skills.
  - **Service operations are requests too, and every request gets its intents (user decisions, 2026-10-09).** In the Basislink adoption the code had no commands or queries, only Business services called from controllers. The agent applied §4 (HTTP settings, security) to the service operations but skipped §5 (Entity Actions), because §§0, 4, 5 and 6 only said "command and query". The user's rules, now in the skill:
    - A service is either **public** (an endpoint calls its operations directly, so each operation is that endpoint's request, exactly like a command or query, with HTTP settings and security) or **internal** (only application code calls it; no HTTP settings). §1 extracts which, and §3 models both the same way.
    - **Both kinds get their intent modelled** (§5). Intent means every interaction the element performs on purpose (user's definition): **entity actions** (Create/Update/Delete/Query Entity Action), **invocations** (`Perform Invocation`, menu "Invoke Service", of service operations, commands, queries, domain service and repository operations, stored procedures and Service Proxy operations), and **published integration events / sent integration commands**. It doesn't spell out every step: what an intent implies is left out (an update reads the entity first, so `Update Entity Action` alone is enough), and a caller that delegates models the invocation, not the callee's own intent. This replaced, first, "one primary Entity Action per request, no secondary actions", and then an interim "primary Entity Action plus published events and sent commands" that the user rejected as too narrow for leaving out invocations.
    - **Verified association ends** (Intent.Modules source, `*.designer.settings`): Entity Actions, Publish Integration Event and Send Integration Command accept a Services `Operation` as source. `Perform Invocation` goes from `Operation` or any `[Processing Handler]` (Command, Query, Domain Services Operation, the handler association ends) to `Operation` or any `[Invokable]` (Command, Query, and the Operations of Services, Domain Services, Repositories and Service Proxies (Intent.Modelers.Types.ServiceProxies), plus Stored Procedure). Secured/Unsecured apply to Service and Operation.
    - Service routes (verified in Intent.Modules.Metadata.WebApi's `HttpEndpointModelFactory`): an operation's `Http Settings.Route` is appended to its Service's `Http Service Settings.Route`, and `~/` makes it absolute, so §4 puts the controller prefix on the Service.
    - §6 lays out services in the same left column as commands and queries, each followed by a 100px gap below its bottom edge (a service grows with its operations).
  - **Editing gotcha:** edit the skill text with a plain-text editor. Intent's `patch_file`/`write_file` formatter flattens the indentation inside the raw string, which changes the rendered markdown.

- **File Config stereotype: renamed and multi-type files (user decision).** `File Config.Filename` (Service, Command, Query, DTO, Enum) handles code that isn't one type per file named after it, e.g. `psMembersDTO.cs` holding `PsMembersDTO`, or several DTOs in one file. Mechanism:
  - **Renamed file:** `CSharpFile.WithFileName`. Type resolution reads the class name from config metadata, not the file name, so references still resolve. The value is a file name only; `.cs` is stripped, and a path separator or invalid character raises an `ElementException`.
  - **Grouping by real output path, not by Filename.** All contract templates whose `GetMetadata().GetFilePath()` is equal (OrdinalIgnoreCase, as the engine itself compares when it throws `DuplicateOutputPathException`) form one file. Elements without the stereotype take part, so only the extra types need it.
  - **Owner:** the member whose name equals the file name (ordinal, then case-insensitive), otherwise the first by ordinal name, then by id. The owner declares its own type in the constructor, so it stays the file's class name. At OnBuild priority 0 it adds the other members through `ContractTypeBuilders.AddContract`, so their configuration runs in the same band as every template's own type.
  - **Non-owners:** `CanRunTemplate()` returns false, but they stay discoverable (`CanDiscoverTemplate` is separate), so references to their types resolve. FileBuilderHelper only builds runnable templates, so their own `CSharpFile` is never built.
  - **Why a separate partial:** the override and the `IServicesContractTemplate` marker live in hand-written `*Template.FileGroup.cs` files, because the generated partial's base list and members are regenerated from the designer.
  - **Rejected:** grouping on designer folder + Filename, because template outputs can sit in different folders; and filtering non-owners out in the registration, because it removes the template instance that type resolution needs.
  - **Risks:** a third-party extension calling `CanRunTemplate()` before registration finishes would see an incomplete group (the call isn't cached, so later engine calls are correct). Pointing an already-generated type at another file makes the SF offer to delete its old file. Each member's Type Configuration must still match the existing declaration (`kindsMustMatch`).
  - **Namespace override (user decision).** `File Config.Namespace` is optional, like Filename; each applies only when set. A non-empty value replaces `this.GetNamespace()` in `new CSharpFile(...)` via `GetContractNamespace(...)`. Type resolution follows automatically: `CSharpFile.GetConfig()` → FileMetadata → `CSharpTemplateBase.Namespace`, so `using`s in other files match. Validation is strict on purpose: each part must be a plain C# identifier, and a keyword part needs `@`. The builder runs `ToCSharpNamespace()` on the value, which would silently alter anything else, so this guarantees the generated namespace is exactly what was modelled. Casing is never changed. Every member of a multi-type file must end up with the same namespace; a mismatch raises an `ElementException` asking for the same Namespace (or none) on every type in the file.

- **Collection Type stereotype (user decision).** The template default is `List<T>`. The consumer's Business-object services use `IEnumerable<T>`, `IQueryable<T>` and `T[]`, and plain Merge rewrites every matched signature to the generated one, so the default alone would break about 100 of their 264 methods. `Collection Type` (on DTO-Field, Parameter and Operation, for its return type) chooses IEnumerable, ICollection, IList, IReadOnlyCollection, IReadOnlyList, List, HashSet, ISet, IQueryable, Array (`{0}[]`) or Custom (`Custom Format` with `{0}`). All resolution goes through `ContractCollectionTypes.GetContractTypeName`. With no stereotype, an empty Type or a non-collection reference it is exactly `template.GetTypeName(typeReference)`. Otherwise it calls `GetTypeName(typeReference, format)` with a **fully qualified** format (not `UseType`): the C# resolver splits it into namespace and name and adds the `using`, so a fully qualified Custom Format gets its `using` too. The collection is applied before the async Task wrapping. An explicit format also applies to collection-typed generic arguments inside the reference (`TypeResolverContextBase.Get` passes it down).
- **No Namespace on File Config (user decision).** For types declared in the global namespace.
  - `CSharpFile.ToString()` always writes a `namespace {ns} { }` block, so `RunTemplate()` in the hand-written partials removes it through `GlobalNamespaceOutput.UnwrapGlobalNamespace`. This is the module's one deliberate exception to "no raw structural strings": the builder has no global-namespace support. The helper accepts only the exact shape `ToString()` produces and throws `InvalidOperationException` otherwise.
  - **Trap:** `"".ToCSharpNamespace()` is `""`, `CSharpFileConfig` then omits the Namespace key, and `CSharpTemplateBase.Namespace` falls back to `OutputTarget.Name`. Other files would silently get `<Project>.Type` and a bogus `using`. The partials therefore override `Namespace` to return `""`, so references get an unqualified name and no `using`.
  - Setting No Namespace together with Namespace is an `ElementException`. In multi-type files every member must agree on No Namespace.

- **Parameter Modifier stereotype (user decision).** `Modifier`: `ref`, `out`, `in`, `ref readonly` or `params`, on parameters, so Merge mode keeps the code's modifiers instead of dropping them. Implemented in `ContractParameterModifiers`. The builder emits `ref`, `out` and `params` on method parameters (`WithRef/Out/ParamsParameterModifier`). Its `WithInParameterModifier()` sets an empty modifier (a builder bug), constructor parameters have no modifier API, and there is nothing for `ref readonly`. In those cases the modifier is written as a prefix of the parameter's type text, which was probed and renders correctly. `this` (extension methods) is deliberately not offered: it needs a static class, which the contract templates can't model.

- **Minimum Visual Studio module version (user decision).** The `.imodspec` declares, in a hand-maintained `<interoperability>` / `<!-- Minimum Compatible Versions -->` block (the same convention as Intent.Application.FluentValidation and 11 other modules), that a detected `Intent.VisualStudio.Projects` must be at least `4.1.11-pre.0`. The Module Builder doesn't model interoperability, and the Software Factory preserves the block on regeneration (verified). At the time of writing `4.1.11-pre.0` exists only on the local test feed, while the public feed tops out at `4.1.10`, so installing from elsewhere fails until that version is published.

- **Domain Event Handlers: class-only contract, with no dependency on Intent.Modelers.Domain.Events (user decisions).** `DomainEventHandlerContract` emits only `class {Name}` (`RepresentsModel`, no members), because handle-method signatures are framework-specific and Merge keeps the existing ones.
  - **No dependency:** the reverse-engineering skill installs the Domain Events modeler only when the code has domain events. The template therefore uses a custom model type (`Intent.Metadata.Models.IElement`, fully qualified so the generated `TemplateExtensions.cs` gets its `using`), and `GetModels` calls `Services(app).GetElementsOfType(OptionalModelerMetadata.DomainEventHandlerTypeId)`, which is empty when the modeler isn't installed.
  - **Its File Config** is a separate stereotype definition (in the "Optional Modeler Elements" folder, called "Domain Events" until integration eventing widened it) targeted by a filter function on `element.specializationId`. Typed targeting would make the Module Builder reference, and so depend on, the Domain Events package. It has no typed accessor, so `OptionalModelerMetadata` (formerly `DomainEventsMetadata`) reads it by definition id and property name. Renaming a property in the designer would silently make it read empty.
  - **`IElement` models don't implement `IHasFolder`,** so the built-in `GetNamespace()` / `GetFolderPath()` ignore designer folders. `GetContractNamespace(IElement …)` and `GetElementFolderPath()` apply the same folder rule instead.
  - **Multi-type groups:** handlers join through the `ContractTypeBuilders` dispatcher (`IsDomainEventHandler()` is checked first).
  - **Modifiers:** plain Merge replaces class modifiers, and handlers are commonly `internal sealed`. A handler takes the Default Type Modifiers setting, or its own filter-targeted **Type Configuration** in the "Optional Modeler Elements" folder, which has only `Modifiers`, because a handler is always a class. That stereotype is read by definition id and property name in `OptionalModelerMetadata.GetHandlerModifiers` (see Type modifiers below).

- **Integration eventing: four raw-element contracts, with no dependency on Intent.Modelers.Eventing or Intent.Modelers.Services.EventInteractions.** Since Eventing 6.0 the Message ("Integration Event"), Integration Command and Eventing DTO elements (Eventing) and the Integration Event Handler (EventInteractions) live in the Services designer. `IntegrationEventContract`, `IntegrationCommandContract` and `EventingDtoContract` are built like `CommandContract` / `DtoContract`; `IntegrationEventHandlerContract` is built like `DomainEventHandlerContract` (`ContractTypeBuilders.AddHandler` serves both).
  - **No modeler dependency (applied from the Domain Event Handler user decision, for the same reason).** The reverse-engineering skill installs Eventing and EventInteractions only when the code has messaging, and EventInteractions would also pull Intent.Modelers.Domain into Services-only applications. So the templates use the raw `IElement` model type, `GetModels` is `Services(app).GetElementsOfType(type id)`, and every type, child and association id lives in `OptionalModelerMetadata`. The same caveat applies: a property renamed in one of this module's filter-targeted stereotypes silently reads empty.
  - **Handlers are class-only (applied from the Domain Event Handler user decision).** Handle methods depend on the broker (MassTransit `Consume(ConsumeContext<T>)`, NServiceBus `Handle(T, IMessageHandlerContext)`, Intent's `HandleAsync(T, CancellationToken)`), so Merge keeps them and the handler interfaces. The Subscribe Integration Event / Subscribe Integration Command associations are documentation only; the template doesn't read them.
  - **Only this application's own packages (agent recommendation, accepted with the plan).** Eventing packages are routinely referenced across applications (a subscriber references the publisher's package), and their elements then appear in the subscriber's Services designer. The four new registrations and `EnumContract` keep only elements whose `Package.ApplicationId` is the application (`OptionalModelerMetadata.IsOwnedBy`); EnumContract got the filter because enums arrive through the same references. The other registrations are unchanged. Rejected: no filter, which would generate every message, eventing DTO and enum of every referenced package into the subscriber.
  - **Stereotypes: one definition per concept across the optional modeler elements.** The existing filter-targeted File Config and handler Type Configuration were widened (filter functions now list several type ids) rather than duplicated, so their definition ids, and therefore existing applied values, are unchanged; the folder was renamed from "Domain Events" to "Optional Modeler Elements". New filter-targeted definitions in that folder: a **Type Configuration** (Type + Modifiers) for Message, Integration Command and Eventing DTO, and a **Collection Type** (Type + Custom Format) for the Eventing `Property` and `Eventing DTO-Field`. Their options are copied from the typed (package-level) definitions. Rejected: retargeting the typed Type Configuration / Collection Type at the eventing elements, because typed targeting references the Eventing package and so creates the dependency. The folder therefore holds two definitions named "Type Configuration" (handlers vs messages/DTOs); the Module Builder accepts this, and no element is targeted by both.
  - **Eventing DTO inheritance.** The parent is the target end of the Eventing `Generalization` association, matched by **type id** (`ccf59371-…`), because the Services designer's own DTO Generalization has the same name but a different id. More than one generalization is an `ElementException`. A kind mismatch with the parent raises an `ElementException` as for DTOs, and the setting's `sealed` is left off an Eventing DTO with a Generalization source end (another Eventing DTO inherits from it).
  - **Deferred (documented as limitations in the README and skill):** positional records (merging property-style output into one would duplicate members; the builder's `AddPrimaryConstructor` makes a later `Type = positional record` option feasible); property accessors (`init`, get-only; already true of DTOs); message property initializers (the Eventing designer allows no Value on a `Property`, only on an `Eventing DTO-Field`); a subscriber's own copy of a message modelled in another application's package; handle methods.
  - **Not verified in a consumer (user decision, 2026-10-09: consumer verification skipped).** The module builds clean and its own SF run is idempotent, but no consumer output has been inspected. Unproven assumptions to check first if something misbehaves: that `Services(app).GetElementsOfType` returns elements of packages referenced from another application, with that application's id in `IElement.Package.ApplicationId` (the SDK documents it as "the owning Application's Id"); that role type sources resolve raw `IElement` models, so an Eventing DTO used as a property type or base type gets its contract's name and `using`; and what Merge does to an existing `init` or get-only accessor.

- **Type modifiers: Type Configuration → Modifiers plus a Default Type Modifiers module setting (user decision).** This is the same design as the Domain module; its CONTEXT.md records the validation rules, the rejected options and the probe results.
  - `ContractTypeModifiers` is a copy of the Domain one; keep the two in step. The setting group here is "Services Guardrails Contracts Settings".
  - The setting's `sealed` is dropped for abstract DTOs and Eventing DTOs, and for DTOs another DTO inherits from (`ParentDtoTypeReference`) or Eventing DTOs another Eventing DTO inherits from (`IsInheritedByAnyEventingDto`). Services, commands, queries, integration events, integration commands and handlers have no modelled inheritance.
  - Enums have their own **Enum Configuration** stereotype (`Access Modifier`: `public` / `internal`) and otherwise take the setting's access modifier. This is the same design as the Domain module; see its CONTEXT.md.

- **Modeler dependency version (user decision): Intent.Modelers.Services 4.0.17-pre.1.** It was updated (metadata only) in this Module Builder application, and the SF then wrote the version into the `.imodspec`. The csproj `Intent.Modules.Modelers.Services` reference matches. That package exists only in `D:\Dev\.nuget-packages`, which isn't a registered NuGet source on this machine, so it was restored with an explicit `-s`.

- **RoslynWeaver dependency (user decision): Intent.OutputManager.RoslynWeaver 5.0.2-pre.3, kept in step with the Domain module.** The `.imodspec` value is set by hand. The Module Builder adds this dependency to any module with a C# template, with a hard-coded minimum of 4.5.1 (`IModSpecTemplate` / `IntentModule.IntentRoslynWeaver`), and this application's "Dependency version overwrite behavior" is `if-newer`. So the SF keeps a higher value but never raises it: updating the installed RoslynWeaver in this application does not change the `.imodspec` (verified). The installed RoslynWeaver here was also updated to 5.0.2-pre.3; that only affects how this module's own source is merged. 5.0.2-pre.3 is on the public feed and in `D:\Dev\.intent-modules`.

- **Short names for generic collections: a workaround for an arity-blind check in Intent.Modules.Common.CSharp.** Reported by the user: `public System.Collections.Generic.IEnumerable<BasisBuyBidDTO> CalculateBasisList(string oneId, ref System.Collections.Generic.IEnumerable<BasisBuyBidDTO> bidList)`, although the `using` was present.
  - **Cause:** `CSharpTemplateBase.NormalizeNamespace` (3.10.5, 3.10.11 and the `development` source in `D:\Dev\Intent.Modules`, `Modules/Intent.Modules.Common.CSharp/Templates/CSharpTemplateBase.cs`) shortens a name only when exactly one using namespace holds a type of that simple name. Its known-types registry (`CSharpTypesCache.GetCommonKnownTypes`) holds every non-open-generic type of the loaded `System.*` assemblies, so it includes `System.Collections.IEnumerable`, but nothing records arity. `GenericCSharpTypeParser` passes only the bare name to the check. So when the usings include `System.Collections`, `IEnumerable<T>` counts as ambiguous and stays fully qualified, although C# tells the two apart by arity. The usings include the existing file on disk, and legacy files often import `System.Collections`, which is why merged contracts hit this more than greenfield templates.
  - **Probe** (the internal static `NormalizeNamespace` from 3.10.11, called by reflection): with usings `System` and `System.Collections.Generic` the result is `IEnumerable`; after adding `System.Collections` it is `System.Collections.Generic.IEnumerable`.
  - **Workaround:** each template's hand-written `*Template.FileGroup.cs` overrides `NormalizeNamespace`, which every `GetTypeName` and `UseType` result passes through. It calls `ContractTypeNames.WithoutArityOnlyQualifiers`, which removes the `System.Collections.Generic.` qualifier only from generic uses (the name followed by `<`) of the names `System.Collections` also defines: Comparer, ICollection, IComparer, IDictionary, IEnumerable, IEnumerator, IEqualityComparer, IList, Queue, SortedList, Stack. It also adds the `using System.Collections.Generic`. `global::` forms and every other type are left alone (probed against the built module).
  - **Residual risk:** if an imported consumer namespace defines a _generic_ type with one of those names (e.g. its own `IList<T>`), the qualification was genuinely needed and the short name won't compile.
  - **Root-cause fix (not made; offered to the user):** make the check arity-aware in Intent.Modules.Common.CSharp. `GenericCSharpTypeParser` would pass the type-argument count, and the registry and conflict check would ignore entries whose arity differs. Remove this workaround once consumers run a Common.CSharp with that fix.

- **Default values from designer Values (user request).** A service operation parameter's Value becomes its C# default, and a DTO, command or query field's Value becomes the property's initializer (`ContractDefaultValues`, a copy of the Domain module's; keep the two in step). Before this, the module ignored Value entirely. The Domain module's CONTEXT.md records the formatting rules (Intent.Modules.Common.CSharp's `AsFormattedValidTypeValue`), the `ref`/`out`/`params` validation, the probe of the user's `LogMainEvent` example, and the unverified merge of property initializers.

## Invariants & Constraints

- **No casing changes, ever (user decision).** The designer is reverse-engineered from the code and is the authoritative view of it, so every generated name must be exactly the designer name: types, members, parameters, literals and namespaces. Always pass `element.Name` as a string to the builder. Its model overloads (e.g. `AddProperty(type, model)`) Pascal-case the name, so `lowerProp` becomes `LowerProp`. Under Merge that would add a second, renamed member beside the real one. The string overloads, `AddClass`/`AddRecord`/`AddEnum`/`AddLiteral` and `ToCSharpNamespace` were all probed (Common.CSharp 3.10.5) and keep names verbatim.
- The role strings are a shared contract with `Intent.Domain.Guardrails.Contracts` and with the Output Anchors in consumer applications. Changing any of them needs a synchronised bump of both modules.
- The Type Configuration stereotype is defined separately here and in the Domain module, because neither module can reference the other. Keep the options identical.
- The filter-targeted Type Configuration and Collection Type in "Optional Modeler Elements" must keep the same option strings as the typed ones. `OptionalModelerMetadata` reads them by property name and parses the Collection Type option with `Enum.TryParse` into `ContractCollectionKind` (an unknown option is an `InvalidOperationException`), and `IsRecord()` compares Type to `record`.
- Never call `RepresentsModel` on a `CSharpEnum` or `CSharpEnumLiteral`. It throws in Intent.Modules.Common.CSharp 3.10.5 to 3.10.11 and blocks the consumer's whole Software Factory run (see the Domain module's CONTEXT.md for the probe details).
- `Templates/TemplateExtensions.cs` is Fully managed. Shared builder logic lives in the hand-written `ContractBuilderExtensions.cs` and `ContractTypeKind.cs`.

## Module Interactions

- **Intent.Domain.Guardrails.Contracts**: four of its roles are resolved by string. There is no package or module dependency between the two.

## Superseded

- **The `Intent.Guardrails.Contracts` entry module and its `reverse-engineer-designers` skill.** Removed by the user; this module is installed directly. It used to bundle the designers, both contract modules and a skill that imported existing code and applied the Type Configuration and Async Configuration stereotypes. Each contract module now ships its own skill instead (see Architectural Decisions).
- **Targeted Body/Signature Ignore member default, and Signature = Ignore as the plan's fallback.** Removed by the user in favour of plain `Mode.Merge`.
- **Plain `Mode.Merge` as the only directive.** Replaced by the user with plain Merge plus a targeted constructor/method default (`Signature = Mode.Fully, Attributes = Mode.Merge, Comments = Mode.Merge`); see Architectural Decisions.
- **"Records are not supported; every DTO, command and query is a class."** Replaced by the Type Configuration stereotype.
