# Bump module NuGet packages

Move every NuGet package the modules install into consumer applications to its latest version, and leave a record of every judgement made on the way: which locks held and why, what each package's release notes said, and why each module moved the version component it did. Maintainers read about this process in `docs/nuget-package-bump.md`; you work from this file.

$ARGUMENTS

## The contract

- **The model is the source of truth.** Versions change only through `run_designer_script` on each module's Module Builder designer. `NugetPackages.cs` and the `.imodspec` are regenerated by the Software Factory. Never hand-edit them, and never read or edit `Intent.Metadata`.
- **A lock changes only after the user agrees** (§3). A lock is someone's earlier decision; you report on it, you do not overrule it.
- **A template break is never yours to settle** (§4, §9). Fixing the template or locking the package is the user's call, every time.
- **Never downgrade.** A row ahead of nuget.org stays where it is.
- **Scope is the consumer-facing `NuGet Package` elements only.** A module's own `.csproj` SDK references raise the minimum Intent Architect version, which is a separate decision. Hand-written `IntentIgnore` branches in `NugetPackages.cs` are reported, never edited.
- **`.nuget-bump/` is the run's state.** It is git-ignored. Keep its `report.md` current at the end of every phase, so a resumed run (or the next person) knows exactly where you stopped.

Which skill owns what. Load each when you reach its phase, and follow it over anything paraphrased here (`.claude/rules/guidance-precedence.md`):

| Skill                                                              | Phase                                     |
| ------------------------------------------------------------------ | ----------------------------------------- |
| `scripting-the-model`, `exploring-the-model`, `changing-the-model` | §3 reads, §5 model edits                  |
| `module-version-increment`, `module-versioning`                    | §6                                        |
| `module-docs-chore`                                                | §7                                        |
| `generating-and-applying-code`                                     | §8                                        |
| `working-with-modules`                                             | §9                                        |
| `module-context-capture`, `file-builder-expert`                    | a template fix the user chose in §4 or §9 |

`module-versioning` and `file-builder-expert` ship with Intent Architect rather than this repository: load them with `use_skill`.

## 0. Resume

With `--resume`, or when `.nuget-bump/report.md` already exists, read its `## Progress` checklist and its review sections, and `.nuget-bump/candidates.json`. Carry on from the first unticked phase. Re-run the inventory (§2) only if `candidates.json` is older than the branch's last merge from `development`, or the user asks: a re-run rewrites only the inventory block of `report.md`, so the review notes survive.

## 1. Preflight

Stop on any failure here: the inventory would be stale.

1. **A clean branch off an up-to-date `development`.** `git status --short` shows nothing outside `.nuget-bump/`. The branch is not `development` or `master` itself, and `git fetch origin development && git log --oneline HEAD..origin/development` prints nothing.
2. **Intent Architect is running and connected.** `get_applications` answers.
3. **No outstanding Software Factory changes in the modules**, so every generated `NugetPackages.cs` matches its model:

   ```powershell
   ./PipelineScripts/ensure-no-outstanding-sf-changes.ps1 -IslnPath Modules/Intent.Modules.NET.isln
   ```

   It needs `INTENT_PACKAGER_USERNAME` and `INTENT_PACKAGER_PASSWORD` set; without them it prompts for a password. When they are not set, ask the user to run it and tell you the result rather than running it yourself.

   **Ignore `Intent.ObsoleteModule`.** Its application sometimes reports an outstanding overwrite of `Modules/Intent.Modules.NET.sln`: the project-type GUID on its `Intent.Modules.ObsoleteModule.csproj` line flips between `{52B49DB5-…}` (committed) and `{FAE04EC0-…}` outside the Software Factory. It has nothing to do with NuGet packages. When it is the only failure, put the committed line back (apply that application's staged `.sln` change, or ask the user to) and carry on; never treat it as a stale inventory, and never bump, document or regenerate that module for it. The same applies when it is the only failure in §9's pre-commit checks.

## 2. Inventory

```powershell
pwsh .claude/skills/module-nuget-bump/scripts/Get-NuGetBumpCandidates.ps1 [-ModuleFilter '<filter>']
```

It reads every generated `Modules/*/NugetPackages.cs`, asks nuget.org for the latest version per target framework using the old `Intent.NuGetReferenceUpdater` rules, and writes only under `.nuget-bump/`. It takes about a minute and a half for every module, and caches lookups in `.nuget-bump/cache/`.

Read the inventory block of `.nuget-bump/report.md` first, then `candidates.json` for detail:

| `candidates.json`                       | What it holds                                                                                                                                                                                                                                           |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `modules[]`                             | Each module with anything to do: `version`, `isPrerelease`, `csprojVersion`, `packagesToChange`, the module's `deltaClass` and `needsBreakingReview`, draft `releaseNoteRows`, and its `lockedBehind`, `lockedOrphans`, `lockConflicts`, `manualBehind` and `ahead` rows |
| `modules[].lockedBehind[]`, `lockedOrphans[]` | `latestInLockedLine` is the newest version in the row's major whose dependency tree fits the module's other locks; `lockedLineSkipped` lists newer versions in the line that do not, and `lockedLineSkippedConflicts` says why the newest of them fails |
| `modules[].lockConflicts[]`             | Rows whose version, after the proposed changes, needs a package the module's locks hold lower on the same consumer framework: `kind` `direct` (a locked package, so NU1605 at restore) or `tree` (a lockstep dependency of a locked package needed at a higher major), with `lockedBy`, `requiredVersion` and the `via` chain. `proposed: false` means the row is already in the model |
| `packages[].latest[]`                   | Per framework: `tfm`, `frameworkName` (the exact `Minimum Target Framework` value), `version`, and `dependencies[]` (`id`, `version`) to recreate as `NuGet Dependency` children                                                                        |
| `packages[].usages[].rows[]`            | Per module and framework row, the proposed `action` (below), `current`, `latest`, `delta` and `locked`                                                                                                                                                  |
| `packages[].usages[].consumerChanges[]` | What a consumer on each of net6.0 to net10.0 resolves before and after the proposed rows: the basis for the delta class and the release-note rows                                                                                                       |
| `packages[]`                            | `repositoryUrl`, `projectUrl`, `nugetUrl`, a `releaseNotes` excerpt, and `deprecation`                                                                                                                                                                  |
| `drift[]`, `errors[]`                   | The same package at different versions across modules; packages nuget.org could not resolve, with the deprecation that usually explains why                                                                                                             |

| Row `action`    | Meaning                                                                                       | What happens to it                          |
| --------------- | --------------------------------------------------------------------------------------------- | ------------------------------------------- |
| `update`        | Unlocked row behind nuget.org                                                                 | §5 renames it and rebuilds its dependencies |
| `add`           | nuget.org resolves a framework the package has no row for                                     | §5 adds the row                             |
| `remove`        | Unlocked row for a framework nuget.org no longer resolves                                     | §5 deletes it                               |
| `locked-behind` | Locked row behind nuget.org                                                                   | §3                                          |
| `locked-add`    | A new row that consumers would take instead of a locked row: adding it would bypass that lock | §3. Never added without the user agreeing   |
| `locked-orphan` | Locked row for a framework nuget.org no longer resolves                                       | §3                                          |
| `ahead`         | Row newer than nuget.org                                                                      | Left alone, listed in the report            |
| `current`       | Up to date                                                                                    | Nothing                                     |

Rows in a usage with `manual: true` sit in hand-written `IntentIgnore` code. Never touch them; list them under `## Deferred` with their line number.

A deprecated package (`deprecation`, or a lookup error saying every version is unlisted) is not something this run can bump: replacing it changes what the templates emit. Record it under `## Deferred` with the replacement nuget.org names, and raise it in the final report.

## 3. Lock review

Only for locks the inventory flagged: `lockedBehind` (including `locked-add`) and `lockedOrphans`, plus every `lockConflicts` entry.

A lock often holds a whole stack, not one package: the net6.0 in-process Azure Functions rows keep every `Microsoft.Extensions.*` on 6.x. Staying in a locked package's major does not keep its dependencies there (`Microsoft.Azure.WebJobs.Extensions.Storage.Queues` 5.3.10 needs `Microsoft.Extensions.Hosting` 10.x), so the inventory walks each candidate's dependency tree on nuget.org against the module's other locks. Trust `latestInLockedLine` over the newest version in the major, and treat each `lockConflicts` entry as a lock to settle: move the row to a version that fits (for a row already in the model, the newest that fits is what `latestInLockedLine` would give from the row's previous version), or review the lock it breaks. The check assumes a consumer gets every locked row of the module on that framework; when the templates never put the two packages in the same project, confirm that in the template code (which template adds each package, and under what condition), record it in `## Lock review` and leave the row. A conflict already in the model before the run (`proposed: false` on a row this run did not touch) goes under `## Deferred` unless the user asks for it to be fixed.

1. **Read the authoritative lock state from the model** for each module concerned. The generated code shows a row as locked, but not whether the lock is on the row or the whole package, and not why. Find the module's application with `get_applications` (its name drops the `Intent.Modules.` prefix; confirm by its output location), load `scripting-the-model`, and query its Module Builder designer:

   ```js
   const settings = (el, name) => {
     const s = el.getStereotypes().find(x => x.getName() === name);
     return s ? Object.fromEntries(s.getProperties().map(p => [p.getName(), p.getValue()])) : null;
   };
   return findElements({ specialization: "NuGet Package" })
     .filter(p => ["Microsoft.EntityFrameworkCore" /* the packages concerned */].includes(p.getName()))
     .map(p => ({
       name: p.getName(),
       comment: p.getComment(),
       packageLocked: settings(p, "Package Settings")?.Locked,
       rows: p.getChildren().map(v => ({
         version: v.getName(),
         framework: settings(v, "Package Version Settings")?.["Minimum Target Framework"],
         locked: settings(v, "Package Version Settings")?.Locked,
         comment: v.getComment(),
       })),
     }));
   ```

2. **Take the reason from the comment**, on the `Package Version` row or, for a package-level lock, on the `NuGet Package`. A lock with no reason is a finding in itself: say so in the report, and recommend that a reason is added whatever else is decided.
3. **Research whether the reason still holds**, with evidence: the providers a reason names now have versions for that framework, the issue it cites is closed, the license change it guards against still applies. A lock that guards a licence change (MediatR, AutoMapper, MassTransit and the like) holds unless the user says otherwise.
4. **Recommend one of keep, keep and patch, unlock, or an alternative.** Keeping a lock need not mean missing its patches: when the row has a `latestInLockedLine` (the newest version in its locked major that fits the module's other locks, such as EF Core 8.0.28 → 8.0.33), _keep and patch_ moves the row to it and leaves the lock and its reason in place. When `lockedLineSkipped` is not empty, add to the lock's comment why the row stops short of them. An alternative is, for example, a different package, or a per-framework split that adds a new row while the locked one stays.
5. **Ask before changing any lock**, with `ask_user_question`. Group locks that share a reason into one question (every EF Core provider row locked for the same reason is one question). Each question names the module, packages and frameworks, the reason, your evidence and your recommendation (`recommended: true`). At most four questions per call: with more groups, ask in successive calls, and change nothing until every group has an answer.
6. **Record every lock** in `## Lock review`:

   | Module | Package | Framework | Locked at | Latest | Reason | Recommendation | Decision |
   | ------ | ------- | --------- | --------- | ------ | ------ | -------------- | -------- |

   An unlocked row joins the §4 review with its own delta. A kept lock is not mentioned in the module's release notes.

## 4. Breaking-change review

**Which packages:** every package with `needsBreakingReview: true` (a minor or major consumer-visible change, or any change on a 0.x package), and every row §3 unlocked. A patch change on a package at 1.0 or above is not reviewed; §9's build is its test.

**Group by family** so each changelog is read once: by id prefix (`Microsoft.EntityFrameworkCore.*`, `Microsoft.Extensions.*`, `AWSSDK.*`, `Azure.*`, `OpenTelemetry.*`, ...) and by shared `repositoryUrl`.

**Fan out one read-only sub-agent per family**, several in one turn. Give each one the family's packages, their `from → to` versions, `repositoryUrl` / `projectUrl` / `nugetUrl`, and the module folders that use them (from `candidates.json`). Each one:

1. Finds the release notes between the two versions: GitHub releases (`gh api repos/{owner}/{repo}/releases --paginate`, or `Invoke-RestMethod https://api.github.com/repos/{owner}/{repo}/releases` where `gh` is not on the path), `CHANGELOG.md` in the repository, or the vendor's official breaking-changes or migration guide (EF Core, ASP.NET Core and the Azure SDKs publish one per major version).
2. Lists every breaking item with a link.
3. Greps each owning module's `Templates/`, `FactoryExtensions/` and `CONTEXT.md` for the APIs each item affects, and returns the file and line of every hit.
4. Returns a verdict per package from the matrix below, with its evidence. It changes nothing.

### Versioning matrix

| Package delta  | Release notes say                                                      | Impact found          | Module bump                                                      |
| -------------- | ---------------------------------------------------------------------- | --------------------- | ---------------------------------------------------------------- |
| patch          | not reviewed                                                           | none                  | patch                                                            |
| minor or major | no breaking changes                                                    | builds and tests pass | patch                                                            |
| any            | breaking, but not on APIs generated code or typical consumer code uses | none                  | patch, verdict recorded in the report                            |
| any            | breaking on APIs consumers commonly use                                | generated code fine   | **minor**, and the ⚠️ block in the release notes                  |
| any            | breaking on APIs the templates emit                                    | generated code breaks | **stop and ask**: fix the template (minor) or lock with a reason |

Record each verdict in `## Breaking-change review`:

| Package(s) | From → to | Breaking items (linked) | Template hits | Verdict | Module bump |
| ---------- | --------- | ----------------------- | ------------- | ------- | ----------- |

### Checkpoint: a template would emit broken code

Stop **for that package only** and ask with `ask_user_question`, with the evidence: the breaking item, the template lines it hits, and the release-note link. Every unaffected package carries on. The two options:

- **Fix the module.** The template change goes through the normal module-building workflow (`.claude/rules/module-building-workflow.instructions.md`): read `CONTEXT.md` (`module-context-capture`), capture the generated output before the change, implement it (`file-builder-expert`), and regenerate. The module takes a **minor** bump, and its release notes describe the package move and the template change.
- **Lock it.** In §5, leave the package's rows at their current version, set `Locked` on them, and write the reason in the comment: the breaking item, its link, and today's date. The next run's lock review will surface it. The package is left out of that module's release notes.

## 5. Update the model

For each module with something to change after §3 and §4, one `run_designer_script` on its Module Builder designer. Load `scripting-the-model` and `changing-the-model` first, and call `get_designer_rules` for the designer in the same response as your first read of it.

**Check the packages are modelled before changing anything in a module.** A module's `NugetPackages.cs` can outlive its model: elements lost in a merge, or a file that was never generated from that designer, leave a generated file listing packages the designer has no `NuGet Package` element for, so the inventory finds rows the designer cannot change. Query first (`findElements({ specialization: "NuGet Package" })` names), and when a package is not there, leave that module out of this run entirely: no model change, no version (§6), no release notes (§7), no Software Factory run (§8). List it under `## Deferred` as needing its packages modelled; modelling them is a separate piece of work. Setting the version first and finding nothing to change afterwards leaves a version in the model that the repository's gate will not let you set back.

The model's shape (confirmed by the §3 query):

- `NuGet Package` element, named by package id, with the `Package Settings` stereotype (`Locked`).
- `Package Version` children, named by version, with the `Package Version Settings` stereotype: `Minimum Target Framework` (the row's `frameworkName`, such as `.NETCoreApp,Version=v10.0`) and `Locked`.
- `NuGet Dependency` children of a `Package Version`: named by dependency id, with the minimum version as the element's value.

Apply each row's action from `candidates.json`, as adjusted by §3 and §4:

| Action                 | Model change                                                                                                                              |
| ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `update`               | Rename the `Package Version` to `latest`; delete its `NuGet Dependency` children and recreate them from `dependencies`                    |
| `add`                  | Add a `Package Version` named `latest`, with `Minimum Target Framework` = `frameworkName` and `Locked` = false, and its dependencies      |
| `remove`               | Delete the row                                                                                                                            |
| unlocked in §3         | Set `Locked` to false (on the row, or the package for a package-level lock), then apply the row's action                                  |
| kept and patched in §3 | Rename the row to `latestInLockedLine` and recreate its dependencies from `latestInLockedLineDependencies`; `Locked` and the comment stay |
| locked in §4 or §9     | Leave the version, set `Locked` to true, and set the element comment to the reason                                                        |
| anything else          | Untouched                                                                                                                                 |

- **Shared packages end at the same version in every module.** `candidates.json` resolves each package once, so following it converges them. The report's drift table shows where they had diverged.
- **Skip a package whose only changes are invisible to consumers** (its `releaseNoteRows` entry says "row changes only"), unless the module is changing anyway. A version bump with nothing for a consumer to read is noise.
- **Verify from the script result:** each renamed row is `updated`, each new row and dependency appears once as `created`, and `errors[]` is empty. Save on the last successful script for the module.

## 6. Version

Load `module-version-increment` and run its gate, _Is This Version Already In Flight?_, for every module changed in §5, and only those: a module §5 left out (its packages are not modelled, or nothing in it needed to move) keeps its version. A module already on an unpublished `-pre` stays where it is, unless this run's impact needs a higher component. Choose the component from the matrix in §4; when two rows of the matrix apply, take the higher.

Set the version as `module-versioning` says: `Module Settings` → `Version` on the module's package, which the §8 Software Factory run writes into the `.imodspec`. Some modules also carry a `<Version>` in their `.csproj` (`csprojVersion` in `candidates.json`), which nothing regenerates: raise it to match, as `module-version-increment`'s _Keep The Version Consistent Everywhere_ requires.

Record each module in `## Module versions`:

| Module | Version | Component and why | Model | Regenerated | Built |
| ------ | ------- | ----------------- | ----- | ----------- | ----- |

## 7. Release notes

Load `module-docs-chore` and follow it, including its `Include Release Notes` check. Write the entry in the format in [resources/release-notes-format.md](resources/release-notes-format.md), starting from the module's `releaseNoteRows` adjusted for §3 and §4. Add the ⚠️ block when §4 found consumer code impacted.

## 8. Regenerate and build

For each changed module, run `run_software_factory` for its application (`generating-and-applying-code`). Check the `NugetPackages.cs` diff against your plan: every row you changed moved, every lock you kept did not, and the `.imodspec` `<version>` moved. Fix a discrepancy in the model and regenerate; never in the generated file.

Build each changed module with `dotnet build <module>.csproj --no-incremental`, so its `.imod` is repackaged. On `NU1605`, follow `.claude/rules/known-build-gotchas.instructions.md`.

## 9. Tests

1. **Update the Tests applications to the new local module versions**: load `working-with-modules`, and for each changed module, update every Tests application that has it installed (`solutionPath: Tests/Intent.Modules.NET.Tests.isln`). One module per call, one call at a time.
2. **Apply the Tests solution's pending changes**: `./apply-template-testing.ps1`. It normally applies changes blindly; it is right here because only the modules this run changed have moved.
3. **Run the pre-commit checks**: `./run-pre-commit-checks.ps1`. Among other things it validates that `modules.config` matches each `.imodspec` and that every module has a release-notes heading for its version.

When a build breaks:

- **Generated code no longer compiles**: the §4 checkpoint, with the build error as evidence. When the user chooses to lock, revert that package's rows in §5's way, regenerate, and roll back its release-note row.
- **Hand-written code in a Tests application no longer compiles**: consumer code is impacted. Fix the test code, raise the module to **minor**, and add the ⚠️ block.
- **Restore fails with `NU1605` through a locked row's dependencies** (a package the module locks, pulled higher by another row): the lock check missed it or it was overridden. Run the inventory with `-ModuleFilter` for that module and settle its `lockConflicts` as §3 says.

Lowering a row is not enough for a Tests application that already has the higher version: the Software Factory only ever raises a package reference. After regenerating, set the reference in that application's `.csproj` to the row's version by hand, then rebuild it.

## 10. Report

Finalise `.nuget-bump/report.md`, tick `## Progress`, and give the user a short summary with a link to it. It is the pull request description, so it must stand alone:

- the packages moved, per module;
- every lock reviewed: kept or changed, and why;
- every breaking-change verdict, with its links;
- the version each module took, and why that component;
- everything deferred: hand-written branches, deprecated packages, locks without a reason, `ahead` rows.

Commit only when the user asks.
