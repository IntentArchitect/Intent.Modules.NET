# Context: Intent.Common.DriftEngine

## Purpose

The drift engine that converges Intent.Common.Drift and the custom drift modules built per adoption (eShopCustom, the Java spike) (plan: `docs/plan.md`; specification: `docs/spec/`). It is the shared foundation those modules kept rebuilding: scope, code readers, turning the model into claims, the verified, contradicted or can't-verify policy, and reporting. Modules extend it through code with no ceiling; recipes are a shortcut for simple claims. Phase 1 delivers the C# reader, the structure checks (Domain and Services packs), scope and the extension API; the Java reader, with JPA and Spring MVC, was built ahead of phase 4 to prove the engine is language-agnostic.

## Architectural Decisions

- **A module states what to check in C#, not only how to read the code (user decision, 2026-11-13: "this is literally the whole point").** An extension's `ClaimSources` (`IClaimSource`) return `ClaimSpec`s: the element, the kind, the value the model states, anything the source worked out for its reader (`Value`, such as the module's own model of the element), the claim it waits on (any element, any designer), and where the model states it. Its `Kinds` define kinds in code, and its `Designers` name the designers it reads (a module's own designer the engine doesn't know). A source reads the model through the engine (`ModelContext`, below), or with the module's own generated API (`DriftEngineExtensionBase.Application` gives the run's application). A pack's vocabulary is the same thing as data, a shortcut; a source's claim with a pack claim's designer, element and kind replaces it. An existence claim's reader can locate anything (`ClaimReading.Found(object, Span)`) and the claims waiting on it get it (`ClaimContext.Located<T>`). Why: the JSON expression language was the only way to say what the model states, so a module whose model reading it couldn't express was stuck. A check is never trimmed to fit the engine; one that doesn't fit is an engine gap to fix. Proved with eShopCustom's Domain Event Origin links and its Services sends and publishes.
- **The engine reads no language itself; a language is an extension (user decision, 2026-11-13).** An `ILanguage` reads its in-scope files into the graph's files, types and members, and keeps its own syntax on the graph for the extensions that read that language. The stock C# language (`Stacks/CSharp`, extension `csharp`) parses each file once with Roslyn and shares the trees as `CSharpSyntax`; EF Core, ASP.NET Core and modules' own readers all read that one parse. Its profile (type names, collections, type kinds) is its own pack, `csharp`. Code is compared under its own language's profile (C3, 2026-11-14): a type or member by its file's language, a type reference by the language its reader stamps on it (`TypeRefNode.Language`), and a type is looked for under the name each language gives it. The language that read the most files is only the fallback, for what no code says the language of (a refiner's own type reference). Why: the Java eShop's Java and TypeScript are one application, and under one profile the language with fewer files reads as drift (`Engine/MixedLanguageTests`). The Core has no Roslyn reference. Java is another language extension (`Stacks/Java`, extension `intent.java`) with its own parser and profile, `java`. How a language names and wraps the model's members is its profile's too, never the core's (2026-11-13): `naming` gives a pattern per kind of code (`{Name|camel}` for a Java field or method; C#'s `interface` is `I{Name}`, used when the conventions allow only an interface, which is how the Domain Repository finds `IOrderRepository`), and `async` lists the wrappers `operation.returns` unwraps (C#'s `Task<T>`, with `Task` as void). A kind with no pattern is named as modelled. `Engine/LanguageProfileTests` proves it with a made-up language. The type comparer compares type arguments only when the model states them.
- **Java is read with ANTLR, a pure .NET parser (user decision, 2026-11-13).** Its generated C# lexer and parser are checked in, so running it needs no Java; only regenerating the grammar does. Rejected: JavaParser through a Java process (a JDK wherever the Software Factory runs) or IKVM (unproven), though JavaParser's typed tree and type solver are friendlier to an AI. Why the AST matters less than it seems: only the Java language reader touches it, written once, while the house rules an agent writes read the engine's neutral reading, and Java frameworks state almost everything in annotations, which the reading carries. Working out which method a call reaches, JavaParser's real advantage, belongs in the engine for every language, since C# needs it too. The rule audit behind this is `docs/rule-audit.md`. The spike (`D:\Dev\Temp\JavaAntlrSpike`) parsed all 58 files of the Java eShop's backend with no errors: grammars-v4's `java/java` (pinned at `85e2dd1779`, Java 24), runtime `Antlr4.Runtime.Standard` 4.13.1, the newest on NuGet, so the tool jar must be 4.13.1 too. The grammar must carry one patch: upstream `classType` repeats a name with no dot between, so `x instanceof String s` silently parses `String s` as a type, and most files fall back to the slow full parse. The patch keeps one leading name and then only dotted ones; with it there are no fallbacks and parsing is 4 to 6 times faster. Not `java/java20`, a copy of the official grammar that the grammars-v4 README says is slower and stops at Java 20. `GetText()` drops whitespace, so the reader slices source text from token positions.
- **TypeScript is read with TypeScript's own parser, on Intent Architect's own Node.js (2026-11-14).** `typescript.js` 6.0.2, the last JavaScript release (TypeScript 7 is native Go), comes from the `Microsoft.TypeScript.MSBuild` NuGet package (`tools/tsc`, referenced with `ExcludeAssets="all"` only to embed the file) and is embedded in the Stacks assembly with the worker (`TypeScript/Worker/ts-reader.js`), written once to `%TEMP%/intent-drift-engine/typescript-<hash>/`. One Node.js process parses every in-scope file of a run, syntax only (`ts.createSourceFile`, no program or type checker), and returns each tree as JSON by TypeScript's own kind and property names, which `TypeScriptSyntax` keeps for any extension that reads TypeScript. In a Software Factory run it is Intent's `INodeJsProcessManager` (Intent Architect is Electron, and its own TypeScript weaver runs the same way), so the machine needs no Node.js; tests use the machine's `node` (`INodeRunner`). Intent's Node.js is Electron run as Node.js, which differs in three ways the worker handles, all found only by a planted `.ts` file in a real Software Factory run (tests use real `node`): it passes `<exe> <script> --node <script> <arguments>`, so the worker takes its request and response as the last two arguments (`IntentLikeNode` in `TypeScriptFactsTests` guards it); the process doesn't end when the script does, so the worker calls `process.exit`, or the runner waits out its 5-minute timeout; and what the worker writes to its error output doesn't reach `OnError`, so it writes a failure into the response file. Rejected on measurements over the Java eShop's 32 front-end files: grammars-v4's ANTLR TypeScript grammar (29 s, and it fails on ordinary TypeScript) and Jint hosting `typescript.js` in-process (1.8 s to load, then 30–90 ms a file). The worker takes about 0.8 s, Node.js start-up included. `typescript.js` is Apache-2.0 and keeps its licence header. Representation: a file is a namespace named by its path without its extension; what it declares outside its types is a `module` type named for the file with its extension (`client.ts`), so module functions are methods a call can reach like any other; a `const` holding an object literal is an `object` type; a `.vue` file is a `component` type whose script members, props (`property`) and emits (`event`) are its members. JavaScript files aren't read: no rule needs them yet. Nullability follows the nearest `tsconfig.json`'s `strict` or `strictNullChecks`, else `unknown`, as Java's unannotated references.
- **A Razor component is the C# the Razor compiler generates for it, read by the C# language (`Stacks/CSharp/RazorFile.cs`, E3, 2026-11-14).** `Microsoft.AspNetCore.Razor.Language` 6.0.36 from NuGet (the last release there; one assembly, no dependencies) generates each `.razor` file's C# with its `_Imports.razor` files, and Roslyn parses it, so a component is what the compiler sees: one `component` type with its code-behind (Razor components are read before `.cs` files, so the `.razor` part makes the type), in its `@namespace` or its project's `RootNamespace` (now read from the `.csproj`) and folders. Placement follows the generated code's `#line`; what a directive generates without one (`@page`'s `[Route]`, `@layout`'s `[Layout]`, `@inject`'s property) is placed at the directive, which a pass at the start of Razor's pipeline (`Capture`) records, since Razor's syntax tree is internal. Only what the file writes is read: `@code` and `@inject` members, never `BuildRenderTree`; its own `@using`s are its imports, and `_Imports.razor`'s are that file's, which the component has imports from (`FileNode.ImportsFrom`, so an import rule reports one `_Imports.razor` line once, not once per component). A Razor diagnostic doesn't fail the file, as C# syntax errors don't. Its markup isn't read from the generated code: without the referenced assemblies' components the compiler leaves a directive attribute such as `@onclick="() => Save()"` as HTML text, so markup is read from Razor's own parse (E4, below). The ASP.NET Core detector ignores a component's `[Route]`: a page route isn't an endpoint. Rejected: Intent.Code.Weaving.Razor's fork of the compiler (a .NET 8-era build, not on NuGet, and its syntax tree is internal to everyone but the weaver, so it offers nothing 6.0 doesn't but `@rendermode`); Microsoft's current compiler from the .NET SDK (needs Roslyn 5.9, against the 5.0 the engine and RoslynWeaver share) and its NuGet toolset (previews only). Both share assembly names with the fork, which a C# application with the Razor weaver loads; 6.0's name is its own. On eShopCustom's 40 `.razor` files 6.0 and the fork generate the same members with no failures; 6.0 reports `<script>` in a component as RZ9992, which is only a diagnostic. Proven in a real Software Factory run: a `Buyer.razor` planted beside Ordering's `Buyer` class, with `@namespace`, joined it, and the engine reported its kind as `component`.
- **Markup is one shape for every language: `FileNode.Markup` (`MarkupNode`, `MarkupAttributeNode`, E4, 2026-11-14).** A Razor component's markup and a Vue template's give the same nodes: an element's tag as written, the component it names (a type ref that `CodeGraph.TypeFor` resolves from the component's type, as any type), its attributes, the elements inside it, and its content. What an attribute means to a framework (a component parameter, a link's route) is left to stacks, as the reader only splits a directive as its language writes it (Razor's `@bind-Value:event`, Vue's `v-model:title.trim`, `:to`, `@click`) into directive, argument and modifiers. Text content and a plain value are `LiteralNode`s like a C# string's, `interpolated` when code is written in them, so a rule reads `href="/orders/@id"` as it reads `$"orders/{id}"`; text is trimmed with whitespace runs reduced and character references resolved, while an element's canonical text keeps them as written (`CanonicalText.OfMarkup`). Razor's is read from its compiler's intermediate representation, captured in the same early pass as the directives, because its later passes fold static markup into strings and encode it. Vue's is read by `VueTemplate`, C# that reads a single-file component as Vue's compiler does (`@vue/compiler-dom` 3.5's `sfc` parse: its HTML, SVG and MathML tag lists, its component test, its directive shorthands, RCDATA `<textarea>` and `<title>`, its recovery from unclosed and stray tags). Rejected: running Vue's own compiler on the TypeScript worker, as TypeScript's parser runs; it is on no NuGet package, so it would be an 83 KB vendored file, which the repository's edit-tool rule leaves no way to add byte for byte, and the engine already reads a `.vue` file's blocks in C#. Proven against Vue's compiler as an oracle (`D:\Dev\Temp\VueProbe`): every element, position, component, directive, argument, modifier, value and content of the Java spike's 8 components (563 lines) and an edge-case file matched, bar the oracle's own entity decoding. There's no `directive` node: a Razor directive is the code it compiles to, and `@rendermode` isn't read, since Razor 6 parses only its identifier form (`@rendermode InteractiveServer`), not eShopCustom's `@rendermode @(new InteractiveServerRenderMode(prerender: false))`. The `markup` find step reaches a type's markup; `markup with` keeps only the innermost matching elements, as an element's text holds its children's. No stock check reads markup yet: it is for UI stacks and house rules.
- **A value's string is evaluated once, in the core, from facts every language gives it (`CodeGraph.StringOf`, `Code/StringValues.cs`, B10, 2026-11-14).** A language reader says where a value comes from in neutral terms (`ValueNode.Joined` for `+`, `Given` for what it stands for, `Parameter`, `Field`, `Call`, `Trimmed`; `FunctionNode.Changes` for every change but a plain `=`), and its library's string functions become those facts there (C#'s `string.Concat`, `ToString()`, `new Uri(x)`, `TrimEnd(chars)`; TypeScript's `concat`, `String(x)`, `new URL(x)`, `trim()`), so the evaluation, its parameter binding and its agreement rule are written once. Rejected: an evaluator per language, as the eShopCustom Blazor module carries one (~360 lines over Roslyn), which every module and language would repeat. It is lazy (`StringOf` walks the facts when asked; a local's values are `GivenOf`, read on demand), so readers pay nothing for values no rule evaluates. Initializers are read again with the bodies (`MemberNode.Value` is now settable, as `Body` is), so a field's initializer can name another type's constant. Conservative by design: a value given several ways, or a helper with several returns, is known only when they agree; a number, boolean, formatted hole, library call or loop-built string is a hole; a local or field changed by `+=` is a hole. The `+=` rule came from the eShopCustom probe, where `GetAllCatalogItemsUri`'s `filterQs += ...` had first evaluated to the empty string, which claimed a text the code can extend. Checked by hand against the code on eShopCustom's WebApp, WebAppComponents, HybridApp and ClientApp (every `GetFromJsonAsync`, `GetAsync`, `HttpRequestMessage` and `NavigateTo` URI, including `Pages.User.LogIn.Url(Nav)` across types and HybridApp's duplicated `&api-version=2.0`, which its code really sends) and the Java spike's `client.ts`. Markup values and Java aren't evaluated yet: no rule reads them.
- **Protobuf is a language of its own, read by its own parser (`Stacks/Protobuf`, `intent.protobuf`, E5, 2026-11-14).** `ProtobufReader` parses proto2, proto3 and editions by the language's grammar, with every token's position, and recovers after a syntax error at the end of its statement. Rejected: protobuf-net.Reflection 3.4.40, which parses well but keeps every source position non-public (`SourceCodeInfo` is null), and would ship two more assemblies; ANTLR's grammars-v4 protobuf grammar, since generating its parser needs the ANTLR tool on Java, which this machine lacks, and the generated files would have to be written by a script, which the repository's edit-tool rule forbids. Proven against protobuf-net as an oracle (`D:\Dev\Temp\ProtoSpike\oracle.cs`): over 72 real files (Grpc.Tools 2.84's `google/protobuf`, `descriptor.proto` included; Google.Api.CommonProtos 2.17's `google/api`, `google/type` and `google/rpc`; eShopCustom's `basket.proto`; two edge files with proto2 groups, oneofs, maps, streams, scoping and aggregate options) every message, field, number, label, type, enum value, rpc and field presence matched, 1,411 lines. As protoc does, `stream` in an rpc is always the keyword. Three choices of representation, each departing from the first draft of the spec: nullability is the field's presence, not only `optional`, because Intent's own gRPC module (`Intent.AspNetCore.Grpc`, `GrpcTypeResolverExtension`) writes a nullable value as a `google.protobuf.*Value` wrapper, a message, and a model's non-nullable `int` as a plain `int32`; whether a name is a message or an enum is resolved by protoc's scoping among the `.proto` files only, so a C# class of the same name never answers. A streamed rpc side is a `stream` type ref over its message, as `repeated` is a collection over its item, rather than a `stream` modifier, because a parameter has no modifiers and a method's modifier would have to say which side. The gRPC conventions (protoc's renaming, `ServerCallContext`) stay `intent.grpc`'s, still to build: the reader keeps names as written.
- **The Java reader gives a body's calls and creations as the C# reader does (`JavaBody`, 2026-11-13).** Same facts and the same rules for an argument's types, so a house rule over calls reads Java with no change: `Http.parseEnum(OrderStatus.class, status, "status")` is a call named `parseEnum` on `Http`, its second argument the `String` parameter `status`. Java-specific: `this(...)` and `super(...)` call a constructor, so aren't calls; a lambda's parameter is typed only when it's written (`(Order o) ->`, not `o ->` or `(var o) ->`); an array creation isn't a creation. A static call's receiver is a type name, which isn't typed, as in C#.
- **A call has the method it reaches, and a call used as a value is what that method returns (`CallNode.Target`, `CodeGraph.Targets`, B4, 2026-11-13).** Both languages set it the same way once every type is read: on the type of what it's called on, on the type a static call names, or on its own type with nothing to call it on, with what that type inherits; an override hides what it overrides. A method is reached by name and number of arguments, never by the arguments' types: a parameter with a default may be left out and a last array parameter (`params`, varargs) takes any number. A call more than one method can take has no target, rather than a guessed one, because the readers don't type every argument. A method's own type parameter, or its type's, isn't a returned type (`<T> T first(..)` gives an unknown value). C# `await` gives a `Task<T>`'s or `ValueTask<T>`'s `T`. A method reference is a call with `IsReference` and no arguments: Java's `this::audit` and `Order::markAsPaid` (an instance method through a type name, which a call can't reach), not `Order::new`; C#'s method group (`items.ForEach(Audit)`) only when the code doesn't type the name as a value and an in-scope method has it, since C# writes both alike. `CallsFrom` follows a reference as it does a call: a method passed on is one that runs.
- **A call made on a call has it (`CallNode.On`, B3, 2026-11-13).** `ResponseEntity.noContent().build()`'s `build` is made on `noContent`; each call of a chain is also one of the body's calls, the same node, so a rule can walk a chain either way.
- **A literal is its value, not its text (`ValueNode.Literal`, B1, 2026-11-14).** A rule compares `LiteralNode.Value`, which is the same whatever the quoting: C#'s `"a"`, `@"a"` and raw strings, Java's strings with every escape resolved (octal and `\uXXXX` too) and text blocks with their indentation stripped (JLS 3.10.6). Its `Kind` tells `"true"` from `true` and `"null"` from `null`. A number keeps its sign and is as written (`18.4m`, `42L`), as an enum member's value is. An interpolated string has its text and holes in order, a hole typed as any body value is, so a URI rule reads `orders/` and `id` without evaluating anything; evaluating a string through fields and helpers is B10. A type literal (`typeof(Order)`, `Order.class`) has its type: the Java eShop's `Http.parseEnum(OrderStatus.class, ...)`. C#'s `nameof(Order.Total)` is the string `Total` and no longer a call; attribute arguments read the same literal, so `[ForeignKey(nameof(Customer))]` reads `Customer`. A field's or property's initializer has its literal too, for B10 to follow. Literals have no `Types`: the language's own types for a literal weren't needed, and naming them would put each language's primitive names in the readers for nothing.
- **An import says what it brings in, and a type name resolves through imports (B9, 2026-11-14).** `Wildcard` marks an import of everything its target holds, a C# namespace `using` as much as Java's `.*` (whose target no longer carries the `.*`, so a Java wildcard import reaches its package as a `using` does); an import that is none of wildcard, static or aliased names one type. `CodeGraph.TypeOf(import)` gives the in-scope type an import names (single-type, static, alias), so a rule finds the files it resolves to. `TypeFor` resolves an unqualified name through the file's alias or single-type import first (Java's import shadows its own package's type; an import of a library's type resolves to nothing), then a type of its own or an enclosing namespace, then the only one a wildcard import reaches. Before, two same-named types in other namespaces resolved to neither, and an alias to nothing. The JPA stack's import check matches `jakarta.persistence.*` by its target, `jakarta.persistence`.
- **Code runs in units, one shape for all of them (`FunctionNode`, B7 and B8, 2026-11-14).** A method's or constructor's body (`MemberNode.Body`; `Calls` and `Creations` read from it), a lambda (`ValueNode.Function`: a Minimal API handler's `[FromRoute] Guid id`, an options callback's `o.Title = "Orders"`) and a file's top-level statements (`FileNode.TopLevel`, Program.cs's registrations) each have parameters, calls, creations, plain assignments and returns. Everything written inside a unit counts, its lambdas' code too, as the same nodes the lambda's unit has, so a rule reads Program.cs whole or one handler alone. A return is the unit's own unless a nested lambda, local function or Java anonymous class holds it; a `void` method's expression body returns nothing. Top-level code's unqualified calls reach the global namespace's `Program` when a partial one is declared (C#'s own rule); its types and their members aren't top-level code. Why one shape rather than a lambda node beside the member's calls: a rule following a handler, a method group or Program.cs shouldn't need three APIs. Not built: TypeScript module-level code and Vue `<script setup>` (with E2), and an `args` parameter for top-level code.
- **A creation is a node with what it's given, and a value knows the creations it can be (`CreationNode`, B5, 2026-11-14).** A body's `Creations` have their arguments, an object initializer's assignments (a member by name, an indexer as written, a nested initializer as its text) and a collection initializer's items; `Creates` is now their types. A value's `Creations` follow the same ways its `Types` do (a local, a cast, a conditional), and they're the body's own nodes, so `SendAsync(request)` reaches what `request` was created with: each creation's type is one node, and a value's types are looked up by reference. A target-typed `new()` names no type and isn't read. A creation is set with the calls, after every type is read, since its arguments are typed.
- **A call has its type arguments (`CallNode.TypeArguments`, B2, 2026-11-14).** `AddScoped<IOrders, Orders>()` and `AddSubscription<M, H>()`, a C# method group's (`Map<Order>`), Java's rare explicit ones (`this.<Order>create()`, which the reader now reads as a call at all) and a Java method reference's (`this::<Order>create`). A method that returns its own type parameter gives the type the call passes (`CallTarget.ReturnsGiven`), so `var o = Create<Order>()` is an `Order`; without type arguments it stays unknown, since inferring them would need the arguments' types.
- **A house refines what a stack reads; it never repeats the stack's comparison (`IMemberRefiner`, 2026-11-13).** Proving a Java house rule on the engine showed the gap: the Java eShop binds `String status` and turns it into an `OrderStatus` with its own `Http.parseEnum(OrderStatus.class, status, "status")`, and responds with `Http.created(body)`. Only the house knows those helpers, but the comparisons (a handler's bound parameters, a `ResponseEntity<T>`'s body) are the Spring MVC stack's, and a house claim reader would have had to redo them whole. So a refiner gives the member a claim's dependency located as the house reads it (`member with { Parameters = ... }`, `status: String as OrderStatus`), before any reader runs, and every reader, the engine's own rules included, reads that one. Refiners run in extension order, so a house's run after the stock ones, each on what the one before left. Rejected: a delegating `context.Next(member)` for readers (the engine's own rules write the claim directly, so they couldn't be reached), and making the stack's readings public for the house to call (each house rule would still repeat the comparison). `MemberNode` and `ParameterNode` are records for `with`, but equal only to themselves, as graph nodes. The Java eShop's Services module (`HttpHelpers`) is the proof: its 27 Services findings (25 `ResponseEntity<Object>` returns, 2 parsed enums) are 0, with plants in each caught.
- **One Roslyn at run time, so a module's own C# reader runs on the engine's trees (proven 2026-11-13).** The engine compiles against Roslyn 5.0.0 and ships it (below); eShopCustom's modules compile against 5.0 and bundle it. In the Software Factory the Domain module's reader, built against 5.0, reads the trees the engine's C# language parsed, and caught four planted domain-event drifts. This replaces an earlier, unproven note that an extension built against another Roslyn would fail. Neither eShopCustom extension reads the trees itself any more: both read the engine's code reading (below).
- **A framework's extension answers only when its framework is in the code (2026-11-13).** EF Core reads only when the code configures an entity or declares a `DbContext`; ASP.NET Core only with a controller, an attribute-routed action or a Minimal API endpoint. Otherwise their claim readers return null, so the claim goes to another framework's extension (JPA, Dapper's) or, with none, can't be verified, never a false "the code doesn't state it".
- **The core knows no technology; everything else is an extension (user decision, 2026-11-13).** An extension (`IDriftExtension`) brings languages, packs (kinds, vocabulary), claim sources, code readers (`ICodeReader`, given the graph, with its language's syntax on it, and keeping what it finds there with `CodeGraph.Set`), claim readers (`IClaimReader`) and comparers (`IValueComparer`). The engine's own comparers are `exact`, `ignoreCase`, `number` and `set`. An extension's claim reader runs before the core's structure rules, and a later extension's before an earlier one's, so a module can read any kind, the core's included; returning null passes the claim on. A throw is `ruleFailed` on the claim plus one `config/pluginFailed` finding. Why: the engine must do everything the custom modules did, so it may not limit them; EF Core and ASP.NET Core code had crept into `DriftEngine.cs`, turning it into a Common.Drift replacement.
- **What the model states is framework-neutral; how a framework's code states it is a separate extension (user decision, 2026-11-13).** `intent.rdbms` (tables, keys, columns, indexes, foreign keys, from the RDBMS stereotypes, with the `storeType` and `literal` comparers) and `intent.http` (routes, verbs, parameter sources, security, with the `route` comparer) read no code. `intent.efcore` and `intent.jpa`, `intent.aspnetcore` and `intent.springmvc` only read those claims from their code, each with no change to the others. They live in `Intent.Modules.Common.DriftEngine.Stacks` (`StockExtensions.All`), using only the public API.
- **Modules register an extension the way reporters register with the hub.** `Api/DriftEngineExtensionBase` is a factory extension that publishes itself on the run's event dispatcher before template registration; `DriftEngineReporter` subscribes at the run's start and runs the registered extensions after the stock ones. eShopCustom's Architecture module is the first to use it (its Layers as claims, its import check as a rule), and its Domain module the second (its own stereotypes, read through the stock EF Core reading); a module compiles against the engine's assemblies and ships none of them, depending on Intent.Common.DriftEngine instead.

- **The engine is its own assembly, `Intent.Modules.Common.DriftEngine.Core`, shipped in the `.imod` beside the module's (2026-11-13).** It depends on the SDK's model interfaces only (Roslyn is the Stacks' C# language's), so the acceptance suite (`Intent.Modules.Common.DriftEngine.Tests`) runs it from fixture data with no Software Factory. The module project holds only the hosting: `DriftEngineReporter`, `Reporting/DriftEngineReport` and the extension base. The `.imodspec` lists the Core and Stacks `.dll` and `.pdb` by hand.
- **The engine ships its languages' parsers and depends on no language's modules (2026-11-13).** The `.imod` carries Roslyn (`Microsoft.CodeAnalysis` and `.CSharp` 5.0.0) and the Razor compiler (`Microsoft.AspNetCore.Razor.Language` 6.0.36) for C#, the ANTLR runtime for Java and `typescript.js` (inside the Stacks assembly) for TypeScript; Protobuf's parser is the engine's own code, so it ships nothing more. The `.imodspec` depends on no RoslynWeaver or Intent.Common.CSharp, so a Java application installs no C# modules and gets none of their `.agents` guidelines. Roslyn 5.0.0 is the exact build Intent.OutputManager.RoslynWeaver 5.0.3 ships, so a C# application that has both loads one Roslyn: eShopCustom's Ordering stayed at 0 engine findings, and the Java eShop kept its 3. Rejected: depending on RoslynWeaver for Roslyn, as the engine first did and Intent.Common.Drift does, which made every Java application a C# one too. When RoslynWeaver moves to another Roslyn, the engine's moves with it.
- **Reports through Intent.Common.DriftReporting with its own Areas (plan decision: both engines run side by side).** A designer's findings go in the Area `<Designer> (DriftEngine)`; scope, config and reader findings go in `Drift Scope (DriftEngine)`. A claim finding is a Model / Code finding on the element, against the code's file and line.
- **The report holds only drift (user decision, 2026-11-13, spec decision 30).** An AI reads the report, so anything that isn't drift is noise. An Area is created by its first finding and declares no categories, because the hub renders a declared category with no findings as "✓ Clean". `info` findings (the scope coverage listing, the `engine/notStated` note) and the run's claim counts go to the Software Factory log only. Don't add an Info severity to the hub to put them in the report.
- **No Drift Scope only warns (spec decision 28).** The run result still carries `scope/missing` as an error; the host logs it as a warning and adds no Area, because an error would untick every staged change, including the ones that set scope up.
- **Designers are read by id, copied from each designer module's `ApiMetadataDesignerExtensions`.** Packs name designers (`Domain`, `Services`); the host maps the name to the id so it needs none of those modules installed. An extension adds its own designers' ids (`IDriftExtension.Designers`); the SDK can only fetch a designer by id.
- **Features are built lean, end to end on eShopCustom (user decision, 2026-11-13).** eShopCustom (`D:\Dev\Temp\eShopCustom`) is the system: its custom modules (Domain, Services, FrontEnd, Architecture) are what the engine must do, each rebuilt as an extension. basislink5 and CrmBus are Common.Drift examples; rebuilding Common.Drift's checks on them is replication, not the goal. Each slice goes model claim or rule, reader, hosted run, then planted drift: every plant caught as one finding, the unchanged code clean. Cases for every example come later; existing cases must keep passing.
- **A rule reads the model as a claim source does, and packages other applications own are references only (C4, 2026-11-14).** `RuleContext.Model` is the same `ModelContext` (links, stereotypes, owners), and `RuleContext.TypeMatches` compares as `member.type` does, so a module rule never rebuilds either. The host passes a designer's packages from other applications as `DriftInput.References` (`ModelContext.References`, `ReferencedElements`): a FrontEnd's Service Proxies target another application's operations, and a rule may read them, but nothing claims on them, since their code isn't in this application's output.
- **A rule is a check that isn't one claim's value (`IDriftRule`, plan block 4).** It sees the designers' elements, the evaluated claims, the in-scope code and the scope (`RuleContext`), and returns findings with an Area, a category, a subject and what else they involve (`Finding.Against`). Rules run after the claims, only when a Drift Scope is set; the engine marks each Area ` (DriftEngine)`. Why: the Architecture module's import check is one finding per import across Layers, not a value on one element.
- **Every reader gives the graph each file's declared namespaces and imports (`FileNode`, `ImportNode`).** They are the language-neutral facts a rule over imports needs; the C# reader reads `namespace` declarations and `using` directives, a Java reader will read `package` and `import`.
- **An extension can locate the code an existence claim is about (`ClaimReading.Found`), so the claims that depend on it read that.** eShopCustom's Backing Field makes an attribute's member a private field; an EF Core shadow property is a member the reader makes, typed with `CSharpSyntax.TypeOf` (the C# reader's own nullability rule). Without it a house reader could only say "present", and the attribute's type and column claims would have no member to read.
- **A claim can wait on any claim, not only on its existence (2026-11-13).** A pack's `dependsOn` names one on the same element or its owner; a claim source's names any. eShopCustom's Backing Field column waits on the field's `Property("_field")` mapping, so an unmapped field is one finding, not a second one for its column. Such a claim is still named with its owner (`PaymentMethod.Expiration`), because naming follows the chain down to `member.exists`. A missing element's "N claims on it can't be checked" counts the whole chain.
- **The engine reads the model and the code for a module, so a module's check is its own rules, never its own parser (user decision, 2026-11-13: "give the module access to read the model and read the code, part of the whole point here was not to have every module build its own parser and own common logic").** The model: `ModelContext.Elements(designer, type)`, `Links(element, association)` (the elements an association from it points at, with the end, as `ModelLink`), `HasStereotype` and `Stereotype(element, stereotype, property)`; a claim reader has it as `ClaimContext.Model`. The code, as language-neutral facts a Java reader fills the same way (the spec's `call` and `creation` nodes, code-reader.md): each method's and constructor's calls (`CallNode`: name, receiver, the receiver's type when the code says it, its arguments, its text and place), the types it creates, and every member's access. An argument (`ValueNode`) carries the types the code says it is: a creation is its type; a local, its initializer and its assignments before the call, else its declared type; a parameter, field or property, its declared type; a cast, its inner value, else the cast type; a conditional, both branches; a property path, through in-scope types. When the code doesn't say, it is unknown, and the check says it can't verify rather than guess. `CodeGraph.CallsFrom(type, member, follow)` gives a member's calls and those of the type's own methods it calls, so a raise or a send in a private helper counts; `TypeFor` finds the in-scope type a reference names. A reader passes its own finding text to `ClaimReading.Compared(actual, at, same, message)`, and the report uses it for a contradicted claim, so the module's wording and fix stay. The language reader sets calls once it has read every type, since what an argument is can depend on another type. Why: the first versions had the Domain module bring its own Roslyn reader and the Services module reuse its house parser, which is what the engine exists to stop. Proved on eShop.Ordering, neither module reading code itself, both clean on the real code. The Services module's `ServicesInteractions` compares an operation's Perform Invocation links to Commands with the `Send(...)` calls in it, and the Publish Integration Event links of a command handler, domain event handler or integration event handler with its outbox or event-bus publishes; it caught six plants: a wrong command sent, a wrong command sent from a helper method, an Identified Command sent bare, a wrong event published, a missing publish, and a `Send(CommandFor(@event))` it can't verify. The Domain module's Domain Event Origin links caught four: a wrong event through a local in the private helper the constructor calls, a removed raise, a swapped event, and an `AddDomainEvent(StockConfirmedEvent())` it can't verify.
- **An empty set is `none` on both sides.** A set kind stated always (`type.base`, or a house kind such as the events an operation raises) with nothing in the model reads `none`, as one read from the code does, so a finding never says "model ``".
- **A field's attributes are read, as a property's are.** eShop's Ordering.Domain is nullable-disabled and marks its backing fields `[Required]`, which EF's nullability rule reads from the member. Without the field's attributes, every required backing field read as nullable.
- **A reader that compares a value itself says so (`ClaimReading.Compared`, with `ClaimContext.TypeMatches`).** A type can't be compared as text: `Order` in the model is `Ok<Order>` under `Task<Results<...>>` in a Minimal API handler.
- **Members include inherited ones (`CodeGraph.Bases`, `MembersOf`).** A base type is found by name among the in-scope types; with several, the one in the type's namespace or an enclosing one. eShop's entities inherit `Id` from SeedWork's `Entity`.
- **A Command or Query is the class or record of its name**, like a DTO. Only its type is claimed so far; its fields aren't.
- **`type.base` is built as the spec's claim catalog has it (a set, compared `subset`), ahead of its phase 2 cases, because eShopCustom's SeedWork needs it.** `CodeGraph.Supertypes` gives an in-scope base by its qualified name, and its own bases in turn, and a library base by its name as written and its bare name, without generic arguments. So a house pack names its own SeedWork types qualified (`eShop.Ordering.Domain.Seedwork.Entity`), and a same-named base that isn't declared in scope doesn't match. The expression language has the spec's association forms for the vocabulary that states it: `associations('Generalization')`, `it`, and an end's `isSource`, `isTarget`, `otherEnd`, `association`, `multiplicity` (`1`, `0..1`, `*`, `1..*`), `isNavigable` and `element`, plus number literals (`count(...) == 0`). `type.marker`, which needs the spec's discriminator, isn't built; a house extension states its markers as its own kinds meanwhile (eShopCustom's `seedwork.aggregateRoot`).
- **The RDBMS Primary Key's Data source and the Index stereotype on attributes are claimed (`column.valueGeneration`, `index.columns`, `index.unique`).** User supplied is `ValueGeneratedNever()` or `[DatabaseGenerated(None)]`, Auto-generated a call that generates it (`ValueGeneratedOnAdd`, `UseIdentityColumn`, `UseHiLo`, `UseSequence`) or `[DatabaseGenerated(Identity)]`; Default states nothing. Both were stock stereotypes eShop.Ordering's model uses that no claim covered, so they went unchecked.
- **Several claims of one kind on one element are told apart by a discriminator (`ClaimSpec.Discriminator`, `Claim.Discriminator`, 2026-11-13).** The Index stereotypes on a class's attributes are one index per UniqueKey, in their Order, and an attribute with no UniqueKey is an index of its own: `intent.rdbms`'s `AttributeIndexes` claim source states each as `index.columns` and `index.unique` on the class, keyed by its name, else its columns (`Email`), with a `ModelIndex` as the value its framework reader finds it by: by name, else by columns. Before this only an unnamed one-attribute index was claimed, on the attribute, so a named or composite index went unchecked. `index.columns` is `stated: always`, as the claim catalog has it: code that declares no such index states there is none. `ClaimRef` keeps its three-part constructor beside the four-part one: eShopCustom's extensions, built against the engine before the discriminator, failed with `MissingMethodException` until it was restored, so a public signature only ever gains overloads.
- **An Index stereotype on an association's target end puts that end's foreign key column in the index (2026-11-13).** Intent.Metadata.RDBMS defines Index on Association Target End too, though its own `GetIndexes` reads only attributes and Index elements. Java has no field for a one-to-many's join column (`wishlist_id`, owned by `Wishlist.items`), so the end is the only place the model can put it. The index is on the class whose table holds the column: a one-to-many's "many" side, else the class the end navigates from; a many-to-many's is a join table and is left out. The end's column is its Foreign Key Column Name, else its name, so a JPA constraint's raw column (`wishlist_id`) matches with no mapping. Before this the Java eShop's WishlistItem index read as `ProductId` alone and was reported missing, though the model had it right.
- **The acceptance fixture builds associations (`FixtureModel`, 2026-11-13).** The fixture schema always allowed `associations`, but the harness never built them, so every case that needed an end could only be skipped or wrongly pass. Each end is in its other end's element's `AssociatedElements`, a target end has its association's id, and an end whose `element` is an association's id stands for that association's target end.
- **An index's name isn't compared.** The catalog has no kind for it: a UniqueKey (Intent's EF Core module makes it `HasDatabaseName`) finds the code's index by name, else the index is found by its columns. The Index stereotype can't group a composite index without a UniqueKey, so the Java eShop's model names an index its unnamed `@UniqueConstraint` doesn't, and that isn't reported.
- **A `whenSet` kind takes no value from silence (R4).** A claim reader's `Absent` on a `whenSet` kind is "the code doesn't state it", with no value read; on an `always` kind it is `none`, from silence. The acceptance cases for JPA's `@Column` with no `length` or `name` found it.
- **Any designer can carry claims, the Codebase Structure included**, and a pack's vocabulary can name the Area its findings go in (`"area"`), so a module's Layers report in `Architecture (DriftEngine)`, not `Codebase Structure (DriftEngine)`. An existence kind an extension reads reports a miss with `ClaimReading.Missing(where, searched)`, and a claim reader can ask the scope whether code it didn't find is there but out of scope (`ClaimContext.Scope`).
- **A Service or Service Proxy is the class or interface of its name; an Operation is its method.** basislink5's Services model both controllers (`FuturesController`) and business classes (`Bid`). `operation.parameters` is the spec's list of `name: type`, so a changed parameter type is one finding on the operation; `parameter.type` stays unbuilt until its phase 2 cases. The profile's `injectedParameters` (`CancellationToken`) are never part of a signature. Overloads with the same parameter names are told apart by type (`Update(BidsDTO bid)` beside `Update(bids bid)`).
- **Of several types with an element's name, the one whose namespace ends with the element's designer folders is it.** Intent's convention is folders become namespaces; basislink5 has a Domain `ReportListUser` (folder `Entities`) and a Services one (folder `BusinessObject/Reports`).
- **`intent.aspnetcore` reads attribute routing** (`[Route]`, `[Http*]` templates and the `[controller]` and `[action]` tokens) **and Minimal APIs** (`Stacks/AspNetCore/MinimalApis`). Routes compare case-insensitively without slashes or constraints. A Minimal API router is the static class whose method maps handlers with `MapGet`/`MapPost`/... on a method group, so a Service is its router and an Operation its handler. A `MapGroup` prefix is the service's route, followed through a local variable's initializer chain. `RequireAuthorization`/`AllowAnonymous` count on the endpoint, the group, or a call chained on the router's mapping method anywhere (`orders.MapOrdersApiV1().RequireAuthorization()` in Program.cs). A handler's return type is its `Results<...>`'s success result's `T`, under `Task`. Its parameters exclude what the framework injects: `[FromServices]`, framework types (`CancellationToken`, `HttpContext`, ...), interfaces, DbContexts, and `[AsParameters]` holders with any service property. Why: eShop.Ordering, the first Services model on eShopCustom, is Minimal APIs.
- **A navigable association end is a member of the element at its other end** (`IAssociationEnd.OtherEnd()`), reached through `AssociatedElements`. `member.nullable` is claimed for single ends only: a collection end's nullable is its multiplicity, not C# nullability.
- **`intent.efcore` reads EF Core's fluent configuration and data annotations from syntax (`Stacks/EfCore/EfCoreReader`).** `modelBuilder.Entity<T>(e => ...)` and `IEntityTypeConfiguration<T>.Configure(builder)` bodies are read as call chains on the builder: a chain starting `Property(e => e.X)` or `Property("_x")` configures that property, the rest (`ToTable`, `HasKey`, `HasOne`) the entity. A call names members by its lambdas, or by its strings when every argument is a string (`HasForeignKey("_cardTypeId")`; `HasIndex(e => e.A, "IX_A")` names an index). A configuration is a type's when the names match and the configuring file reaches the type's namespace, through its own or its project's global usings, so eShop's Services `Order` view model isn't the `Order` entity.
- **An EF Core shadow property is the entity's member (2026-11-13).** `Property<int>("BuyerId")`, with no member of that name on the class, answers the attribute's `member.exists`, typed by the call, so its type, nullability and column claims read it. eShop.Ordering's `PaymentMethod.BuyerId` and `OrderItem.OrderId` are modelled this way. It is explicit code, so it isn't a convention. eShopCustom's own Domain check accepted one only for a foreign key; the engine accepts any, since the call states the property whatever it is for.
- **The EF Core reading is public (`EfCoreModel`, `EntityConfig`, `FluentCall`)**, so a house extension checks its own stereotypes against the same configuration (`code.Get<EfCoreModel>()?.Of(type, code)`) instead of reading it again. eShopCustom's Backing Field reads `Property("_field")` and `HasColumnName` from it.
- **A stated value is only what the code states explicitly (user decision, 2026-11-12).** A Table Name with no `ToTable` is drift even when EF's DbSet-name convention gives the same table: basislink5's three WebCommonDBContext entities report exactly that. The one exception is nullability, where the code always states something: outside a nullable context `IsRequired()`, `[Required]` or `HasKey` make a column required and silence leaves a reference type optional (EF Core's rule), so `member.nullable` gains this second rule from `intent.efcore` (spec decision 13) and only for mapped entities. Association ends are left to their foreign keys.
- **The model's EF values are compared as Intent's EF Core module writes them.** A Default Constraint Value may be quoted or not (its `EscapeHelper` accepts both), so `column.default` compares unquoted; a value default reads as the C# literal written, a SQL default as the string's content. A Column Type compares without case or spaces (`decimal(18, 4)`), and a text column's facets state its store type too: `HasMaxLength(1).IsUnicode(false).IsFixedLength()` is `char(1)`. Precision and scale come from `HasPrecision` or a `decimal(p, s)` column type.
- **A foreign key is read by EF Core's convention too, for the same reason (2026-11-13).** The Domain designer always marks an association's foreign key, so it can't leave a conventional one unstated either. eShop's `PaymentMethod.BuyerId` and `OrderItem.OrderId` are shadow properties EF links to `Buyer.PaymentMethods` and `Order.OrderItems` by name, with no `HasForeignKey`. Reading only explicit code reported both on the code the model was drawn from, which can't be drift (user, 2026-11-13: a finding on an unchanged adoption baseline is an engine or model bug). With no `HasForeignKey` or `[ForeignKey]` on the relationship the model names, the dependent's property named after the dependent's navigation or the principal type, followed by the principal's key or `Id`, is its foreign key. An `Ignore` on the navigation, or a `HasForeignKey` naming another property, is drift as before.
- **A key is an EF Core convention the engine reads (2026-11-13).** The Domain designer always marks an entity's key with Primary Key, so unlike a Table Name the model can't leave a conventional key unstated. With no `HasKey`, `[Key]` or `[PrimaryKey]`, the code's key is EF Core's: a single property named `Id` or `<Entity>Id`. basislink5's scaffolder leaves `HasKey` out for 32 such entities. `table.key` is a set: EF orders a composite key by `HasKey`, the model by its attributes.
- **A Foreign Key states its navigation:** its `Association` property gives the association end, so `column.foreignKey` compares the navigation's name. It is read from the entity's own `HasOne(d => d.Nav)...HasForeignKey(d => d.Fk)` chain, the principal's `WithOne(d => d.Nav).HasForeignKey(...)`, or `[ForeignKey]`. `EntityConfig.Chains` keeps each chain whole for this.
- **The expression language has the spec's `where`, `map`, `join` and `count`, and an element-valued stereotype property gives the element.** Inside `where` and `map`, the item is self: `join(map(where(children('Attribute'), hasStereotype('Primary Key')), name), ', ')`.
- **File Config is checked as `type.file` and `type.namespace` (core kinds, stated when set).** `Filename` is the file holding the type, without extension; basislink5 keeps several DTOs and its enums in one file each (`UserManagementDTO.cs`, `Enums.cs`). `No Namespace` isn't claimed yet.
- **An EF index is found by its name (`HasIndex(..., "IX_...")` or `HasDatabaseName`), else by its columns.** `index.columns` compares in order, as a composite index's column order matters to the database.
- **A parameter source is stated only by its binding attribute (user decision, 2026-11-13).** `[FromBody]`, `[FromRoute]`, `[FromQuery]`, `[FromHeader]` or `[FromForm]`, and `[FromServices]`, which reads `From Services`, so a modelled request Parameter the code injects is drift; ASP.NET's inference from the route template or the parameter's type isn't read, as with a Table Name. basislink5 reports 93 `From Route` and 12 `From Body` parameters without one, until their model Source is Default or the attribute is added. Kept by the user on eShop, the same day, over reading ASP.NET's inference: its 5 such parameters were drawn as From Body or From Route by the adopting AI, which was a modelling error, and are now Default. So a model drawn from code says Default wherever the code has no binding attribute. With Default the engine makes no claim, so a later change to how such a parameter binds isn't the engine's to catch. eShopCustom's Services module, which reads ASP.NET's inference, still catches it: a planted `[FromQuery]` on `CancelOrderAsync.command` was caught by it, not by the engine. Spring MVC is the same: `@PathVariable`, `@RequestParam`, `@RequestBody` and `@RequestHeader` state a source, and Default claims nothing. The spec's two cases that had the model infer Default (`default-not-claimed`, `java-default-not-claimed`) were rewritten to expect no claim; an inference claim source was tried and removed the same day, since it reported eShop.Ordering's convention-bound Minimal API parameters. The three that read ASP.NET's inference as stating a source are now `contradicted-*-not-stated`, and the claim catalog's row is `whenSet`, as `intent.http` declares it.
- **The ASP.NET Core extension reads ASP.NET Core's own `[Authorize]` and `[AllowAnonymous]` only (user decision, 2026-11-13).** A custom authorization filter, like basislink5's `[Authorization]`, belongs in a house extension (spec open question 3, where house packs live); until one exists its 24 Secured services and operations report. Roles come from `[Authorize(Roles = "...")]` and compare as a set.
- **Java states nullability only by annotation, and the profile says how (2026-11-13).** The `java` profile's `nullable` lists the wrappers (`Optional<T>`), the nullable and non-null annotations and the boxed types: a primitive is not nullable, a boxed type or `Optional` is, an annotated reference is as annotated, and any other reference is `unknown`, as code-reader.md has it, never guessed nullable. An unknown reading makes no finding of its own but one `engine/notStated` note, logged only, whose why-and-fix text is the profile's `nullable.notStated`, so the core holds no language's wording. `intent.jpa` adds JPA's rule for a mapped entity's attributes and association ends, as `intent.efcore` does EF's (spec decision 13): `@Id` is required, `@Column(nullable)`, `@JoinColumn(nullable)` or `@ManyToOne(optional)` state it, and silence is nullable. Not for a DTO, even one resolving to an `@Embeddable` of the same name. Package-level `@NonNullApi` defaults aren't read yet.
- **Spring MVC maps a Service to its controller in the claim reader, not a pack (2026-11-13).** A Service with Http Service Settings, or an operation with Http Settings, is the `@RestController` named `{Name without Service}Controller`, else the class of its name; a pack can't be gated on a framework being present, so the mapping lives in `intent.springmvc`'s `type.exists` reader, which answers only when Spring is in the code. The body parameter is the `@RequestBody` one whatever its Java name (model `input`, code `body`); others match by their binding annotation's name. A path is read without its leading `/`. `ResponseEntity<Object>`, or a wildcard, doesn't state its body type, so the stack reads what the handler builds its successful responses with, each a chain from a `ResponseEntity` factory (`ok(x)`, `of(optional)`, `.body(x)`, or no body for `.build()`; `ok`, `of`, `created`, `accepted`, `noContent` and `status(..)` of a 2xx are successes, the rest errors, which the model doesn't state); a response built by another method, such as a house helper, is a house refiner's to read (2026-11-13). Security is `@PreAuthorize` (`hasRole`, `hasAnyRole`, `isAuthenticated()`, `permitAll()`), `@Secured`, `@RolesAllowed` and `@PermitAll`, with `ROLE_` dropped.
- **Secured's roles are its `Roles` text, else its `Security Roles` elements.** The expression language reads a stereotype property holding several elements (`IStereotypeProperty<IElement[]>`) as the elements, so `join(map(stereotype('Secured')['Security Roles'], name), ', ')` names them. The Java eShop's model uses only Security Roles, so its roles went unchecked before.
- **The acceptance suite runs the languages and the code-free vocabularies always, and a framework only when a case names it.** `intent.rdbms` and `intent.http` are what a case's `intent.domain` and `intent.services` meant when the spec was written; a framework left unnamed lets a case leave a kind unread (`noRule`). The suite counts every stock extension's kinds, not only the core's, so the 25 Java and HTTP cases those kinds gated now run, and phase 4's C# `parameter.source` cases run too, since they pin the binding decision.
- **Every stock pack and extension runs until the `Drift Check` stereotype chooses them (not built yet).** One whose designer isn't installed makes no claims, and a framework's extension with its framework absent reads nothing.
- **`Drift Scope` targets the Root Folder and Folders only (spec decision 27).** The Visual Studio project types made Module Builder generate accessors that need Intent.VisualStudio.Projects, which a Java codebase doesn't have.
- **An item list reaches the engine as `IStereotypeProperty<IStereotype[]>`, one stereotype per row.** Its `Value` text isn't the rows. Multi-line text properties (`Glob`, `Types`) hold one value per line. The suite's fixture builder hands item lists over the same way, so the engine reads one shape.
- **"Code the model doesn't describe" is the engine's, once, for every module (D1, 2026-11-14).** Code is located when a claim's reading came from it or from code inside it (`LocatedCode`: existence results, `_located` nodes, and every reading's span), and a type with a located member is located. The engine runs an opt-in rule only when the Root Folder's `Drift Check` lists `optin/{id}`, then applies the row's Glob (narrows, never widens), Context, the exceptions (last match; one matching nothing warns only if its rule ran) and the overrides, the same for its own `unmodelled.file`/`.type`/`.member` and a module's `IOptInRule`, which only finds code (`UnmodelledCode`). A module's rule of the same id replaces the engine's. Why: every house module had rebuilt "what no claim located" as Backlog, which is the shared logic a module is not meant to carry. `unmodelled.member` skips an override only when the type has a modelled base: a hosted service's `StopAsync` and a gRPC service's methods override a framework's base and are the type's own operations. A find path the engine can't read is `config/ruleInvalid`, not a plug-in failure: it is the pack's error.
- **Find paths match canonical text, so a pattern is independent of formatting (2026-11-14).** C# joins tokens with one space only between two words, keeping an interpolated string's parts joined; Java joins its parse tree's terminals, so comments never count. It is computed only when a find path asks (`TextOf`). An element type says which members it can state in its stock convention (`states`), and a house pack says what its own types look like (`find`, `files`, `typeKinds`, and a designer's `members`); a house convention that says nothing of `states` keeps the stock pack's.
- **A `Context` scope row is read, never checked (D2, 2026-11-14).** Rules need facts from files that mustn't be reported themselves (Program.cs registrations, the DbContext); In made opt-in rules report them, Out made them unreadable. Claims still verify from a Context file, since the model describing code there is the model's business; only findings about the file's own code are dropped: opt-in findings, and an `IDriftRule` finding whose subject is the file. `CodeScope.Includes` means read, `Checks` means checked. A Context row needs a reason, as an Out row does.
- **Opt-in findings are anchored on the code; overrides set any finding's severity (D3, 2026-11-14).** An opt-in finding's subject is the file and line, in the Area of the designer whose convention or element found it (`unmodelled.file`'s in `Drift Scope (DriftEngine)`), against the element whose type holds the code. It is an error by default; a `Severity Overrides` row (`*` wildcards, Error or Warning, a reason, the last match wins) changes any non-info finding, claims' included. Rejected: per-rule default warnings as the house modules had, which hid Backlog in a passing run; a team that wants that says so in the model, with a reason.

## Invariants

- The engine never writes to the codebase; checks prove it on real codebases with `git status` before and after (`Real/RealStructureRunTests`).
- A client's code, model export and results stay on the machine that ran them. Committed files carry counts only.
- A public engine signature only gains overloads: modules compiled against an earlier engine load the new one unchanged.

## Known gaps

- Module Builder stages `Intent.Modules.Common.CSharp` 3.8.1 back into the module's `.csproj` on every Software Factory run (its default for a module project). Don't apply that change: the engine references no C# module (see "The engine ships its languages' parsers").
- The `Drift Check`'s `Packs` list isn't modelled: every installed pack runs. `unmodelled.interaction`, `.exposed` and `.value`, the `chain` and `markup` find steps, and locating a Minimal API router as its Service aren't built; the acceptance harness skips their cases with the reason.
