# Context: Intent.Common.Drift

## Purpose

The drift check that compares a designer's model with hand-written code, and the always-on rule and skills that go with it, shared by every module that contributes a designer. It knows no designer: Intent.Domain.Guardrails.Contracts and Intent.Services.Guardrails.Contracts each contribute one (`DriftDesigner`), and a later module (a UI Guardrails module, or any other) contributes the same way.

From 2.0 it is also how an application leaves that check: updating to 2.0 moves the application onto Intent.Common.DriftEngine (below, "Moving onto the drift engine").

## Architectural Decisions

- **Reports through Intent.Common.DriftReporting, not a report template per designer (user decision, 2026-11-10, plan "Drift reporting purely through modules"; supersedes the report template, `DriftReportRunner`, the per-designer `<Designer>DriftReport.mdx` and the one-error-per-designer failure below).** Each contributing module's drift reporter (a factory extension deriving from this module's `DesignerDriftReporter`, a `DriftReporterBase`) reports with `DriftCheckRunner.Report(context, designer)` after template execution, and the designer becomes the Area of the application's one drift report named `DriftDesigner.Name` (Domain, Services, UI), so the names guidance and the brownfield harness use stay. The hub logs one error for the run's drift (one warning when there are only warnings) and writes `.cache/drift/<application>/DriftReport.mdx`; this module no longer renders Markdown or logs failures.
  - **Mapping (`HubMapping`).** Contradicted, missing, undescribed and unverifiable-fact rows are Model / Code errors on the innermost row element `ReadElements` resolves (else the row's name, or its file), against the row's file and line (a missing type's expected file as text). A recipe problem, or the check failing, is a Code error on the recipe file; a kind with no recipe and a stale exception are Code warnings on it. Counts, the pending message and the changed-on-both-sides explanation are notes. "The check is off" stays a warning status line, not a finding.
  - **The `x != _template` filter went.** By `AfterTemplateExecution` every template has run, so every contract template's C# file is built; there is no report template to leave out. Baselines (`<Designer>.model.json`) stay in `.cache/guardrails/<application>/` and still aren't kept on CI (below); the runner deletes any `<Designer>DriftReport.mdx|md` an earlier version left there.
  - **Discovery is this module's own, not the hub's (user decision, 2026-11-10: the hub's contract is the base both drift approaches sit on, so it carries nothing one implementation needs).** `DesignerDriftReporter` records its designer at the start of the run, keyed by the run's event dispatcher, and `ModelSyncGuidance.Designers` reads that record, before any template is registered. The hub has no list of reporters. `IDriftDesignerSource` is gone: nothing discovers designers by interface any more.
  - **A CI/CD run is the CLI's `--param ensure-no-outstanding-changes=true`, and it breaks on drift in the hub (user decision, 2026-11-10; it replaced the `TF_BUILD` placeholder).** Intent.Common.DriftReporting writes no report then, and throws once every finding is logged when there is a drift error: that applies to every reporter, so it isn't this module's. `DriftCheckRunner` reads the same parameter only to skip keeping the baseline. `GetParameter` is SDK 3.16, newer than this module builds against, so both read it by reflection. The guidance names the one report (`DriftReports.RelativePath`) and each designer as an Area.

- **The drift check is its own module (user request and decisions, 2026-10-29, plan `Modules/intent/.plans/2026-10-29-extract-drift-engine-module.mdx`).** The Domain and Services Guardrails modules each carried a full copy of the engine, the guidance and near-copies of the report template and the ValidateDriftRecipes task, about 5,300 lines kept identical by a test; every change was made twice, and a third designer would have meant a third copy. This reverses the Domain module's "the engine is copied, not shared" decision, which rejected a shared module because it meant a third module and a new dependency for consumers: both costs are now accepted. The user's decisions:
  - **Id and folder:** `Intent.Common.Drift`, in `Modules/Intent.Modules.Common.Drift`, an application of the Guardrails solution.
  - **Consumer paths and names don't change:** `guardrails/<designer>.drift.json`, `.cache/guardrails/<application>/` with `<Designer>DriftReport.mdx` and `<Designer>.model.json`, the skill names, both task ids and the report template ids stay, because Domain and Services 1.0.0-pre.2 were published with them. The guidance text stays byte-identical, "Guardrails application" included; wording for reuse beyond Guardrails is a later, separate change.
  - **Only the drift check moves.** The other duplicated Guardrails code (`ContractAsync`, `ContractMemberModifiers`, `ContractTypeModifiers`, `ContractDefaultValues`, `IntentManagedContractMerge`) stays copied, for a separate follow-up.
  - **The code index stays C# only:** other files are read as text through `file:` finds and regular expression read cases. Intent.UI.Guardrails.Contracts (2026-11-01) reads Razor, TypeScript, HTML and JSX that way, with the engine additions below, so no second index (Razor, TypeScript) behind the `find` grammar was needed.
- **What is common and what each module supplies.** Core: the code index, the recipe engine and file format, the probe and wrong-element checks, ownership and exceptions, the structure comparer and `Modellable`, the baseline memory, report rendering, `DriftCheck.Run`, `RecipeValidation`, the report template's logic (`DriftReportRunner`), the module task's logic (`RecipeValidationTask`) and the five guidance templates. Each contributing module: its kinds of fact, its model reader (`DriftModel`), its contract templates, its text in the guidance (`DriftGuidance`), its technology guides and reverse-engineer skill, and a report template and module task that delegate to core with their ids unchanged.
- **The contribution contract.** `DriftDesigner(Name, DesignerId, Order, Kinds, ReadFacts, ReadElements, ValidateTaskId, Guidance)`.
  - **Discovered, not registered.** The guidance templates take every template instance of the run that implements `IDriftDesignerSource` (each module's drift report template does), one per designer name, ordered by `Order` (Domain 10, Services 20, so the text lists them as before). It is the find-the-template pattern (Wolverine's `FindTemplateInstance`), so there is no static registry to reset between runs. Discovery ignores `CanRunTemplate`: a report template turns itself off once its check finds nothing to report, and its designer still counts.
  - **Two readers, not one `ReadModel` (deviation from the plan's sketch, my call).** `ReadFacts` and `ReadElements` are the two `DriftModel` calls the report template already made; the module task reads only facts, so one combined reading would have made it read every element for nothing.
  - **`IDriftStructureSource : ICSharpFileBuilderTemplate`, naming its designer.** Each Guardrails module's contract marker interface (`IDomainContractTemplate`, `IServicesContractTemplate`) derives from it and implements `Designer` as a default interface member, so no contract template's file changed. The runner compares only the structure sources of its own designer.
  - **One contribution per designer.** A designer has one recipe file and one catalog; fact keys are already namespaced (`column.*`, `intent.*`), so merging two modules' kinds for one designer later is additive.
- **The report template takes the interface, so its signature is merged (my call, verified).** Module Builder generates a Markdown template's class with `[IntentManaged(Mode.Merge, Signature = Mode.Fully)]` and no `partial`, so `IDriftDesignerSource` can't be added in a sibling file the way the contract templates add their marker. Each module's `DriftReportTemplate` is marked `Signature = Mode.Merge`, as this repo's MediatR and ServiceImplementations templates are, and the Software Factory rerun kept the interface (it only added the template's own usings). Composition, not inheritance: the template holds a `DriftReportRunner`, takes its `ReportFile` as `MarkdownFile`, and answers `CanRunTemplate` from `CanRun`.
- **The guidance templates build their text in `AfterBuild`, and are written only once a designer is contributed.** Contributions are template lookups, which resolve only once every template is registered. `CanRunTemplate` is false with no contribution, so installing this module alone writes nothing (before the move, no Guardrails module meant no guidance either).
- **Each kind names its own element and describes its placeholders (plan step 4).** `FactKind` takes its placeholders as `FactPlaceholder(Name, Description)` and an explicit, required `Own` list (validated to be some of its placeholders), replacing the central `Describe` switch and the `OwnPlaceholders` name heuristic, which knew both designers' placeholder names. Each module's lists are set to what the heuristic chose, and `FactKindTests` pins them to it. The `Entity` and `Member` descriptions mention both designers' meanings and are repeated in both contributions, because the configure-drift-check skill used to describe a placeholder once for both and its text is kept as it was. The engine takes a designer's kinds as an input (`DriftCheckInput.Kinds`, `RecipeValidationInput.Kinds`, `RecipeFile.Parse(json, designer, kinds)`) instead of looking them up by name.
- **Public surface: only what a contributing module calls.** `DriftDesigner`, `DriftGuidance`, `IDriftDesignerSource`, `IDriftStructureSource`, `FactKind`, `FactPlaceholder`, `ModelFact`, `Modellable`, `DriftReportRunner` (with `ReportPath`) and `RecipeValidationTask`. The rest is internal, with `InternalsVisibleTo` for `Intent.Modules.Guardrails.Contracts.Tests`. `GeneratedFile` stays internal (the plan listed it as public): the runner builds them, and no module needs to.
- **`Modellable.MetadataKey` is `Drift.Modellable`, was `Guardrails.Modellable`.** It lives only in memory during one run, from the contract templates to the report template, and both sides use the constant.
- **Proof that the move changed nothing a consumer sees: golden renders captured before it.** `GoldenTests` renders the rule and the four skills for three installs (both designers, Domain only, Services only), each report template's report and log, and each task's JSON, against `Fixtures/Golden/`, which were captured on the pre-move code (and matched between two checkouts). After the move they match exactly; regenerate them with `GUARDRAILS_GOLDEN=update` only for an intended change. `FakeDesignerTests` contributes a third designer with one kind and runs it through the recipe parser, the check, the task and the guidance.
- **Package and dependency versions.** The csproj references `Intent.Modules.Common` 3.11.1, the lower of the two Guardrails modules' (Services 3.11.1, Domain 3.11.8): a higher one would fail the Services module's restore with NU1605 once it references this project. `Intent.Modules.Common.CSharp` 3.10.12-pre.2, SDK 3.14.0-pre.1 and compile-only Roslyn 4.14.0 match both. The `.imodspec` dependencies are hand-added to match (Intent.Common 3.11.1, Intent.Common.CSharp 3.10.12-pre.2) plus Intent.OutputManager.RoslynWeaver 5.0.3-pre.2, whose lib folder supplies Roslyn at run time; the module has no C# template, so the Software Factory doesn't add it. `supportedClientVersions` was `[5.1.0-a,6.0.0)` until 2.0 (the SDK needs 5.0 and RoslynWeaver 5.1); 2.0 raised it to `[5.4.2-a,6.0.0)`, Intent.Common.DriftEngine's floor, which its migration's persistence needs too (below).

- **Reading UI code (plan `2026-11-01-ui-guardrails-module`, built 2026-11-01, version 1.0.0-pre.1 because 1.0.0-pre.0 was published).** Four generic additions, each tested in `ComponentFilesTests`:
  - **The files of one component are one place (plan).** `AsOneUnit` also accepts whole-file hits in one folder whose names are the same up to the first dot (`Checkout.razor`, `.razor.cs` and `.razor.css`; `customer-list.component.ts`, `.html` and `.scss`). Before, two such files were "matches 2 places; narrow the find", the same as two unrelated types. Accepted (plan): the rule applies to every designer's recipes, but only turns what was an ambiguous find into a reading, and no Domain or Services guide finds files that way; their goldens changed only in configure-drift-check's find-path and filter text.
  - **A `kebab` filter (plan).** `{Component|kebab}` gives `customer-add-page`, worded as Intent's own `ToKebabCase` (Humanizer's `Kebaberize`): `HTMLParser` is `html-parser`, a digit stays with the word before it.
  - **A `replace:<text>:<with>` filter (my call, beyond the plan).** Angular navigates with segment arrays (`navigate(['/customer', 'edit', id])`), which no route-text match can read; `{RouteStart|replace:/:','}` writes a route as one. Rejected: a URL-specific `segments` filter (technology knowledge in the engine) and marking array navigation `unreadable` (every Angular navigation would be can't-be-verified). A `replace` without `:<with>` is a recipe error.
  - **Interpolated strings read as written (fix, found by the Blazor guide's tests).** The canonical text put a space after an interpolated string's `$"`, because `NeedsSpace` treats `"` as a word end: `NavigateTo($"customer/edit/{id}")` read `$" customer/edit/{id}"`, contradicting "string contents verbatim". `CodeText.Of` now joins an interpolated string's start, text and end tokens with no space. No existing test or golden changed.
- **A designer with no generated types contributes only facts.** The User Interface designer has no structure sources: its report has fact rows and `own` rows only, as `FakeDesignerTests` proved before it existed.

## Moving onto the drift engine (2.0.0-pre.0, 2026-11-23)

Plan `intent/.plans/2026-11-23-common-drift-migrates-to-drift-engine.mdx` (user request: updating this module is the whole move). Rejected: the manual procedure used on the New Engine copies (uninstall the Guardrails modules, strip their stereotypes, back up and restore every contract file).

- **2.0 is major, and depends on Intent.Common.DriftEngine 1.0.0-pre.0.** It changes how the drift check is used: recipes and contract generation give way to the engine. Updating installs the new dependency before Common.Drift's migrations run, so DriftEngine's stereotypes exist when the migration writes rows on them. Releasing 2.0 needs DriftEngine 1.0.0-pre.0 published first.
- **One move, three entry points (`DriftEngineMigration.Run`).**
  - The 2.0.0-pre.0 Version Migration.
  - An On-Install Migration, for Guardrails 1.0.0 applications: those carried their own engine and don't depend on this module, so they have nothing to update. On-Install migrations don't run on updates, so the move never runs twice.
  - The Migrate to Drift Engine module task, for recovery.

  Every step looks before it acts, so a second run changes nothing. Only packages with this application's id are touched, because `GetPackages()` also returns packages other applications own (shared Eventing packages), which may still be on v1.
- **Files before the model.** The order is: release the contract files and prune the output records, save the model changes together, then delete the recipes and baselines. If the save fails, the Guardrails modules are still installed; their next run merges the attributes back and logs the files again, so nothing is deleted. In the opposite order, the modules would be gone with the records unpruned, and the next run would delete every contract file. Verified on eShop10 with a read-only contract file: 74 files were stripped before the failure, and the next run restored them byte for byte and deleted nothing.
- **A failure is logged, not thrown, and the task recovers it.** Intent doesn't run a migration again: `modules.config` is already at 2.0, and updating to the same version runs none. So `Move` logs one failure naming the cause, the task's id and its argument. A migration's constructor takes only injected services, because one that throws stops every migration in the application. `Down()` only warns: going back means reinstalling the Guardrails modules and restoring the recipe files.
- **The task tells the developer to reopen the solution (SDK limitation).** After migrations, Intent reloads the application from disk and rebuilds module settings. After a module task it doesn't, and a task has no way to ask it to. On eShop10, the Software Factory kept loading the removed Guardrails modules, and failed on their missing Template Outputs, until the application was reloaded (a module reinstall did it). So `Run` returns whether it moved anything, and the task adds the reopen line when it did.
- **v1's code stays in 2.0, and the module stays installed.** Published Guardrails modules still install beside 2.0 and compile against `DesignerDriftReporter`, `IDriftStructureSource`, `FactKind`, `Modellable` and `RecipeValidationTask`. A failed move leaves v1 working. The migration reads recipes as v1 did: `RecipeEngine.JsonOptions` (made public for it, the comment-skipping options `RecipeFile.Parse` uses), `Glob` and `LooksLikeGlob`. A later major version removes the v1 code. After the move the module carries the per-machine pruning and the task; the README says to uninstall it once every machine has run the Software Factory.
- **Recipes become rows (`RecipeConversion`: pure, and tested on the five codebases' real recipe files read in place).**
  - **Scope is one `**` In row (user decision, 2026-11-23, replacing the plan's In rows from top-level `files`).** v1 checked code wherever its recipes' finds reached, and only two of the five codebases have top-level `files`, so In rows from `files` alone would have left most checked code out of scope. File-pattern exceptions (`Glob.LooksLikeGlob`) become Out rows, grouped by reason. Accepted: `**` also brings in code v1 never read, which the first run reports and the developer narrows with Out rows.
  - **The member row covers `**/*.cs`.** One `optin/unmodelled.member` row stands for v1's always-on report of unmodelled public members of modelled types, and is written only when there is a Domain or Services recipe. Over `**` it reported UI components' members, which v1 never did.
  - **Conventions are globs (DriftEngine's decision, 2026-11-16).** Each `own` entry becomes an `optin/unmodelled.type` row over its `files`, else its recipe's, else `**/*.cs`, with its `kind` as the Description. Rows with the same rule and globs merge. The find and its regular expression are dropped, so a convention reports every unmodelled type in its glob (accepted in the plan).
  - **Exceptions.**
    - A type name becomes an `unmodelled.type` Exceptions row, and a `Type.Member` an `unmodelled.member` row. There is one row per rule and reason, compared ordinally (CrmBus has two reasons that differ only in case). A missing reason becomes "From guardrails/x, which gives no reason".
    - Any other exception names a convention's finding (eShop10's `CatalogApi: MapGet [catalogtypes]`). The `own` entry whose name template it matches gets no row, and a note is logged. Rejected: carrying these over as exceptions, which no engine rule would match.
  - **What v1 didn't report gets exceptions (`V1Coverage`; user decision, 2026-11-24, "Except what v1 skipped", replacing the plan's accepted "a convention reports every unmodelled type in its glob").** basislink5, clean on v1, had 188 findings after the move; 52 were the wider rows (every unmodelled type under v1's recipe `files`, and `MainBidRequestDTO`'s public fields). The migration runs each `own` entry's find with v1's own `RecipeEngine` over v1's `CodeFiles`, before the contract files are released, and writes, one row per reason: an unmodelled type in a type row's files that no find matched (the reason names every row's conventions covering its file); one a find matched in a contract file, which v1's ownership counted as modelled (`ValidKCRoleAttribute`); and a modelled type's unmodelled public field, for element types whose conventions state fields. A type a find matched elsewhere stays reported, as v1 reported it, so the move doesn't hide v1's own outstanding findings. Found is by type name, as an exception matches: a partial type's other file (`BasislinkContextExt.cs`) is the same type. "Modelled" copies `DriftEngine.TypeExists` and `LocateCode`: an element's name; for a Service, Service Proxy, Repository or Domain Service with no type of its name, `I{Name}` and the classes implementing it; and every located class's interfaces, its base classes' included (`IBlobStorage` for the modelled `AzureBlobStorage`). Getting it wrong costs a stale-exception warning or a leftover finding, which the basislink5 rerun checks. Only C# is read. A find that fails (a regex timeout) gives its rows no exceptions and a note. Exceptions a converted recipe exception already names are left out, since the engine matches the last row and the other would be stale. Rejected: per-file globs from the finds' matches (a type later added beside a controller wouldn't be caught, and unmatched types in matched files would still be reported); writing no convention rows (loses v1's coverage); a type-shape filter on opt-in rows (conventions are globs, user decision 2026-11-16).
  - **What v1 didn't report, widened by CrmBus.Api (2026-11-24).** Its move showed more kinds of thing v1 never reported, which the engine does, so `V1Coverage` excepts them too, each with its own reason. A type nested in another gets none: the engine never reports it on its own. A first cut excepted nested types, after CrmBus's handler's nested `QuoteTypes` was reported, but that was an engine bug (a partial type's other part didn't enclose it), and the rerun warned on five exceptions that matched nothing (private response classes inside handlers).
    - A further declaration of a modelled type's name in the type rows' files (`CopyReason`): v1 counted it as modelled by name, while the engine locates one type per element. CrmBus's API project has a second `FtpHeartBeatPingRequest`. Only declarations in covered files are counted, so an exception is never written for a copy no row reports.
    - A public method of an Integration Event or Domain Event Handler (`HandlerMethodReason`): v1's handler contract stated its modifiers only (`methods: false`), while the engine's handler conventions state methods. The method taking a modelled message is the subscription's, which the engine locates, and overrides aren't reported, so neither is excepted. CrmBus's `DeriveProduct`.
    - **Converted exceptions that would match nothing are left out (`DriftEngineMigration.DropUnmatched`).** v1's exceptions naming a modelled type covered its own conventions' findings (CrmBus's `Container`, a restated relationship; `JustApplicant`, a generation filter). The engine never reports a modelled type declared once as unmodelled (`V1Coverage.NeverUnmodelled`), so each row would have warned on the first run. Each one left out is logged with v1's reason.
  - **Conventional Table Names are cleared (`ConventionalTableNames`; user decision, 2026-11-24).** v1's basislink recipe read a table's name from its `DbSet` property, so three Classes stated `Application_Basislink_Document_Docs`-style names with no `ToTable`, which the engine contradicts (user decision, 2026-11-14). The migration clears a Class's Table Name (its Name only; Schema and the stereotype stay) when no `ToTable`, `ToView` or `[Table]` is attributed to the entity and the name is a `DbSet<Entity>` property's or the class's. A table call is attributed by `Entity<T>()` in its receiver chain, an enclosing `Entity<T>(e => …)`, an `EntityTypeBuilder<T>` parameter or an `IEntityTypeConfiguration<T>` class; one it can't attribute clears nothing, with a note. Any other name stays and is reported. Rejected: the engine reading the `DbSet` name (reverses the 2026-11-14 rule).
  - **A v1 model's own form needed engine changes, not model edits.** The other 133 basislink5 findings were the model stating what v1's contract needed: `IActionResult` return types (127) and a 200 for actions returning their data (6). The engine now verifies both (Intent.Common.DriftEngine's CONTEXT.md), since the migration can't read method bodies to restate them.
  - **Globs** are written as v1's `Glob` normalises them. Braces become one line per alternative, because the engine's matcher (File Classification's) takes none. Anything else it can't take is written as it is, so the first run reports `config/glob` instead of the move quietly changing its meaning. A recipe file that is only comments counts as `{}`, and one that won't parse is a note.
  - **Rows are written only where the engine isn't set up.** A Drift Scope or Drift Check anywhere in this application's Codebase Structure skips them, with a log line. They go on the first Codebase Structure package the application owns.
- **The contract files are kept as code (`ContractRelease`, `OutputLogPruning`; user decision: forget the templates' files and strip the Intent attributes, rather than let the Software Factory delete them).**
  - **Which files.** They are the entries of the 18 contract templates (the template id before `#` in the correlation id) in `.intent/output-log.xml` and the legacy `<App>.application.output.log`, plus every `.cs` file whose header has `[assembly: IntentTemplate("<contract id>"`. The header scan exists because basislink5's log lacked its contract entries. It skips build, VCS and Intent folders and other applications' output folders, and it is skipped altogether when another application writes to the same output folder, because there its contract files can't be told apart. `GeneratedFilesProvider` isn't used: it reads only the machine log, and throws on an entry with no correlation id.
  - **Stripping.** Roslyn locates the attributes and whole lines are removed, so formatting, encoding (BOM) and line endings are kept. A file is written only if it changed. A read-only file throws, which fails the run in a way the task can recover. The attribute names are RoslynWeaver.Attributes 3.0.0's, and unqualified names count only where the file has the `using`.
  - **Records.** Only contract entries are removed (user decision), so the next run proposes deleting the old AI files, which would otherwise keep pointing agents at recipe files. `output.config.xml` entries are matched by path. `managed-files.xml`, the committed inventory Changes Review reads, is pruned too, by template id (2026-11-24): the Software Factory rebuilds it from each run's outputs, and on a teammate's machine the stand-ins below are outputs listed under the contract template ids. Each record keeps its newline style, declaration, trailing whitespace and BOM.
- **Teammates: stand-ins keep the files, pruning ends them (user decisions: prune per machine, 2026-11-23; stand-in templates, 2026-11-24).**
  - **Why module code can't simply prune first.** Intent reads `.intent/output-log.xml` when it builds the run, before Start, and works out deletes from that copy. `SaveEntriesForExistingFiles` then writes the copy back before After Template Execution, so an edit to the file at Start or Metadata Load changes nothing.
  - **Stand-ins.** `ReleasedContractFileRegistration` registers a `ReleasedContractFileTemplate` for each contract file the machine's logs still list and that is on disk. It goes into the output target the log recorded, or else the innermost one holding the file, under the entry's own correlation id. The Software Factory then counts the file as generated this run: `GetFilesNoLongerBeingGenerated` matches by correlation id or path, so it proposes no delete.
  - **Hand-written registration, not a Module Builder template.** A template declared in the `.imodspec` with a role gets a Template Output in the consumer's Codebase Structure on install. The explicit-target `RegisterTemplate` overload needs none, and an undeclared template id gets an enabled default config.
  - **Overwrite disabled, not once-off.** Both lock the change to the file on disk, so nothing is written. Once-off also records `once-off-generated` in the committed `output.config.xml`, and Intent reads every entry there back as ignored. On a teammate's first run, once-off created that file where the application had none.
  - **Pruning.** `GuardrailsOutputLogPruner` removes the contract entries from the records at After Template Execution, and again at After Commit Changes, because the Software Factory writes the log and the inventory from memory before each. Once the log is pruned, no stand-in registers. Both run only when no Guardrails module is installed; the pruner also deletes `.cache/guardrails/<app>/`.
  - **An apply through an agent** writes the log and `managed-files.xml` back from memory, with no hook after it. The next run registers the stand-ins again, so it still proposes no delete, and prunes both again. Until then, that machine's `managed-files.xml` lists the contract files.
  - **Rejected.** A platform hook to forget a file before deletes are worked out, which would need an Intent release and a higher client minimum. A committed ignore list, which shows the ignored deletes on every machine on every run.
  - **Verified** 2026-11-24 on the CrmBus copy with a teammate's unpruned log (36 contract entries). Run 1 proposed no contract delete and changed no committed file. Run 2 was clean. After an agent apply, the entries were back in the log and `managed-files.xml`; run 3 still proposed no contract delete and restored both. Without the stand-ins, run 1 proposed the 36 deletes, and so did every run after an agent apply.
- **The uninstall is the migration's own (`GuardrailsModelCleanup`).** A migration has no access to Intent's module installer.
  - **Order.** It deletes the subscription links first. Then it strips the stereotypes defined by a Guardrails module, on packages, elements, associations and association ends. Last, it removes the modules: their designer settings references (Guardrails Eventing Extension's included), package references, Template Outputs and module entries. A Template Output is a Guardrails one when its external reference is a Guardrails module id or its name starts with `<moduleId>.`.
  - **Why links first.** Without the Services module's association types, the Eventing packages holding the links fail to load and the Services designer can't save, which is the failure eShop10 hit.
  - **No `ModuleUninstalledEvent` is published.** Intent's save after migrations reloads the designers; every designer loaded and the Services designer saved on the CrmBus and eShop10 copies.
  - **API limitations it works around.** `RemoveReference` saves the package and publishes at once, so references are removed from the list instead. `RemoveTemplateOutputs` cleans only a designer's first package and throws on a designer without outputs, so the outputs are deleted from every owned package by hand.
- **Persistence is V1's `ApplicationPersistable` (`Intent.Architect.Persistence` 3.7.4).**
  - **Why V1.** The V2 SDK (`IPersistenceLoader`) can't write item-list rows or reach associations stored inside elements. 3.7.4 is the first package with `ItemList`. The client's own assembly loads at run time, so the client minimum is what counts.
  - **Reflection.** `GetAllAssociations` and `RemoveAssociation` exist only in the client's persistence (5.3+), so they are called by reflection.
  - **Fresh reads.** The task host caches what it reads, so `XmlSerializationHelper.ClearCache()` runs first. It throws when caching was never switched on, which is caught.
  - **Labels.** Item-list labels are serialised with relaxed JSON escaping, as the designer writes them.

- **Drift check: every Software Factory run compares the model with the code (user decisions, plan `2026-10-20-drift-check-compares-model-with-code`, built 2026-10-20).** The Basislink authority audit compared 1,588 facts and found 6 where the model and the code disagreed (two routes, three text types, one column type). The module-task check reported `No drift` for all 6, because it only compared each side with fingerprints taken at the last save, and the adoption's first save had accepted them. Its other findings: false alarms on things that agree (F-4, F-8), wrong labels (O-1, O-3), and blind spots for signatures and removed members (F-2, F-3). The design keeps the old one's generic idea, that the AI understands the technology once and the check is deterministic, but the AI now records how to read each kind of fact, not where each fact is, and there is no baseline and no save.
  - **Shape.** A `DriftReport` File Template (Markdown File Builder, Single File, no model, role `Default`) in each contributing module is where the check runs, through `DriftReportRunner`, and outputs the report into the solution's `.cache` folder (see "Reports in the solution's `.cache` folder" below). Every Wrong line is also one `Log.Failure`, so the run fails, and so does the CLI on CI. An exception inside the check is caught, logged as a failure, and written into the report, so the rest of the run still generates (though, being a failure, its changes then aren't applied by themselves).
  - **`Log.Failure`, not a thrown `FriendlyException` (user asked for one; rejected with evidence, 2026-10-20).** A `FriendlyException` thrown from a build callback is wrapped in a plain `Exception` by `FileBuilderHelper.PerformConfiguration` (Intent.Modules.Common; only `ElementException` passes through unwrapped), so it shows as a stack trace. Even unwrapped (re-checked in the Intent Architect source, 2026-10-21), `TaskTracker.StartTask` publishes the friendly message but rethrows it as a `HandledException`: its `_throwExceptions` is always true, since nothing calls `DoNotThrowExceptions()`. `SoftwareFactoryExecutionEnvironment.StartAsync` then ends the run before staging and sends Intent a problem report for any exception, `ElementException` included. Nothing would be staged, so a model-first change's output could never land and its drift could never clear. Instead the failure is logged, not thrown. **Logged as friendly and element errors (user, 2026-10-21):** the user had Intent Architect changed so that `Log.Failure(Exception)` publishes a `FriendlyErrorMessage` for a `FriendlyException` and an `ElementErrorMessage` for an `ElementException`, without ending the run (handover `handover-log-failure-friendly-exceptions.md`). **One error, an element error when it can be (user decision, 2026-10-22, replacing a friendly error plus up to five element errors):** `LogFailures` logs exactly one failure, `FailureMessage`: "The Domain model and the code have drifted: N drifts detected and listed in the drift report (path)", plain text, the path with forward slashes because the card's Markdown ate a backslash path's underscore. It is an `ElementException` on the first row's innermost model element that `DriftModel.ElementsById` resolves (`DriftReport.FailureElementIds`, in the report's order, so a contradiction's element first), because Intent offers **Try fix with AI** on an element error: a developer who ran the Software Factory by hand gets a clear call to action that hands the whole report to the AI. With no resolvable element it is a `FriendlyException` with the same message. On CI no report is written, so it is a `FriendlyException` listing the lines. **Rejected (the earlier design):** a friendly error naming the report plus an element error per row when no more than five rows had an element; it gave no single AI entry point, and per-row errors invited fixing rows one by one. On a client without that change each shows as a plain error prefixed with the exception type; the exceptions are never thrown, so there's no stack trace. `supportedClientVersions` isn't raised until the release that has the change is known.
  - **Off until the recipe file exists (user decision, 2026-10-20, after the first Basislink install; supersedes the plan's "a missing recipe file is one Wrong line").** A `Log.Failure` stops Intent applying the run: the client unticks every staged change when a run has errors (`SoftwareFactoryRunHost.ts`, `performChange = false`), and the AI's `run_software_factory` only auto-applies a run without errors (`RunSoftwareFactoryTool.cs`). The first run after installing failed (the missing recipe file, plus 26 structure lines in Services), so the configure-drift-check skill that run generated was never applied: the check blocked its own set-up. Now `BuildAndCheck` looks for `guardrails/<designer>.drift.json` first; without it, nothing is read or rendered, the report says the check is off and how to set it up, and the run gets one `Log.Warning`, which doesn't untick anything. `DriftCheck.Run` treats a null recipe the same way (`DriftReport.Off`). The structure check is off too, as the user asked ("not do checks"): it is part of the same opt-in. Writing the file, even as `{}`, turns everything on.
  - **After-build, not OnBuild (deviation from the plan, my decision).** The plan said `MarkdownFile.OnBuild(…, int.MaxValue)`. `CSharpFile.ToString()` throws until `FileBuilderHelper` marks the whole build step done, so the contract templates' output can't be read during it. The check is registered with `AfterBuild(…, int.MaxValue)` instead. `FileBuilderFactoryExtension` runs the build step at After Template Registrations and the after-build step at Before Template Execution, both before the Software Factory calls each template's `CanRunTemplate()` to run it (read in `D:\Dev\Intent`'s `SoftwareFactoryProcessOrchestrator.ExecuteTemplates`).

  - **The fact catalogue (each contributing module's kinds: `DomainDrift`, `ServicesDrift`; `Drift/FactKinds.cs` until 2026-10-29)** is the list of facts each designer states: key, report label, placeholders, model values and source. The engine validates recipes against it, each designer's reader uses it, and the configure-drift-check skill's fact tables are generated from it, so the skill can't drift from the code. Each module carries only its own designer's facts; until 2026-10-29 both modules carried both designers' facts, because whichever module wrote the skill documented both.
  - **Recipe engine (`Engine/RecipeEngine.cs`), no technology knowledge.** `guardrails/<designer>.drift.json` beside the `.application.config`; JSON with `//` comments allowed. Per fact kind: `find` (a path, or alternatives tried in order), `read` cases (first match wins; `value`, `case`, `part`, `in`), `default`, `absent`, `inherit`, `replace`, `case`, `files`; plus `own` and `exceptions`. Decisions taken while building it:
    - **Code is read as canonical text:** tokens joined with no whitespace except one space between two words, comments and disabled code dropped, string contents verbatim. Regular expressions then don't depend on layout. Anchors (`statement:…`, `chain:…`) are tokenised with Roslyn's lexer and joined the same way, so `Property(e => e.Name)` matches however it is laid out. Non-C# files collapse whitespace the same way.
    - **Find steps:** `class`, `method`, `property`, `parameter` by name; `statement` and `chain` by contained text; `file` by pattern; any kind `with <regex>`; or a bare kind. Text and regex steps return the smallest node of the kind around each match; `chain` returns the whole fluent call chain. A fact's find must end at one node, or the parts of one partial type; several is unverifiable. Overloads of a Service operation are chosen by the model's parameter names (model knowledge, not technology).
    - **`part` (declaration or body) and `in` (an enclosing kind) were added beyond the plan.** Without `part`, `inherit: class` would find a method's `[Authorize]` inside the class's text; without `in`, a parameter's binding couldn't be inferred from its method's route template (the plan's tests require inferred binding).
    - **`absent` was added beyond the plan:** the value when find finds no code. Code states some facts by saying nothing (an unconfigured string column is `DEFAULT` with no max length); without it every unconfigured column would be unverifiable. `default` stays the value when the code is found and no case matches. Both are used as written; only read values pass through `replace` and `case`.
    - **Placeholders with filters** (`{Service|trimEnd:Controller}`, `lower`, `upper`, `camel`, `pascal`, `trimStart`): ASP.NET's `[controller]` token can't be compared without them. Inside a regular expression a placeholder is escaped; `\{` is never one. An unknown placeholder is a recipe error.
    - **Every problem is collected, never thrown:** invalid JSON, an unknown fact key or property (typos), a bad find path, regex or placeholder are each a Wrong line, and a broken recipe's facts aren't then reported one by one. A fact kind with no recipe is one line with its count. A missing recipe file turns the check off (above).
    - **Ownership:** code an `own` entry finds is modelled when some fact's find located it, or code inside it, or (since 2026-10-21) it is a generated type or a type in a file a template writes. Exceptions are a file pattern (a `/`, `*`, `?` or `.cs`), a type, a `Type.Member` or an ownership name, optionally `{ "match", "reason" }`, and cover only unmodelled code. A type or `Type.Member` covers only declarations, never code a convention finds inside a member (since the re-test fixes, C8b). The report lists each with its count; one that matches nothing is a warning (since 2026-10-21; it was an informational list of every exception and its count).
  - **Structure (`Engine/StructureComparer.cs`).** Each runnable contract template (an `IDriftStructureSource` of the designer, such as `IDomainContractTemplate`; file-group owners only) is rendered with `CSharpFile.ToString()`, parsed with Roslyn and compared with its file on disk (`GetMetadata().GetFilePath()`): kind, type modifiers, type parameters, a record's or primary constructor's parameters, base types (the model's must all be there; extra code bases are fine, as Merge keeps them), and members by name and, for methods and constructors, parameter types. Method modifiers are compared except `partial`; property modifiers except `virtual` and `partial`, which Merge doesn't change. Type spellings are compared by meaning (`TypeKey`: `Nullable<T>` is `T?`, `Int32` is `int`, a qualified name is its last part). An unmodelled method, property or constructor is reported only when it is public (since 2026-10-28, see below); constructors count only in a type with a modelled constructor; enum literals always. An unmodelled member found by both an `own` entry and the structure check is reported once.

## Invariants & Constraints

- **The project lives in `Modules/Intent.Modules.NET.sln`, like its siblings.** The Codebase Structure's Visual Studio Solution element is named `Intent.Modules.NET`, as in both Guardrails applications. Creation named it after the Intent solution (`Intent.Modules.NET.Contract.Guardrails`), so every Software Factory run staged a new `Modules/Intent.Modules.NET.Contract.Guardrails.sln`; renamed on 2026-10-29 (user correction), after which the run stages nothing for the solution file.
- **Exactly one copy of this assembly, and of Intent.Common.DriftReporting's, loads.** This module and each contributing module reference the hub as the `Intent.Modules.Common.DriftReporting` NuGet package (its dll isn't in their `.imod`s) and declare `<dependency id="Intent.Common.DriftReporting" …/>`; the installed hub module supplies the one runtime copy, and a second copy would make the run's event dispatcher's cast throw. For this module's own assembly: A contributing module references this project with `Private="false"` (compiled against, never copied to its output) and declares `<dependency id="Intent.Common.Drift" …/>` in its `.imodspec`; the installed drift module supplies the DLL. If a contributing module's `.imod` carried its own copy, the loader would bind whichever loaded first, its reporters would record their designers in the other copy, and the guidance would list no designer. `Intent.Modules.Application.Wolverine.csproj` records the same trap. Checked on 2026-10-29: each `.imod`'s `lib` holds only its own DLL.
- **Guidance text is edited with a plain-text editor.** Intent's `write_file` / `patch_file` re-indent raw strings. A raw string's line breaks are the source file's, so a file saved with LF and one with CRLF render differently until git normalises them; the golden tests compare with line breaks normalised.
- **The recipe format, the fact keys and their vocabulary are a contract with consumers' committed recipe files** (see the Domain module's Invariants), and so are the consumer paths above.
