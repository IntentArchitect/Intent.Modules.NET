# Context: Intent.Common.DriftEngine

## Purpose

The drift engine that converges Intent.Common.Drift and the custom drift modules built per adoption (eShopCustom, the Java spike) (plan: `docs/plan.md`; specification: `docs/spec/`). It is the shared foundation those modules kept rebuilding: scope, code readers, turning the model into claims, the verified, contradicted or can't-verify policy, and reporting. Modules extend it through code with no ceiling; recipes are a shortcut for simple claims. Phase 1 delivers the C# reader, the structure checks (Domain and Services packs), scope and the extension API; the Java reader, with JPA and Spring MVC, was built ahead of phase 4 to prove the engine is language-agnostic.

## Architectural Decisions

- **A module states what to check in C#, not only how to read the code (user decision, 2026-11-13: "this is literally the whole point").** An extension's `ClaimSources` (`IClaimSource`) return `ClaimSpec`s: the element, the kind, the value the model states, anything the source worked out for its reader (`Value`, such as the module's own model of the element), the claim it waits on (any element, any designer), and where the model states it. Its `Kinds` define kinds in code, and its `Designers` name the designers it reads (a module's own designer the engine doesn't know). A source reads the model through the engine (`ModelContext`, below), or with the module's own generated API (`DriftEngineExtensionBase.Application` gives the run's application). A pack's vocabulary is the same thing as data, a shortcut; a source's claim with a pack claim's designer, element and kind replaces it. An existence claim's reader can locate anything (`ClaimReading.Found(object, Span)`) and the claims waiting on it get it (`ClaimContext.Located<T>`). Why: the JSON expression language was the only way to say what the model states, so a module whose model reading it couldn't express was stuck. A check is never trimmed to fit the engine; one that doesn't fit is an engine gap to fix. Proved with eShopCustom's Domain Event Origin links and its Services sends and publishes.
- **The engine reads no language itself; a language is an extension (user decision, 2026-11-13).** An `ILanguage` reads its in-scope files into the graph's files, types and members, and keeps its own syntax on the graph for the extensions that read that language. The stock C# language (`Stacks/CSharp`, extension `csharp`) parses each file once with Roslyn and shares the trees as `CSharpSyntax`; EF Core, ASP.NET Core and modules' own readers all read that one parse. Its profile (type names, collections, type kinds) is its own pack, `csharp`. Code is compared under its own language's profile (C3, 2026-11-14): a type or member by its file's language, a type reference by the language its reader stamps on it (`TypeRefNode.Language`), and a type is looked for under the name each language gives it. The language that read the most files is only the fallback, for what no code says the language of (a refiner's own type reference). Why: the Java eShop's Java and TypeScript are one application, and under one profile the language with fewer files reads as drift (`Engine/MixedLanguageTests`). The Core has no Roslyn reference. Java is another language extension (`Stacks/Java`, extension `intent.java`) with its own parser and profile, `java`. How a language names and wraps the model's members is its profile's too, never the core's (2026-11-13): `naming` gives a pattern per kind of code (`{Name|camel}` for a Java field or method; C#'s `interface` is `I{Name}`, used when the conventions allow only an interface, which is how the Domain Repository finds `IOrderRepository`), and `async` lists the wrappers `operation.returns` unwraps (C#'s `Task<T>`, with `Task` as void). A kind with no pattern is named as modelled. `Engine/LanguageProfileTests` proves it with a made-up language. The type comparer compares type arguments only when the model states them.
- **Java is read with ANTLR, a pure .NET parser (user decision, 2026-11-13).** Its generated C# lexer and parser are checked in, so running it needs no Java; only regenerating the grammar does. Rejected: JavaParser through a Java process (a JDK wherever the Software Factory runs) or IKVM (unproven), though JavaParser's typed tree and type solver are friendlier to an AI. Why the AST matters less than it seems: only the Java language reader touches it, written once, while the house rules an agent writes read the engine's neutral reading, and Java frameworks state almost everything in annotations, which the reading carries. Working out which method a call reaches, JavaParser's real advantage, belongs in the engine for every language, since C# needs it too. The rule audit behind this is `docs/rule-audit.md`. The spike (`D:\Dev\Temp\JavaAntlrSpike`) parsed all 58 files of the Java eShop's backend with no errors: grammars-v4's `java/java` (pinned at `85e2dd1779`, Java 24), runtime `Antlr4.Runtime.Standard` 4.13.1, the newest on NuGet, so the tool jar must be 4.13.1 too. The grammar must carry one patch: upstream `classType` repeats a name with no dot between, so `x instanceof String s` silently parses `String s` as a type, and most files fall back to the slow full parse. The patch keeps one leading name and then only dotted ones; with it there are no fallbacks and parsing is 4 to 6 times faster. Not `java/java20`, a copy of the official grammar that the grammars-v4 README says is slower and stops at Java 20. `GetText()` drops whitespace, so the reader slices source text from token positions.
- **TypeScript is read with TypeScript's own parser, on Intent Architect's own Node.js (2026-11-14).** `typescript.js` 6.0.2, the last JavaScript release (TypeScript 7 is native Go), comes from the `Microsoft.TypeScript.MSBuild` NuGet package (`tools/tsc`, referenced with `ExcludeAssets="all"` only to embed the file) and is embedded in the Stacks assembly with the worker (`TypeScript/Worker/ts-reader.js`), written to `%TEMP%/intent-drift-engine/typescript-<hash>/` and checked there on every run (`TypeScriptWorkerTests`): the Software Factory's process stays alive between runs (Intent Architect re-runs in it as an optimisation, user, 2026-11-14), and a temp folder cleaned in between failed every later run until a restart. Checking costs two file lookups a run, so a reset on the re-run hook isn't needed. One Node.js process parses every in-scope file of a run, syntax only (`ts.createSourceFile`, no program or type checker), and returns each tree as JSON by TypeScript's own kind and property names, which `TypeScriptSyntax` keeps for any extension that reads TypeScript. In a Software Factory run it is Intent's `INodeJsProcessManager` (Intent Architect is Electron, and its own TypeScript weaver runs the same way), so the machine needs no Node.js; tests use the machine's `node` (`INodeRunner`). Intent's Node.js is Electron run as Node.js, which differs in three ways the worker handles, all found only by a planted `.ts` file in a real Software Factory run (tests use real `node`): it passes `<exe> <script> --node <script> <arguments>`, so the worker takes its request and response as the last two arguments (`IntentLikeNode` in `TypeScriptFactsTests` guards it); the process doesn't end when the script does, so the worker calls `process.exit`, or the runner waits out its 5-minute timeout; and what the worker writes to its error output doesn't reach `OnError`, so it writes a failure into the response file. Rejected on measurements over the Java eShop's 32 front-end files: grammars-v4's ANTLR TypeScript grammar (29 s, and it fails on ordinary TypeScript) and Jint hosting `typescript.js` in-process (1.8 s to load, then 30–90 ms a file). The worker takes about 0.8 s, Node.js start-up included. `typescript.js` is Apache-2.0 and keeps its licence header. Representation: a file is a namespace named by its path without its extension; what it declares outside its types is a `module` type named for the file with its extension (`client.ts`), so module functions are methods a call can reach like any other; a `const` holding an object literal is an `object` type; a `.vue` file is a `component` type whose script members, props (`property`) and emits (`event`) are its members. JavaScript files aren't read: no rule needs them yet. Nullability follows the nearest `tsconfig.json`'s `strict` or `strictNullChecks`, else `unknown`, as Java's unannotated references.
- **A Razor component is the C# the Razor compiler generates for it, read by the C# language (`Stacks/CSharp/RazorFile.cs`, E3, 2026-11-14).** `Microsoft.AspNetCore.Razor.Language` 6.0.36 from NuGet (the last release there; one assembly, no dependencies) generates each `.razor` file's C# with its `_Imports.razor` files, and Roslyn parses it, so a component is what the compiler sees: one `component` type with its code-behind (Razor components are read before `.cs` files, so the `.razor` part makes the type), in its `@namespace` or its project's `RootNamespace` (now read from the `.csproj`) and folders. Placement follows the generated code's `#line`; what a directive generates without one (`@page`'s `[Route]`, `@layout`'s `[Layout]`, `@inject`'s property) is placed at the directive, which a pass at the start of Razor's pipeline (`Capture`) records, since Razor's syntax tree is internal. Only what the file writes is read: `@code` and `@inject` members, never `BuildRenderTree`; its own `@using`s are its imports, and `_Imports.razor`'s are that file's, which the component has imports from (`FileNode.ImportsFrom`, so an import rule reports one `_Imports.razor` line once, not once per component). A Razor diagnostic doesn't fail the file, as C# syntax errors don't. Its markup isn't read from the generated code: without the referenced assemblies' components the compiler leaves a directive attribute such as `@onclick="() => Save()"` as HTML text, so markup is read from Razor's own parse (E4, below). The ASP.NET Core detector ignores a component's `[Route]`: a page route isn't an endpoint. Rejected: Intent.Code.Weaving.Razor's fork of the compiler (a .NET 8-era build, not on NuGet, and its syntax tree is internal to everyone but the weaver, so it offers nothing 6.0 doesn't but `@rendermode`); Microsoft's current compiler from the .NET SDK (needs Roslyn 5.9, against the 5.0 the engine and RoslynWeaver share) and its NuGet toolset (previews only). Both share assembly names with the fork, which a C# application with the Razor weaver loads; 6.0's name is its own. On eShopCustom's 40 `.razor` files 6.0 and the fork generate the same members with no failures; 6.0 reports `<script>` in a component as RZ9992, which is only a diagnostic. Proven in a real Software Factory run: a `Buyer.razor` planted beside Ordering's `Buyer` class, with `@namespace`, joined it, and the engine reported its kind as `component`.
- **Markup is one shape for every language: `FileNode.Markup` (`MarkupNode`, `MarkupAttributeNode`, E4, 2026-11-14).** A Razor component's markup and a Vue template's give the same nodes: an element's tag as written, the component it names (a type ref that `CodeGraph.TypeFor` resolves from the component's type, as any type), its attributes, the elements inside it, and its content. What an attribute means to a framework (a component parameter, a link's route) is left to stacks, as the reader only splits a directive as its language writes it (Razor's `@bind-Value:event`, Vue's `v-model:title.trim`, `:to`, `@click`) into directive, argument and modifiers. Text content and a plain value are `LiteralNode`s like a C# string's, `interpolated` when code is written in them, so a rule reads `href="/orders/@id"` as it reads `$"orders/{id}"`; text is trimmed with whitespace runs reduced and character references resolved, while an element's canonical text keeps them as written (`CanonicalText.OfMarkup`). Razor's is read from its compiler's intermediate representation, captured in the same early pass as the directives, because its later passes fold static markup into strings and encode it. Vue's is read by `VueTemplate`, C# that reads a single-file component as Vue's compiler does (`@vue/compiler-dom` 3.5's `sfc` parse: its HTML, SVG and MathML tag lists, its component test, its directive shorthands, RCDATA `<textarea>` and `<title>`, its recovery from unclosed and stray tags). Rejected: running Vue's own compiler on the TypeScript worker, as TypeScript's parser runs; it is on no NuGet package, so it would be an 83 KB vendored file, which the repository's edit-tool rule leaves no way to add byte for byte, and the engine already reads a `.vue` file's blocks in C#. Proven against Vue's compiler as an oracle (`D:\Dev\Temp\VueProbe`): every element, position, component, directive, argument, modifier, value and content of the Java spike's 8 components (563 lines) and an edge-case file matched, bar the oracle's own entity decoding. There's no `directive` node: a Razor directive is the code it compiles to, and `@rendermode` isn't read, since Razor 6 parses only its identifier form (`@rendermode InteractiveServer`), not eShopCustom's `@rendermode @(new InteractiveServerRenderMode(prerender: false))`. The `markup` find step reaches a type's markup; `markup with` keeps only the innermost matching elements, as an element's text holds its children's. No stock check reads markup yet: it is for UI stacks and house rules.
- **A value's string is evaluated once, in the core, from facts every language gives it (`CodeGraph.StringOf`, `Code/StringValues.cs`, B10, 2026-11-14).** A language reader says where a value comes from in neutral terms (`ValueNode.Joined` for `+`, `Given` for what it stands for, `Parameter`, `Field`, `Call`, `Trimmed`; `FunctionNode.Changes` for every change but a plain `=`), and its library's string functions become those facts there (C#'s `string.Concat`, `ToString()`, `new Uri(x)`, `TrimEnd(chars)`; TypeScript's `concat`, `String(x)`, `new URL(x)`, `trim()`), so the evaluation, its parameter binding and its agreement rule are written once. Rejected: an evaluator per language, as the eShopCustom Blazor module carries one (~360 lines over Roslyn), which every module and language would repeat. It is lazy (`StringOf` walks the facts when asked; a local's values are `GivenOf`, read on demand), so readers pay nothing for values no rule evaluates. Initializers are read again with the bodies (`MemberNode.Value` is now settable, as `Body` is), so a field's initializer can name another type's constant. Conservative by design: a value given several ways, or a helper with several returns, is known only when they agree; a number, boolean, formatted hole, library call or loop-built string is a hole; a local or field changed by `+=` is a hole. The `+=` rule came from the eShopCustom probe, where `GetAllCatalogItemsUri`'s `filterQs += ...` had first evaluated to the empty string, which claimed a text the code can extend. Checked by hand against the code on eShopCustom's WebApp, WebAppComponents, HybridApp and ClientApp (every `GetFromJsonAsync`, `GetAsync`, `HttpRequestMessage` and `NavigateTo` URI, including `Pages.User.LogIn.Url(Nav)` across types and HybridApp's duplicated `&api-version=2.0`, which its code really sends) and the Java spike's `client.ts`. Markup values and Java aren't evaluated yet: no rule reads them.
- **Protobuf is a language of its own, read by its own parser (`Stacks/Protobuf`, `intent.protobuf`, E5, 2026-11-14).** `ProtobufReader` parses proto2, proto3 and editions by the language's grammar, with every token's position, and recovers after a syntax error at the end of its statement. Rejected: protobuf-net.Reflection 3.4.40, which parses well but keeps every source position non-public (`SourceCodeInfo` is null), and would ship two more assemblies; ANTLR's grammars-v4 protobuf grammar, since generating its parser needs the ANTLR tool on Java, which this machine lacks, and the generated files would have to be written by a script, which the repository's edit-tool rule forbids. Proven against protobuf-net as an oracle (`D:\Dev\Temp\ProtoSpike\oracle.cs`): over 72 real files (Grpc.Tools 2.84's `google/protobuf`, `descriptor.proto` included; Google.Api.CommonProtos 2.17's `google/api`, `google/type` and `google/rpc`; eShopCustom's `basket.proto`; two edge files with proto2 groups, oneofs, maps, streams, scoping and aggregate options) every message, field, number, label, type, enum value, rpc and field presence matched, 1,411 lines. As protoc does, `stream` in an rpc is always the keyword. Three choices of representation, each departing from the first draft of the spec: nullability is the field's presence, not only `optional`, because Intent's own gRPC module (`Intent.AspNetCore.Grpc`, `GrpcTypeResolverExtension`) writes a nullable value as a `google.protobuf.*Value` wrapper, a message, and a model's non-nullable `int` as a plain `int32`; whether a name is a message or an enum is resolved by protoc's scoping among the `.proto` files only, so a C# class of the same name never answers. A streamed rpc side is a `stream` type ref over its message, as `repeated` is a collection over its item, rather than a `stream` modifier, because a parameter has no modifiers and a method's modifier would have to say which side. The gRPC conventions (protoc's renaming, `ServerCallContext`) stay `intent.grpc`'s, still to build: the reader keeps names as written.
- **The Java reader gives a body's calls and creations as the C# reader does (`JavaBody`, 2026-11-13).** Same facts and the same rules for an argument's types, so a house rule over calls reads Java with no change: `Http.parseEnum(OrderStatus.class, status, "status")` is a call named `parseEnum` on `Http`, its second argument the `String` parameter `status`. Java-specific: `this(...)` and `super(...)` call a constructor, so aren't calls; a lambda's parameter is typed only when it's written (`(Order o) ->`, not `o ->` or `(var o) ->`); an array creation isn't a creation. A static call's receiver is a type name, which isn't typed, as in C#.
- **A call has the method it reaches, and a call used as a value is what that method returns (`CallNode.Target`, `CodeGraph.Targets`, B4, 2026-11-13).** Both languages set it the same way once every type is read: on the type of what it's called on, on the type a static call names, or on its own type with nothing to call it on, with what that type inherits; an override hides what it overrides. A method is reached by name and number of arguments, never by the arguments' types: a parameter with a default may be left out and a last array parameter (`params`, varargs) takes any number. A call more than one method can take has no target, rather than a guessed one, because the readers don't type every argument. A method's own type parameter, or its type's, isn't a returned type (`<T> T first(..)` gives an unknown value). C# `await` gives a `Task<T>`'s or `ValueTask<T>`'s `T`. A method reference is a call with `IsReference` and no arguments: Java's `this::audit` and `Order::markAsPaid` (an instance method through a type name, which a call can't reach), not `Order::new`; C#'s method group (`items.ForEach(Audit)`) only when the code doesn't type the name as a value and an in-scope method has it, since C# writes both alike. `CallsFrom` follows a reference as it does a call: a method passed on is one that runs.
- **A call made on a call has it (`CallNode.On`, B3, 2026-11-13).** `ResponseEntity.noContent().build()`'s `build` is made on `noContent`; each call of a chain is also one of the body's calls, the same node, so a rule can walk a chain either way.
- **A literal is its value, not its text (`ValueNode.Literal`, B1, 2026-11-14).** A rule compares `LiteralNode.Value`, which is the same whatever the quoting: C#'s `"a"`, `@"a"` and raw strings, Java's strings with every escape resolved (octal and `\uXXXX` too) and text blocks with their indentation stripped (JLS 3.10.6). Its `Kind` tells `"true"` from `true` and `"null"` from `null`. A number keeps its sign and is as written (`18.4m`, `42L`), as an enum member's value is. An interpolated string has its text and holes in order, a hole typed as any body value is, so a URI rule reads `orders/` and `id` without evaluating anything; evaluating a string through fields and helpers is B10. A type literal (`typeof(Order)`, `Order.class`) has its type: the Java eShop's `Http.parseEnum(OrderStatus.class, ...)`. C#'s `nameof(Order.Total)` is the string `Total` and no longer a call; attribute arguments read the same literal, so `[ForeignKey(nameof(Customer))]` reads `Customer`. A field's or property's initializer has its literal too, for B10 to follow. Literals have no `Types`: the language's own types for a literal weren't needed, and naming them would put each language's primitive names in the readers for nothing.
- **An import says what it brings in, and a type name resolves through imports (B9, 2026-11-14).** `Wildcard` marks an import of everything its target holds, a C# namespace `using` as much as Java's `.*` (whose target no longer carries the `.*`, so a Java wildcard import reaches its package as a `using` does); an import that is none of wildcard, static or aliased names one type. `CodeGraph.TypeOf(import)` gives the in-scope type an import names (single-type, static, alias), so a rule finds the files it resolves to. `TypeFor` resolves an unqualified name through the file's alias or single-type import first (Java's import shadows its own package's type; an import of a library's type resolves to nothing), then a type of its own or an enclosing namespace, then the only one a wildcard import reaches. Before, two same-named types in other namespaces resolved to neither, and an alias to nothing. The JPA stack's import check matches `jakarta.persistence.*` by its target, `jakarta.persistence`.
- **Code runs in units, one shape for all of them (`FunctionNode`, B7 and B8, 2026-11-14).** A method's or constructor's body (`MemberNode.Body`; `Calls` and `Creations` read from it), a lambda (`ValueNode.Function`: a Minimal API handler's `[FromRoute] Guid id`, an options callback's `o.Title = "Orders"`) and a file's top-level statements (`FileNode.TopLevel`, Program.cs's registrations) each have parameters, calls, creations, plain assignments and returns. Everything written inside a unit counts, its lambdas' code too, as the same nodes the lambda's unit has, so a rule reads Program.cs whole or one handler alone. A return is the unit's own unless a nested lambda, local function or Java anonymous class holds it; a `void` method's expression body returns nothing. Top-level code's unqualified calls reach the global namespace's `Program` when a partial one is declared (C#'s own rule); its types and their members aren't top-level code. Why one shape rather than a lambda node beside the member's calls: a rule following a handler, a method group or Program.cs shouldn't need three APIs. Not built: TypeScript module-level code and Vue `<script setup>` (with E2), and an `args` parameter for top-level code.
- **A creation is a node with what it's given, and a value knows the creations it can be (`CreationNode`, B5, 2026-11-14).** A body's `Creations` have their arguments, an object initializer's assignments (a member by name, an indexer as written, a nested initializer as its text) and a collection initializer's items; `Creates` is now their types. A value's `Creations` follow the same ways its `Types` do (a local, a cast, a conditional), and they're the body's own nodes, so `SendAsync(request)` reaches what `request` was created with: each creation's type is one node, and a value's types are looked up by reference. A target-typed `new()` names no type and isn't read. A creation is set with the calls, after every type is read, since its arguments are typed.
- **A call has its type arguments (`CallNode.TypeArguments`, B2, 2026-11-14).** `AddScoped<IOrders, Orders>()` and `AddSubscription<M, H>()`, a C# method group's (`Map<Order>`), Java's rare explicit ones (`this.<Order>create()`, which the reader now reads as a call at all) and a Java method reference's (`this::<Order>create`). A method that returns its own type parameter gives the type the call passes (`CallTarget.ReturnsGiven`), so `var o = Create<Order>()` is an `Order`; without type arguments it stays unknown, since inferring them would need the arguments' types.
- **A house refines what a stack reads; it never repeats the stack's comparison (`IMemberRefiner`, 2026-11-13).** Proving a Java house rule on the engine showed the gap: the Java eShop binds `String status` and turns it into an `OrderStatus` with its own `Http.parseEnum(OrderStatus.class, status, "status")`, and responds with `Http.created(body)`. Only the house knows those helpers, but the comparisons (a handler's bound parameters, a `ResponseEntity<T>`'s body) are the Spring MVC stack's, and a house claim reader would have had to redo them whole. So a refiner gives the member a claim's dependency located as the house reads it (`member with { Parameters = ... }`, `status: String as OrderStatus`), before any reader runs, and every reader, the engine's own rules included, reads that one. Refiners run in extension order, so a house's run after the stock ones, each on what the one before left. Rejected: a delegating `context.Next(member)` for readers (the engine's own rules write the claim directly, so they couldn't be reached), and making the stack's readings public for the house to call (each house rule would still repeat the comparison). `MemberNode` and `ParameterNode` are records for `with`, but equal only to themselves, as graph nodes. The Java eShop's Services module (`HttpHelpers`) is the proof: its 27 Services findings (25 `ResponseEntity<Object>` returns, 2 parsed enums) are 0, with plants in each caught.
- **One Roslyn at run time, so a module's own C# reader runs on the engine's trees (proven 2026-11-13).** The engine compiles against Roslyn 5.0.0 and ships it (below); eShopCustom's modules compile against 5.0 and bundle it. In the Software Factory the Domain module's reader, built against 5.0, reads the trees the engine's C# language parsed, and caught four planted domain-event drifts. This replaces an earlier, unproven note that an extension built against another Roslyn would fail. Neither eShopCustom extension reads the trees itself any more: both read the engine's code reading (below).
- **A framework's extension answers only when its framework is in the code (2026-11-13).** EF Core reads only when the code configures an entity or declares a `DbContext`; ASP.NET Core only with a controller, an attribute-routed action or a Minimal API endpoint. Otherwise their claim readers return null, so the claim goes to another framework's extension (JPA, Dapper's) or, with none, can't be verified, never a false "the code doesn't state it".
- **The core knows no technology; everything else is an extension (user decision, 2026-11-13).** An extension (`IDriftExtension`) brings languages, packs (kinds, vocabulary), claim sources, code readers (`ICodeReader`, given the graph, with its language's syntax on it, and keeping what it finds there with `CodeGraph.Set`), claim readers (`IClaimReader`) and comparers (`IValueComparer`). The engine's own comparers are `exact`, `ignoreCase`, `number` and `set`. An extension's claim reader runs before the core's structure rules, and a later extension's before an earlier one's, so a module can read any kind, the core's included; returning null passes the claim on. A throw is `ruleFailed` on the claim plus one `config/pluginFailed` finding. Why: the engine must do everything the custom modules did, so it may not limit them; EF Core and ASP.NET Core code had crept into `DriftEngine.cs`, turning it into a Common.Drift replacement.
- **What the model states is framework-neutral; how a framework's code states it is a separate extension (user decision, 2026-11-13).** `intent.rdbms` (tables, keys, columns, indexes, foreign keys, from the RDBMS stereotypes, with the `storeType` and `literal` comparers) and `intent.http` (routes, verbs, parameter sources, security, with the `route` comparer) read no code. `intent.efcore` and `intent.jpa`, `intent.aspnetcore` and `intent.springmvc` only read those claims from their code, each with no change to the others. They live in `Intent.Modules.Common.DriftEngine.Stacks` (`StockExtensions.All`), using only the public API.
- **Modules register an extension the way reporters register with the hub.** `Api/DriftEngineExtensionBase` is a factory extension that publishes itself on the run's event dispatcher before template registration; `DriftEngineReporter` subscribes at the run's start and runs the registered extensions after the stock ones. eShopCustom's Architecture module is the first to use it (its Layers as claims, its import check as a rule), and its Domain module the second (its own stereotypes, read through the stock EF Core reading); a module compiles against the engine's assemblies and ships none of them, depending on Intent.Common.DriftEngine instead. Every part of `IDriftExtension` is a virtual on the base (`ModuleExtensionTests` checks each): a part the base doesn't implement maps to the interface's empty default, so a module's own member of that name compiles and is never called. `Languages` was such a part until 2026-11-14 (user: "let modules add a language through DriftEngineExtensionBase").

- **The engine is its own assembly, `Intent.Modules.Common.DriftEngine.Core`, shipped in the `.imod` beside the module's (2026-11-13).** It depends on the SDK's model interfaces only (Roslyn is the Stacks' C# language's), so the acceptance suite (`Intent.Modules.Common.DriftEngine.Tests`) runs it from fixture data with no Software Factory. The module project holds only the hosting: `DriftEngineReporter`, `Reporting/DriftEngineReport` and the extension base. The `.imodspec` lists the Core and Stacks `.dll` and `.pdb` by hand.
- **The engine ships its languages' parsers and depends on no language's modules (2026-11-13).** The `.imod` carries Roslyn (`Microsoft.CodeAnalysis` and `.CSharp` 5.0.0) and the Razor compiler (`Microsoft.AspNetCore.Razor.Language` 6.0.36) for C#, the ANTLR runtime for Java and `typescript.js` (inside the Stacks assembly) for TypeScript; Protobuf's parser is the engine's own code, so it ships nothing more. The `.imodspec` depends on no RoslynWeaver or Intent.Common.CSharp, so a Java application installs no C# modules and gets none of their `.agents` guidelines. ## Invariants

- The engine never writes to the codebase; checks prove it on real codebases with `git status` before and after (`Real/RealStructureRunTests`).
- A client's code, model export and results stay on the machine that ran them. Committed files carry counts only.
- A public engine signature only gains overloads: modules compiled against an earlier engine load the new one unchanged.
