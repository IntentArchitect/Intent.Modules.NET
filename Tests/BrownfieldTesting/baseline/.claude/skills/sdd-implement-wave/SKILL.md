# SDD — Implement a wave

You are implementing **one wave** of an approved spec. The orchestrator (**`/sdd-implement`** or **`/sdd-run`**) dispatched you for this wave, told you which wave `id` to do, and passed forward the **cross-wave context** from earlier waves in your instructions. Implement **only the wave you were told to implement**, then **report back to the orchestrator** and stop — it sequences the waves and fires the next.

You already know how to model, generate, write code, and build/test — run **your normal module → model → generate → code → verify workflow** on this wave's tasks; this skill only tells you _which_ tasks are yours to work explicitly, _when_ generation and the build/test pass happen automatically, _how to record progress_, and _what to report back_.

## Honour the solution's governance

When the spec's framework declares governance documents — Spec Kit's `.specify/memory/constitution.md`, say — `read_spec` returns them as `governanceDocuments` and the Specs panel lists them. **Read them first and treat their rules as binding on what you produce.** They are the user's standing constraints, not background reading. If a requirement and a governance rule genuinely conflict, say so and ask rather than silently picking one.

## What to do

1. `read_spec(slug, artifact: "tasks")` and `read_spec(slug, artifact: "design")` (and `read_spec(slug, artifact: "requirements")` for the acceptance criteria). The `## Task Dependency Graph` lists the **waves**;
2. **Work the wave in strict phase order — create applications, install modules, model everything, generate, _then_ code.** Do **not** route tasks by their position in `tasks.md` and do **not** interleave modelling and coding: create any `[app]` prerequisites and install any `[module]` prerequisites first (their stereotypes must exist before the model work can apply them), complete **all** of the wave's `[model]` tasks next, run the Software Factory once so the generated code is on disk, and **only then** dispatch any `[code]` sub-agent. A `[code]` agent dispatched before generation would be writing bodies against contracts that don't exist yet — that is the ordering this phase split exists to prevent. Throughout, work only the **unchecked (`[ ]`)** tasks, one at a time (sequential — never in parallel). **Skip any task already ticked `[x]`** — it is already done: do **not** re-run it, re-install its module, re-apply its `[model]` script, or re-dispatch its `[code]` agent. On a resume the orchestrator hands you a wave that mixes ticked and open tasks — work **only** the open ones; the ticked work must be left exactly as it is.

   - **Phase 0a — create prerequisite applications (only if the wave has `[app]` tasks).** For each open `[app]` task, create the application with `create_application` at the name + architecture the task names — the choice was already put to the user during design, so **don't re-confirm it**; load the **creating-applications** skill for the mechanics. This has to happen before anything writes into that codebase area: the application's output is what `write_file` / `patch_file` resolve against and what a traceability file link is relative to, so without it Phase 3's code lands outside Intent's view and its links have no base. Tick each `[app]` task once the application exists, and pass its `applicationId` to the Phase 3 coding agent for work in that area.
   - **Phase 0 — install prerequisite modules (only if the wave has `[module]` tasks).** For each open `[module]` task, install the module at the exact id + version the task names with `install_or_update_modules` — the module choice was already approved during design, so **don't re-confirm with the user**. Installing makes the module's designers, stereotypes, and settings available to Phase 1's model scripts; its generated infrastructure lands in Phase 2's single Software Factory run, so **don't run the Software Factory separately here**. Tick each `[module]` task once its install succeeds. If the wave has no `[module]` task, skip this phase.
   - **Phase 1 — all `[model]` tasks.** Apply every open `[model]` task in the wave (`run_designer_script`) and fix what each result's `errors[]` lists — the problems your change introduced. When a wave's model work spans designers, apply it in dependency order **Domain → Services → UI** (create the element an outer layer references before the referencer). Model the **public surface**; where custom logic has a natural public operation, model that operation (with a behaviour comment) so generation emits a body stub — but don't contort the model for private helpers / implementation detail, leave those to code. Finish and verify every `[model]` task before moving on — nothing in Phase 3 starts until the model is complete.
   - **Phase 2 — generate (never its own task), then tick the `[model]` tasks.** **Once every open `[model]` task this run is applied and verified**, run the Software Factory **once** and apply the staged changes, so the generated contracts and body stubs are on disk **before any `[code]` task starts**. This run is also what makes the wave's `[model]` tasks recordable and completable — it persists the in-memory model to disk, and both `record_spec_traceability` and `complete_spec_task` refuse to progress a `[model]`/`[code]` task before that happens (see step 3). So **record and tick every `[model]` task now, immediately after this run and before Phase 3 starts** — never sweep them up at the end of the wave, where a late failure would lose credit for model work that genuinely landed. **If you applied no `[model]` script this run** — every `[model]` task in the wave was already `[x]` (e.g. a resume that reopened only a `[code]` task) — **skip this**: the model is already generated, so don't re-run the Software Factory or re-apply the whole model just to reach an open `[code]` task.
   - **Phase 3 — all `[code]` tasks, in ONE `coding` sub-agent.** Only now, with the code generated, dispatch **exactly one** `coding` sub-agent for the wave, covering **all** of its open `[code]` tasks. Pass it the slug, the `applicationId`, the **task ids**, the exact files/operations for each, the intent, the acceptance criteria, that every test it writes cites the numbered criteria it asserts in its own title (`[spec:<slug> R2.1]`, never a bare `R2` or a `describe` block), **only those its assertions prove** — a test that just checks how a collaborator or host is called proves no behaviour criterion, so it cites none rather than borrowing one — and that test files are not linked, and **require it to report the relative paths of the files it wrote, every model gap it needs you to fix, and every hand-written member a regeneration could reclaim**. Don't hand-write business logic yourself, and don't re-impose the coding agent's own rules in its instructions — it already knows how to work; just point it at the work and the intent.
     - **It reports model gaps; YOU fix them.** The coding agent has no designer tools, by design — **the model stays yours**. It implements as completely and thoroughly as it can, sweeps all its tasks' contracts up front, and hands back **one** consolidated list of the public/structural surface the model is missing (a field, parameter, DTO member, operation, or domain method), together with anything it hand-wrote in the meantime to keep its code complete. On that report: **(a)** model the whole list in one `run_designer_script` (Domain → Services → UI) and verify the scoped `errors[]`; **(b)** re-run the Software Factory and **inspect `get_file_diffs` BEFORE applying — your model fix must not discard the code the coding agent just wrote**: where a diff would delete or overwrite its bodies or hand-written members, model that surface properly or protect it with a code-management _ignore_ directive first, per step 5; **(c)** **resume the same coding agent** (don't dispatch a new one — it already holds the context) to finish and tick whatever the gap blocked. That one model→generate→resume round trip is expected, not a failure. A genuine **design flaw** — the realization the design chose can't be cleanly expressed in the model — comes back to you the same way, and it's yours to resolve, escalating per _When you're stuck_ if it needs the user's decision.
     - **Never fan out.** If a wave's `[code]` work looks too big for one agent, that is a **wave-sizing defect** from `sdd-tasks` (a wave's `[code]` tasks should total no more than ~5–8 implementation points) — **say so in your report** so the task list can be re-waved. Do **not** split the work across several coding agents. Resuming the one agent after a model fix is not fanning out; starting a second agent for the same wave's code is.
   - **Phase 4 — build/test (never its own task).** **Once this wave's `[code]` tasks are done** (including any test-writing tasks), run the wave's build and test task(s) — you can pipe them in one `run_task` call (e.g. `build | test`) so test only runs if build passed. This is a whole-wave **confirmation** of the per-task build/test the coding agent already ran, not a substitute for it. If it fails, **fix the cause and re-run**; keep diagnosing and re-running until it's green. **Never finish a wave on a red build** — if the same failure survives genuinely different attempts, escalate per "When you're stuck" rather than leaving the responsible task unchecked.

   (An older `tasks.md` may still carry an explicit `[generate]` or `[verify]` task written before this convention — honour it exactly the same way if you see one; it just means that step is spelled out rather than implicit.)
3. **Record progress as you go — but tick only what genuinely completed.** You own the progress of the wave's **`[app]`, `[module]` and `[model]` tasks only**; the `coding` sub-agent records and ticks its own **`[code]`** tasks as each one's build/test passes, so don't record or tick those yourself. Per task you own, in **this order**: **(1)** `record_spec_traceability`, **(2)** read the result's `failures`, fix them and re-record until the call comes back clean, **(3)** `complete_spec_task`. **Never tick a task whose traceability isn't recorded with zero `failures`** — the record is the durable evidence, the tick is what the orchestrator reads, and `complete_spec_task` refuses the tick anyway while any of that task's recorded links is broken. A `failures` entry means the link was **rejected, not stored** — see the **sdd-record-traceability** skill for the contract. (`[app]` and `[module]` tasks are the exception: they have no targets to record, so tick one as soon as the application exists / the install succeeds.)
   - **The trace contract itself lives in `/sdd-record-traceability`** — which ids to record against, what a valid model/file target is, the record → check `failures` → re-record → tick loop, and the end-of-wave broken-link sweep (which is **yours, over the WHOLE wave**, covering the links the `coding` sub-agent recorded as well as your own). Follow it; it is the same contract `/sdd-heal`, `/sdd-trace-reconcile` and framework-driven runs use, so it is stated once. The rest of this bullet is only what is specific to a wave:
   - **This is where the model-state gate bites.** `record_spec_traceability` **refuses** to record model targets for a still-open `[model]`/`[code]` task while a designer still has unsaved changes — i.e. the Software Factory hasn't run since your last model edit, so the links would point at code that was never generated and a reload would lose the work. A refusal is the signal to **run `run_software_factory` and `apply_staged_file_changes`, then re-record** — treat it as "go generate", not an error to route around (the refusal already saved your in-memory model and wrote no links, so nothing is lost or half-written).
   - **When a task satisfies several requirements**, take the per-requirement member map from the task's detail bullets and set each target's own `requirementIds` (a subset of the task's `satisfies`), so a requirement links only to the members that realize it — e.g. under a create-the-aggregate task, `IsDeleted`/`SoftDelete()` carry `requirementIds: ["R5"]` while `Name`/`Price` carry `["R1"]`, instead of every requirement sweeping in the whole entity. Omit a target's `requirementIds` only when that element genuinely serves **every** requirement the task satisfies (then it falls back to the task's full list).
   - **On a re-run (e.g. a resume)**, re-record the **full** set of targets the task actually touched this time — passing `targets` replaces the task's prior links. Passing **no** targets now **preserves** the existing links (so an idempotent re-run where generation reported no changes keeps its coverage instead of unlinking it); pass `clear: true` only to genuinely drop a task's links.
   - **A `[module]` or `[app]` task** produces no designed element of its own, so it records no model-element/file targets — tick it once installed / created (Phase 0) and leave its requirement's concrete traceability to the `[model]` or `[code]` task that builds on it (that task carries the shared `satisfies` id and links the real element or file).
   - **Spell a file target's `relativePath` the way you actually know it** — relative to the `applicationId` you passed, relative to the workspace root, or with a `../` escape out of an application output. All are probed and rewritten to one canonical form, so the base is not something to guess; prefer the **workspace-relative** form for anything outside the application you were dispatched with. A refusal lists the concrete directories probed — act on it, don't re-guess. If a file genuinely belongs to no application, the wave is missing its `[app]` prerequisite: record the link (it stores workspace-relative) and **say so in your report**.
   - **A `[model]`/`[code]` task cannot be ticked with nothing recorded** — `complete_spec_task` refuses it, because a ticked task is never revisited. If such a task genuinely produced nothing traceable, affirm that explicitly: `record_spec_traceability(slug, taskId, requirementIds: [], targets: [], clear: true, note: "<why>")`.
   - `complete_spec_task(slug, taskId)` ticks a task `[x]` (parent milestones roll up automatically) — **only once its record call came back clean.** **Tick a `[model]` task immediately after Phase 2's Software Factory run has generated it** — never at the end of Phase 1, and never swept up at the end of the wave. `[code]` ticks and their traceability belong to the `coding` sub-agent, which ticks each one as that task's build/test passes; a legacy `[generate]`/`[verify]` task, if a `tasks.md` still has one, is yours and is ticked once the wave's build/test pass has succeeded. The tick carries the same model-state gate as a second line of defence, so a refusal here means the same thing as on the record call: go generate, then re-tick. **Never tick a task you couldn't complete** (blocked, still failing, deferred): leave it `[ ]`, escalate per "When you're stuck", and call it out in your report. The orchestrator reads these checkboxes to decide the next wave, so a false tick silently skips the work.
4. Keep the **model the source of truth**: structural surface is modelled, never hand-written — and **you** are the one who models it. The `coding` sub-agent never touches the model; when it reports a gap, you model it, regenerate, and make sure that regeneration doesn't break the code it wrote (step 5's rules apply mid-wave to a gap fix, not just at the end).
5. **Verify model↔code alignment before reporting (idempotency check).** Once coding is done, re-run `run_software_factory` and inspect `get_file_diffs` **before applying**. If the Software Factory wants to delete or overwrite any hand-written code, that code isn't protected yet: if it's **public surface the designer can represent** (an operation, property, association, DTO field), model it, regenerate, and re-fill the body; if it **can't or shouldn't be modeled** (a private helper, local logic, implementation detail), protect it with Intent's code-management _ignore_ directive the way it's already used elsewhere (e.g. an `[IntentManaged(Mode.Ignore)]` / `[IntentIgnore]` attribute, or set the file/region's code-management mode to Ignore — match the existing convention). Re-run until regeneration is **idempotent** (no destructive diff to any hand-written code) and the build passes.

## When you're stuck — ask the user, never give up quietly

The wave is complete only when **every open task is ticked, its traceability is clean, regeneration is idempotent, and build/test are green.** Anything short of that isn't "I did all I could" — it's **stuck**, and stuck has exactly one exit: **ask the user.**

You are stuck when any of these is true:

- the same build or test failure survives ~2–3 **genuinely different** fix attempts (re-running the same idea doesn't count);
- more than ~2 model↔code cycles — i.e. after Phase 2 you find yourself re-modelling, regenerating, and resuming the coding agent again and again to get the wave green (**one** gap-report round trip is the expected shape, not a trigger);
- a **design flaw**, yours or one the coding agent reported: the realization the design chose can't be cleanly expressed in the model;
- a designer rule forbids the change the design asks for;
- the design or the task is ambiguous, or contradicts what is actually in the model;
- a module or capability the task needs isn't available;
- a task's acceptance criteria can't be met as written.

**When you're stuck, `ask_user_question`.** It works from a dispatched sub-agent — the question surfaces in the user's chat and the answer comes back to you. Say what you tried and why it failed, then offer **2–4 concrete options**, drawn from what actually applies:

- an alternative realization you can implement now;
- a narrower compromise for this wave;
- model it, vs. protect the hand-written code with a code-management _ignore_ directive;
- defer the task to a later wave or to `/sdd-heal`;
- **revise the design — stop the run and go to `/sdd-design`**;
- stop here.

Then **act on the answer and carry on to completion**. The **only** ways to return with an open task are an explicit user decision to stop / defer / revise the design (quote it in your report), or a question the user cancelled or never answered.

## Then report back and stop

When the wave is done, **reply to the orchestrator with a concise report** — this is your only channel to the next wave (there is no handover document, so anything you don't report is lost), and the orchestrator **trusts it without re-verifying anything**, so it must be accurate.

Lead with a **one-line verdict** — e.g. _"Wave 2 complete — all 6 tasks ticked, traceability clean, SF idempotent, build + test green"_ — then state, in your own words:

- **Each open task id** → ticked or not (yours and the coding agent's); for anything left unticked, why, and **which explicit user decision** it rests on.
- **What the coding agent's gap report added to the model** — every element you modelled after Phase 3 to make its bodies possible. Later waves must see these: they are real model changes that appear in **no** `[model]` task.
- **Traceability** — recorded for every ticked task with no `failures`, and the end-of-wave `coverage` rollup shows no broken links.
- **Generation** — the Software Factory ran, its staged changes were applied, and the idempotency re-run (step 5) proposes no changes to hand-written code.
- **Build/test** — the exact task(s) you ran (e.g. `build | test`) and their result.
- **Any `ask_user_question` outcome that changed the plan** — yours or the coding agent's; quote the decision.
- **If this wave has a `checkpoint`** — how the user can see the result: a screenshot you captured if your tools can produce one, otherwise the exact steps to open it. Say what to look at.
- **If a wave-sizing defect showed up** — the wave's `[code]` volume genuinely exceeded what one coding agent can carry (Phase 3), so `sdd-tasks` should re-wave it.
- **If you stopped for a design revision** — the requirement id, what the design assumed, and why the model/architecture can't realize it, precise enough for the user to act on in `/sdd-design`.
- **What the next waves need and can't read off the model** — names you chose, shared helpers/conventions you introduced, anything you deferred to a later wave, and gotchas hit. Keep it terse — it is **not** a restatement of the spec, the model, or the code.

Then **stop**. Don't start another wave, and **never call `advance_spec_phase`** — the phase gate belongs to the orchestrating conversation and the user, never to a wave. The orchestrator sequences the waves, and `/sdd-verify` is the review once they're all done. (If your wave happens to tick the spec's last task, `complete_spec_task` moves it into the **verification** phase for you — a mechanical consequence, not a gate. Report and stop as usual; don't start the review.)
