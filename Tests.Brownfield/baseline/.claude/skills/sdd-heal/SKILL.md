# SDD — Heal

You are running the **heal** step — the targeted repair after `/sdd-verify` recorded a verdict with **gaps**. Your job is to make each failing requirement genuinely satisfied, fixing **only** what verify judged deficient. When you finish, **stop** — `/sdd-verify` re-judges the gaps (in a Run, `/sdd-run` dispatches it; after a chat's change, `/sdd-sync` does; otherwise the user runs it).

This is **gap-driven, not a task re-run**: the implementation's `tasks.md` checkboxes stay exactly as they are (`[x]`). **Never tick or untick a task** (`complete_spec_task`) and **never call `advance_spec_phase`** — the heal is proven by the re-run of verify, not by checkboxes, and the phase follows that verdict. The tasks already passed; the review found specific defects, and those are all you touch. The spec stays in its phase throughout: at **verification** until the review passes, or at **done**, where a verdict with gaps leaves it.

You already know how to model, generate, write code, and build/test — run **your normal model → generate → code → verify workflow**, scoped to each gap. This skill only tells you _which_ defects to fix, _how to track_ the work, and _what not to touch_.

## Honour the solution's governance

When the spec's framework declares governance documents — Spec Kit's `.specify/memory/constitution.md`, say — `read_spec` returns them as `governanceDocuments` and the Specs panel lists them. **Read them first and treat their rules as binding on what you produce.** They are the user's standing constraints, not background reading. If a requirement and a governance rule genuinely conflict, say so and ask rather than silently picking one.

## What to do

**First, resolve the slug — never guess it.** If you weren't handed an exact slug, call **`read_spec` with no `slug`**: it lists every spec in the solution with its `slug`, `phase` and progress. Match what the user named against that list. Specs live under `intent/.specs/` and are reachable **only** through `read_spec` — never glob or grep the workspace hunting for spec artifacts. If nothing there plausibly matches what they named, `ask_user_question` offering the closest specs as options rather than inventing a slug.

**Questions that cite requirements.** Pass the slug as `spec` on every `ask_user_question` that names a requirement id, so the card links each id to its requirement, and say in plain words what each cited requirement requires: the user may not remember what `R3.14` is.

1. **Load the gaps and the context.**
   - `read_spec(slug, artifact: "verdict")` — the per-requirement verdict. Each **gap** carries your brief: `reason` (the summary), `expected` (what the acceptance criterion requires — your goal), `actual` (what's there now / the deficiency), and `location` (the file(s)/element(s) to fix). Ignore the `pass` rows. A gap whose `reason` starts with `Disagreement:` is a criterion its citing test disagrees with: heal it only as the user answered (below). Gap briefs your dispatcher hands you are gaps too: heal them alongside the verdict's.
   - **The user's answers to disagreements**, when your dispatcher hands them over. Apply each exactly as chosen: **fix the code** so the criterion and its test hold, **change the test** so it asserts what the criterion says, or **reword the criterion** — write the wording with `write_spec` and leave the Spec review to your dispatcher (in a Run the orchestrator raises one for every rewording). Never pick a side yourself. A new criterion goes in the spec whose description covers it, from `read_spec()`, whichever spec traces the code; ask the user when more than one fits. Before you write any wording, check each claim in it against the code, including glossary entries and other criteria you reword along the way, never only against the spec's existing prose. Give the `file:line` that shows each one in your report.
   - `read_spec(slug, artifact: "tests")` — each criterion that is not yet tested, with its test status, and the orphan citations. The **untested** criteria, and the missing clauses of **partly tested** ones, are yours to cover (step 5), but only among the criteria your gaps name (each gap's `expected` starts with their ids) and in the requirements your dispatcher names. Read which clauses are missing, and the tests already citing each criterion, with `read_spec(slug, artifact: "tests", requirementId)` for each of those requirements.
   - `read_spec(slug, artifact: "requirements")` — the EARS acceptance criteria for the failing requirements.
   - `read_spec(slug, artifact: "design")` — the intended model changes + realization plan, so your fix fits the design.
   - `read_spec(slug, artifact: "traceability")` — which tasks/elements/files already realize each failing requirement (i.e. **where** the fix lands). Compact target summaries by default; `read_spec(slug, artifact: "traceability", requirementId: "Rn")` pulls one failing requirement's full targets.
2. **Turn the gaps into a todo list.** Call `todo_update` with **one entry per gap** (e.g. `Heal R2 — <short reason>`), all `pending`. This gap-level list is the live progress the user watches — one item per failing requirement, nothing for the requirements that passed, plus one `Write missing tests` item when any criterion in your scope (step 1) is untested or partly tested, or an orphan citation falls in the requirements you work on.
3. **Close the traceability gaps first.** These are gaps whose whole brief is a missing, broken or stale link, or an untraced element or file that realizes the requirement. Re-record the owning task's links (see the traceability bullets below) and confirm that the call returns no `failures`. Don't dispatch a sub-agent, run a build or regenerate for them, because there is no code to change.
4. **Heal each remaining gap, one at a time** (mark it `in_progress`, fix it, mark it `completed`). For each gap:
   - **Target the specific defect.** The gap's `expected` is the goal, `actual` is what's wrong, and `location` + the requirement's traceability targets tell you where. Make the **smallest change that closes the gap** — do **not** rebuild work that already passed, and do **not** re-do requirements that verified clean.
   - **Run your normal workflow** on that defect: model the public surface with `run_designer_script` (Domain → Services → UI order when it spans designers) and validate the scoped `errors[]`; if you changed the model, run the Software Factory **once** and apply the staged changes so the code is on disk; dispatch a **`coding`** sub-agent for operation bodies / custom logic / tests (pass it the `slug`, the `applicationId`, the exact files/operations, the gap's `expected` **and** `actual`, the acceptance criteria, and require it to report the relative paths it wrote, any **model gap** it needs you to fill, and any hand-written member a regeneration would reclaim). It has no designer tools, so a gap comes back to you: model it, regenerate, and **inspect `get_file_diffs` before applying so your fix doesn't discard the code it just wrote**, then resume the same agent to finish. **Tell it explicitly that this is a heal, so it must NOT tick or untick any task** — the coding agent can call `complete_spec_task`, but heal's no-ticking rule governs, and a heal dispatch that ticks would fake progress the verify re-run never confirmed. Then run the build and test task(s) and **fix the cause and re-run** until green.
   - **Re-record traceability for what you touched.** For the task that satisfies the healed requirement, `record_spec_traceability(slug, taskId, requirementIds, targets, designerId)` with the targets you changed this run (`{ id, name }` for model elements, `{ kind: "file", relativePath }` for code) — passing `targets` replaces that task's links; passing **none** preserves them. If you only edited already-linked files and added no new element/file, there's nothing new to record. If you **reworded a criterion**, its links stay as they are: the next verify re-judges it against the new wording. Reword by splitting, never by lengthening: extended behaviour gets a new criterion id, and a criterion that would go over the atomicity limit in **sdd-requirements** keeps its id for the core behaviour, with each extra behaviour under a new id, split as **sdd-requirements** says.
   - **A broken/failed link is healed by re-recording the corrected target, never by editing `traceability.json` by hand.** If the gap was a broken link (an id/path that no longer resolves), re-record the task with the right element id (from `run_designer_script`'s `changes`) or the corrected `relativePath` — re-recording replaces the task's links. Then confirm the record call comes back with **no `failures`** before ticking the gap done: a `failures` entry means the corrected target was **rejected too, and nothing was stored**, so the requirement is still unlinked. Fix the target itself, not the message.
   - **Tick the gap's todo `completed` only once the defect is genuinely addressed and the build passes.** If you can't close a gap, **leave its todo open** and call it out in your report — never mark it done to move on. A build or test command that fails before any test runs because a file it writes is locked or in use by another process (another agent is building) is no result: run it again once, and if it is still locked, report it as blocked rather than as a disagreement.
5. **Write the missing tests.** For each **untested** criterion, and each missing clause of a **partly tested** one, write a narrow test in the project's existing test style whose title cites it: `it("[spec:<slug> R2.1] …")` in jest, `[Fact(DisplayName = "[spec:<slug> R2.1] …")]` in xUnit, listing several ids when one test asserts them all (`[spec:<slug> R1.4, R1.5]`). Cite numbered criteria on test titles only, as **sdd-record-traceability** says. Retitle each orphan citation in the requirements you work on the same way: a test or `describe` title citing a bare requirement (`R12`), or an id the spec lacks, gets the ids of the criteria its test asserts on the test itself. Don't link test files with `record_spec_traceability`: the citation is the link. Give the tests to the `coding` sub-agent you already dispatch when you can, rather than to a new one, and run them. A test that fails shows a real defect: fix it as a gap, or report it if you can't. A criterion no automated test could assert (a visual judgement, a timing under real load) gets no test: name it in your report as untestable, with the reason in a few words. Only verify records it as untestable; until then it shows as untested.

   Then have sceptic sub-agents judge the new tests, one per about twelve criteria, grouped by requirement and dispatched in a single response, with your host's own sub-agent tool when it has one (Claude Code's `Agent`), because those run in parallel, and otherwise with `create_sub_agent` and `agentId: "discovery"`. Give each one the slug and the criterion ids to judge, have it read each criterion with `read_spec(slug, artifact: "tests", requirementId: <criterion id>)` for its numbered `clauses` and every citing test with its body, `unconfirmed` ones marked, and have it return one line per judged test, `criterion · file:line · degree · covered clauses or reason`. Have them judge each unconfirmed test, crediting it with a clause it checks part of when the criterion's tests together check all of it — `full`, `partial` (the `covered` clause numbers), `mismatch` or `untestable`. A test that sets up a case and asserts nothing, or asserts its own fixture back, covers nothing. Strengthen any test it finds short through the `coding` sub-agent, then send it back to a sceptic to re-judge: never grade a test you wrote yourself. Have each sceptic record its own `full` and `partial` judgements, the final ones after any re-judge, with `record_spec_verdict(slug, bindings)` and **no `results`**, one per test: `{ criterion, test: "file:line", degree: "full" }` or `{ criterion, test, degree: "partial", covered: [1, 3] }`. It never records `untestable` or `mismatch`: report an untestable criterion with its reason, and verify judges it. Without results it writes only `test-judgements.tsv` and leaves the verdict alone, so the Specs panel shows the tests now and verify only judges what changes later. It fixes each binding the tool refuses and records it again, except one refused because it changed that test itself, which it returns: leave that for verify to confirm and say so in the report. Leave a test still at `mismatch` unrecorded and say why in the report: verify judges it.
6. **Idempotency check before you finish.** Skip it when every gap was a traceability gap. Re-run the Software Factory and inspect `get_file_diffs` **before applying**. If regeneration would delete or overwrite hand-written code, either model that surface (regenerate, re-fill the body) or protect it with Intent's code-management _ignore_ directive the way it's already used elsewhere. Re-run until regeneration is idempotent (no destructive diff) and the build passes.

## Then stop

When every gap's todo is `completed` (or you've done all you can), **reply with a concise report**: which gaps you closed and the elements/files you touched for each, marking each one **trace** or **behaviour**, how you applied each disagreement answer (and every criterion you reworded), the criteria you wrote tests for with each test's file and title, the bindings you recorded, the criteria you judged untestable with each reason, and **any gap you couldn't close and why**. The orchestrator uses the trace/behaviour split to decide how much the next verify checks. Change nothing else — `tasks.md` stays exactly as implementation left it, and you do **not** record a verdict.

Then **stop**. Do not re-verify yourself and do not advance the phase — `/sdd-verify` re-judges the gaps once you finish (in a Run, `/sdd-run` dispatches it; after a chat's change, `/sdd-sync` does; otherwise the user runs it).

## Rules

- Keep the **model the source of truth**: if a fix needs structural change, adjust the model and re-run the Software Factory rather than hand-writing structural code.
- **Never touch the `tasks.md` checklist** (`complete_spec_task`) and never pass `results` to `record_spec_verdict`: bindings alone (step 5) are heal's one call to it — heal repairs; verify judges. This applies to any `coding` sub-agent you dispatch too: it has `complete_spec_task` for spec-wave work, so say in its instructions that a heal dispatch ticks nothing.
- Only use ids / slugs returned from tool responses. Never invent them.
