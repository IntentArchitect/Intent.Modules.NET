### Version 1.0.0

- New Feature: Added `MappingExtensions` template that generates `{DtoName}MappingExtensions.cs` static classes with explicit `MapTo{Name}()` and `MapTo{Name}List()` extension methods for every DTO with a `[map from]` domain mapping.
- New Feature: Generated mapping bodies handle flat primitives, nullable navigation properties (`?.`), nested DTO composition (recursive `MapTo` calls), collection projections (`Select(...).ToList()`), FK extraction from association ends, collection multi-hop paths, and explicit enum-to-enum casts.
- New Feature: Added the `Object Mapping` → `Null Path Handling` application setting, with values `Strict` (default) and `Lenient`. It decides, per nullable hop, what a mapping path does when it crosses an optional association or nullable property on its way to a non-nullable DTO field: `Strict` emits `!.` and throws `NullReferenceException` rather than returning a partially populated DTO; `Lenient` emits `?.` plus a trailing `?? default!` and returns the CLR default for that one field with every other field populated normally. A non-nullable hop is unaffected by the setting, and a nullable hop into a nullable field emits `?.` under both values.
- New Feature: Expression Mappings now recognise both Prefix Forms. `src.` is rewritten to `projectFrom.` at every occurrence in the expression (not only the leading one, so multi-reference expressions normalise correctly), an expression already in the `projectFrom.` form is left untouched, and any other form has `projectFrom.` prepended to the expression as a whole — matching `Intent.Application.Dtos.AutoMapper` byte for byte, including the cases where that is not what the author meant. The two recognised forms produce byte-identical output.
- New Feature: Call Sites. With `Intent.Application.DomainInteractions` v1.2.10-pre.0 or later installed, query handler bodies are generated to call these extension methods directly — `order.MapToOrderDto()`, `orders.MapToOrderDtoList()`, `order?.MapToOrderDto()` and `orders.MapToPagedResult(x => x.MapToOrderDto())` — and no `IMapper` is injected into any handler.
- Improvement: Collection projections now end `?? []` only when the DTO field is non-nullable. A nullable collection field ends bare, so it can carry `null` rather than being silently normalised to an empty list.
- Improvement: An unresolvable mapping source now raises an `ElementException` scoped to the DTO element, so the designer highlights the offending element, instead of a bare `System.Exception`.
- Improvement: The generated class's namespace is derived from the output structure rather than by stripping the substring `.Mappings` from the namespace, which corrupted any application with an unrelated `Mappings` path segment.
- Improvement: `MappingExtensions` template now declares an explicit `Mappings` Default Location (matching the `Intent.Application.Dtos.AutoMapper`/`Mapperly` convention) instead of relying on an implicit default. No change to generated output.
- Improvement: Removed the unused `ObjectMappingCrudFactoryExtension` scaffold stub. It was a permanent no-op with no generated output; the module has no factory extension.
- Fixed: A DTO field projecting the primary keys of a to-many association (e.g. `LineIds`) emitted code that did not compile. The guard used `GetTypeInfo(field.TypeReference).IsPrimitive`, which resolves a collection field to `List<Guid>` and reports it non-primitive, so the field fell through to the bare navigation path. Replaced with a collection-aware check. Note: `Intent.Application.Dtos.AutoMapper` carries the identical unguarded form and very likely has the same defect; it has not been fixed there.
- Breaking Change: The `CanRunTemplate()` guard that suppressed this module when `Intent.Application.Dtos.AutoMapper` was installed has been removed. Both providers can now be installed together and both will generate, with no error or warning about the other's presence. An application that relied on this module standing down will now generate two mapping implementations over the same DTOs — uninstall the provider you are migrating away from.

#### Not verified in this release

- **Cursor paging.** The offset-paged Call Site is exercised end to end; the cursor-paged equivalent is not, and is deferred. No module in this repository fulfils the `Application.Common.CursorPagedList` template role except `Intent.Modules.Azure.TableStorage`, a persistence provider that would compete with EF Core for the repository roles, so a cursor-paged query could not be modelled to test against.
- **Four expression branches.** The casing-conversion branch of `PascalCasePropertyAccesses`, the prepend-the-whole-expression branch for an unrecognised prefix form, a nullable hop inside a collection projection, and a nullable hop feeding an enum cast are implemented but exercised by no test — they rest on inspection only.
