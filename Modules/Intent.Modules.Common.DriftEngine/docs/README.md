# Intent.Common.DriftEngine

> **Pre-release.** Phase 1 of the drift engine ([plan](plan.md)): C# code, the Domain and Services designers' structure, and scope.

The drift engine checks that hand-written code still matches the model. Each modelled fact (a class exists, an attribute has this type, a class is abstract) becomes a claim, and the engine reads the code to verify it, contradict it, or say why it can't be verified. It reads code and never writes it.

## Setting scope

Nothing is checked until the model says what code to read. Apply the **Drift Scope** stereotype to the Codebase Structure designer's Root Folder (or a Folder) and add rows:

| Glob | Scope | Reason |
| --- | --- | --- |
| `src/MyApp.Domain/**` | In | |
| `src/MyApp.Domain/Migrations/**` | Out | Generated by EF Core |

- **Glob**: one or more globs, one per line, relative to the element's folder.
- **Scope**: In or Out. Every Out row needs a reason.
- **Types**: optional, on an Out row, type names to leave out of otherwise in-scope files.

The deepest element with a matching row decides, and its last matching row wins. `bin`, `obj`, `.git`, `node_modules`, hidden folders and Intent's own folders are always out.

## What it checks

- **Domain**: classes, attributes, associations (navigation properties), operations, constructors and enums. Members a class inherits count as its own, and an EF Core shadow property (`Property<int>("BuyerId")`) is an attribute's member.
- **Services**: DTOs, commands, queries, services, service proxies, enums, and each operation's return type and parameters.
- **File Config**: the file a type is declared in and its namespace, where the model sets them.
- **HTTP**: routes, verbs, parameter sources, and Secured, Unsecured and roles. Read today from ASP.NET Core: attribute routing, Minimal API endpoint mappings and their `MapGroup` prefixes, `[FromBody]`, `[FromRoute]` and the like, and `[Authorize]`, `[AllowAnonymous]`, `RequireAuthorization()` and `AllowAnonymous()`. A source ASP.NET infers without an attribute isn't stated, so a modelled one is drift.
- **Base types**: a base a house pack says the model implies, such as the SeedWork `Entity` every Class derives, checked against everything the type derives from or implements.
- **Relational databases**: an entity's table, schema, primary key and its value generation, and indexes (columns, unique, filter), and its columns' names, types, text types, max lengths, precision, scale, defaults, foreign keys and whether they're required. Read today from EF Core's fluent configuration and data annotations. A value the model states that the code doesn't state explicitly is drift, even when EF's convention would give the same result. The exceptions are what the model always marks: a key named `Id` or `<Entity>Id`, and a foreign key EF Core finds by its name (`BuyerId` for a relationship to `Buyer`).

## Extending it

The engine knows no technology, not even a language. C# is a stock language extension; what the model states (HTTP, relational) and how a framework's code states it (ASP.NET Core, EF Core) are separate extensions, so another framework, or another language, reads the same claims. A framework's extension reads only when its framework is in the code, so a project without EF Core gets no EF Core answers.

A module extends the engine with a factory extension deriving from `DriftEngineExtensionBase`, entirely in C#, with nothing it can't express:

- **What the model states** (`ClaimSources`): the module says for each element what the code must say. The engine reads the model for it (`ModelContext`): a designer's elements, the elements an association links them to, and their stereotypes. Kinds are defined in code (`Kinds`), and its own designers are named in `Designers`. JSON packs say the same thing as data, as a shortcut.
- **What the code says** (`ClaimReaders`): the engine reads the code for it, so a module brings rules, not a parser. Besides every type and member, it gives each method's calls: what each is called on, its arguments and what the code says they are (`Send(new CreateOrderCommand(...))` sends a `CreateOrderCommand`, also through a local, a field or a cast), its text and where it is, following calls into the type's own helper methods. When the code doesn't say what an argument is, the check reports it can't verify instead of guessing. A claim reader can word its own finding, with the fix.
- **Anything else**: comparers, rules over the model and the code together (such as layer imports), and code readers that add to what the engine reads.

For example, eShopCustom's Services module checks that a service operation sends the Integration Command its Perform Invocation link names. The engine gives it the operation's links and the `Send(...)` calls in its code, with what each sends; the module compares the two and words the fix.

A claim reader can say where an element's code is when the engine wouldn't find it, such as the private field a house stereotype names, in whatever form its reader keeps it, and the claims waiting on it get that. A claim can wait on any other claim, such as a column on its mapping, so one fault in the code is one finding. A module can also build on the stock EF Core reading rather than reading the configuration again.

## What it reports

Each run adds its drift to the application's drift report (Intent.Common.DriftReporting): a designer's in `Domain (DriftEngine)` or `Services (DriftEngine)`, scope and configuration problems in `Drift Scope (DriftEngine)`. The report holds only drift: an Area appears only when it has a finding. Without a Drift Scope the run only warns.

The Software Factory log says what each run checked: how many claims, against how many files, and how many were verified, contradicted or couldn't be verified, so a clean run can be told from one that checked nothing. It also lists the files left out of scope and why, and the nullability claims that code outside a nullable context can't state. None of these are drift, so they never appear in the report.
