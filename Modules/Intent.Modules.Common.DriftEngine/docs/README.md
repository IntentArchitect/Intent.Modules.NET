# Intent.Common.DriftEngine

> Phase 1 of the drift engine ([plan](plan.md)): C# (with Razor components), Java, Python, TypeScript and Protobuf code, the Domain, Services and User Interface designers' structure, scope, and the opt-in "must be modelled" rules.

The drift engine checks that hand-written code still matches the model. Each modelled fact (a class exists, an attribute has this type, a class is abstract) becomes a claim, and the engine reads the code to verify it, contradict it, or say why it can't be verified. It reads code and never writes it.

It replaces Intent.Common.Drift, the recipe-based check of the Guardrails Contracts modules. To move an application across, update Intent.Common.Drift to 2.0: the update installs this module, turns the recipe files into the Drift Scope and Drift Check rows below, and removes the Guardrails Contracts modules, keeping the code they generated. Intent.Common.Drift's README says what the update does and what the first run shows.

## Setting scope

Nothing is checked until the model says what code to read. Apply the **Drift Scope** stereotype to the Codebase Structure designer's Root Folder (or a Folder) and add rows:

| Glob | Scope | Reason |
| --- | --- | --- |
| `src/MyApp.Domain/**` | In | |
| `src/MyApp.Domain/Migrations/**` | Out | Generated by EF Core |
| `src/MyApp.Api/Program.cs` | Context | The composition root: read for what it registers, not modelled |

- **Glob**: one or more globs, one per line, relative to the element's folder.
- **Scope**: In, Out or Context. In is read and checked; Out isn't read. Context is read, so claims verify from it and rules use what it says, but nothing is reported about its own code. Every Out and Context row needs a reason.
- **Types**: optional, on an Out row, type names to leave out of otherwise in-scope files.

The deepest element with a matching row decides, and its last matching row wins. `bin`, `obj`, `.git`, `node_modules`, hidden folders, Intent's own folders and NuGet's `packages` folder (known by the `.nupkg` files in it, so a monorepo's `packages` source folder is still read) are always out.

## Code the model doesn't describe

Code the model doesn't mention isn't drift on its own, so by default nothing reports it. A team that wants every in-scope type, member or file described turns on an opt-in rule with the **Drift Check** stereotype on the Root Folder:

| List | Row | What it does |
| --- | --- | --- |
| Opt-in Rules | Rule, Glob, Description | Turns a rule on, optionally narrowed to some files: `optin/unmodelled.file`, `.type`, `.member`, `.interaction`, `.exposed`, `.value`, `.index` or `.endpoint`, or a module's own. The Description says what the row's files are (`Domain layer: entities and repositories`), and the list shows it beside the rule, so rows of the same rule over different layers can be told apart; without one, the list shows the first glob. |
| Exceptions | Rule, Match, Reason | Code a rule mustn't report: file globs, type names or `Type.Member`s, one per line, with one reason for them all. An entry that matches nothing is a warning. |
| Severity Overrides | Rule, Severity, Reason | Another severity for the findings whose rule matches (`*` matches anything): `optin/unmodelled.*` as Warning while the model catches up |

- **`unmodelled.file`**: an in-scope file in which no claim located anything.
- **`unmodelled.type`**: a type under the row's Glob, such as `Data/Model/Entities/**`, that no element describes. The row is the whole setup; a module can narrow it further with a convention's `find`, such as only a base class's subclasses.
- **`unmodelled.member`**: a public member of a modelled type, of a kind its element type can state (a Class's properties, fields, constructors and methods; a DTO's properties), that the model doesn't state. Overrides of a modelled base, `Equals`/`GetHashCode`/`ToString`, a record's primary constructor, and a modelled field's Java accessors aren't reported.
- **`unmodelled.interaction`**: a call the model's interactions could show that no link describes, such as a query of an entity with no Query Entity Action. Messages the diagram could show are already drift by default (below), so they aren't reported twice.
- **`unmodelled.exposed`**: a type an endpoint takes or returns, or one reached through its type arguments and public properties, that no element describes. The types an endpoint exposes come from a convention's `exposed` find path.
- **`unmodelled.value`**: a value the code states explicitly that the model leaves unset, such as a `ToTable` for a class with no Table Name, or a success status for an operation with none.
- **`unmodelled.index`**: an EF Core `HasIndex` that no Index describes.
- **`unmodelled.endpoint`**: a Minimal API endpoint, such as `api.MapGet("/catalogtypes", async (...) => ...)`, that no Operation describes. A controller's actions are `unmodelled.member`'s.

Each finding is an error unless an override says otherwise, and a row without a reason, or naming a rule no installed module provides, is a configuration error.

## What it checks

- **Domain**: classes, attributes, associations (navigation properties), operations, constructors, enums and their literals (in the model's order; the code may have more), domain events, value objects, domain services with their operations, data contracts (a class or record) with their attributes, and repositories with their operations, the entity each serves and a class implementing it. A repository, service or domain service is the type of its name, else the interface its language names it (`IOrderData`), and of several the one in the namespace or folder its designer folders name: a Repository `OrderData` in the folder `Shop.Sales.Data` is `Shop.Sales.Data.IOrderData`, even with an `OrderData` class elsewhere. An interface no class implements is implemented at run time by whatever the code gives it to as a type argument: a proxy library's factory (`factory.Create<IOrderQueries>()`), the code's own generic factory or a container registration (`Bind<IOrderQueries>()`). Fetching one from the container (`GetRequiredService<IOrderQueries>()`) doesn't count. Members a class inherits count as its own, and an EF Core shadow property (`Property<int>("BuyerId")`) is an attribute's member.
- **Services**: DTOs with their type parameters, commands, queries, services, service proxies, enums and their literals, and each operation's return type and parameters. An action whose return type doesn't say what it succeeds with (`IActionResult`, Web API 2's `IHttpActionResult`) returns what its success results carry (`Ok(data)`, `Content(HttpStatusCode.OK, data)`, also through `Task.FromResult`), error results aside; a stub that builds none, or a success whose value the code doesn't type, returns what its `[ResponseType]` or `[ProducesResponseType]` declares. A model may instead state the action's own result type (`IActionResult`), which is true of its signature whatever it returns. A Success Response Code is checked against the status each success result builds; an action that returns its data itself (`Task<string>`, `ActionResult<OrderDto>` returning the DTO) is sent with the framework's 200. A field whose Serialization Settings Naming Convention is Custom has its serialized name checked (`[JsonPropertyName]`, `[JsonProperty]`, `[DataMember]`, Java's `@JsonProperty` and `@SerializedName`).
- **Commands and queries**: each one's result and its handler, read from MediatR (the request's `IRequest<T>`, a command with no type being `IRequest` or `IRequest<Unit>`, and a concrete class implementing `IRequestHandler<TRequest, T>`), Mediator (`IRequest`, `ICommand` and `IQuery` with their own handler interfaces) or Wolverine (the `Handle`/`Consume` method its conventions find, whose return type is the result), through the code's own bases over them. The namespace a file imports says whether `IRequest` is MediatR's or Mediator's. A request no framework in the code handles can't be verified rather than reported.
- **Messages**: each Domain Event Origin, Publish Integration Event and Send Integration Command link, whatever the code raises it through (`AddDomainEvent`, an outbox, a bus or a wrapper of its own): the constructor, operation, command handler or event handler hands the message on, one it creates or a value the code types as it (a local an awaited call gives, a property of what a call returns), itself or in a method of its class or of a collaborator it calls. A method of the code that only reads a message it is given processes it in place, and a method that returns the message builds it for its caller; neither raises it. The other direction is checked by default, with no Drift Check row, wherever the diagram could show it: a domain event, integration event or command type in the code must be modelled, and a raise of one needs its link when it's in, or called from, a modelled constructor, operation, command or handler, a method of a modelled class or service, or a handler of a modelled message. A raise from code the diagram can't show, such as a background router, isn't drift. The messages are the modelled ones and any type sharing what they all derive from or implement (`INotification`, an `IntegrationEvent` base).
- **HTTP**: whether each operation of an HTTP service is an endpoint (one without Http Settings states it isn't, so a controller action or mapped handler for it is drift), routes, verbs, each parameter's source, type, nullability and default, API versions (the service's and each operation's Api Version Settings, and whether the version is in the route), and each operation's security: Secured or Unsecured on the operation, else on its service, with Secured's roles (its Roles or its Security Roles) and policy. Read from ASP.NET Core and ASP.NET Web API 2: attribute routing (`[Route]`, and Web API's `[RoutePrefix]`), Minimal API endpoint mappings (`MapMethods` with one verb included), lambda handlers included (named by `.WithName`, or matched by verb and route; one that doesn't write its return type returns what its body returns: a success result's payload, a value's type, or an EF Core query's list), and their `MapGroup` prefixes; Web API 2's verb from an unattributed action's name (`GetOrders` is GET), and its route from the conventional `MapHttpRoute` template rather than the controller's `[RoutePrefix]` (an Operation whose empty Route puts it under its service's Route is reported); a parameter's source from `[FromBody]`, `[FromRoute]` and the like, or, without one, where ASP.NET binds it (a name in the route template is the route, a simple type the query string, any other type the body, a class the code registers with the container injected); and `[Authorize]` (or an attribute of the code's own deriving from it, roles given as constants by their value, and policies), `[AllowAnonymous]`, `RequireAuthorization()` and `AllowAnonymous()`, on controllers and gRPC services alike, where `[AllowAnonymous]` anywhere wins; API versions from Asp.Versioning's `[ApiVersion]`, `[MapToApiVersion]` and `HasApiVersion`. Roles or a policy the code doesn't give as a value can't be verified. A file result (`FileStreamHttpResult`) returns a `Stream`. Read from Spring MVC: a Service is its `@RestController` (`OrdersService` is `OrdersController`), with `@RequestMapping` and `@GetMapping`-style mappings, `@PathVariable`, `@RequestParam`, `@RequestBody` and `@RequestHeader`, and `@PreAuthorize`, `@Secured`, `@RolesAllowed` and `@PermitAll`. Spring MVC's source is its annotation; a parameter left at Default isn't checked. A Service, Domain Service or Repository is the type of its name, else the interface its language names it (`IPricingService`, which `TieredPricingService` implements), and that interface's classes are its code too. A `ResponseEntity<Object>` doesn't say what it returns, so its return type can't be verified.
- **User Interface (the standard designer 2.0.0)**: pages, dialogs, layouts, components, stores, UI services, utilities, behaviours, proxies, contracts and enums, read from Vue and React (and Blazor, below). Each is where its Implementation Path says, else where its designer folders and name put it, and its Owned Files must exist. A store is a Pinia `defineStore`, a Redux Toolkit `createSlice` or a Zustand store (`use{Name}Store`), with its state and actions; a service, utility or proxy is a TypeScript or JavaScript file named for it. A Vue page is a component a vue-router route record mounts, with its route (`/products/:id` is `/products/{id}`), and a layout hosts a `<RouterView>`; Properties are props or state, Event Emitters emits, operations functions; Composition is the child's tag in the template, and Navigation a `<RouterLink to>` or `router.push` to the target page's route. A React component is a function component (also through `memo` or `forwardRef`) or a class component, in `.tsx`, `.jsx` or `.js`; a page is one a react-router route mounts, as a route object (`createBrowserRouter`, `useRoutes`, with `element`, `Component` or `lazy`) or a `<Route>` element, nested routes joined, and a layout renders an `<Outlet />`; Properties are props or `useState` state, Event Emitters `on...` callback props, operations the functions it declares, a route parameter what it reads from `useParams()`, a query parameter what it gets from `useSearchParams()`, and a bindable Property one with an `on{Name}Change` callback; its title is a rendered `<title>` or `document.title`; Composition is the child's tag in its JSX, Navigation a `<Link>`, `<NavLink>` or `<Navigate>` `to`, a `navigate(...)` or a route `loader`'s `redirect(...)`. A route its file's path gives (Next.js, Remix) isn't read, so a page there has no rule. In both, Uses is a value import, and a Call Service Operation Action a call of the proxy's method, from the caller's code (hooks and handlers included) or the code it calls. From a Proxy Operation, the action's backend Operation (or the HTTP Request stereotype) gives the verb and route the operation's `fetch`, axios (an `axios.create()` instance included) or `HttpClient` request must send, read through the code's own request helpers, the base URL dropped. A house designer gets the same reading by claiming these kinds on its own elements, with the same bindings, in a pack that requires `intent.ui`.
- **User Interface (the 1.x designer)**: components, layouts, model definitions and service proxies, read from Blazor. A Component with the Page stereotype is a page (`@page`), with its routes (`/` and parameter names don't matter, so `/orders/{id:int}` is `orders/{id}`) and title (`<PageTitle>`); a Layout derives `LayoutComponentBase`; any other component has neither. A component's Secured or Unsecured stereotype is its `[Authorize]` or `[AllowAnonymous]`, with roles and policy. Its properties and event emitters are `[Parameter]`s (an emitter an `EventCallback<T>`), with `[Query Parameter]` as `[SupplyParameterFromQuery]`, `[Route Parameter]` as a `{Name}` in a route and `[Bindable]` as a `{Name}Changed` callback. Its links: a Composition or a layout's Display Component is a tag of the child in its markup; a Navigation an `href`, form `action` or `NavigateTo` to the page's route, a value in it standing for a route parameter, through the code's own URL helpers; a Show Dialog a `Show` or `Open` of the dialog; and a Call Service Operation Action a call of the operation on the proxy, made by the component or by the code it calls (`CartPage` calls `BasketState`, which calls `BasketService`), including methods it hands on to be called and the constructors of what it creates. A component's `.razor` and `.razor.cs` are one component.
- **Service proxies**: each operation's request, read from the proxy's own method and the methods of its type it calls: an `HttpClient` verb method (`GetFromJsonAsync`, `PostAsJsonAsync` and the like) or `SendAsync` with an `HttpRequestMessage`, with its verb, its route (the URI the code builds, without its query string), its API version (`api-version=` in the query, or `AddApiVersion` on the proxy's `AddHttpClient<T>()`) and its headers (`Headers.Add`); or a generated gRPC client's call, with its RPC and service.
- **Base types**: a base a house pack says the model implies, such as the SeedWork `Entity` every Class derives, checked against everything the type derives from or implements.
- **Relational databases**: whether anything maps a Table or View class at all (a DbContext's `DbSet`, `Entity<T>` or applied configuration, a mapped entity's navigation to it, or JPA's `@Entity`; a class nothing maps is one finding, its other checks waiting on it), an entity's table, schema, primary key and its value generation, the multiplicity of an association end no navigation property states, and indexes (columns, unique, filter, and the index's own name when Use Default Name is off: an Index element, or the Index stereotypes on its attributes and on the association ends whose foreign key column is in its table, one index per UniqueKey), and its columns' names, types, text types, max lengths, precision, scale, defaults (a SQL expression default as `HasDefaultValueSql`), foreign keys and whether they're required; an attribute isn't ignored (`Ignore`, `[NotMapped]`), and a Value Object attribute is owned (`OwnsOne`); and an association's navigability where the model leaves an end unnavigable, and a JPA join column. Read from EF Core's fluent configuration and data annotations (Entity Framework 6's too: its `IDbSet`, its `HasRequired`/`HasOptional` relationships, and `[Table]`; a `[Table]` class no DbContext maps is reported, as EF never reads or writes its table), and from JPA's annotations (`@Table` and its indexes and unique constraints, `@Id`, `@Column`, `@GeneratedValue`). A value the model states that the code doesn't state explicitly is drift, even when the framework's convention would give the same result. The exceptions are what the model always marks: a key named `Id` or `<Entity>Id`, and a foreign key EF Core finds by its name (`BuyerId` for a relationship to `Buyer`).
- **Razor components**: a `.razor` file is read as the C# the Razor compiler generates for it, so a component and its code-behind (`X.razor.cs`) are one type: `@page` routes and `@attribute`s are its attributes, `@inherits` and `@implements` its bases, `@inject` a property, and `@code` its members, with what they call. Its `@using`s and those of the `_Imports.razor` files above it are its imports, and each fact points at the line it is written on.
- **Markup**: a Razor component's markup, a Vue component's template and JSX are read the same way, as each framework's compiler parses them: elements with their attributes, the component a tag names (resolved through the file's imports, as the framework resolves it), directives such as `@onclick`, `@bind-Value`, `:to` and `@click` split into directive, argument and modifiers, and an element's text and an attribute's value as literals with the code in them as holes (`href="/orders/@id"`, `` to={`/orders/${id}`} ``). So a check can ask what a page renders, links to or titles itself, in any of them.
- **TypeScript, JavaScript, Vue and React**: `.ts`, `.tsx`, `.js`, `.jsx` and Vue single-file components' scripts are read with TypeScript's own parser, on Intent Architect's own Node.js, so nothing needs installing. Interfaces, type aliases, classes and enums are types; a module's functions and variables, and a `const` holding an object literal, are types too, so a module's API client is checked like a class; a Vue component has its props, emits and `<script setup>` members, and its template is its markup; a React component, several to a file if need be, has its props, state and functions, and its JSX is its markup. Imports resolve through relative paths and `tsconfig.json`'s or `jsconfig.json`'s `paths` and `baseUrl`, and a type's nullability is checked only under `strict` or `strictNullChecks`. JavaScript states no types, so a type check of it has nothing to compare; a minified `.min.js` isn't read.
- **Protobuf**: `.proto` files (proto2, proto3 and editions) are read with a parser of their own grammar, so no `protoc` is needed. Messages, enums and gRPC services are types; a field is a property with its number, `repeated` a collection and `map<K, V>` a map; an rpc is a method taking its request, with a streamed side as `stream` of its message; options are annotations. A field is nullable when it can be left unset: `optional`, in a `oneof`, or a message, such as `google.protobuf.Int32Value`. A model's field names are written as protoc writes them (`ProductId` is `product_id`), a message is a DTO's class or record, and a DTO with the Proto Message stereotype is the `.proto` message of its name even where a C# type shares it.
- **Python**: `.py` files and `.pyi` stubs are read with the engine's own parser (Python 3.13's syntax, `match`, type parameters and f-strings included), so no Python is needed. A file's module name comes from its packages (`__init__.py`) and what the code imports, so a `src/` layout and namespace packages work. Classes are types (a `Protocol` an interface, an `Enum` an enum, a `type` alias a type alias), and a module's functions and variables are a type of their own, as TypeScript's are. A class's annotated attributes and what `__init__` assigns to `self` are its fields, `@property` methods its properties, `__init__` its constructor and `self` no parameter. The profile names a model's members in snake case (`QuantityOnHand` is `quantity_on_hand`). An annotation states nullability as a type checker reads it: `Optional[T]` and `T | None` can be `None`, any other type can't, and `Any` doesn't say. Python has no `new`, so a call to a class the code declares or imports, or to a CapWords name, is a creation; keyword arguments are named. A serialized name is Pydantic's `Field(serialization_alias=...)` or `Field(alias=...)`, marshmallow's `data_key` or msgspec's `field(name=...)`.
- **Nullability in Java**: Java doesn't say whether a reference is nullable, so it is checked only where the code states it: a primitive isn't, a boxed type or `Optional` is, `@Nullable` and `@NonNull` (and their kin) say so, and a JPA entity's `@Id`, `@Column(nullable)` and `@ManyToOne(optional)` state its columns'.

## Extending it

The engine knows no technology, not even a language. C# (Razor components included), Java, Python, TypeScript and Protobuf are stock language extensions; what the model states (HTTP, relational) and how a framework's code states it (ASP.NET Core and Spring MVC, EF Core and JPA) are separate extensions, so another framework, or another language, reads the same claims. A framework's extension reads only when its framework is in the code, so a project without EF Core gets no EF Core answers.

A module extends the engine with a factory extension deriving from `DriftEngineExtensionBase`, entirely in C#, with nothing it can't express:

- **What the model states** (`ClaimSources`): the module says for each element what the code must say. The engine reads the model for it (`ModelContext`): a designer's elements, the elements an association links them to, and their stereotypes. Kinds are defined in code (`Kinds`), and its own designers are named in `Designers`. JSON packs say the same thing as data, as a shortcut.
- **What the code says** (`ClaimReaders`): the engine reads the code for it, so a module brings rules, not a parser. Besides every type and member, it gives each method's calls: what each is called on, its arguments and what the code says they are (`Send(new CreateOrderCommand(...))` sends a `CreateOrderCommand`, also through a local, a field, a cast or what a called method returns, and a message the method a link starts from takes as a parameter and hands to code that sends it), a literal argument's value whatever its quoting (`"Orders"`, the text and holes of `$"orders/{id}"`, `typeof(Order)` or `Order.class`), the type arguments it passes (`AddScoped<IOrders, Orders>()`), what each `new` is given, its initializer included, and which creation a value is, even through a local, each lambda and Program.cs's top-level statements as a unit with its own parameters, calls, assignments and returns, the method it reaches, even on another type, its text and where it is, following calls into the type's own helper methods, a component's markup (`CodeGraph.MarkupOf`), and the string a value builds (`CodeGraph.StringOf`): `GetFromJsonAsync(uri)` after `var uri = $"{baseUrl}items/{id}";` is `api/catalog/items/` with `id` as a hole, through fields, constants, `+`, trims and the code's own helper methods with their arguments bound, in C# and TypeScript. A method passed as a value (`this::audit`, `items.ForEach(Audit)`) counts as a call to it. When the code doesn't say what an argument is, the check reports it can't verify instead of guessing. A claim reader can word its own finding, with the fix.
- **A language** (`Languages`): one the engine doesn't read, or its own reader for a stock one, which replaces it. Its profile, how it names and wraps the model's members, comes in a pack.
- **Anything else**: comparers, rules over the model and the code together (such as layer imports), and code readers that add to what the engine reads. A rule's finding about a Context file isn't reported.
- **House checks are C#.** A kind a house's own stereotypes state, such as a concurrency token, enum storage, a HiLo sequence, a backing field, a delete behaviour, a file's location, a registration, a validator or an identified command, is read by a claim reader in the house's module; its pack only says what the model states. A module's reader is asked before the stock ones, so it can also take over a stock reading for the claims it reads and leave the rest. A module's rule (`IDriftRule`) with a stock rule's id replaces it, and the Software Factory log says so.
- **Code the model doesn't describe** (`OptInRules`): a rule that only finds such code, by what the claims located (`RuleContext.IsLocated`). The engine does the rest as it does for its own: it runs the rule only when a Drift Check row turns it on, and applies the row's glob, Context, the exceptions and the severity overrides.

For example, eShopCustom's Services module checks that a service operation sends the Integration Command its Perform Invocation link names. The engine gives it the operation's links and the `Send(...)` calls in its code, with what each sends; the module compares the two and words the fix.

A claim reader or rule can give, with a finding the code settles, the model change that settles it (`ClaimReading.Correcting`, `Finding.Corrections`): a link to draw or remove, a stereotype's properties to set, a stale exception to drop. The stock extensions give them for unshown sends and publishes, links the code never bears out, an action's Http Settings and Web API 2's conventional routes. Intent.Common.Drift's move from v1 applies them. They aren't shown in the report.

A claim reader can say where an element's code is when the engine wouldn't find it, such as the private field a house stereotype names, in whatever form its reader keeps it, and the claims waiting on it get that. A claim can wait on any other claim, such as a column on its mapping, so one fault in the code is one finding. A module can also build on the stock EF Core reading rather than reading the configuration again.

When the house's own code changes what a framework's reading should see, a module refines the method instead of reading the claim itself (`Refiners`). The Java eShop parses a query string into an enum with its own `Http.parseEnum(OrderStatus.class, status, "status")` and responds through `Http.created(body)`; its module gives the handler with `status` as an `OrderStatus` and the response holding what `created` is given, and the stock Spring MVC reading compares the parameters and the return type as usual.

## What it reports

Each run adds its drift to the application's drift report (Intent.Common.DriftReporting): a designer's in `Domain (DriftEngine)`, `Services (DriftEngine)` or `User Interface (DriftEngine)`, scope and configuration problems in `Drift Scope (DriftEngine)`. The report holds only drift: an Area appears only when it has a finding. Without a Drift Scope the run only warns.

Each run also links every element to its code for Intent Architect's **View Code** and **Open in IDE**, and for **Changes Review**, which counts a changed line covered by a link as verified. So an element is linked only to the code its checks verified: a class to its declaration without its members, each member to its own declaration, an association to its navigations and the `HasOne(...).WithMany(...)` and `HasForeignKey(...)` that configure it, and an attribute to its EF Core configuration too. No line holding drift, or code the model doesn't describe, such as an unmodelled method inside a modelled class, is linked to anything. An element whose code holds drift is linked to its file instead, so View Code still opens it, with no lines counted as verified. The links are written to `.intent/model-links.json` on every run, which needs Intent Architect 5.4.2 or later.

The Software Factory log says what each run checked: how many claims, against how many files, how many were verified, contradicted or couldn't be verified, and how many elements were linked to their code, so a clean run can be told from one that checked nothing. It also lists the files left out of scope and why, and the nullability claims the code can't state (C# outside a nullable context, an unannotated Java reference, TypeScript without `strict`), with how to make them checkable, and how long the run took: reading the model, each language and code reader, building and reading the claims (with the slowest kinds), the rules and the opt-in rules. None of these are drift, so they never appear in the report.
