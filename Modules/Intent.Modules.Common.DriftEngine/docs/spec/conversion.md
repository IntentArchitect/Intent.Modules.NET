# Conversion from Common.Drift

Phase 6 maps every Common.Drift recipe file onto the engine ([R55](requirements.md)), and runs both engines side by side ([R57](requirements.md)). The engine has no recipes (user decision, 2026-11-16: a JSON way of reading code beside C# claim readers was a second system to learn and choose between). So a recipe isn't copied: the fact it reads is the stock reader's, where one reads its kind, and otherwise a claim reader in the house's module. This document fixes what each construct becomes, and which verdicts change and why. The acceptance suite's conversion test keeps it complete: it reads the real recipe files and fails on any construct this map doesn't cover.

The conversion is Intent.Common.Drift 2.0's migration (user decision, 2026-11-23: updating Common.Drift is the whole move). It writes the rows itself, on the first Codebase Structure package's Root Folder, unless the application already has a Drift Scope or Drift Check, and logs each one ([R56](requirements.md)). Its tests read the same five codebases' recipe files.

## What converts into what

| Common.Drift                          | DriftEngine                                                                                                                                                                               |
| ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `guardrails/<designer>.drift.json`    | Nothing of its own: its facts, `own` entries and exceptions each go as below. The migration deletes it                                                                                    |
| The code v1 checked                   | One scope `In` row for `**`: v1 checked code wherever its recipes' finds reached, so top-level `files` don't bound it (user decision, 2026-11-23). Last, one `Out` row for each project (a folder with a `.csproj`) no recipe's `files`, fact's `files`, `own` entry's `files` or contract file reached, which v1 never read (2026-11-25); one `Out` row for the code inside projects v1 read that it never read and that copies a modelled type (the highest such folder holding no file v1 read, else the file); and one `Context` row for the files those rows take out that declare a modelled type nothing in scope declares |
| `facts.<kind>`                        | Nothing: the kind's stock reader reads it by name, or, where none does, it is `noRule` until the house's module reads it                                                                  |
| `own` entries                         | An `optin/unmodelled.type` Opt-in Rules row each, over the entry's `files` (else its recipe file's, else `**/*.cs`), with its `kind` as the Description. Rows with the same globs merge. Exceptions keep each to what its find matched (below) |
| v1's always-on unmodelled members     | One `optin/unmodelled.member` row over `**/*.cs`, where there is a Domain or Services recipe                                                                                               |
| A file-pattern exception              | A scope `Context` row, with the exception's reason: v1's exception covered only the file's unmodelled code, so the model's claims about it are still checked (user decision, 2026-11-25) |
| A type or `Type.Member` exception     | An `Exceptions` row for `optin/unmodelled.type` or `optin/unmodelled.member`, one row per reason                                                                                          |
| An exception naming an `own` finding  | Nothing: that `own` entry gets no row, and the migration says so                                                                                                                          |
| `note`, `//` comments                 | Dropped; they stay in git history                                                                                                                                                         |

Conventions are globs only (user decision, 2026-11-16), so an `own` entry's find, placeholder filters and regular expressions don't carry over: the row reports every unmodelled type in its globs. So the migration keeps the rows to what v1 reported on the code as it is (user decision, 2026-11-24: "Except what v1 skipped"): it runs each `own` find on the C# code, and writes an Exceptions row, one per reason, for each unmodelled type in a row's globs that no find matched, each one a find matched in a file v1 generated a modelled type into (which v1 counted as modelled), and each public field of a modelled type, which v1 never reported. A type a find matched that v1 reported stays reported, and a type added later is reported as the glob says. "Unmodelled" is as the engine locates types: a type of an element's name, a Service's, Repository's or Domain Service's interface when no type has its name, the classes implementing that interface, and every located class's interfaces.

## What the migration decides for the model

- **Recipes that re-derive a convention.** ClientA's `table.name` read the `DbSet` property's name when there is no `ToTable`. The stock reader reads only what the code states (decision 4), so the migration clears a Class's Table Name when the code has no `ToTable`, `ToView` or `[Table]` for the entity and the name is its `DbSet` property's or class's, which EF Core uses anyway (user decision, 2026-11-24). Any other Table Name stays, and is contradicted. A table statement whose entity the migration can't tell clears nothing.
- **A v1 model's own form.** Common.Drift's contract was the signature, so a v1 model states an action's own result type (`IActionResult`), and its reverse engineering stated a 200 for an action returning its data itself. The engine verifies both (claim catalog, `operation.returns` and `operation.status`), so the migration changes neither.
- **What v1's recipes passed and the code doesn't bear out (user decision, 2026-11-25).** A recipe could verify a link because the code creates its message, put an unrouted Web API 2 action at its controller's route, or leave out the Http Settings of overloads it couldn't tell apart. v1 never looked for a send the diagram leaves out. The migration runs the engine on the moved model and applies each finding's model correction (`Finding.Corrections`, given only where the code settles it): it adds the link, removes the link, applies the Http Settings or sets the Route. Then it drops the converted exceptions the engine says match nothing. This qualifies change 13: the verdict still follows the reader, and the move then brings the model into line with it.

## What the migration can't decide

The first Software Factory run after the migration shows these as findings, for the developer to resolve:

- **A model element the code lacks.** v1's contract templates would have written it, so v1 showed it as a pending change; nothing generates it now, so it is drift (change 4).
- **Code v1 never read, in a project v1 read.** The `**` In row brings in everything under the output folder that isn't always out, and the migration's Out rows take out only whole projects v1 never read and the code that copies modelled types; within a project v1 read, other files no recipe reached are in, and the developer narrows them with Out rows, or models what they find.
- **Globs the engine's matcher can't take.** Braces are expanded; anything else is written as it is, so the run reports it as `config/glob` rather than the migration changing its meaning.
- **Exceptions that hide claims.** None of the 25 do; Common.Drift never let them. A converted exception that matches no opt-in finding is removed by the migration (above).
- **A finding whose fix is a judgement.** Modelling an unmodelled message or operation, or choosing between registering a `[Table]` class and removing its Table stereotype, carries no correction, so it stays a finding.

## The migration's output

1. Rows on the first Codebase Structure package's Root Folder: a Drift Scope with the `**` In row, the Context rows, the Out rows for projects v1 never read and for code that copies modelled types, and the Context row for modelled types only that code declares, and a Drift Check with the opt-in rows and exceptions.
2. The model corrections the engine's reading settles.
3. A line in the install's output for each row, each correction with the finding behind it, each note (an `own` entry dropped for an exception naming its finding, a recipe file that won't parse), and each contract file it released.

The facts no stock reader reads aren't listed: they are `noRule` findings on the first run.

## The conversion test (phase 0)

The suite's conversion test ([acceptance-suite.md](acceptance-suite.md#what-runs-now)) reads the five codebases' recipe files from their local paths, skipping any that isn't present, and checks that every construct each uses appears in `Acceptance/conversion-map.json` with one of the dispositions above. A construct the map lacks fails the test, so a new recipe feature can't arrive without this document saying what it becomes. Common.Drift's `RecipeConversionTests` convert the same files and check the rows each gives. ClientB's recipe files are read in place and never copied into the repository.
