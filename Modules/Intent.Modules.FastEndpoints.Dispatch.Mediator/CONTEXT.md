# Context: Intent.FastEndpoints.Dispatch.Mediator

## Purpose

Makes the FastEndpoints endpoints generated by `Intent.FastEndpoints` dispatch Commands and Queries through Mediator's
`ISender`. A satellite of `Intent.Application.Mediator` (plan: `intent/.plans/2026-10-13-mediator-dispatch-modules.mdx`,
decisions G1, G2, G5, G11). It is a port of `Intent.FastEndpoints.Dispatch.Wolverine`; only the injected type, the call and a
metadata tag differ.

## Architectural Decisions

- **Ported from the Wolverine dispatch module; the only changes are the type, the call and the tag.** The injected type is
  `Mediator.ISender` (field `_sender`), the call is `await _sender.Send(req, ct)`, and the dispatch statement is tagged
  `mediator-dispatch` metadata (plan, "Dispatch modules").
- **No type argument on `Send`.** Mediator's `ICommand`, `ICommand<T>` and `IQuery<T>` resolve through the same
  `ISender.Send` overloads, so the response type is inferred. Wolverine needs `InvokeAsync<T>` for a typed result; do not copy
  that shape back.
- **The module replaces the `EndpointTemplate` registration.** `EndpointTemplateRegistration` registers `EndpointTemplate.TemplateId`
  itself, building `MediatorEndpointModel`s for every Command and Query with HTTP settings. `MediatorEndpointExtension`
  only touches templates whose model is `MediatorEndpointModel`.
- **One class per operation, not per folder.** FastEndpoints' own convention is one endpoint class per operation, so the
  container model groups by parent element for naming but yields a separate endpoint per element. Do not turn this into a
  controller-style grouping.
- **String ids, no reference to the core.** This module has no project reference to `Intent.Modules.Application.Mediator`
  (G11: each module owns its seam; dispatch modules use string ids). It needs the core only at generation and compile time
  of the application, through the `Mediator` package the core adds.
- **Constructor injection with a guard.** `ISender` is injected in the endpoint constructor with an `ArgumentNullException`
  guard, as in every other dispatch module of the family; not `[FromServices]` on `HandleAsync`.
- **Priority 2 `OnBuild`.** The dispatch statements are added after the base `EndpointTemplate` has built the class and the
  `handle` method (priorities 0-1).

## Invariants & Constraints

- **Mutually exclusive with `Intent.FastEndpoints.Dispatch.Wolverine` and `Intent.FastEndpoints.Dispatch.MediatR`.** All
  three replace FastEndpoints' `EndpointTemplate` registration for the same Commands and Queries, so installing more than
  one produces conflicting endpoint files. Documented in the README, deliberately not guarded by a `FriendlyException` (G3:
  coexistence is documented only).
- **The imodspec must declare `Intent.Application.Mediator`.** The generated endpoint calls `Mediator.ISender` and sends the
  core's `ICommand`/`IQuery` types; none of the other declared dependencies bring them in, so without the entry an install
  of this module alone succeeds and the application then fails to compile. The entry was added by hand (see the dependency
  decision below).
- **`mediator-dispatch` metadata is a contract.** Other modules may look the dispatch statement up by that key.

## Module Interactions

- **Intent.FastEndpoints** - supplies `EndpointTemplate`, `IEndpointModel` and the `handle` method metadata the extension
  hooks. Built against `Intent.FastEndpoints` `1.2.1`.
- **Intent.Application.Mediator** - written against `1.0.0-pre.0`, declared at `1.0.0-pre.1` to keep the family's
  versions together. Its imodspec interoperability installs this module when
  `Intent.FastEndpoints` is detected.
- **Intent.FastEndpoints.Dispatch.Wolverine / .MediatR** - siblings; mutually exclusive (above).

## Dependency Decision: why the core is declared here

`Intent.AspNetCore.Controllers.Dispatch.Mediator` declared `Intent.Application.Mediator` and this module did not. Both were
made to declare it. Reasoning:

- The core is a real requirement, not a heuristic gap: it is the only source of `Mediator.ISender`, the command and query
  types and the handlers the endpoint dispatches to, and nothing else in the dependency list reaches it.
- The audit rule is to care about referenced-but-undeclared dependencies, and dependency entries are added if absent and
  never pruned, so a hand-added entry is durable.
- The existing counterparts are inconsistent: Controllers.Dispatch.Wolverine and FastEndpoints.Dispatch.MediatR declare their
  core, FastEndpoints.Dispatch.Wolverine does not (despite a project reference to its core and a README that lists it as a
  prerequisite). The declaring form is the correct one.
- Circularity is not a problem: the core's interoperability installs the dispatch module, and the dispatch module's
  dependency pulls the core; the Controllers module already works this way.

The source-level fix (install the core in this module's own application so the Software Factory detects it) was not available:
module installation in the authoring environment was failing.
