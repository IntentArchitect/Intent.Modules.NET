# Context: Intent.AspNetCore.Identity

## Purpose
Introduces ASP.NET Core Identity for user authentication and account management using Entity Framework Core, including the IdentityUser/IdentityRole/etc. domain classes and DbContext wiring.

## Architectural Decisions
- **Identity classes are stubbed, not generated.** `IdentityUser<T>`, `IdentityRole<T>`, `IdentityUserClaim<T>`, `IdentityUserLogin<T>`, `IdentityUserRole<T>`, `IdentityRoleClaim<T>`, `IdentityUserToken<T>` are modelled as Domain classes in the referenced `Intent.AspNetCore.Identity.Domain` package purely so consumer entities can generalize from them and so type resolution works, but no file is ever generated for them — they resolve to the real `Microsoft.AspNetCore.Identity.*` framework types instead. `MockTemplateRegistrations/DomainEntityTemplateStubRegistration.cs` and `EntityTypeConfigurationTemplateStubRegistration.cs` implement this by re-registering `Intent.Modules.Entities`'/`Intent.Modules.EntityFrameworkCore`'s own template registrations against these classes, forcing the namespace to `Microsoft.AspNetCore.Identity`, and setting `CanRun = false` so the template instance exists (for role/type resolution and CRUD inspection) but writes nothing to disk.

## Invariants & Constraints
- **Every entity-template role that `Intent.Modules.Entities` fulfils for a normal domain entity must have a matching stub registration here for the Identity classes, or any consumer entity that generalizes from one of them will fail at Software Factory time.** This was missed for the `Domain.Entity.State` role when `Intent.Entities` 5.3.2 changed `DomainEntityStateTemplatePartial` to resolve its parent's base type via a live template instance (`GetTemplate(role, parent)`) instead of by name — the previous name-based resolution never needed a template instance to exist, so the missing stub went unnoticed until a consumer entity actually generalized from `IdentityUser<T>` with "Separate State from Behaviour" enabled. `MockTemplateRegistrations/DomainEntityStateTemplateStubRegistration.cs` is the fix; it fulfils both `Domain.Entity.State` and `Domain.Entity` (the state template calls `FulfillsRole(TemplateRoles.Domain.Entity.Primary)`, i.e. `"Domain.Entity"`, unconditionally in its constructor), which also incidentally unblocks `Intent.Modules.EntityFrameworkCore`'s `EntityTypeConfigurationTemplatePartial`, which tries `Domain.Entity.State` then falls back to `Domain.Entity` for the same parent lookup.
- **Any new `Domain.Entity.State`-style stub registration must gate on the "Separate State from Behaviour" setting itself, returning no models when it is off.** With the setting off, the existing behaviour stub alone fulfils `Domain.Entity` for the Identity classes; a second stub producing instances at the same time would make role resolution ambiguous for the same model and break the merged-state Identity path.

## Module Interactions
- **Intent.Modules.Entities** — this module re-registers `DomainEntityTemplateRegistration` and (as of this change) `DomainEntityStateTemplateRegistration` for its own referenced Identity classes; any new entity-template role Entities introduces is a candidate for a new stub here.
- **Intent.Modules.EntityFrameworkCore** — this module re-registers `EntityTypeConfigurationTemplateRegistration` the same way (`EntityTypeConfigurationTemplateStubRegistration.cs`), and `FactoryExtensions/IdentityUserFactoryExtension.cs`'s `DbContextFactoryExtension` strips the generated `DbSet<IdentityX>` properties and configuration-apply statements from the consumer's DbContext.
- **Intent.AspNetCore.IdentityService** — creates the consumer's concrete Identity user class (e.g. `ApplicationIdentityUser`) via install/version migrations, generalizing it from this module's `IdentityUser<T>` stub, and rewrites that class's EF `HasBaseType` call by matching `ClassModel.ParentClass.Name` against the seven Identity class names.
