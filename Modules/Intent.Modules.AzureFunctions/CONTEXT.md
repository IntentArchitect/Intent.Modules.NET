# Context: Intent.AzureFunctions

## Purpose

Lets Services designer elements (Operations, Commands, Queries, Azure Function elements) be exposed as Azure Functions via the `Azure Function` stereotype, and generates the function class for each. The trigger (HTTP, Service Bus, Queue, Timer, etc.) is chosen per element and rendered by a trigger strategy under `Templates/AzureFunctionClass/TriggerStrategies`.

## Architectural Decisions

- **New `IAzureFunctionModel` members use default interface implementations.** `IAzureFunctionModel` is implemented outside this module by `Intent.AzureFunctions.Dispatch.Services` (`ServiceOperationAzureFunctionModel`) and `Intent.AzureFunctions.Dispatch.MediatR` (`CqrsAzureFunctionModel`). Those modules are versioned and published separately and only pin a minimum version of this one, so a consumer can run a newer Intent.AzureFunctions with an older dispatch module. Adding an abstract member would make those older implementers fail to load during the Software Factory run. `SubscriptionName` was therefore added as a default member that reads the `Azure Function` stereotype directly (all implementers expose `IHasStereotypes`). Rejected: adding an abstract member and bumping both dispatch modules plus their minimum-version floors — more modules to release, and still broken for anyone who updates only this module. Verified: published Dispatch.Services 5.0.6 and Dispatch.MediatR 2.0.5 generate topic triggers correctly against 5.0.27-pre.0.
- **A topic subscription is signalled by `Subscription Name` alone.** When it is set, the Service Bus trigger emits the `(topicName, subscriptionName)` form and `Queue Name` is the topic name. When it is blank, output is the queue form, unchanged from before the property existed. Rejected: a separate Queue/Topic selector — it adds a second property that must agree with the first, and a blank subscription already means "queue" unambiguously.

## Invariants & Constraints

- **Trigger names are literal unless the app opts in.** By default trigger values are written verbatim into the attribute (users can still hand-enter `%Setting:Key%`). The `Trigger Names From App Settings` module setting, default off, switches them to `%AzureFunctions:{FunctionName}:{Part}%` references and seeds `local.settings.json` with the modelled values. All handlers go through `TriggerStrategies/TriggerAppSettings`; a new trigger strategy should use it rather than emit literals directly. It must stay opt-in with a false default: an unset module setting takes its default, so defaulting it on would change every existing app on upgrade, and `local.settings.json` is not deployed, so Function Apps without the settings would stop binding those triggers. Keys use the `[Function]` name (`AzureFunctionClassTemplate.GetFunctionName()`), so they are unique per app and follow `Simple Function Names`. They deliberately avoid the Eventing `AzureServiceBus:{MessageName}` keys, which could collide with an Eventing message of the same name pointing at a different entity. Values already written as `%...%` are emitted unchanged and never seeded.
- **Only properties confirmed to resolve `%...%` are converted.** Service Bus queue/topic/subscription and RabbitMQ queue were confirmed in the extensions' binding providers (`ResolveWholeString`); Storage Queue queue, Event Hub name, Cosmos DB database/container and the Timer schedule are documented by Microsoft. Cosmos DB lease database/container/prefix are deliberately left literal because resolution could not be confirmed. Queue Output Binding names are out of scope (an output binding, possibly several per function, so per-function keys don't fit). Connection properties are always app setting names already; when opted in they are seeded with an empty value, except Storage Queue and RabbitMQ, which keep seeding their existing local defaults.
- **The setting was renamed before release.** It shipped in no published version as `Service Bus Trigger Names From App Settings`; the id (`20b1fcbd-…`) is unchanged, so nothing migrates.
- **Service Bus triggers on service operations are not registered with the shared Azure Service Bus IaC registry** (`Intent.Modules.Integration.IaC.Shared.AzureServiceBus`). Only Eventing-designer subscriptions handled by `Intent.AzureFunctions.AzureServiceBus` are, so IaC templates do not provision the queues and topics modelled here.

## Module Interactions

- **Intent.AzureFunctions.Dispatch.Services / Dispatch.MediatR** — implement `IAzureFunctionModel` for Operations and Commands/Queries respectively; see the compatibility decision above.
- **Intent.AzureFunctions.AzureServiceBus** — a separate path for Eventing-designer integration event handlers. It emits `%AzureServiceBus:…%` setting references and seeds `local.settings.json`; it does not use this module's Service Bus trigger strategy.
