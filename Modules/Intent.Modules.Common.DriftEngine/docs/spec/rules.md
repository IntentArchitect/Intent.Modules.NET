# Rules (blocks 3 and 4)

A rule reads a claim's value from the code graph and returns a [reading](claims-and-findings.md#the-reading) ([R45](requirements.md)). There are two kinds:

| Kind         | For                                                                                       | Written as                                                   |
| ------------ | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Structure    | Types, members, signatures and enums, for any language with a language profile (block 3)  | built in, configured by conventions and the language profile |
| Claim reader | Anything else: a framework's code, or what a house's own stereotypes state                | C#, in a module's extension ([Plug-ins](#plug-ins))           |

Reading code is C# only. A pack is data, its vocabulary, conventions and language profiles, and never says how to read code (user decision, 2026-11-16: recipes, a JSON way of reading code beside claim readers, were removed, so a check has one way in).

## Choosing a rule

For each claim, the extensions' claim readers come first, the most recently registered first, then the engine's structure rules. The engine registers the stock extensions before any module's, so a module's reader is asked before a stock one, and can read any kind, the engine's included ([R46](requirements.md)). A reader returns nothing for a claim it doesn't read, and the next is asked; a claim nothing reads is `noRule`. So a house that disagrees with a stock reading for some of its code reads just those claims and leaves the rest to the stock reader.

A reader is keyed by kind, not by the pack whose vocabulary produced the claim. A framework's reader therefore reads claims a module's or a house pack's vocabulary states, such as On Delete from eShopCustom's own stereotype ([packs.md](packs.md#who-ships-what)).

## Structure (block 3)

Structure claims are compared from the code graph, describe-only: nothing is generated and no template is involved ([R41](requirements.md)). Common.Drift compared each type a Guardrails contract template generated with its file; that tied structure to C# and to the templates. The engine instead locates each element's code and compares what the element can state ([R44](requirements.md)).

### Locating an element's code

1. **Types.** The pack's conventions give, per element type, the code type kinds allowed (`Class` → `class` or `record`; `Enum` → `enum`), an optional name pattern (`I{Name}` for a Repository's interface) and optional locations (globs such as `src/Contracts/**`). The element's type is the in-scope type node with that name (by default the language profile's naming), of any kind, within those locations. An element type whose kinds include both `class` and `interface` (a Service, Service Proxy, Domain Service or Repository) with no type of its name, and no name pattern, is the interface its language names it (C#'s `IPricingService`), which a class of another name implements. None gives `notFound` (so `type.exists` is contradicted), and several give `ambiguous` with every candidate ([R43](requirements.md)). The allowed kinds are `type.kind`'s expected value, so a type of the wrong kind is found and reported as the wrong kind, not as missing.
2. **Members.** Inside the located type: an attribute is a property (or, in Java, a field with its accessors); a constructor is a constructor; a parameter is a parameter by name; an enum literal is an enum member. An attribute with a `member.backingField` claim is its property, or, when the type has no property of that name, the field the claim names.
3. **Operations.** An operation is the method of its name. When several overloads have that name, the one whose parameter names are the claim's `parameterNames`, in order, is chosen, and of several with those names, the one whose parameter types match too (ClientA has `Update(BidsDTO bid)` beside `Update(bids bid)`); failing that, the one whose parameter types all match, whatever their names, since a class may rename the parameters its interface declares (AutoMapper's `Map(List<T> rows)` for `IAutoMapper`'s `list`); failing that, the one with as many parameters; failing that, `ambiguous`. A single method of that name is the operation's method whatever its parameters, so a wrong parameter list is a contradicted `operation.parameters`, not a missing member.

The packs' conventions also name **injected parameters**: parameters the framework supplies, which are part of no operation's signature, such as `CancellationToken`, `ServerCallContext` and anything marked `[FromServices]`. `operation.parameters` and the `parameter.*` kinds skip them.

#### Which conventions apply

Conventions are keyed by element type, and each may be narrowed by a `where` expression, so an application service and a hosted service can be located differently. When two packs give conventions for the same element type that both apply to an element, the pack that requires the other wins: a house pack's conventions override a stack pack's, and a stack pack's override the core's. They override field by field: each field (`typeKinds`, `name`, `locations`, `states`, `uniqueNames`) comes from the last pack whose convention states it, so a house pack that changes only what a type states keeps the stock pack's type kinds without copying them. Two packs neither of which requires the other are a `config/conventionConflict` error for that element type.

### What is compared

| Kind                                                        | Model                                          | Code                                                       | Comparer                                       |
| ----------------------------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------- | ---------------------------------------------- |
| `type.exists`                                               | the element                                    | its type node                                              | `presence`                                     |
| `type.kind`                                                 | the code kinds the conventions allow           | `typeKind`                                                 | `within`                                       |
| `type.abstract`                                             | `abstract` on the element                      | the `abstract` modifier                                    | `exact`                                        |
| `type.generalization`                                       | the generalization's target                    | the base class, by name, resolved where possible           | `type`                                         |
| `type.generics`                                             | the element's generic type parameters          | `typeParameters`                                           | `list`                                         |
| `member.exists`                                             | the attribute, operation or constructor        | the member node                                            | `presence`                                     |
| `member.type`                                               | the attribute's type reference                 | the property's type ref                                    | `type`                                         |
| `member.nullable`                                           | the type reference's nullable                  | the type ref's `nullable`                                  | `exact` (an `unknown` reading is `unresolved`) |
| `member.static`                                             | `static` on the element                        | the `static` modifier                                      | `exact`                                        |
| `operation.returns`                                         | the operation's type reference                 | the return type, unwrapped of the profile's async wrappers and the conventions' result wrappers | `type`                    |
| `operation.parameters`                                      | the parameters, in order, each `name: type`    | the method's parameters, less injected ones                | `list` of `type`                               |
| `parameter.type`, `parameter.nullable`, `parameter.default` | the parameter's type reference and default     | the parameter node                                         | `type`, `exact`, `exact`                       |
| `enum.literals`                                             | the literals, in model order                   | the enum members                                           | `subsequence`                                  |
| `enum.literal.value`                                        | the literal's value, where modelled            | the member's `value`                                       | `number`                                       |

All but `parameter.default` and `enum.literal.value` are `stated: always`: a class with no `abstract` modifier states that it isn't abstract. A modelled member that isn't there is contradicted ([R8](requirements.md)). An unmodelled member is never a finding unless the `unmodelled.member` opt-in rule is on.

Four more structure kinds take their expected value from vocabulary and conventions rather than from the element alone: `type.location` (where the type's file must be), `type.base` (a base type the model implies, such as `IAggregateRoot` for an aggregate root), `type.marker` (a named marker, present exactly when modelled) and `file.exists` (a file an element stands for, such as a Vue component). [claim-catalog.md](claim-catalog.md#structure) lists every structure kind.

### Language profiles

A language profile is pack data ([R42](requirements.md)). Its schema is [`schemas/language-profile.schema.json`](schemas/language-profile.schema.json). One run may read several languages, and each file's code is compared under its own language's profile: an element's type is looked for under the name each language gives it, and a member, a type reference or a parameter list is read as its own language writes it.

| Section       | Says                                                    | C# example                                           | Java example                              |
| ------------- | ------------------------------------------------------- | ---------------------------------------------------- | ----------------------------------------- |
| `types`       | Each model type's names in code                         | `datetime` → `DateTime`, `System.DateTime`           | `datetime` → `LocalDateTime`, `Instant`   |
| `collections` | The generic types and forms that mean "a collection of" | `List<T>`, `ICollection<T>`, `IEnumerable<T>`, `T[]` | `List<T>`, `Set<T>`, `Collection<T>`      |
| `async`       | Wrappers unwrapped from return types                    | `Task<T>`, `ValueTask<T>`; `Task` means void         | `CompletableFuture<T>`, `Mono<T>`         |
| `nullable`    | How a type ref says nullable                            | `T?` in a nullable context; `Nullable<T>`            | `@Nullable`; a boxed type for value types |
| `untyped`     | That a declaration may leave its type out, and how to state it | none: C# always states a member's type      | none                                      |
| `naming`      | From an element name to a type, member and file name    | interface `I{Name}`; the rest as modelled            | field, method `{Name\|camel}`             |
| `typeKinds`   | The code kinds the language has                         | `class`, `record`, `struct`, `interface`, `enum`     | `class`, `record`, `interface`, `enum`    |

A language with `untyped` lets a declaration leave its type out: JavaScript declares none, TypeScript infers one a declaration leaves out, and Python states one only in an annotation. Against a type the model states, a member, return or parameter whose code leaves its type out is can't verify, `unresolved`, as a nullability the code doesn't state is: neither side can be wrong, so it has no finding of its own and is listed in the language's `engine/notStated` note on types, whose text is `untyped.notStated`. `operation.parameters` then compares such parameters by name alone. Its nullability is in the same note, since without a type there is no nullability to state. A language without `untyped` always states its types, so a member the reader gives no type is still `notFound`.

The `type` comparer maps the model's type through `types` and `collections`, then compares with the code's type ref: model `OrderItem[]` matches C# `ICollection<OrderItem>` and Java `List<OrderItem>`. Nullability isn't part of it: model `guid?` against C# `Guid` is one finding, from `member.nullable` or `parameter.nullable`, never a second from `member.type`. A model type that is a modelled element matches the code type that element is located as: where the reader resolves names, the code's type ref must resolve to that node, so a same-named type in another namespace doesn't match; where it can't resolve, the names are compared. A library type, or a primitive the profile doesn't list, is compared by name.

A member typed by a type parameter is read as true three ways, since each is (2026-11-26, "less precise is not drift"): as written (`T`), as the type argument the class being checked gives it through its bases (`UserName : ValidatableObject<string>` makes `ValidatableObject<T>.Value` a `string`, through any number of bases), and, where nothing binds it, as the profile's `object` (the first name its `types` give `object`). So a designer that has no generics and models it as `object`, one that states `T`, and one that states the bound type all verify; the finding, when none matches, shows the type as the bases bind it (`T` when they don't). The engine does this for every language and designer, as the `type` comparer's own reading of a type parameter, not in a stack; a type parameter's constraints aren't read, so a constrained `T` is `object` too.

A run's languages may be several, and the profile of a file no language reads, or of a model with no code, is the run's primary one: the profile of the language that read the most files and has one. A markup language that declares no types (XAML) has no profile, so it never stands for the code's, however many views there are.

Result wrappers beyond async ones belong to frameworks, so the conventions of a framework pack list them, with `T` for the result and `…` for any further type arguments: ASP.NET Core's `ActionResult<T>`, `Ok<T>`, `Results<Ok<T>, …>`; Spring's `ResponseEntity<T>`. `operation.returns` unwraps them as it unwraps `Task<T>`. A return type that names no result, ASP.NET Core's `IActionResult`, `ActionResult` and `IResult` or Web API 2's `IHttpActionResult` (as Spring's `ResponseEntity<Object>`), is read from the method's body: what each return's success result carries, `Ok(data)` being `data`'s type and `NoContent()` nothing. Error results aren't modelled; a result the stack doesn't read, or a body whose type the code doesn't say, is can't verify. A model that states the return type itself (`IActionResult`, under `Task` too) states the signature, which is true whatever the body carries, so it verifies without the body being read (user, 2026-11-24: "its still true its just not as accurate").

## Find paths

A convention's `find` ([`schemas/conventions.schema.json`](schemas/conventions.schema.json)) reaches places in the code graph: the code an `unmodelled.*` opt-in rule looks at, or the types a type convention narrows to. Its steps are joined by ` > `, each a kind of node, optionally `with` a .NET regular expression its canonical text must match somewhere ([code-reader.md](code-reader.md#canonical-text)). `type:` (or `class:`) starts it; `method`, `property`, `field`, `constructor` and `member` go into a type's members, `parameter` into a member's parameters, `call` into a member's calls, `chain` into its call chains, `annotation` onto the node before, and `markup` into the markup elements of a type's files or of the element before. `^` and `$` anchor to the start and end of a node's text. A markup element's text includes its children's, so `markup with` keeps only the innermost elements that match.

Names in a find path, and a convention's `name`, are `{Name}` placeholders, filtered and chained as Common.Drift's were: `camel`, `pascal`, `kebab`, `lower`, `upper`, `trimStart:`, `trimEnd:` and `replace:` (`{Name|trimEnd:Service}Controller`).

A find path only finds code. Reading a value from what it finds is a claim reader's job.

## Plug-ins

A module extends the engine in C#, through its extension (`DriftEngineExtensionBase`), with one or more of these ([R48](requirements.md)):

| Interface          | Given                                                    | Returns                                                       |
| ------------------ | -------------------------------------------------------- | ------------------------------------------------------------- |
| `ICodeReader`      | in-scope files of its languages, and the project nodes   | graph nodes and edges, and its capabilities                   |
| `IFrameworkReader` | committed artifacts its patterns match                   | framework nodes, located in the artifacts                     |
| `IClaimReader`     | one claim (kind, element, bindings) and the scoped graph | a reading, or nothing to leave the claim to the next rule     |
| `IValueComparer`   | the expected value and a reading                         | verified or contradicted, with the text to show for each side |
| `IModelFunction`   | a model element and arguments                            | a value; it declares the stereotypes and properties it reads  |
| `IOptInRule`       | the scoped graph and the claims' readings                | the code it finds unmodelled                                  |
| `IDriftRule`       | the scoped graph, the model and the claims' readings     | findings that are no one claim's, under its own id            |

A claim reader that finds the code it needs only in a file the Drift Scope leaves out says so (`ClaimReading.OutOfScope`), and the claim is can't verify, `outOfScope`, naming the scope row. One that finds nothing anywhere states silence without a place (`ClaimReading.Absent(null, value)`).

An `IDriftRule` has an id (`messaging/unmodelled`, `aspnetcore/conventional.route`), and only the last registered rule of each id runs: a module's rule replaces a stock one of its id (user decision, 2026-11-16), and the Software Factory log says which it replaced (`scope/replacedRule`). A house that disagrees with a stock rule copies it and changes it, or turns it off with one of the same id that reports nothing. An opt-in rule is replaced the same way, by its id.

The rules a plug-in must follow:

- It sees only in-scope code, through the graph. It never opens files itself.
- It never writes anything: no files, no model.
- It throws only for its own bugs. A throw is caught and becomes `ruleFailed` on each claim it was reading, naming the module.

## Opt-in "must be modelled" rules

By principle 1, code the model doesn't mention is never drift. A team that wants some kind of code always modelled turns a rule on in the model's `Drift Check` stereotype ([scope.md](scope.md#the-drift-check-stereotype)). Each rule applies within scope only, and each finding can be excepted, with a reason ([R49](requirements.md)).

The Drift Check's exceptions also take `scope/unread`, which is always on: an in-scope file no reader reads ([code-reader.md](code-reader.md#claimed-files)), whose Match is the file's path or a glob.

| Rule                     | Reports                                                                                                                      | Replaces                                 |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| `unmodelled.type`        | An in-scope type under the row's Glob (`Acme.Data/Model/Entities/**`) that no claim located                                  | Common.Drift's `own` conventions         |
| `unmodelled.member`      | A public member of a located type, of a kind its element type can state, that no claim located                               | Common.Drift's unmodelled public members |
| `unmodelled.interaction` | A call the model's interactions can state (a repository's `Add` in a handler) that no `intent.*` claim located               | eShopCustom's code-only interactions     |
| `unmodelled.exposed`     | An in-scope type an endpoint exposes (a request or response type) that no element describes                                  | eShopCustom Services' exposure check     |
| `unmodelled.file`        | An in-scope file in which no claim located anything                                                                          | eShopCustom's Strict scope mode          |
| `unmodelled.value`       | An explicit value the code states for a `whenSet` kind that the model leaves unset (a `ToTable` with no modelled table name) | decision 6                               |
| `unmodelled.index`       | An index the EF Core configuration declares (`HasIndex`) that no Index element or Index stereotype describes                  | Common.Drift's `own` entry for indexes   |
| `unmodelled.endpoint`    | A Minimal API endpoint, a lambda or a method group, that no Operation's `endpoint.exists` located                             | Common.Drift's `own` entry for endpoints |
| `unmodelled.region`      | A named placement point of a located component with more than one (a Blazor `<SectionOutlet>` or `RenderFragment` parameter, an MVC view's `RenderSection`, a .NET MAUI Shell's item) that no Region of its element names | an eShop house rule                      |

Code is **located** when some claim's reading came from it or from code inside it, as Common.Drift's ownership is. An element's type is located by its `type.exists` reading, so "the type an element is located as" and "code a claim located" are the same idea. A located class's interfaces are located with it, since a Service's, Domain Service's or Repository's interface beside its class is no element of its own; the other way round, such an element located as its interface locates the classes implementing it. A subscription's reading locates every method of the handler that takes its message, and a subscriber's copy of another application's message, or of an Eventing DTO the message carries, is located by its `message.copy` reading. A Service whose class derives from a generated gRPC base locates the `.proto` service it implements, with its rpcs and its file (`grpc.service.rpcs`).

What each rule looks at, precisely:

- **`unmodelled.type`** reports the in-scope types under the row's Glob that no claim located, so the row alone sets it up, as a Common.Drift `own` entry's `files` did (user decision, 2026-11-16). A type nested in another is part of it, and what a file declares outside its types (TypeScript's `module`) isn't a type. A finding names the designer whose located types are in the type's folder, or the nearest folder above it, so a new entity beside the modelled ones is reported with the Domain designer's findings; with none, it is reported with the scope's. A module that wants more, such as only a base class's subclasses, gives an element type's convention a `find`: within the convention's `files` only the types it reaches (and of its `typeKinds`) are reported, as that element type, and outside them the row alone decides.
- **`unmodelled.member`** looks inside located types only, as do the conventions' `members` entries. It reports the public properties, fields, methods, constructors and events of a kind the element type can state (its type convention's `states`: a Class's properties, fields, constructors and methods, a DTO's properties and fields) that no claim located. An override of a modelled base type's member, a record's primary constructor, a located field's accessors (the language profile's `accessors`, as Java's `getName`) and the members every type has (`Equals`, `GetHashCode`, `ToString`; Java's `equals`, `hashCode`, `toString`) are never reported. An override of a framework's base (a hosted service's `StopAsync`) is the type's own, and is. A `members` convention's find path may end inside a member, at a parameter or a call; the hit is unmodelled when no claim's reading came from it. Parameters aren't members of their own: a parameter list is `operation.parameters`. A member a framework's reader knows a link states (`CodeGraph.StatedByLink`: a Blazor component's `@inject` or `[Inject]` service is its Uses) is never reported, and no rule asks for the link: whether a use is significant enough to draw is the modeller's call, as a lookup's is. A Uses the model draws is checked by `intent.uses`. Nor is a member a framework's reader knows no designer can state (`CodeGraph.Unmodellable`: a property EF doesn't map, a Razor component's property that is no parameter, such as a `[SupplyParameterFromForm]` value, which the User Interface designer says is written in code, and in .NET MAUI a page's property no `[QueryProperty]` binds, a component's no `BindableProperty` backs, and the static `BindableProperty` behind a property), or the element's type can't (`CodeGraph.Unstatable`, asked only of a member the rule would report: a User Interface Proxy's method that sends no request, which the designer's validation keeps from being a Proxy Operation). Where a type convention says the designer names the element type's members uniquely (`uniqueNames`, the User Interface designer's Pages, Dialogs, Components, Layouts and Proxies), only one of a type's overloads can be stated: none is reported when one is located, else only the first. What an element type states follows its designer's own rules: a Store and a View Model state only their Properties ("Don't model actions or getters", "Don't model its methods"), and a UI Service, Utility or Behaviour no members at all.
- **`unmodelled.interaction`** reports the calls the conventions' `interactions` reach inside located methods that no `intent.*` claim located.
- **`unmodelled.exposed`** follows what an endpoint exposes: each located operation's parameter types and unwrapped return type, then, transitively, the types of those types' public properties. It reports each in-scope type on the way that no element describes. Library types and generic type parameters are skipped.
- **`unmodelled.file`** reports in-scope files in which no claim located anything.
- **`unmodelled.endpoint`** (ASP.NET Core's) reports each Minimal API endpoint the code maps, a lambda or a method group, that no `endpoint.exists` located, named by its verb and route. A controller's actions are public methods, which `unmodelled.member` reports, and a router or controller no Service describes is `unmodelled.type`'s, so neither is reported twice.
- **`unmodelled.region`** (Blazor's, which MVC views' sections and .NET MAUI Shells' items join) reports each `<SectionOutlet SectionName="...">`, each section an MVC view renders (`RenderSection("...")`, `RenderSectionAsync`), and each item of a MAUI Shell (`<Tab Route="Profile">`, named by its Route, or with none by its only content's, `<ShellContent Route="Login">`), in checked code of a component some element describes, whose name no `region.outlet` claim on a child of that element states, at the outlet, named `Component.section`. Which children are Regions is read from their claims, so a house designer that claims `region.outlet` gets the rule unchanged. A component no element describes is `unmodelled.type`'s, a `<SectionContent>` a page fills an outlet with is no placement point of the page, and a layout's `@Body` or `RenderBody()` is never asked for: the designer adds a Region for a named placement point, and the code doesn't name it.
- **`unmodelled.value`** runs a `whenSet` kind's rule for each element of the specialization the kind's vocabulary entry selects (its `for`, ignoring `where` and `when`) that has no claim of that kind, and reports each value read from code. Silence is never a value, so a framework convention is never reported, and nor is a reader's `Absent` with no value (an endpoint with no name states no OpenAPI operationId). An entry's `applies` keeps the probe to where the kind applies at all: a Required constraint is probed only on a nullable attribute, as a non-nullable one is implicitly required, and a maximum length only where the attribute's Text Constraints don't already state it.

A finding's subject is where the code is: the line a node starts on (its first attribute or annotation, if it has any), or line 1 for a file. It is in the Area of the designer whose convention or element found it (`Domain (DriftEngine)`), and names the element whose type holds the code, if any; `unmodelled.file`'s is in `Drift Scope (DriftEngine)`. A rule reports nothing in a file a `Context` scope row decides: that code is read, not checked ([scope.md](scope.md#what-scope-decides)).

A module adds an opt-in rule as an `IOptInRule` (`OptInRules` on its extension): given the run, it returns the code it finds unmodelled, using what the claims located (`RuleContext.IsLocated`), and the engine applies everything else above the same way as for its own rules. A module's rule of the same id replaces the engine's. A rule turned on whose convention has a find path the engine can't read is a `config/ruleInvalid` error, and the rule doesn't run.

An exception is a row of `Rule`, `Match` and `Reason` on the `Drift Check` stereotype. `Match` lists one or more entries, one per line, each a file glob (relative to the output folder), a type name, a `Type.Member`, or the name a finding gives, so code skipped for one reason is one row; the designer shows a row as its entries and reason. An entry that matches nothing is an `optin/staleException` warning naming it; one with no reason is a `config/exceptionReason` error. Both name the Root Folder that holds the row, and the row.

Each opt-in rule has one default severity, an error. A team that wants some of a rule's findings as warnings overrides the rule's severity ([claims-and-findings.md](claims-and-findings.md#overrides)); eShopCustom's notes-only checks become errors unless it does.

Opt-in rules are policy (block 5) and arrive in phase 1 with scope. Each case's phase is the latest phase of the packs and kinds it relies on: a rule over Domain conventions is phase 1, one over EF Core configuration phase 4.

## Messages the diagram could show

Domain events, integration events and integration commands are the one exception to principle 1 (user decision, 2026-11-14): they are always significant, so they are checked both ways by default, with no `Drift Check` row. The test is whether the diagram could show it: "if the diagram can't reflect it, it's not drift; if the diagram could reflect it and they're not in sync, it's drift." Other interactions stay case by case: a query that fetches the aggregate a service exists for may matter, incidental lookups are noise, so `unmodelled.interaction` stays opt-in.

The messaging pack, `intent.messaging`, reads them whatever the codebase raises them through (`AddDomainEvent`, an outbox, a bus, its own wrapper):

- **A link** (`Domain Event Origin`, `Publish Integration Event`, `Send Integration Command`) is an `intent.raises`, `intent.publishes` or `intent.sends` claim on its target end. It is verified when the code it starts from hands a new message of the linked type to a call: a constructor's or operation's method, a command's method that takes it, or a handler's method that takes what it subscribes to, each with the code's own methods it calls, its class's and its collaborators' (a field of an interface the code implements is each implementation). A message handed to a library's method (a bus, an outbox, a list) is raised. One handed to a method of the code is raised only when that method hands the parameter on in turn, into a call that does, something it creates, or something it keeps: a method that only reads it processes it in place. A call in what a method returns, when the method returns the message, builds it for its caller (`return Task.FromResult(message)`). A link says the code can raise the message, not that it always does (user decision, 2026-11-16): a raise in any branch bears it out, and so does a raise of what a method of the code returns, awaited or not, when one of the messages it can return is the linked one (`AddDomainEvent(StatusChanged())`). A message handed on that the code doesn't say, such as a library factory's or one typed only as what the message derives from (`INotification`), is can't verify, `unreadable`. When the code doesn't raise it, the link is contradicted, at the method.
- **A message type the diagram doesn't show** is reported by `messaging/unmodelled.message`, at its declaration, in checked code only. The messages are the modelled ones and every type of the code that has what all the modelled ones of that kind derive from or implement (`INotification`, an `IntegrationEvent` base); with none modelled there is nothing to learn from, and nothing is reported. Another application's message is modelled too, whether its referenced package is handed over or only a Subscribe link of this application reaches it, and a subscriber's own copy of its name is that message.
- **A raise no link covers** is reported by `messaging/unmodelled.raise`, `.publish` or `.send`, at the call, when the diagram has somewhere to draw the link from, which the fix names:
  - a modelled constructor, operation, command, query or handler subscription whose code reaches the call, itself or through the code's own methods it calls, nearest first: a helper's send is the handler's that calls it;
  - a method of a modelled class or service, which the diagram can show as an operation;
  - a method of a handler of a modelled message, which the diagram can show as a subscription.

  A raise from code the diagram can't show, such as a background router, isn't drift: only its message must be modelled. When the message isn't modelled either, the raise's finding asks for both, and the message has no finding of its own.

A Severity Overrides row can lower a `messaging/*` rule like any other. A per-technology pack (NServiceBus, MassTransit) may sharpen the reading, such as telling a publish from a send, and a house extension may add a mechanism the neutral reading can't see, such as an interceptor that creates events from state changes.

## Routes Web API 2 serves conventionally

ASP.NET Web API 2's attribute routing covers only actions with a `[Route]` of their own. A controller's `[RoutePrefix]` doesn't route the others: Web API 2 serves them on its conventional routes, the first `MapHttpRoute` template with a `{controller}` (`api/{controller}/{id}` by default), with the action's `{controller}` and `{action}` filled in and an optional value it doesn't take (`id = RouteParameter.Optional`) left out. So an unattributed `PostAsync` on `PolicyController` is at `api/Policy`, outside its controller's prefix. The `intent.aspnetcore` extension reads it two ways:

- **A Route the Operation states** is compared with that route as an absolute one, `~/api/Policy`, which is how the model writes a route outside its service's.
- **An empty Route** makes no `operation.route` claim (it is stated only when set), yet it puts the endpoint at its service's Route. When Web API 2 serves the action elsewhere, `aspnetcore/conventional.route` reports it at the action, asking for a `[Route]` in the code or the absolute route in the model. A service whose Route is the conventional route itself (a controller with no prefix, modelled at `api/Claims`) isn't reported.

A parameter's source reads the same route: such an action binds from the conventional template, not its controller's prefix.

ASP.NET Core MVC routes an action conventionally only when neither it nor its controller has an attribute route: a controller's `[Route]` routes all its actions, and `[ApiController]` requires one. Its conventional routes are the first `MapControllerRoute` pattern with a `{controller}` and an `{action}`, or `MapDefaultControllerRoute()`'s `{controller=Home}/{action=Index}/{id?}`. A token's default makes it optional, but the action's own name still fills it, so `AccountController.Login` is `~/Account/Login`, read and reported the same two ways. An ASP.NET Core action with no verb attribute serves every verb, so whichever verb the model gives is verified, as a convention the code doesn't state.

## OpenAPI operationIds and exclusions

`intent.aspnetcore` reads `operation.openApi.operationId` and `operation.openApi.ignore` as ASP.NET Core's own API description and OpenAPI document do, not as any one generator's options might:

- **The operationId** is the action's route name (`AttributeRouteInfo.Name`), else its last endpoint name metadata (`OpenApiDocumentService.GetOperationId`, as Swashbuckle's default selector). For a Minimal API endpoint that is its last `.WithName(...)`, else its handler's `[EndpointName]`, and an OpenAPI operation callback chained on it that sets `OperationId` (`.WithOpenApi(op => ...)`, .NET 10's `.AddOpenApiOperationTransformer(...)`) overrides both, the last such callback winning. For a controller action it is its route attribute's `Name` (`[HttpGet("{id}", Name = "GetItem")]`, `[Route(..., Name = ...)]`; its controller's route's name when none of its routes gives a template or a name), else its `[EndpointName]`. With none, the endpoint states no operationId: `Absent`, so `unmodelled.value` never reads "none" as a value. A value the code computes is `unreadable`; a constant is read.
- **Not read as an operationId:** an ASP.NET Web API 2 controller's route name (Web API 2 has no OpenAPI of its own, so what a generator names the action isn't in the code), and a library's attribute such as Swashbuckle's `[SwaggerOperation(OperationId = ...)]` or NSwag's `[OpenApiOperation]`, which name it only with the library's options on. Both are can't verify, `unresolved`.
- **An exclusion** for a Minimal API endpoint is `ExcludeFromDescription()`, or the metadata it adds (`.WithMetadata(new ExcludeFromDescriptionAttribute())`), on the endpoint, on a group it is mapped on (where the group is made, or a statement on its variable that reaches no `Map*` call), or on its router's mapping call (`app.MapOrdersApi().ExcludeFromDescription()`), or `[ExcludeFromDescription]` on its handler, a lambda's included: the only metadata Minimal APIs' description provider reads. For a controller action it is the first `[ApiExplorerSettings]` on the action, else on its controller or the controller's bases, as MVC's application model reads it, so an action's `[ApiExplorerSettings(GroupName = "v1")]` makes it described under a controller that ignores the rest; MVC doesn't read `[ExcludeFromDescription]`. With none, the endpoint is described: `false`, from silence.

## Domain constraints from validation attributes

`intent.dataannotations` and `intent.beanvalidation` read the `constraint.*` claims from the validation attributes on the member an attribute's `member.exists` located, each only where its framework is in the code:

- **DataAnnotations** answers for a C# member of a type that validates with System.ComponentModel.DataAnnotations: one of its members, or its bases', carries one of the validation attributes. A type with none validates some other way (FluentValidation, a domain method), so its claims are left to another reader or can't be verified (`noRule`), never read as stating nothing. `[Required]`, `[EmailAddress]`, `[Url]` and `[Base64String]` state their constraints by being there; `[MinLength]`, `[MaxLength]`, `[StringLength(max, MinimumLength = min)]` and `[Length(min, max)]` a string's length or a collection's count (`[StringLength]` only a string's); `[RegularExpression(pattern, ErrorMessage = ...)]` a pattern and message, one from resources (`ErrorMessageResourceName`) can't be verified; `[Range(min, max)]` or `[Range(typeof(T), "min", "max")]` the numeric limits, with `MinimumIsExclusive` and `MaximumIsExclusive`.
- **Bean Validation** answers for a Java field whose file imports `jakarta.validation.constraints` or `javax.validation.constraints` (or Hibernate Validator's `org.hibernate.validator.constraints`), and an annotation counts only when imported from them, so JetBrains' or Lombok's `@NotNull` isn't a constraint. `@NotNull`, `@NotBlank` and `@NotEmpty` state Required; `@Size(min, max)` a length or count, and Hibernate's `@Length` a string's; `@Pattern(regexp, message)` a pattern and message, a `{key}` message, looked up in `ValidationMessages.properties`, can't be verified; `@Email` and Hibernate's `@URL` their constraints; `@Min`, `@Max`, `@DecimalMin`, `@DecimalMax` (with `inclusive`), `@Positive`, `@PositiveOrZero`, `@Negative`, `@NegativeOrZero` and Hibernate's `@Range` (whose `min` defaults to 0) the numeric limits. Bean Validation has no Base64 constraint, so a Base64 claim is can't verify, `unresolved`.
- **In both**, silence is `false` for a constraint stated by presence or a boundary, and `0` for a minimum length or count; a maximum, a pattern, a message or a numeric bound the code doesn't give is not stated. A bound written as its type's extreme (`int.MaxValue`, `Long.MAX_VALUE`) is no bound. A limit given as a constant the code declares is read, anything else computed is `unreadable`. Text Limits on a collection limit each item's length, which neither framework states on the member, so they can't be verified. The readers read only the `constraint.*` kinds: EF Core and JPA read the same attributes for their own column claims.

## User Interface from Blazor markup

`intent.blazor` reads what the User Interface designer (2.0.0) states of a Razor component's placement points, behaviours, dependencies and form posts from its markup (`CodeGraph.MarkupOf`) and code, and the JavaScript the TypeScript language reads, each only for code it recognises, so a Vue or React reader keeps the rest:

- **A Region** (`region.outlet`) is a `<SectionOutlet SectionName>` of its name in its component's markup, or a `[Parameter] RenderFragment` (or `RenderFragment<T>`) of its name, content a parent fills; a name the code computes can't be verified. A `RenderFragment` parameter is never asked for as a Property by `unmodelled.member`, and `unmodelled.region` asks for no Region of a component with only one placement point (its body counted), as the designer adds Regions only where there are several. A layout (a component deriving `LayoutComponentBase`) renders its page at `@Body`, a placement point the code doesn't name, so the layout's one Region no outlet names is it, or, of several, the one whose Composition places a Page, as the designer places pages in a layout. An outlet no Region names, when there is one, is what the Region was renamed from, and the finding names it.
- **A Uses of a Behaviour** (the vocabulary binds `Behaviour`) is a JS interop import of the behaviour's script (`InvokeAsync`/`InvokeVoidAsync` given `"import"` and a path relative to the application's root, a library's under `_content/{Library}/`), or the script loaded for the whole application by a component's `<script src>` (relative to the host's project's `wwwroot`, or `_content/{Library}/`) and acting on an element of the component's markup: one that matches a selector the script passes to `querySelector`, `querySelectorAll`, `closest` or `matches`, or names through `getElementById` or `getElementsByClassName`, read through constants. Only a selector whose subject (its last compound) names a class, an id or a `data-` attribute marks an element; a bare tag or an ARIA attribute matches any markup of its kind. A component's tag counts as its element, since Blazor passes an attribute it doesn't take on to what it renders. Any other script module it uses must be imported.
- **A Uses from a plain class** (a View Model, a Store, a UI Service: an element located as a C# class, not a component) or a component's Uses of one is a dependency the shared finder `Stacks/Ui/Dependencies` reads from the graph alone: a field, property or constructor parameter (a primary constructor's too) of the used element's located type, of an interface of the code it implements or of a generic type over either; else an object of it the class creates; else a call through a dependency's property typed by it. Types are resolved as the code names them, so another type of the name doesn't count, and nor does a library interface the type also implements (`IDisposable`).
- **A Call Service Operation Action** from a component to an operation with Http Settings is also a plain `<form method="post" action="...">` with no `@onsubmit` (a handled form's action is only its fallback) whose action's path is the operation's route: its Route under its Service's, or alone when it starts with `/`, compared as a proxy's request route is. The operation must take a POST. A computed action can't be verified.

## User Interface from MVC views

`intent.mvc` reads what the User Interface designer (2.0.0) states of ASP.NET Core MVC views and Razor Pages, which the C# language reads as components named after their files ([code-reader.md](code-reader.md#razor-components)), with the controllers that render them. It answers only for a view a `.cshtml` file declares (and a view component's class), so Blazor's, Vue's and React's readers keep theirs. ASP.NET Core's routing is the `intent.aspnetcore` stack's own: an action's URLs are its attribute routes (its own templates under its controller's, `[controller]` and `[action]` filled in) or, with none, every URL the conventional routes serve it at (`MapDefaultControllerRoute()`, `MapControllerRoute`, ASP.NET MVC's `MapRoute` with its defaults object), a trailing segment a default fills or an optional parameter left out in turn, so `HomeController.Index` is `/Home/Index`, `/Home` and `/`.

- **Which view an action renders** is read from its returns: `View()` is the action's own name (its `[ActionName]`), `View("Name", model)` the name, through locals and conditionals, the code's own methods it returns and its controller extension methods, each with its parameters bound to the call's arguments (`this.LoadingPage("Redirect", url)` renders `Redirect`). The name is found as MVC finds it: `Views/{Controller}/{Name}.cshtml`, then `Views/Shared/{Name}.cshtml` (an `[Area]` controller's area first), in the controller's project, then in another (a Razor class library's); an app-relative path as written. A partial or a layout is found from the view naming it: its folder, then its `Views` folder's `Shared`, or for a Razor Page each folder up to `Pages`, then `Pages/Shared` and `Views/Shared`. A view's layout is its own `Layout = "..."`, else that of the nearest `_ViewStart.cshtml` above it.
- **What a view is** (`component.kind`): a layout when a view's or a `_ViewStart.cshtml`'s `Layout` names it; a page when it is a Razor Page or an action renders it with `View(...)`; a component when an action renders it as a `PartialView` or a view renders it as a partial, and from silence otherwise. A dialog has no rule. A view component's class (`: ViewComponent`, `[ViewComponent]`, or named `...ViewComponent`) is a component.
- **A page's routes** (`page.route`) are the URLs of the actions that take a GET and render it, and a Razor Page's its path under `Pages` (an `Index` its folder's too) with its `@page` template (an absolute one alone). Its **title** is `ViewData["Title"]` or `ViewBag.Title`; one the view computes can't be verified.
- **Security** is `None`, a finding saying so when the model secures the view: a view carries no authorization; the action that renders it does, and the Services model states it on its Operation. A Razor Page is its own endpoint, so its `@attribute [Authorize]` or `[AllowAnonymous]`, or its page model's, is its security.
- **A Region** (`region.outlet`) is a section the view renders (`RenderSection("name")`, `RenderSectionAsync`); `RenderBody()` is the Region no section names, when only one is, else the one placing a Page, a Region named for a section some page fills (`@section`) never being it. A Region's **Composition** of a page is the page shown in that layout (the body's) or filling that section (`@section name`).
- **A Composition** of a component is a partial the view renders (`<partial name>`, `Html.Partial`, `PartialAsync`, `RenderPartial`, `RenderPartialAsync`), resolved as above, or a view component (`<vc:cart-summary />`, `Component.InvokeAsync("CartSummary")`, `InvokeAsync<T>()`, `typeof(T)`). A **Uses** is what the view `@inject`s, read as any class's dependency (`Stacks/Ui/Dependencies`); a Behaviour isn't read. A view's injected members are its Uses (`StatedByLink`), and its other members are written in code (`Unmodellable`), so `unmodelled.member` asks for none.
- **A Navigation** is a link reaching an action that takes a GET and renders the target page, or the target Razor Page: `<a href>` (its path, `~/` dropped, matched against the actions' URLs as a proxy's route is, `ProxyRequests.RouteMatches`), `<a asp-controller asp-action>` (each defaulting to the view's rendering action's), `asp-route` (the actions whose route has that `Name`), `asp-page`, `Html.ActionLink`, `Html.RouteLink`, and an `href` that is all a URL helper's call (`Url.Action`, `Url.RouteUrl`, `Url.Page`, `Url.Content`). A link to another site reaches nothing; a computed one, when none reaches the target, can't be verified.
- **A Call Service Operation Action** is a form reaching the operation's controller action (the method the Services model locates the operation as, else the action its Service's and its own name give) with its Http Settings Verb, the target then the operation's service. A form the tag helper builds (any `asp-` attribute) posts unless its `method` says otherwise, to `asp-controller`/`asp-action`, or the route `asp-route` names (with no action's route of that name and no controller or action named, the URL the view was shown at, as the tag helper writes no action); `Html.BeginForm` and `BeginRouteForm` post unless their `FormMethod` says otherwise; a plain form GETs unless `method="post"`, to its `action`'s path or a URL helper's; any form with nothing naming where it goes, to the URL the view was shown at (the actions taking its verb at a URL its rendering actions are served at). A Razor Page handler (`asp-page-handler`) is no controller's action.

## User Interface from .NET MAUI

`intent.maui` reads what the User Interface designer (2.0.0) states of a .NET MAUI app's views: a view is its XAML and its code-behind, one type ([code-reader.md](code-reader.md#the-xaml-reader)), or a view written in C# alone. MAUI is in a project when a view's XAML is in MAUI's (or Xamarin.Forms') XAML namespace, a file imports one of their namespaces, or the code builds a `MauiApp`; the stack answers only for a view of such a project, so a WPF, WinUI or Avalonia view, read by the same XAML language, is never MAUI's, and Blazor's reader keeps a Blazor Hybrid app's components. MAUI's reading of the code (`MauiSite`, once per graph) is the Shell's items, the registered routes, each view's binding contexts, the types its XAML uses and the navigations each type's code makes.

- **What a view is** (`component.kind`) is the first framework base on its base chain, its XAML root included: a `Layout` for `Shell`, `NavigationPage`, `TabbedPage` or `FlyoutPage` (a host of other pages), a `Page` for `ContentPage`, a `Dialog` for CommunityToolkit.Maui's `Popup`, and a `Component` for a `ContentView` or any other view. A page's code doesn't say whether it is pushed modally, so a `Dialog` modelled for a page can't be verified, `noRule`.
- **A page's routes** (`page.route`, a `subset`) are the paths of the Shell contents showing it, from the Shell down (`/Main/Catalog`), and each route `Routing.RegisterRoute("Basket", typeof(BasketView))` registers for it, with a leading `/`. Its **title** is its XAML root's `Title`, else a `Title = ...` its constructor sets; a bound or computed one can't be verified. Its **security** is `None`: a MAUI view carries no authorization; the API it calls secures its operations.
- **A Property** is a query parameter when a `[QueryProperty(nameof(X), "x")]` on the page or its binding context, or their bases, names it; a page that takes its query through `IQueryAttributable` sets what it likes, so a modelled query parameter can't be verified there. It is bindable when a static `{Name}Property` `BindableProperty` backs it, or CommunityToolkit.Maui's `[BindableProperty]` generates one. Shell has no route parameters, so a route parameter is always contradicted. For `unmodelled.member`, a page's property no `[QueryProperty]` binds and a component's no `BindableProperty` backs are written in code, and the static `BindableProperty` is its property's (`Unmodellable`).
- **A Region of a Shell** (`region.outlet`) is a Shell item (`FlyoutItem`, `TabBar`, `ShellItem`, a `Tab`, or a bare `ShellContent`, which MAUI wraps in an item of its own) named by its Route, or, with none, by its only content's, so `//Login` names a `FlyoutItem` with no Route showing `<ShellContent Route="Login">`. A Region naming no item, when exactly one item is named by no Region, is that item renamed: the Region has one finding, and its Compositions are read through the renamed item. Each unnamed item is `unmodelled.region`'s, at the item.
- **A Region's Composition** of a page is a `ShellContent` of its item showing the page: its `ContentTemplate="{DataTemplate views:CatalogView}"`, else a view in its `ShellContent.ContentTemplate` or `ShellContent.Content`, else the element written inside it. Its **Entry** (`entry.*`) is how the tab or flyout item presents the page: Label its `Title`, Icon its `Icon` (a resource's key for `{StaticResource}` or `{DynamicResource}`), Key its `Route`, each the content's own, else that of the tab or item holding it alone. Shell has no keyboard shortcut. For `unmodelled.value`, a label that is the page's own name is no Entry the designer needs.
- **A view's Composition** of a component is the component in its XAML: an object element of it (`<templates:ProductTemplate />`), a data template making it (`{DataTemplate views:ProductTemplate}`), or an `{x:Type}` naming it (a Blazor Hybrid app's root component), each of a CLR namespace, resolved by full name.
- **A Uses** is, first, the view's binding context: `BindingContext = viewModel` in its code (a parameter, field or created object, through a chained assignment) or an object in a `<ContentPage.BindingContext>` element, not its `x:DataType`, which only types its compiled bindings; then an object its XAML creates (a behaviour it attaches); then what it holds or creates, read as any class's dependency (`Stacks/Ui/Dependencies`).
- **A Navigation** is a navigation in the view's code or its binding context's reaching the target page: `GoToAsync` on the Shell (`Shell.Current`, a Shell of the code's, something typed as one, or the Shell's own code) with a route that reaches the page, an absolute one (`//Main/Catalog`) against the Shell contents' paths and item names, a relative one against the registered routes too, its query no part of it; a call of the code's own method that hands the route it is given to such a navigation, directly, through a local or a `ShellNavigationState`, or through another such method, found by data flow to a fixed point, so `_navigationService.NavigateToAsync("Basket")` reaches `BasketView` whatever the wrapper is named; or `Navigation.PushAsync(new BasketView())` (or `PushModalAsync`). A Shell also navigates to each page its contents show. When none reaches the page and a route the code navigates to is computed, it can't be verified.
- **A Persisted Store** (`store.persisted`) is a Store whose class reads or writes the device's `Preferences` or `SecureStorage` (their `Default` instances, or an `IPreferences` or `ISecureStorage` it is given), anywhere in its code, its property accessors included, read from its syntax trees. It answers only for a Store of a MAUI app.

## App Events from the MVVM Toolkit

`intent.mvvmtoolkit` reads an element's Publishes and Subscribes of an App Event from CommunityToolkit.Mvvm's messenger, in C# code of any framework the toolkit serves (MAUI, WPF, WinUI, Avalonia, Blazor), where the toolkit is in the code (a file imports it, or a type is one of its observable objects or recipients). The element's code is its own members and the code's own methods they reach.

- **Publishing** is a `Send` on a messenger (`WeakReferenceMessenger.Default`, `StrongReferenceMessenger.Default`, an `IMessenger`, an `ObservableRecipient`'s `Messenger`) of the event: one created in place, or anywhere it comes from (`MessageCode`: a local, the code's own helper that sends what it is handed), or named as its type argument (`Send<ProductCountChangedMessage>()`).
- **Subscribing** is a `Register` naming the event as a type argument (`Register<CatalogView, ProductCountChangedMessage>`), or the class being an `IRecipient<ProductCountChangedMessage>`, which `RegisterAll` or an active recipient registers. Sending isn't subscribing.
- **The event** must be located (its `type.exists`, by the `App Event` convention); one the code doesn't have is `blocked`, as its own claim is the finding. The toolkit's message bases are declared as library types (`ValueChangedMessage<T>` with its `Value`, `PropertyChangedMessage<T>` with `Sender`, `PropertyName`, `OldValue` and `NewValue`), as the EF Core stack declares ASP.NET Core Identity's, so an App Event deriving from one has those members to check, `Value`'s type bound by the event's base (`ValueChangedMessage<int>` makes it an `int`).
