# SDD — Design

You are running the **design** step. This is what makes Intent Architect's SDD flow different from a generic one: IA is **model-driven** — the designer model is the source of truth and the Software Factory generates code from it. So `design.md` describes **model changes**, never code the generator owns.

## Honour the solution's governance

When the spec's framework declares governance documents — Spec Kit's `.specify/memory/constitution.md`, say — `read_spec` returns them as `governanceDocuments` and the Specs panel lists them. **Read them first and treat their rules as binding on what you produce.** They are the user's standing constraints, not background reading. If a requirement and a governance rule genuinely conflict, say so and ask rather than silently picking one.

## What to do

**First, resolve the slug — never guess it.** If you weren't handed an exact slug, call **`read_spec` with no `slug`**: it lists every spec in the solution with its `slug`, `phase` and progress. Match what the user named against that list. Specs live under `intent/.specs/` and are reachable **only** through `read_spec` — never glob or grep the workspace hunting for spec artifacts. If nothing there plausibly matches what they named, `ask_user_question` offering the closest specs as options rather than inventing a slug.

1. `read_spec(slug, artifact: "requirements")` to load the approved requirements. Read the whole document, not just the acceptance criteria — its framing sections are **design inputs**, and ignoring them is how a design ends up correct against the criteria and wrong against the feature:
   - **Glossary** — the feature's vocabulary, defined once with cardinality. These nouns are your candidate Domain elements and their multiplicities; **name modeled elements after the Glossary terms** wherever they denote the same concept, and don't invent a synonym for one. Where a Glossary term already exists in the model under a different name, say so explicitly rather than modelling it twice.
   - **Non-Goals** and **MVP Scope → Out of Scope** — a hard boundary on the design. Do **not** model capability that lands on this list, however cheap it looks alongside what you are modelling; if something there turns out to be unavoidable, put that to the user rather than quietly designing it in.
   - **Key User Journeys (`UJ-N`)** — the flows the model must actually support end-to-end. Walk each one against your realization plan: every beat needs a modeled operation (command / query / UI interaction) it runs through, and a journey with no path through the design is a hole in it, even when every criterion is covered.
   - A spec imported from an external tool carries the same material under its own headings (a BMAD PRD's Glossary, Non-Goals and `UJ-N` journeys); read it the same way.
   - **Externally-owned requirements are read-only here.** For an imported spec, `read_spec` returns the framework's own documents with `externallyOwned: true` — that IS the requirements artifact. Never write or "normalize" a `requirements.md` for it (`write_spec` refuses, and a copy would be a second truth that drifts). If the requirements are wrong or incomplete, say so and stop — they are edited in the owning tool and brought back in by re-importing the spec.
2. **Inspect before you design — understand the flow, the modules, and the rules.** All of it is **read-only**: this step inspects the model but never mutates it — no designer scripts, no module installs, no Software Factory runs, no code changes. Design decides _what_ will change; implementation is where it actually happens.
   - **The mutation flow.** Load the **exploring-the-model** skill (the read tools and their notation) and the **changing-the-model** skill (how `run_designer_script` actually applies changes — operation ordering, containment, type/package references, associations & cardinality, mapping, and the validate-until-clean loop). The design may only propose changes that are **expressible through that mutation flow**, so understanding it now is what keeps the plan realisable.
   - **The module landscape — patterns _and_ capabilities.** Call `listInstalledModules()` for the application: the installed modules **define its architecture and patterns** (CQRS vs services, persistence style, the designers, stereotypes, and generators available) — your design must fit them, not fight them. Then, for every **cross-cutting / behavioural** requirement (soft delete, auditing, created/modified tracking, concurrency, multi-tenancy, validation, security, domain events, etc.), work out how it is best realized: (a) if an **installed** module already provides the capability, use it; (b) if not, `searchAvailableModules()` to discover whether an **available** module provides it. **Prefer a module capability over hand-modelling it** — a soft-delete or auditing module generates the query filters, DbContext configuration, and stereotypes far more completely and correctly than a hand-added `IsDeleted` attribute or timestamp fields, so when a module covers the requirement, realize it **through that module and drop the hand-modelled equivalent** from the plan. Only hand-model the members when no module covers the requirement. **Do not install anything in this step** — the design step does not mutate the solution; instead **record the module as a prerequisite** (see the output below) and **confirm the choice with the user** (module and architecture decisions are exactly the kind of trade-off to put to them).
   - **Which application owns each part of the work — including the hand-written parts.** Call `get_applications` and, for every codebase area this feature will touch, establish which application's **output** it lands in. Any area that will carry code but sits inside **no** application's output — the classic case is a hand-written front-end beside a modelled backend — is a **gap you must resolve here**, because everything downstream is anchored on the application: `write_file` / `patch_file` refuse a path no application owns, a traceability file link has no output to be relative to (so each wave guesses a different base and records links that resolve nowhere), and the Changes Review has nothing to join those files onto. Put it to the user with `ask_user_question` — add an application for that area (an empty/minimal architecture is enough when nothing will be generated into it), or knowingly leave it outside Intent — and record the answer. When they choose to add one, it is a **prerequisite** (below), not something you create here: this step doesn't mutate the solution.
   - **The designer rules.** **For every designer you intend to mutate, fetch at minimum its `getDesignerSchema()` and its `getDesignerModelStructure()`** — the schema is the designer's _rules_ (which element / association / stereotype types it defines, their settings and containment), the structure is what already exists — plus `getElementDetails()` / `searchElements()` where you need detail. **Adhere to those rules:** design only elements, associations, stereotypes and mappings the schema permits — never a type the designer doesn't define, nor a containment / cardinality its rules forbid.
   - **The stereotypes — the design's precision.** The schema lists each designer's stereotype definitions with their `applicableTo` (use `getStereotypeDefinitions()` if the schema truncated them). When you design an element or member, **inspect the applicable stereotypes and apply the ones the requirement calls for** — e.g. a max-length / required / default-value constraint on a string attribute, a primary-key or index stereotype, an HTTP verb / route on a command or query, a security stereotype naming roles. Requirements carry concrete bounds (lengths, formats, ranges); a plain untyped member throws that precision away — **naming the exact stereotype (and its property values) in the design is what carries the bound into generated code.** For each modeled member, ask "which stereotype makes this constraint real?" and record it.

   **Resolve every genuine design trade-off with the user before you write — this step may not finish with open questions.** This includes every module and architecture decision surfaced above. When a decision has a small set of plausible answers, put it to the user with `ask_user_question` (picking an option is cheaper than typing prose); use a plain chat message only for a genuinely open-ended one. Keep asking in focused rounds until nothing material is unresolved, and do **not** start writing `design.md` while a question is still open. If the user genuinely won't decide a point, pick a sensible default and record it as an assumption in `design.md` — never leave it open.

   **The same gate covers feasibility.** A realization that is novel, fights an installed pattern, or that you are **not confident the model can express cleanly** must be **stress-tested against the actual mutation flow** — load **changing-the-model** and check the specific schema / containment / cardinality rules for that exact change — not asserted. If it doesn't hold up, re-approach it or put the alternatives to the user. **Design may not finish with an unresolved feasibility risk**: implementation has no cheap way to recover from one, so record in `design.md` the resolution (or the assumption) you settled on.
3. Write `design.md` via `write_spec(slug, "design", <content>)` containing:
   - **Application prerequisites** — every application this feature's work lands in, named explicitly, and for a codebase area that has none: either **"add application \<name\> (\<architecture\>) for \<area\>"** as a prerequisite the tasks step schedules before any work in that area, or the user's explicit decision to leave the area outside Intent (record it as such, so a later reviewer sees a choice rather than an oversight). If every area is already covered by an application, say so.
   - **Module & architecture prerequisites** — any module that must be **installed** before the model work (id + a concrete version from `searchAvailableModules()`, plus the requirement(s) it satisfies and why it was chosen over hand-modelling). List these explicitly and up front: the design step does **not** install them, so the tasks step turns each into a prerequisite the implementation installs (and re-runs the Software Factory for) **before** the model work that depends on its stereotypes. If no new module is needed, say so.
   - **Model changes** — the designers / elements / associations / stereotypes to add or change (Domain: entities, value objects, aggregates; Services: commands, queries, DTOs, operations; etc.). **Name the stereotypes and property values each element/member carries** — the max-length / required / index / verb / security stereotype the requirement's bounds demand — so the constraint is realized in generated code, not lost as a plain member.
   - A **per-requirement Realization plan** that classifies the work into two buckets — these become the task-type tags in the next step. **Every requirement must name a concrete realization mechanism**, one of exactly three: **(a)** an installed / prerequisite **module capability or stereotype** (the documented preference — see below), **(b)** a **modeled element type the schema defines** (name it), or **(c)** **hand-written code behind a code-management _ignore_ directive** — for the private helpers / local logic the model can't own. Deciding the model-vs-code boundary **here** is the point: logic with no modeled operation to sit in otherwise has no sanctioned home, and implementation discovers it the hard way.
   - **`[model]`** — designer-model changes. **Most of the work lives here.** Turning this into code (entity / command / query / handler / DTO / DbContext / repository / controller classes and DI wiring) is the Software Factory's job and happens automatically once a wave's model work is done — it's never hand-written, and never its own task.
   - **`[code]`** — the _only_ hand-written code: business logic that fills modeled operation bodies, the tests that cover it, and — mechanism (c) — logic that has no modeled operation to sit in, which the implementation must protect with an _ignore_ directive so regeneration doesn't reclaim it. Say which files/regions those are.

     For **cross-cutting / behavioural** requirements (soft delete, auditing, concurrency, etc.), realize them **module-first**: if a module (installed, or a recorded prerequisite) provides the capability, the realization is **applying that module's stereotype/setting** to the owning element — name that, not a hand-built equivalent. Only when **no module covers it** do you hand-model members on the entity another requirement owns, and then **name the specific members / stereotypes that realize them** (e.g. soft delete with no module → an `IsDeleted` attribute + a `SoftDelete()` operation). Either way this member-/stereotype-level intent is what lets the tasks step author a per-requirement member map, so traceability can later link the requirement to just what realizes it rather than the whole entity.
   - **Cross-requirement dependencies** — for each requirement, note whether it needs another requirement's output to exist first (e.g. R3's handler calls the domain method R1 adds). These are facts about the design, not a schedule: keep them minimal (only genuine dependencies) and leave sequencing to the tasks step, which owns waves and ordering.
   - Keep structural scaffolding out of `[code]` — if the Software Factory generates it automatically, it doesn't belong in a task at all.

## Write it as MDX — the document shape

`design` defaults to `.mdx`, and a design is the artifact the structured blocks pay off on most: it is almost entirely shape, delta, contract and plan, and every one of those reads better as a block than as a paragraph. **`use_skill` authoring-rich-documents BEFORE you draft.** Do not author MDX from memory — that skill also carries the escaping rules, and MDX fails the whole document on a bare `<` or `{` in prose, which a design full of `List<Order>` walks straight into. Pass `format: "md"` only if the user asked for plain markdown.

Everything that isn't a block stays plain Markdown prose. The prescription below says which content shape earns which block — reach for one **where the content calls for it**, not to hit a count.

**Write the sections in the table's order, so the design reads from the high level down to the detail, and lead every section that has a shape with its diagram.** A flow, a structure, a dependency or a sequence is a `` ```mermaid `` fence (or a `<Wireframe>` for UI) first, with prose and tables after it for what the diagram cannot say. Fall back to prose or a table only where a diagram would genuinely communicate worse. The per-entity `<DataModel>` and per-command `<ApiEndpoint>` detail blocks stay mandatory: they are the member-level intent `sdd-tasks` and traceability read.

| Section                                 | Carried by                                                                                                                                                                                                                                                                                                 |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Overview**                            | Open with a `` ```mermaid `` `flowchart` or `sequenceDiagram` of the feature's runtime flow end to end, then prose. Every element that ALREADY exists is an inline `<ModelRef>`, never bare text. Close with one `<Callout tone="info">` summarising the scope in counts (N entities, M commands, K queries). |
| **Decisions confirmed with the user**   | Consecutive `<Callout tone="decision">` (and `tone="risk"` where the choice carries one), **one per decision**, each closing with a bold **Why:** line. These are the answers you gathered above — a design that resolved five trade-offs and mentions none of them reads as if it had no choices to make. |
| **Module & architecture prerequisites** | One `<Callout tone="warning">` — it blocks the first wave, and a warning is what a blocker looks like. Name each module's id + concrete version and the requirement(s) it satisfies. Say so explicitly if none is needed. A **missing application** for a codebase area belongs in the same callout, or in a `tone="decision"` one when the user chose to leave the area outside Intent. |
| **Domain model — aggregate shape**      | A `` ```mermaid `` `classDiagram` with multiplicities and stereotypes on the members, scoped to what this change touches plus its immediate neighbours, followed by prose reading the notation back for a reader who doesn't parse diagrams.                                                               |
| **Per-entity / per-DTO detail**         | One `<DataModel>` per entity and per DTO. `entity` names the ROLE (aggregate root / compositional child / value object), and each field carries its type, its `change`, and the stereotype that realizes its bound. A prose list of an entity's fields is the thing this block exists to replace.          |
| **Endpoints**                           | One `<ApiEndpoint>` per Command / Query. `caption` carries the security posture, the interaction type, the return type and the criterion ids it satisfies.                                                                                                                                                 |
| **Realization plan**                    | One table with a row per requirement and columns for `[model]` / `[code]` / Depends-on. This is what `sdd-tasks` projects its task list from, so it has to be complete and mechanical rather than narrative.                                                                                           |
| **Hand-written code**                   | Prose, plus a `<Diff>` or `<AnnotatedCode>` where you are specifying an actual code change precisely enough to be worth showing.                                                                                                                                                                           |
| **Assumptions**                         | A `<Checklist>` — each assumption then gets worked through and its tick persists, which a bullet list can't do.                                                                                                                                                                                            |

Two conventions the whole document depends on:

- **Every element that exists in the model is a `<ModelRef>` carrying `application`.** The chip shows its CURRENT name, its own type icon, and strikes through if it has since been deleted — which is what stops a design quietly describing a model that has moved on. Where a name is duplicated, address it by the package-rooted `Package/Folder/Name` path `searchElements()` returns. An element this design is _proposing_ does not exist yet: name it in the mermaid fence, the `<DataModel>` or a `<ModelChanges>` entry, never as a `<ModelRef>` that would correctly render broken.
- **Every source file you name is a `<FileRef>`.** It shows red when the path doesn't exist — a cheap, standing check that the `[code]` bucket names real files.
- **Don't restate model structure you can point at.** Describe the DELTA and `<ModelRef>` the element.
- **Link a related spec by its slug**, `[[other-spec]]` or `[[other-spec/design#heading]]`, never by a path. See "Linking documents" in authoring-rich-documents.

In a plain `.md` design (only when the user asked for one), the same live chips are available as `[Order](intent://element/Order?designer=Domain&application=MyApp)` links — but none of the blocks above are.

## Before you call write_spec — self-review

Run this gate over the draft and fix anything that fails:

- [ ] I resolved every material design decision with the user — including every module / architecture decision — and **no design question is left open.**
- [ ] The design uses the requirements' **Glossary** terms verbatim for the concepts it models, respects the **Non-Goals / out-of-MVP** boundary, and every **`UJ-N`** journey has a complete path through the modeled operations.
- [ ] I inspected the installed modules, and for each cross-cutting requirement checked whether an installed or available module provides it — preferring the module over hand-modelling and dropping the hand-modelled equivalent where one applies.
- [ ] Every module that must be installed first is recorded as a prerequisite with an id + concrete version and the requirement(s) it satisfies.
- [ ] Every proposed change is expressible through the designer's rules (schema-permitted types, containment, cardinality, mapping), and each element/member names the stereotypes (with values — max length, required, verb, security, etc.) its requirement's bounds demand — **and every requirement names its concrete realization mechanism (module capability / modeled element type / code behind an ignore directive); every risky or novel realization was stress-tested against the mutation flow and resolved, not asserted.**
- [ ] Each requirement has a `[model]` / `[code]` realization plan, and its cross-requirement dependencies are stated.

Then the document itself — a design that is correct but reads as a wall of prose has thrown away most of what this viewer can do, and every item below is one a block-free document fails:

- [ ] **Every element that already exists** and is named in prose is an inline `<ModelRef>` carrying `application` — not bare text, and not a plain-`.md` link in an `.mdx` document. Every source file I name is a `<FileRef>`.
- [ ] **The document reads high level to detail, diagram first.** The Overview opens with the runtime flow as a `` ```mermaid `` fence, and every structural relationship — the aggregate shape — is a fence placed before the prose and tables about it, not a paragraph describing one.
- [ ] **A related spec is linked by its slug** — `[[other-spec]]`, `[[other-spec/design#heading]]` — never by a path into `intent/.specs`.
- [ ] **Every entity's and DTO's fields** are a `<DataModel>`, and **every Command / Query** is an `<ApiEndpoint>`. No entity's shape is given as a prose list or an ad-hoc table.
- [ ] The **realization plan is a table** with `[model]` / `[code]` / Depends-on columns, complete enough for `sdd-tasks` to project a task list from mechanically.
- [ ] Every **decision I settled with the user** is its own `<Callout tone="decision">` (or `tone="risk"`) with a bold **Why:**, and module prerequisites are a `<Callout tone="warning">`.
- [ ] **Nothing normative lives only inside a block.** A block presents; a claim the implementation must honour is also stated in prose, so a reader skimming the text never misses a requirement.
- [ ] Where a section has NO block, that is a judgement I would defend — the content genuinely is prose — rather than an omission.

## As-built mode (extraction)

When `/sdd-extract` loads this skill, or `/sdd-run` hands it a Capability, the user has decided to **document the design as it exists** — that is a user decision, so these deltas override the design rules above:

- **Describe, never propose.** No module search, no trade-offs to put to the user, and no `ask_user_question`. Application prerequisites, module prerequisites and model changes are all **"none"**.
- Explain the design with **diagrams**: a `` ```mermaid `` flowchart or sequence for the runtime flow, and a `<Wireframe>` for any UI.
- Use a `<FileRef>` for every file you name and a `<ModelRef>` for every modelled element.
- If a designer models any part of the feature, add a **Services contract** table (operation, inputs, result, the requirement it serves).
- The **realization table** maps each requirement to its `[model]` elements, its key files and the tests that cover it. This is what traceability reads, so leave no requirement out.
- Decisions become `<Callout tone="info">` notes on why the code is the way it is, where the code or its history shows it. Don't invent rationale.

## Dispatched by /sdd-run

As a `/sdd-run` sub-agent, stop once `design.md` is written: the orchestrator raises the gate, so skip the section below and end with the report your instructions ask for, naming any assumptions and module or architecture decisions.

## Then raise the phase gate

Tell the user the design is ready to review — call out any assumptions you made, and any **module prerequisites / architecture decisions** you settled with them, so they can correct them. Keep this to a **brief summary**: never paste `design.md` into the chat, because every surface reads the artifact off disk.

Then, with the artifact written and no design question left open, call **`advance_spec_phase(slug, artifact: "design", toPhase: "tasks")`** — this is the approval gate, and it works from every surface. In-app it raises an approval card and blocks until the user decides; under a spec whose manifest carries `gates: auto` it advances immediately. On **reject**, revise `design.md` per the user's feedback with `write_spec` and call the gate again. Phases advance **one gate at a time** (the tool refuses a jump), so this call moves the spec to **tasks** and nothing further — don't write tasks yourself yet.
