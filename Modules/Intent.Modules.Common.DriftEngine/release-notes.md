### Version 1.0.0

- New Feature: The drift engine. It compares the Domain and Services designers' models with hand-written C#, only within the code a `Drift Scope` on the Codebase Structure designer puts in scope, and reports each difference in the application's drift report through Intent.Common.DriftReporting. It reads code and never writes it.
- New Feature: What it checks: classes, attributes, associations (navigation properties), constructors and enums; DTOs, commands, queries, services, service proxies and their operations' return types and parameters; HTTP routes, verbs, parameter sources and authorization, read from ASP.NET Core controllers and Minimal APIs; the file and namespace File Config sets; and relational tables, schemas, primary keys, indexes, foreign keys, column names, types, lengths, precision, defaults and required columns, read from EF Core.
- New Feature: Java code gets the same checks, read with a .NET parser so no JDK is needed: JPA annotations for the relational checks, Spring MVC annotations for HTTP, and nullability where the code annotates it.
- New Feature: TypeScript and Vue single-file components are read with TypeScript's own parser on Intent Architect's own Node.js: their types, module functions, components' props and emits, imports through `tsconfig.json`, and what their code calls.
- New Feature: Razor components are read as the C# they compile to, one type with their code-behind: routes, attributes, injected services, `@code` members and what they call, and `@using`s with `_Imports.razor`'s.
- New Feature: Protobuf `.proto` files (proto2, proto3 and editions) are read: messages, enums and gRPC services, fields with their numbers and whether they can be left unset, rpcs with their streams, and options.
- New Feature: Razor markup and Vue templates are read alike: elements, the components their tags name, attributes and directives, and text and values with the code in them.
- New Feature: Modules extend the engine through code: a `DriftEngineExtensionBase` factory extension adds claim kinds and vocabulary for any designer, code readers, claim readers, comparers and rules over the model and code together, and can say what the house's own helpers mean (a string parsed into an enum, a response helper's body) without redoing a framework's checks. The engine reads the model and the code for them (an element's linked elements, each method's calls, their type arguments and what their arguments are, a literal's value included, and the string a value builds, such as a URI put together from fields, interpolation and helper methods), so a module brings its rules, not a parser. The engine itself knows no technology; EF Core and ASP.NET Core are extensions built the same way.
- New Feature: The `Drift Scope` stereotype on the Codebase Structure designer's Root Folder and Folders: rows of globs marked In, Out or Context (read for what it says, never reported on), every Out and Context row with a reason, so tests, scaffolds and vendored code are left out. The drift report holds only drift; what was left out is listed in the Software Factory log.
- New Feature: The `Drift Check` stereotype on the Root Folder turns on opt-in rules that report code the model doesn't describe (files, types, public members, or a module's own rule), with exceptions and severity overrides, each with a reason.
