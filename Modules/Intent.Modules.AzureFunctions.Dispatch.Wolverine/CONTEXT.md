# CONTEXT.md — Intent.Modules.AzureFunctions.Dispatch.Wolverine

## Purpose

Factory extension module that injects Wolverine dispatch logic into Azure Function classes generated by `Intent.AzureFunctions`. This module contains no templates of its own — it hooks an existing template from another module.

---

## Key Architectural Decisions

### Factory extension only — no new templates

This module is a factory extension. It does not generate new files. It modifies `AzureFunctionClassTemplate` instances produced by `Intent.AzureFunctions` by injecting Wolverine-specific dispatch code into the function method bodies.

This is the correct pattern when a dispatch technology needs to wire into an existing host/trigger infrastructure that is already generated by another module.

### Grouping strategy: one function class per parent folder element

`CqrsAzureFunctionClassTemplateRegistration` groups Commands and Queries that have HTTP trigger settings by their parent folder element in the Services designer. One Azure Function class is generated per folder group — this mirrors the MediatR AzureFunctions dispatch pattern and is the established Intent convention for CQRS-over-HTTP dispatch to Azure Functions.

Do not change to a one-class-per-operation model. The grouping exists so that related operations share a single Function App trigger class, reducing deployment unit count.

### Template filtering: only Command/Query mapped elements

`AzureFunctionsWolverineDispatchExtension` filters `AzureFunctionClassTemplate` instances by checking whether the mapped element is a `CommandModel` or `QueryModel`. Plain (non-CQRS) Azure Functions are left entirely untouched. This filter is load-bearing — removing it would cause the extension to inject Wolverine dispatch into unrelated function classes.

### Dispatch: `IMessageBus.InvokeAsync<T>` vs `InvokeAsync`

- Commands with a return type: `await _sender.InvokeAsync<TResult>(command, cancellationToken)`
- Commands without a return type (void): `await _sender.InvokeAsync(command, cancellationToken)`
- Queries always have a return type: `await _sender.InvokeAsync<TResult>(query, cancellationToken)`

`IMessageBus` is injected via constructor with an `ArgumentNullException` guard (not via `[FromServices]` or field assignment without validation).

### Route parameter mismatch validation

When a function has route parameters that also appear as fields in the body payload, the extension generates an explicit equality comparison and returns `BadRequestObjectResult` on mismatch. This prevents silent data inconsistency where the route says one thing and the body says another.

### HTTP-verb-aware return statement mapping

Return statement generation is conditional on the HTTP verb:

| Verb | Success result | Not-found result |
|---|---|---|
| GET | `OkObjectResult` | `NotFoundResult` |
| POST | `CreatedResult` (with `getById` route when discoverable) | — |
| PUT / PATCH | `NoContentResult` or `OkObjectResult` | — |
| DELETE | `OkResult` or `OkObjectResult` | — |

Do not flatten to a single `OkObjectResult` for all verbs. The verb-aware mapping is intentional and matches REST conventions.

### imodspec dependency: `Intent.Application.Wolverine`, NOT `Intent.AzureFunctions`

This module depends on `Intent.Application.Wolverine` in the imodspec (to access `CommandModelsTemplate.TemplateId` and `QueryModelsTemplate.TemplateId` as type sources).

It does NOT declare `Intent.AzureFunctions` as an imodspec dependency. The `AzureFunctionClassTemplate` is found at SF runtime via `FindTemplateInstances` — a dynamic lookup that does not require a compile-time package reference to the owning module.

## Interactions with Other Modules

| Module | Relationship |
|---|---|
| `Intent.AzureFunctions` | Provides the `AzureFunctionClassTemplate` that this extension hooks. Found at runtime via `FindTemplateInstances`. Not an imodspec dependency. |
| `Intent.Application.Wolverine` | imodspec dependency. Provides `CommandModelsTemplate.TemplateId` and `QueryModelsTemplate.TemplateId`. |

---

## Anti-Patterns

- **Do not add `Intent.AzureFunctions` as an imodspec dependency** to gain access to its template ID constants. Use string constants or the runtime lookup pattern instead.
- **Do not use a single `OkObjectResult` for all HTTP verbs.** The verb-aware return mapping is intentional.
- **Do not skip the route parameter mismatch check.** Silent body/route disagreement is a real data integrity risk in REST APIs.
