# Re-verify mode (dispatched with requirement ids)

When told to re-verify only some ids (as `/sdd-run` does after a heal), the rest of the verdict stands as recorded. Judge only those ids, exactly as `SKILL.md` describes, with these deltas:

- **Ids may be criteria** (`R3.14`): judge only those, and give one result for each requirement they belong to. Judge each by its test status (`judging-tests.md`): a tested criterion's tests are run, never re-read.
- **Load only what they need, once.** Read `catalog` and `coverage` in one call each, passing the requirement of every id as `requirementId`, comma-separated (`R7,R13`; a criterion id finds no catalog or coverage row). `coverage` already carries each requirement's trace targets, so skip `traceability`. Read `tests` once with the same list, plus any requirements whose tests you are told to run, for their statuses, `tests` counts and `testFiles`, and only the journeys those ids name under **Realizes:**. Clauses and citing tests are the sceptic's to read. You don't need the whole requirements document or the design.
- **Review only the new changes.** Leave `refA` unset. Given the spec, the change review starts at the commit the last verify recorded (range line "(last verify)"), because that verify resolved every untraced change before it; it falls back to the default range by itself when that commit is gone.
- **No reader fan-out.** Judge the ids yourself. Challenge the candidate gaps (`challenge.md`).
- **Traceability gaps only:** when told so, judge them from `coverage` and the change review alone. Read no code and dispatch nothing.
- **When told to run the tests citing other requirements**, run them once, by the files they sit in, with the commands in `judging-tests.md`, together with the tests of the ids you judge. Record each failing test as a disagreement on the criteria its title cites, even on a requirement you were not given. When a test fails in its own setup before it asserts any behaviour (a script or module it never loads, a fixture that no longer matches the code's shape), say so in the gap's `actual` and recommend **change the test**. With no ids listed, judge nothing else.
- **Record with `merge: true`**, with one result for each listed id and each requirement a failing citing test gave a gap, and none for any other. Without `merge`, the requirements you didn't judge drop out of the verdict.
- **Problems outside the list are observations, not gaps.** A requirement you weren't asked to judge that looks wrong, or an untraced change that realizes one, goes in your report under "Observations", with `file:line`. Record no result for it, even when `record_spec_verdict`'s feedback asks for a gap.
