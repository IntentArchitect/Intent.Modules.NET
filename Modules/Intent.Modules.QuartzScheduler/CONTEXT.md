# Intent.QuartzScheduler — Context

## Module Interactions

- **Dispatcher for command-publishing jobs (MediatR or Mediator).** A Scheduled Job linked to a command looks up the command through the `Application.Contract.Command` role, which both `Intent.Application.MediatR` and `Intent.Application.Mediator` (from `1.0.1-pre.0`) fill. The template picks the `ISender` from the template that answered: `Intent.Application.Mediator.CommandModels` gives `Mediator.ISender`, anything else `MediatR.ISender`. The id is a string, with no project reference to the Mediator module, which is the same seam pattern EF Core and the eventing modules use for Mediator. Renaming or moving that template in Mediator's Module Builder breaks this silently. Added in `1.0.17-pre.0` (2026-11-03) after a client report that a linked job could not generate when Mediator was installed.
- **The lookup runs in `OnBuild`, not the constructor.** Before 1.0.17 the constructor called `GetTypeName` on the role, and with no template filling it the Software Factory process exited with no error message. Lookups belong in build callbacks anyway, because constructors run while templates are still being registered.
- **Tested in** `Tests/TestMediator.Quartz` (Mediator) and `Tests/AdvancedMappingCrud.Cosmos.Tests` (MediatR, `CommandDelegateJob`).
- **Intent.Bugsnag generates a Quartz `IJobListener`, so it must match the Quartz major this module requests.** A mismatch fails either way: a `Task` listener against Quartz 4 is rejected at startup, and a `ValueTask` listener against Quartz 3 does not compile. Bugsnag (from `1.0.10`) does not repeat this module's rule. It reads the NuGet packages that `QuartzConfigurationTemplate` (role `Distribution.DependencyInjection.Quartz`) requested, and treats a `Quartz*` package at 4.x or later as Quartz 4. So the package request in that template's constructor is a contract: keep requesting a `Quartz*` package from it, at the version the project really gets. Because Bugsnag follows whatever this module requests, it works with this module before and after `1.2.0` and has no `<interoperability>` entry for it. This module's `.imodspec` does have one: installing `1.2.0` with an older Bugsnag would put a `Task` listener on Quartz 4, so it installs Bugsnag `1.0.10`. That detect version is hand-maintained; move it to the release version when the prerelease ships.

## Architectural Decisions

- **Quartz 3 and Quartz 4 are generated side by side. A project gets Quartz 4 only when every framework it targets is `net10.0` or later** (`Templates/QuartzVersion.cs`, used by `ScheduledJobTemplate` and `QuartzConfigurationTemplate`). Quartz 4 ships a `net10.0` build only (no `netstandard2.0`), so `net8.0`/`net9.0` projects cannot move and stay on the still-maintained 3.22.x line. Below `net10` the output is meant to stay byte-for-byte what 1.1.0 generated. Decided 2026-11-13, shipping in 1.2.0 (development released 1.1.0, the .NET 11 support, while this work was in flight). The cost is maintaining both shapes until `net8`/`net9` support is dropped.
  - Rejected (2026-11-18, after review): `GetMaxNetAppVersion().Major >= 10`, the rule first shipped in this work. A `net9.0;net10.0` project would get Quartz 4 for its `net9.0` build, which Quartz 4 does not support. For such a project, packages resolve against the `.NET 9` rows instead of the highest framework (`QuartzVersion.GetPackageFramework`), so every target framework gets Quartz 3.
- **On Quartz 4, web projects request `Quartz.AspNetCore` 4.x, other projects the core `Quartz` package, and `RemoveNugetPackageEvent` is published for `Quartz.Extensions.Hosting` and `Quartz.Extensions.DependencyInjection`.** Intent does not drop a package reference just because no template requests it any more, and a 3.x reference left beside Quartz 4 causes CS0433 duplicate types. Those two are empty forwarding packages on 4.x, and Quartz says to delete them. `Quartz.AspNetCore` is still a real package on 4.x (the HTTP API and health checks), so web projects keep requesting it: an existing 3.x reference is raised in place, and one a consumer added for the 4.x HTTP API survives.
  - Rejected (2026-11-18, after review): request `Quartz` for web projects too and remove `Quartz.AspNetCore`. A removal event fires on every run and cannot tell our reference from a hand-added one, so a consumer using the 4.x HTTP API lost the package on every regeneration, not just once.
  - Known gap: a non-web project with a hand-added `Quartz.AspNetCore` 3.x reference is not raised (that project requests `Quartz`), and the 3.x hosting assembly it brings in transitively clashes with Quartz 4. Raise or remove it by hand.
- **The `net10` row of `Quartz.Extensions.Hosting` is kept in the Module Builder model at 4.x**, though `net10` never requests it. Without a `net10` row, the `net9` 3.x row would resolve for `net10`. The `Quartz.AspNetCore` `net10` row is the one web projects request.
- **The generated `QuartzConfiguration` code is the same for both majors.** `AddQuartz`, `ScheduleJob<T>`, `WithCronSchedule`, `WithIdentity` and `AddQuartzHostedService(o => o.WaitForJobsToComplete = true)` keep their call shapes on 4.x; only the package changes.

## Open Risks

- **Choose the `Execute` shape with `Async(asValueTask: …)`, never `Async()` alone.** `CSharpClassMethod.Async()` is `Async(asValueTask: false)`, and it rewrites a `ValueTask` return type to `Task`. The first 1.2.0-pre.0 build added the method as `ValueTask` and then called `Async()`, so every Quartz 4 job came out as `Task Execute(…)` and did not implement `IJob` (found by installing into a scratch consumer, 2026-11-18).
- **Verified against a consumer (2026-11-18)**, in a throwaway solution whose repository pointed at the build output, upgrading from 1.1.0 / Bugsnag 1.0.9:
  - `net10` worker: `Quartz.Extensions.Hosting` 3.22.10 is replaced by `Quartz` 4.7.3, jobs get the `ValueTask` / `CancellationToken` signature, the dispatch job forwards the token, and the app starts and runs both jobs. A hand-written `Execute` body survived the signature change, so `Body = Mode.Merge` matches the method across a changed return type and parameter list, and no mitigation is needed.
  - `net10` web: `Quartz.AspNetCore` is raised in place to 4.7.3, and the app starts and runs its job.
  - `net9`, and `net9.0;net10.0` multi-target: zero Quartz diff, and both build.
  - The Bugsnag interoperability detect moved Bugsnag 1.0.9 to 1.0.10-pre.0 automatically, and did not install Bugsnag into an application that did not have it.
  - Fresh install on `net10` (this module alone, no prior 1.1.0): `Quartz` 4.7.3 from the first run, Quartz 4 shapes, `[DisallowConcurrentExecution]` kept, and a re-run left the hand-written bodies alone.
  - Central package management, upgrading in two steps. Bugsnag 1.0.10 alone, with this module still on 1.1.0, changed nothing, and the app ran on Quartz 3.22.10. Then 1.2.0 moved the project's `PackageReference` to `Quartz` and added `Quartz` 4.7.3 to `Directory.Packages.props`, and the app ran on Quartz 4.7.3. The `Quartz.Extensions.Hosting` 3.22.10 `PackageVersion` stays in `Directory.Packages.props`: `RemoveNugetPackageEvent` removes a project's reference, not the solution-wide version entry, which another project may still use. An unreferenced `PackageVersion` does not affect the build.
  - The Tests solution apps are on 1.2.0-pre.0. The `net10` apps took the Quartz 4 shape: `WebAndWorker.QuartzWorker` and `BugSnagTest.ServiceHost` moved to `Quartz`, and `TestMediator.Quartz.Api` (Mediator dispatch, web) has `Quartz.AspNetCore` 4.7.3. The `net8`/`net9` apps (`AdvancedMappingCrud.Cosmos.Tests`, `BugSnagTest`, `WindowsServiceHost.Tests`) regenerated with zero source diff. All six build, and the three `net10` apps start on Quartz 4.7.3. `WebAndWorker.QuartzWorker` fails service validation in Development (`AuthorizationPolicyCache` cannot resolve `EndpointDataSource`) on 1.1.0 / Quartz 3 too, so it was run in Production.
