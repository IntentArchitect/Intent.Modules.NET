# Context: Intent.ModuleBuilder.AI.DotNet

## Purpose

Bundles one Intent Architect AI agent skill, `intent-dotnet-module-integration`, into the consuming repo's `.claude/skills` and `.opencode/skills` trees. Unlike `Intent.ModuleBuilder.AI.Modelers` (which documents Intent's own built-in designers), this module documents how to integrate with another **runtime .NET module in this repo** — its dependency identity, template inventory, generated shape, metadata contract, and extension points — so a module-building AI can wire against, say, `Intent.Modules.AspNetCore.Controllers` without reading that module's templates cold. The first (and so far only) resource file covers ASP.NET Core Controllers.

## Architectural Decisions

- **The typed route is the only route taught, deliberately.** An earlier design note framed this module as teaching "cold integration" — reaching a foreign module's generated output via role strings alone, without referencing its package. That framing was dropped before implementation: the skill instead mandates referencing the target module's own NuGet package (a `PackageReference`, following `Dispatch.Wolverine`'s precedent rather than the in-repo `ProjectReference` shortcut `Dispatch.MediatR`/`Dispatch.ServiceContract` use) so an agent gets the typed model interfaces (`IControllerModel` etc.) instead of falling back to `ICSharpFileBuilderTemplate` + a raw `modelId` string. The untyped variant is documented in the resource file's Traps section as a fallback to recognise, not a pattern to copy.
- **Correlate by metadata, never by name — stated as the skill's most important Must.** Generated method/parameter names are transformed (`ToPascalCase`), de-duplicated, and overloaded, so a name-based `FindMethod` breaks silently the moment the designer model changes shape. Every reference file states the exact `TryGetMetadata` keys a target module's generated members carry, for exactly this reason.
- **`SKILL.md` routes; it does not restate `intent-module-orchestrator`'s mechanics.** Callback priorities, the request-publishing vs `FileBuilder`-mutation split, and the `"model"` metadata bridge are generic module-building mechanics that already live in `intent-module-orchestrator`. This skill's `SKILL.md` explicitly points there instead of re-deriving them, so the two skills don't drift out of sync on shared ground.
- **Each resource file states a "Version compatibility" section (§0) — a single verified-against version plus only the facts that are actually version-gated, not a full per-version changelog.** Checked `Intent.AspNetCore.Controllers`' own `release-notes.md` and found two facts elsewhere in the resource file that are NOT true across its whole history: `<decorators>` being empty only holds from v7.0.0 (before that, `ControllerDecorator` was the real extension point, removed in 7.0.0), and the multi-host `FindTemplateInstances` trap only applies from v7.1.6 (multi-host support). Considered instead a full version-by-version fact matrix — rejected as unsustainable maintenance for facts that mostly don't change release-to-release; the "verified against X, here are the known exceptions" shape stays truthful without demanding a changelog audit on every future resource file. `SKILL.md` gained a matching Must/Must Not pair instructing an agent to check this section against the actually-installed version before trusting a version-gated fact.

## Invariants & Constraints

- Same flat layout as `Intent.ModuleBuilder.AI.Modelers`: both `File Template` elements (type `Single File`) sit directly under `Skills/`, named `IntentDotnetModuleIntegration_SkillMd_Agents` / `IntentDotnetModuleIntegration_Resources<Name>Md_Agents`. `File Settings(Output File Content=Text, Templating Method=Markdown File Builder)`; `Template Settings(Source=Lookup Type, Role=AI.Context.Skills)` with `Default Location` left **unset** — the `MarkdownFile` constructor's `relativeLocation` argument carries the real output path (`SkillName` for `SKILL.md`, `"intent-dotnet-module-integration/resources"` for each resource file).
- `.csproj` needed a version bump over what the `Intent.ApplicationTemplate.ModuleBuilder` architecture scaffolds by default in this repo: `Intent.Modules.Common` `3.7.2` (the scaffolded floor) does not yet expose `Intent.Modules.Common.FileBuilders.MarkdownFileBuilder` / `MarkdownBaseTemplate<>` — bumped to `3.11.1` to match this repo's `Intent.Modules.EntityFrameworkCore.Repositories` (a working sibling that already uses the Markdown builder), which in turn forced `Intent.SoftwareFactory.SDK` up to `3.14.0` to clear an `NU1605` downgrade error (`Intent.Modules.Common 3.11.1` requires `Intent.SoftwareFactory.SDK >= 3.14.0-pre.0`). Any future module scaffolded fresh from this same architecture template in this repo will likely need the same two bumps until the template's own defaults are updated.
- `.imodspec` dependencies: `Intent.Common` (`3.11.1`, matching the `.csproj` bump above) + `Intent.Common.Types` (`3.4.0`) only — no factory extensions, no designer models read.
- `authors` is hand-set to `Intent Architect`, matching every sibling module in this repo — the architecture template auto-populates it from the solution name (`Intent.Modules.NET.AI`) instead, which is wrong and must be corrected by hand after scaffolding.

## Critical Implementation Hazards

- **Never edit a `...TemplatePartial.cs` markdown raw string with Intent's `patch_file` / `write_file`.** Confirmed again in this module: the formatter re-indents the whole raw string to the constructor's nesting level and flattens fenced code blocks. Used the host's native file-edit tool for both template partials' `FromMarkdown(...)` bodies instead, and verified via `get_file_diffs` before applying.
- **The Markdown File Builder normalizer breaks a paragraph that starts the physical line with `**`** — it silently becomes `- *text**` (a broken list item). Confirmed live in this module's own generated output on the first attempt (a "Never correlate by name.** ..." paragraph). Bold is safe mid-sentence, and safe immediately after a list marker (`- **Text**`) or blockquote marker (`> **Text**`) — only true column-zero bold breaks. Fixed by rewording the sentence to drop the leading bold rather than working around the normalizer.
- **This Intent Architect session hit repeated stale in-process/generation-cache state while iterating on this module** — three distinct symptoms, not one: (1) a `run_software_factory` call kept returning the pre-fix version of generated markdown content, with an identical `contentHash`, after the module was rebuilt and reinstalled — resolved only after the user restarted Intent Architect; (2) immediately after the restart, a `run_software_factory` run on the *producer* app itself proposed deleting all four hand-authored template files and regenerating a `.imodspec` with a wrong `id`/`version`/empty `<templates>` — even though the live model (read via `get_designer_model_structure`) was confirmed correct throughout; a second `run_software_factory` call (no other change) produced the correct, non-destructive output; (3) later in the same session, after a source fix + rebuild + reinstall, a `run_software_factory` call reported "nothing staged" (falsely implying the fix was already live) — verified false by reading the file straight off disk, and resolved by deleting `Modules/.cache/modules/Intent.ModuleBuilder.AI.DotNet.1.0.0-pre.0` and reinstalling again. **Lesson: never trust a "no changes" or an unexpectedly destructive `run_software_factory` result at face value for a module under active iteration — verify the actual on-disk content (or, for a destructive result, the live model) before applying or before concluding a fix landed.** Clearing the module's own `.cache/modules/<id>.<version>` folder resolved two of the three symptoms; the third needed a full Intent Architect restart.

## Module Interactions

- **Intent.ModuleBuilder.AI.Modelers** — no package dependency, matching that module's own recorded precedent for `Intent.ModuleBuilder.AI.Skills`. The two skills are soft, name-only cross-references in each other's `description`/Must Nots (`intent-modelers-integration` for designer/model integration, `intent-dotnet-module-integration` for runtime .NET module integration) — each must remain independently installable.
- **Intent.Modules.AspNetCore.Controllers** (and its `Dispatch.MediatR` / `Dispatch.Wolverine` / `Dispatch.ServiceContract` satellites) — read-only source of truth for every fact in `resources/aspnetcore-controllers.md`. Not a package dependency; this module never installs against them, it only documents them. Verified directly against `ControllerTemplatePartial.cs`, `IControllerModel.cs`, `TemplateRoles.cs`, `MediatRControllerInstaller.cs`, `ServiceContractControllerInstaller.cs`, both `CqrsControllerModel.cs` files (`Dispatch.MediatR` and `Dispatch.Wolverine`), and `Intent.AspNetCore.Controllers.imodspec`'s `<interoperability>` block — not carried over from an unverified draft.
- **Neither `Dispatch.MediatR` nor `Dispatch.Wolverine` has a `CONTEXT.md`** recording the `IControllerModel.Folder` off-by-one trap (`ServiceControllerModel.Folder` = the service's own folder; `CqrsControllerModel.Folder` = the *parent* of the grouping folder) — despite that being exactly the kind of fact `CONTEXT.md` exists to hold. The resource file cites the source files directly instead of a doc that doesn't exist.
