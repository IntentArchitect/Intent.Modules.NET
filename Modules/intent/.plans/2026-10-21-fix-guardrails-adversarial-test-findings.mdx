# Fix what the adversarial test found in the Guardrails drift check

## Context

The adversarial test (<FileRef path="D:/Dev/basislink_poc2/BasisLinkSolution/intent/.plans/2026-10-20-guardrails-adversarial-test.md" label="test report" />) ran 10 agent cases against BasislinkService:

- **The agents passed.** In all 10 cases the model ended up matching the code, checked against the tester's own Roslyn oracle, not the drift reports.
- **The drift check failed.** It missed 4 of 30 planted mutations and reported a correct model as contradicted once.

So today "No drift" does not yet mean "the model is right", which is the system's whole promise.

**One example, before and after.** Someone adds `MillSummaryDTO.cs` beside the modelled DTOs in `Basislink.DTO/Ssb/` and doesn't model it.

- **After this plan:** the Services report has, under *Wrong: code the model doesn't describe*:

`` `MillSummaryDTO` (class): not modelled. Location: `Basislink.DTO/Ssb/MillSummaryDTO.cs:5` ``

There are no Module Builder model changes, because no templates are added or removed. The version stays at 1.0.0-pre.0 (your earlier decision).

### 1. New classes in expected locations (F1, F2)

- **Expected locations, automatic.** An expected location is a folder that one of the module's own contract templates writes a file into. Every top-level type (class, record, struct, interface or enum) in a C# file there is reported as not modelled, unless:
  - a template in this run generates its file (any template, so another designer's types in a shared folder aren't reported); or
  - it has the same name as a generated type (another part of a partial type).
- **Patterns, from the recipe.** An `own` entry can name types anywhere, for example:
  - `file:Basislink.DTO/**/*.cs > class` (every class in the DTO project);
  - `class with :BaseBusinessObject\\b` (every business class).

  Today such an entry would report every modelled type too, because only code a fact located counts as described. Types the Guardrails templates generate will now count as described, so only unmodelled ones are reported.
- **Exceptions** cover both, by file pattern or type name.

<Callout id="expected-folders-scope" tone="warning" title="Folders only, not their subfolders">

Brand-new folders are only covered by an `own` pattern. A class in a new `Basislink.DTO/Mills/` folder is found by `file:Basislink.DTO/**/*.cs > class`, not by the automatic scan. That's accepted because a recursive scan of each template's output root would sweep in whole projects (DbContexts, migrations, infrastructure) and bury the real lines. configure-drift-check will tell the AI to add a pattern for each kind of type that can appear in a new folder.

</Callout>

<Callout id="helpers-beside-types" tone="warning" title="Helpers kept beside modelled types are reported once">

The first run after upgrading will report any existing unmodelled class in those folders. The AI resolves each as normal: model it, add an exception for a helper, or ask. That's the intended behaviour, not noise.

</Callout>

### 2. "Stated but unreadable" (F6)
- **`unreadable` read case.** A new read case property: `{ "match": "\\[Route\\((?!\")", "unreadable": true }` means the code states the fact, but not in a form the recipe can read, such as a constant or a helper. It is reported under *can't be verified*, quoting the code. Without it, the recipe's `default` stood in, and an identical route read from a constant became "code (none)". A case with both `unreadable` and `value` is a recipe error.
- **The skill** tells the AI to give every recipe that has a `default` an `unreadable` case for other forms of the same declaration. The controllers example shows it for routes.



### 3. Index facts (F3, Domain)

- **Two new facts per index**, read from the `Index` stereotypes on a persisted class's attributes (`UniqueKey`, `Order`, `IsUnique`; the form Basislink's model uses):
  - `index.columns`: the attribute names in `Order`, joined with commas;
  - `index.unique`: `true` or `false`.
- **Placeholders:** `Entity` and `Index` (the index name).
- **Newer `Index` elements:** if the RDBMS module also models indexes as elements, those are read too. Confirm their shape by decompiling the `GetIndexes` extension in `Intent.Modules.Metadata.RDBMS` during implementation; don't guess it.
- The configure-drift-check fact table is generated from `FactKinds`, so it lists the new facts automatically. The EF example gains an index recipe and an `own` entry for `HasIndex` chains.

<Callout id="index-scope" tone="warning" title="Sort direction, filters and included columns aren't checked yet">

The planted mutation was a rename plus `IsUnique`, which columns, name and uniqueness cover. Descending columns, filters and included columns are deferred. Basislink will show one "no recipe" line per index fact until its recipe is extended; that line is what sends the AI back to configure-drift-check.

</Callout>

### 4. Reports in the solution's `.cache` folder (F5, F9)

- **Where:** `intent/.cache/guardrails/<application>/DomainDriftReport.md` and `ServicesDriftReport.md`, in the `.cache` folder beside the solution's `.isln`. Every Intent solution's own `.gitignore` already ignores `.cache/`, so configure-drift-check no longer adds `*DriftReport.md` to `.gitignore`.
- **How:** the check writes the file itself on every run, failing runs included, so the report always matches the latest run. It doesn't write on CI, as today.
- **The template stays.** The `DriftReport` template is still where the check runs (the after-build step), but it no longer outputs a codebase file. Its `CanRunTemplate()` returns false once the check has run: the switch CI uses today, now applied everywhere. No Module Builder change.
- **The path** comes from the solution's configuration; confirm the SDK property during implementation. The drift error and the "check is off" warning name it. The rule and skills are generated per application, so they state the actual path rather than "the root of the application's output".

<Callout id="old-report-copies" tone="warning" title="The first run after upgrading deletes the old report copies">

Because the template no longer outputs them, the Software Factory proposes deleting the copies it generated before (in Basislink, `Basislink.API/DomainDriftReport.md` and `ServicesDriftReport.md`). That deletion is applied once. If that run also has drift errors, the deletion is left unticked like everything else.

</Callout>

<Callout id="write-outside-staging" tone="warning" title="The report is written before anything is applied">

The file is written while the Software Factory runs, not staged for review. That's accepted because it's a git-ignored diagnostic in Intent's own cache folder, not code, and writing it directly is what keeps it current after a failing run.

</Callout>

### 5. Guidance (F7, old sync files)
- **Key columns:** the EF example's `column.required` recipe gets a case that reads `HasKey` membership as `true`.
- **Old sync files:** the rule says `guardrails/*.sync.json` belong to the old drift check, nothing reads them, and they can be deleted. configure-drift-check deletes them.

## Not addressed, and why

<Callout id="f8" tone="info" title="F8: the Software Factory rewrote hand-written DTO members">

That was a planted *model* change (a field's type changed, a field removed). Regenerating DTO members from the model is what the Guardrails contract templates exist to do. The drift check flagged both, and its errors stopped the changes being applied, which is the guard working. Whether member removal should be marked destructive is the Software Factory's classification, not the module's.

</Callout>

<Callout id="f4" tone="decision" title="F4: a second [Route] on an action">

Your call: the model can't express several routes on one action, so a check for it would report drift nobody could fix in the model. A recipe still reads the first route.

</Callout>

<Callout id="f10" tone="info" title="F10: a report-only run leaves git dirty">

Every Software Factory run rewrites `application.deviations.log.xml` and `application.managed-files.xml`. That's platform behaviour, outside these modules. The reports themselves no longer add to it: they're written to the ignored `.cache` folder.

</Callout>

<Callout id="hand-edits" tone="decision" title="Hand-edit contradictions keep asking the developer">

Your decision: sync-model keeps asking one question for contradictions the AI's own work didn't cause.

</Callout>

<Callout id="root-guidance" tone="risk" title="Basislink's agents don't load the generated guidance">

The rule and skills are generated into `Service/BasislinkService/.claude/`, but agents load the workspace root's `.claude/`. The tester copied them across by hand. Until Basislink's AI-context outputs land in the root `.claude/` (an application setup change, not a module change), every module update to the guidance needs that copy repeated.

</Callout>
