# Context: Intent.Common.DriftEngine

## Purpose

The drift engine that converges Intent.Common.Drift and the custom drift modules built per adoption (eShopCustom, the Java spike) (plan: `docs/plan.md`; specification: `docs/spec/`). It is the shared foundation those modules kept rebuilding: scope, code readers, turning the model into claims, the verified, contradicted or can't-verify policy, and reporting. Modules extend it through code with no ceiling; recipes are a shortcut for simple claims. Phase 1 delivers the C# reader, the structure checks (Domain and Services packs), scope and the extension API.

## Architectural Decisions

- **A module states what to check in C#, not only how to read the code (user decision, 2026-11-13: "this is literally the whole point").** An extension's `ClaimSources` (`IClaimSource`) return `ClaimSpec`s: the element, the kind, the value the model states, anything the source worked out for its reader (`Value`, such as the module's own model of the element), the claim it waits on (any element, any designer), and where the model states it. Its `Kinds` define kinds in code, and its `Designers` name the designers it reads (a module's own designer the engine doesn't know). A source reads the model through the engine (`ModelContext`, below), or with the module's own generated API (`DriftEngineExtensionBase.Application` gives the run's application). A pack's vocabulary is the same thing as data, a shortcut; a source's claim with a pack claim's designer, element and kind replaces it. An existence claim's reader can locate anything (`ClaimReading.Found(object, Span)`) and the claims waiting on it get it (`ClaimContext.Located<T>`). Why: the JSON expression language was the only way to say what the model states, so a module whose model reading it couldn't express was stuck. A check is never trimmed to fit the engine; one that doesn't fit is an engine gap to fix. Proved with eShopCustom's Domain Event Origin links and its Services sends and publishes.
- **The engine reads no language itself; a language is an extension (user decision, 2026-11-13).** An `ILanguage` reads its in-scope files into the graph's files, types and members, and keeps its own syntax on the graph for the extensions that read that language. The stock C# language (`Stacks/CSharp`, extension `csharp`) parses each file once with Roslyn and shares the trees as `CSharpSyntax`; EF Core, ASP.NET Core and modules' own readers all read that one parse. Its profile (type names, collections, type kinds) is its own pack, `csharp`; the run uses the profile of the language that read the most files. The Core has no Roslyn reference. Java will be another language extension with its own parser and profile. How a language names and wraps the model's members is its profile's too, never the core's (2026-11-13): `naming` gives a pattern per kind of code (`{Name|camel}` for a Java field or method; C#'s `interface` is `I{Name}`, used when the conventions allow only an interface, which is how the Domain Repository finds `IOrderRepository`), and `async` lists the wrappers `operation.returns` unwraps (C#'s `Task<T>`, with `Task` as void). A kind with no pattern is named as modelled. `Engine/LanguageProfileTests` proves it with a made-up language. The type comparer compares type arguments only when the model states them.
- **Java is read with ANTLR, a pure .NET parser (user decision, 2026-11-13).** Its generated C# lexer and parser are checked in, so running it needs no Java; only regenerating the grammar does. Rejected: JavaParser through a Java process (a JDK wherever the Software Factory runs) or IKVM (unproven), though JavaParser's typed tree and type solver are friendlier to an AI. Why the AST matters less than it seems: only the Java language reader touches it, written once, while the house rules an agent writes read the engine's neutral reading, and Java frameworks state almost everything in annotations, which the reading carries. Working out which method a call reaches, JavaParser's real advantage, belongs in the engine for every language, since C# needs it too. The rule audit behind this is `docs/rule-audit.md`. The spike (`D:\Dev\Temp\JavaAntlrSpike`) parsed all 58 files of the Java eShop's backend with no errors: grammars-v4's `java/java` (pinned at `85e2dd1779`, Java 24), runtime `Antlr4.Runtime.Standard` 4.13.1, the newest on NuGet, so the tool jar must be 4.13.1 too. The grammar must carry one patch: upstream `classType` repeats a name with no dot between, so `x instanceof String s` silently parses `String s` as a type, and most files fall back to the slow full parse. The patch keeps one leading name and then only dotted ones; with it there are no fallbacks and parsing is 4 to 6 times faster. Not `java/java20`, a copy of the official grammar that the grammars-v4 README says is slower and stops at Java 20. `GetText()` drops whitespace, so the reader slices source text from token positions.
- **One Roslyn at run time, so a module's own C# reader runs on the engine's trees (proven 2026-11-13).** The engine compiles against Roslyn 4.14 and ships none; eShopCustom's modules compile against 5.0 and bundle it. In the Software Factory the Domain module's reader, built against 5.0, reads the trees the engine's C# language parsed, and caught four planted domain-event drifts. This replaces an earlier, unproven note that an extension built against another Roslyn would fail. Neither eShopCustom extension reads the trees itself any more: both read the engine's code reading (below).
- **A framework's extension answers only when its framework is in the code (2026-11-13).** EF Core reads only when the code configures an entity or declares a `DbContext`; ASP.NET Core only with a controller, an attribute-routed action or a Minimal API endpoint. Otherwise their claim readers return null, so the claim goes to another framework's extension (JPA, Dapper's) or, with none, can't be verified, never a false "the code doesn't state it".
- **The core knows no technology; everything else is an extension (user decision, 2026-11-13).** An extension (`IDriftExtension`) brings languages, packs (kinds, vocabulary), claim sources, code readers (`ICodeReader`, given the graph, with its language's syntax on it, and keeping what it finds there with `CodeGraph.Set`), claim readers (`IClaimReader`) and comparers (`IValueComparer`). The engine's own comparers are `exact`, `ignoreCase`, `number` and `set`. An extension's claim reader runs before the core's structure rules, and a later extension's before an earlier one's, so a module can read any kind, the core's included; returning null passes the claim on. A throw is `ruleFailed` on the claim plus one `config/pluginFailed` finding. Why: the engine must do everything the custom modules did, so it may not limit them; EF Core and ASP.NET Core code had crept into `DriftEngine.cs`, turning it into a Common.Drift replacement.
- **What the model states is framework-neutral; how a framework's code states it is a separate extension (user decision, 2026-11-13).** `intent.rdbms` (tables, keys, columns, indexes, foreign keys, from the RDBMS stereotypes, with the `storeType` and `literal` comparers) and `intent.http` (routes, verbs, parameter sources, security, with the `route` comparer) read no code. `intent.efcore` and `intent.aspnetcore` only read those claims from their code, so JPA and Spring MVC extensions will read the same claims. The four live in `Intent.Modules.Common.DriftEngine.Stacks` (`StockExtensions.All`), using only the public API.
- **Modules register an extension the way reporters register with the hub.** `Api/DriftEngineExtensionBase` is a factory extension that publishes itself on the run's event dispatcher before template registration; `DriftEngineReporter` subscribes at the run's start and runs the registered extensions after the stock ones. eShopCustom's Architecture module is the first to use it (its Layers as claims, its import check as a rule), and its Domain module the second (its own stereotypes, read through the stock EF Core reading); a module compiles against the engine's assemblies and ships none of them, depending on Intent.Common.DriftEngine instead.

- **The engine is its own assembly, `Intent.Modules.Common.DriftEngine.Core`, shipped in the `.imod` beside the module's (2026-11-13).** It depends on the SDK's model interfaces only (Roslyn is the Stacks' C# language's), so the acceptance suite (`Intent.Modules.Common.DriftEngine.Tests`) runs it from fixture data with no Software Factory. The module project holds only the hosting: `DriftEngineReporter`, `Reporting/DriftEngineReport` and the extension base. The `.imodspec` lists the Core and Stacks `.dll` and `.pdb` by hand. Roslyn isn't shipped: Intent.OutputManager.RoslynWeaver supplies it at run time, as for Intent.Common.Drift.
- **Reports through Intent.Common.DriftReporting with its own Areas (plan decision: both engines run side by side).** A designer's findings go in the Area `<Designer> (DriftEngine)`; scope, config and reader findings go in `Drift Scope (DriftEngine)`. A claim finding is a Model / Code finding on the element, against the code's file and line.
- **The report holds only drift (user decision, 2026-11-13, spec decision 30).** An AI reads the report, so anything that isn't drift is noise. An Area is created by its first finding and declares no categories, because the hub renders a declared category with no findings as "✓ Clean". `info` findings (the scope coverage listing, the `engine/notStated` note) and the run's claim counts go to the Software Factory log only. Don't add an Info severity to the hub to put them in the report.
- **No Drift Scope only warns (spec decision 28).** The run result still carries `scope/missing` as an error; the host logs it as a warning and adds no Area, because an error would untick every staged change, including the ones that set scope up.
- **Designers are read by id, copied from each designer module's `ApiMetadataDesignerExtensions`.** Packs name designers (`Domain`, `Services`); the host maps the name to the id so it needs none of those modules installed. An extension adds its own designers' ids (`IDriftExtension.Designers`); the SDK can only fetch a designer by id.
- **Features are built lean, end to end on eShopCustom (user decision, 2026-11-13).** eShopCustom (`D:\Dev\Temp\eShopCustom`) is the system: its custom modules (Domain, Services, FrontEnd, Architecture) are what the engine must do, each rebuilt as an extension. basislink5 and CrmBus are Common.Drift examples; rebuilding Common.Drift's checks on them is replication, not the goal. Each slice goes model claim or rule, reader, hosted run, then planted drift: every plant caught as one finding, the unchanged code clean. Cases for every example come later; existing cases must keep passing.
- **A rule is a check that isn't one claim's value (`IDriftRule`, plan block 4).** It sees the designers' elements, the evaluated claims, the in-scope code and the scope (`RuleContext`), and returns findings with an Area, a category, a subject and what else they involve (`Finding.Against`). Rules run after the claims, only when a Drift Scope is set; the engine marks each Area ` (DriftEngine)`. Why: the Architecture module's import check is one finding per import across Layers, not a value on one element.
- **Every reader gives the graph each file's declared namespaces and imports (`FileNode`, `ImportNode`).** They are the language-neutral facts a rule over imports needs; the C# reader reads `namespace` declarations and `using` directives, a Java reader will read `package` and `import`.
- **An extension can locate the code an existence claim is about (`ClaimReading.Found`), so the claims that depend on it read that.** eShopCustom's Backing Field makes an attribute's member a private field; an EF Core shadow property is a member the reader makes, typed with `CSharpSyntax.TypeOf` (the C# reader's own nullability rule). Without it a house reader could only say "present", and the attribute's type and column claims would have no member to read.
- **A claim can wait on any claim, not only on its existence (2026-11-13).** A pack's `dependsOn` names one on the same element or its owner; a claim source's names any. eShopCustom's Backing Field column waits on the field's `Property("_field")` mapping, so an unmapped field is one finding, not a second one for its column. Such a claim is still named with its owner (`PaymentMethod.Expiration`), because naming follows the chain down to `member.exists`. A missing element's "N claims on it can't be checked" counts the whole chain.
- **The engine reads the model and the code for a module, so a module's check is its own rules, never its own parser (user decision, 2026-11-13: "give the module access to read the model and read the code, part of the whole point here was not to have every module build its own parser and own common logic").** The model: `ModelContext.Elements(designer, type)`, `Links(element, association)` (the elements an association from it points at, with the end, as `ModelLink`), `HasStereotype` and `Stereotype(element, stereotype, property)`; a claim reader has it as `ClaimContext.Model`. The code, as language-neutral facts a Java reader fills the same way (the spec's `call` and `creation` nodes, code-reader.md): each method's and constructor's calls (`CallNode`: name, receiver, the receiver's type when the code says it, its arguments, its text and place), the types it creates, and every member's access. An argument (`ValueNode`) carries the types the code says it is: a creation is its type; a local, its initializer and its assignments before the call, else its declared type; a parameter, field or property, its declared type; a cast, its inner value, else the cast type; a conditional, both branches; a property path, through in-scope types. When the code doesn't say, it is unknown, and the check says it can't verify rather than guess. `CodeGraph.CallsFrom(type, member, follow)` gives a member's calls and those of the type's own methods it calls, so a raise or a send in a private helper counts; `TypeFor` finds the in-scope type a reference names. A reader passes its own finding text to `ClaimReading.Compared(actual, at, same, message)`, and the report uses it for a contradicted claim, so the module's wording and fix stay. The language reader sets calls once it has read every type, since what an argument is can depend on another type. Why: the first versions had the Domain module bring its own Roslyn reader and the Services module reuse its house parser, which is what the engine exists to stop. Proved on eShop.Ordering, neither module reading code itself, both clean on the real code. The Services module's `ServicesInteractions` compares an operation's Perform Invocation links to Commands with the `Send(...)` calls in it, and the Publish Integration Event links of a command handler, domain event handler or integration event handler with its outbox or event-bus publishes; it caught six plants: a wrong command sent, a wrong command sent from a helper method, an Identified Command sent bare, a wrong event published, a missing publish, and a `Send(CommandFor(@event))` it can't verify. The Domain module's Domain Event Origin links caught four: a wrong event through a local in the private helper the constructor calls, a removed raise, a swapped event, and an `AddDomainEvent(StockConfirmedEvent())` it can't verify.
- **An empty set is `none` on both sides.** A set kind stated always (`type.base`, or a house kind such as the events an operation raises) with nothing in the model reads `none`, as one read from the code does, so a finding never says "model ``".
- **A field's attributes are read, as a property's are.** eShop's Ordering.Domain is nullable-disabled and marks its backing fields `[Required]`, which EF's nullability rule reads from the member. Without the field's attributes, every required backing field read as nullable.
- **A reader that compares a value itself says so (`ClaimReading.Compared`, with `ClaimContext.TypeMatches`).** A type can't be compared as text: `Order` in the model is `Ok<Order>` under `Task<Results<...>>` in a Minimal API handler.
- **Members include inherited ones (`CodeGraph.Bases`, `MembersOf`).** A base type is found by name among the in-scope types; with several, the one in the type's namespace or an enclosing one. eShop's entities inherit `Id` from SeedWork's `Entity`.
- **A Command or Query is the class or record of its name**, like a DTO. Only its type is claimed so far; its fields aren't.
- **`type.base` is built as the spec's claim catalog has it (a set, compared `subset`), ahead of its phase 2 cases, because eShopCustom's SeedWork needs it.** `CodeGraph.Supertypes` gives an in-scope base by its qualified name, and its own bases in turn, and a library base by its name as written and its bare name, without generic arguments. So a house pack names its own SeedWork types qualified (`eShop.Ordering.Domain.Seedwork.Entity`), and a same-named base that isn't declared in scope doesn't match. The expression language has the spec's association forms for the vocabulary that states it: `associations('Generalization')`, `it`, and an end's `isSource`, `isTarget`, `otherEnd`, `association`, `multiplicity` (`1`, `0..1`, `*`, `1..*`), `isNavigable` and `element`, plus number literals (`count(...) == 0`). `type.marker`, which needs the spec's discriminator, isn't built; a house extension states its markers as its own kinds meanwhile (eShopCustom's `seedwork.aggregateRoot`).
- **The RDBMS Primary Key's Data source and the Index stereotype on an attribute are claimed (`column.valueGeneration`, and `index.columns`/`index.unique` for an index with no UniqueKey).** User supplied is `ValueGeneratedNever()` or `[DatabaseGenerated(None)]`, Auto-generated a call that generates it (`ValueGeneratedOnAdd`, `UseIdentityColumn`, `UseHiLo`, `UseSequence`) or `[DatabaseGenerated(Identity)]`; Default states nothing. An attribute's index is found by its column, as an Index element's is. Both were stock stereotypes eShop.Ordering's model uses that no claim covered, so they went unchecked.
- **Any designer can carry claims, the Codebase Structure included**, and a pack's vocabulary can name the Area its findings go in (`"area"`), so a module's Layers report in `Architecture (DriftEngine)`, not `Codebase Structure (DriftEngine)`. An existence kind an extension reads reports a miss with `ClaimReading.Missing(where, searched)`, and a claim reader can ask the scope whether code it didn't find is there but out of scope (`ClaimContext.Scope`).
- **A Service or Service Proxy is the class or interface of its name; an Operation is its method.** basislink5's Services model both controllers (`FuturesController`) and business classes (`Bid`). `operation.parameters` is the spec's list of `name: type`, so a changed parameter type is one finding on the operation; `parameter.type` stays unbuilt until its phase 2 cases. The profile's `injectedParameters` (`CancellationToken`) are never part of a signature. Overloads with the same parameter names are told apart by type (`Update(BidsDTO bid)` beside `Update(bids bid)`).
- **Of several types with an element's name, the one whose namespace ends with the element's designer folders is it.** Intent's convention is folders become namespaces; basislink5 has a Domain `ReportListUser` (folder `Entities`) and a Services one (folder `BusinessObject/Reports`).
- **`intent.aspnetcore` reads attribute routing** (`[Route]`, `[Http*]` templates and the `[controller]` and `[action]` tokens) **and Minimal APIs** (`Stacks/AspNetCore/MinimalApis`). Routes compare case-insensitively without slashes or constraints. A Minimal API router is the static class whose method maps handlers with `MapGet`/`MapPost`/... on a method group, so a Service is its router and an Operation its handler. A `MapGroup` prefix is the service's route, followed through a local variable's initializer chain. `RequireAuthorization`/`AllowAnonymous` count on the endpoint, the group, or a call chained on the router's mapping method anywhere (`orders.MapOrdersApiV1().RequireAuthorization()` in Program.cs). A handler's return type is its `Results<...>`'s success result's `T`, under `Task`. Its parameters exclude what the framework injects: `[FromServices]`, framework types (`CancellationToken`, `HttpContext`, ...), interfaces, DbContexts, and `[AsParameters]` holders with any service property. Why: eShop.Ordering, the first Services model on eShopCustom, is Minimal APIs.
- **A navigable association end is a member of the element at its other end** (`IAssociationEnd.OtherEnd()`), reached through `AssociatedElements`. `member.nullable` is claimed for single ends only: a collection end's nullable is its multiplicity, not C# nullability.
- **`intent.efcore` reads EF Core's fluent configuration and data annotations from syntax (`Stacks/EfCore/EfCoreReader`).** `modelBuilder.Entity<T>(e => ...)` and `IEntityTypeConfiguration<T>.Configure(builder)` bodies are read as call chains on the builder: a chain starting `Property(e => e.X)` or `Property("_x")` configures that property, the rest (`ToTable`, `HasKey`, `HasOne`) the entity. A call names members by its lambdas, or by its strings when every argument is a string (`HasForeignKey("_cardTypeId")`; `HasIndex(e => e.A, "IX_A")` names an index). A configuration is a type's when the names match and the configuring file reaches the type's namespace, through its own or its project's global usings, so eShop's Services `Order` view model isn't the `Order` entity.
- **An EF Core shadow property is the entity's member (2026-11-13).** `Property<int>("BuyerId")`, with no member of that name on the class, answers the attribute's `member.exists`, typed by the call, so its type, nullability and column claims read it. eShop.Ordering's `PaymentMethod.BuyerId` and `OrderItem.OrderId` are modelled this way. It is explicit code, so it isn't a convention. eShopCustom's own Domain check accepted one only for a foreign key; the engine accepts any, since the call states the property whatever it is for.
- **The EF Core reading is public (`EfCoreModel`, `EntityConfig`, `FluentCall`)**, so a house extension checks its own stereotypes against the same configuration (`code.Get<EfCoreModel>()?.Of(type, code)`) instead of reading it again. eShopCustom's Backing Field reads `Property("_field")` and `HasColumnName` from it.
- **A stated value is only what the code states explicitly (user decision, 2026-11-12).** A Table Name with no `ToTable` is drift even when EF's DbSet-name convention gives the same table: basislink5's three WebCommonDBContext entities report exactly that. The one exception is nullability, where the code always states something: outside a nullable context `IsRequired()`, `[Required]` or `HasKey` make a column required and silence leaves a reference type optional (EF Core's rule), so `member.nullable` gains this second rule from `intent.efcore` (spec decision 13) and only for mapped entities. Association ends are left to their foreign keys.
- **The model's EF values are compared as Intent's EF Core module writes them.** A Default Constraint Value may be quoted or not (its `EscapeHelper` accepts both), so `column.default` compares unquoted; a value default reads as the C# literal written, a SQL default as the string's content. A Column Type compares without case or spaces (`decimal(18, 4)`), and a text column's facets state its store type too: `HasMaxLength(1).IsUnicode(false).IsFixedLength()` is `char(1)`. Precision and scale come from `HasPrecision` or a `decimal(p, s)` column type.
- **A foreign key is read by EF Core's convention too, for the same reason (2026-11-13).** The Domain designer always marks an association's foreign key, so it can't leave a conventional one unstated either. eShop's `PaymentMethod.BuyerId` and `OrderItem.OrderId` are shadow properties EF links to `Buyer.PaymentMethods` and `Order.OrderItems` by name, with no `HasForeignKey`. Reading only explicit code reported both on the code the model was drawn from, which can't be drift (user, 2026-11-13: a finding on an unchanged adoption baseline is an engine or model bug). With no `HasForeignKey` or `[ForeignKey]` on the relationship the model names, the dependent's property named after the dependent's navigation or the principal type, followed by the principal's key or `Id`, is its foreign key. An `Ignore` on the navigation, or a `HasForeignKey` naming another property, is drift as before.
- **A key is an EF Core convention the engine reads (2026-11-13).** The Domain designer always marks an entity's key with Primary Key, so unlike a Table Name the model can't leave a conventional key unstated. With no `HasKey`, `[Key]` or `[PrimaryKey]`, the code's key is EF Core's: a single property named `Id` or `<Entity>Id`. basislink5's scaffolder leaves `HasKey` out for 32 such entities. `table.key` is a set: EF orders a composite key by `HasKey`, the model by its attributes.
- **A Foreign Key states its navigation:** its `Association` property gives the association end, so `column.foreignKey` compares the navigation's name. It is read from the entity's own `HasOne(d => d.Nav)...HasForeignKey(d => d.Fk)` chain, the principal's `WithOne(d => d.Nav).HasForeignKey(...)`, or `[ForeignKey]`. `EntityConfig.Chains` keeps each chain whole for this.
- **The expression language has the spec's `where`, `map`, `join` and `count`, and an element-valued stereotype property gives the element.** Inside `where` and `map`, the item is self: `join(map(where(children('Attribute'), hasStereotype('Primary Key')), name), ', ')`.
- **File Config is checked as `type.file` and `type.namespace` (core kinds, stated when set).** `Filename` is the file holding the type, without extension; basislink5 keeps several DTOs and its enums in one file each (`UserManagementDTO.cs`, `Enums.cs`). `No Namespace` isn't claimed yet.
- **An EF index is found by its name (`HasIndex(..., "IX_...")` or `HasDatabaseName`), else by its columns.** `index.columns` compares in order, as a composite index's column order matters to the database.
- **A parameter source is stated only by its binding attribute (user decision, 2026-11-13).** `[FromBody]`, `[FromRoute]`, `[FromQuery]`, `[FromHeader]` or `[FromForm]`; ASP.NET's inference from the route template or the parameter's type isn't read, as with a Table Name. basislink5 reports 93 `From Route` and 12 `From Body` parameters without one, until their model Source is Default or the attribute is added. Kept by the user on eShop, the same day, over reading ASP.NET's inference: its 5 such parameters were drawn as From Body or From Route by the adopting AI, which was a modelling error, and are now Default. So a model drawn from code says Default wherever the code has no binding attribute. With Default the engine makes no claim, so a later change to how such a parameter binds isn't the engine's to catch. eShopCustom's Services module, which reads ASP.NET's inference, still catches it: a planted `[FromQuery]` on `CancelOrderAsync.command` was caught by it, not by the engine.
- **The ASP.NET Core extension reads ASP.NET Core's own `[Authorize]` and `[AllowAnonymous]` only (user decision, 2026-11-13).** A custom authorization filter, like basislink5's `[Authorization]`, belongs in a house extension (spec open question 3, where house packs live); until one exists its 24 Secured services and operations report. Roles come from `[Authorize(Roles = "...")]` and compare as a set.
- **Every stock pack and extension runs until the `Drift Check` stereotype chooses them (not built yet).** One whose designer isn't installed makes no claims, and a framework's extension with its framework absent reads nothing.
- **`Drift Scope` targets the Root Folder and Folders only (spec decision 27).** The Visual Studio project types made Module Builder generate accessors that need Intent.VisualStudio.Projects, which a Java codebase doesn't have.
- **An item list reaches the engine as `IStereotypeProperty<IStereotype[]>`, one stereotype per row.** Its `Value` text isn't the rows. Multi-line text properties (`Glob`, `Types`) hold one value per line. The suite's fixture builder hands item lists over the same way, so the engine reads one shape.

## Invariants

- The engine never writes to the codebase; checks prove it on real codebases with `git status` before and after (`Real/RealStructureRunTests`).
- A client's code, model export and results stay on the machine that ran them. Committed files carry counts only.
