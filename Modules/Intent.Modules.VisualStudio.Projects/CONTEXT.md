# Context: Intent.VisualStudio.Projects

## Purpose

This module generates the Visual Studio solution and project layout (`.sln`/`.slnx`, `.csproj`, `Directory.Packages.props`, `appsettings.json`, `launchSettings.json`, etc.) from the Codebase Structure designer. It owns NuGet package installation into `.csproj` files and Central Package Management (CPM) for a solution.

## Architectural Decisions

- **`Central Package Floating Versions Enabled` is modelled on the `Visual Studio Solution Options` stereotype (per-solution), not as a module setting.** `Manage Package Versions Centrally` already lives there, and a single application's Codebase Structure designer can hold more than one Visual Studio Solution. An application-level module setting could not express "floating on for this solution, off for that one" — it would apply uniformly across every solution in the application.

- **The property is written in `DirectoryPackagesPropsTemplatePartial`'s constructor, not in `SdkSchemeProcessor` (the NuGet factory extension).** The constructor already builds the `ProjectRootElement` that `RunTemplate()` returns, and it already reads `ManagePackageVersionsCentrally()` the same way. Writing the flag there means it always appears when the file is generated, regardless of whether any package happens to change that run — tying it to `SdkSchemeProcessor`'s per-package loop would leave it unset on a run where nothing about package versions actually changed.

- **Unchecking the property leaves an existing `true` value in place; it is never written back to `false`.** `Directory.Packages.props` is `UserControlledWeave` and is seeded from the file already on disk, so a hand-written `CentralPackageFloatingVersionsEnabled` can already be sitting there when this module runs. Writing `false` on an unchecked box would silently revert that on the very next Software Factory run after a developer upgrades to a version of this module carrying the property — so `ApplyFloatingVersionsProperty()` is only ever called when the box is checked, and it only ever sets the value to `"true"`.

- **An existing `launchSettings.json` is merged as a JSON tree (`JObject`), never round-tripped through the typed `LaunchSettings` classes** (see `Templates/LaunchSettings/LaunchSettingsMerger.cs`). The typed round-trip dropped unknown members (`$schema`), reordered properties into C# declaration order, normalised `commandName` casing and rewrote formatting and the trailing newline, so every run produced a diff. `CommandNameConverter` also throws on an unrecognised `commandName`, which crashed the Software Factory. Rejected: adding `[JsonExtensionData]` to the typed classes (keeps unknown members but still reorders properties and normalises enum values); patching the raw text (fragile).

- **Merging is add-only.** A registered profile is appended only when no profile of that name exists. A same-named profile is left untouched even if it lacks fields we would generate, because re-adding fields a developer deliberately removed is worse than an incomplete profile. Environment variables are only added, never overwritten. The HTTP URL for `LaunchProfileHttpPortRequired` is only appended to an `applicationUrl` that has an `https://` entry and no `http://` entry.

- **`launchUrl` on `*.Api` profiles is only kept in sync when it points at an Intent-managed default path** (`swagger` or `scalar/v1`, held in `IntentManagedLaunchUrlPaths`). Swapping Swashbuckle for Scalar therefore still updates it, but a custom `launchUrl` is never touched. Rejected: never updating an existing `launchUrl` (leaves `swagger` behind after switching to Scalar); always rewriting it, which was the previous behaviour and overwrote custom URLs (and threw on a null or relative value).

- **A new file still goes through the typed model**: defaults → `JObject` → the same add-only rules → `ToObject<LaunchSettings>()` → `ToJson()`. One set of rules serves both paths, while ending on the typed serializer keeps a new file byte-identical to what was generated before (e.g. `environmentVariables` stays ahead of `workingDirectory`). Existing `Tests/**/launchSettings.json` outputs therefore don't churn.

- **Sync steps read what is on disk first, and write only what the model can represent and has actually changed.** Driven by the dotnet/eShop brownfield adoption, where each defect was a sync step overwriting something the model can't express or didn't change. The model stays authoritative for everything it _can_ represent: what's on disk only shapes details the model has no setting for (indentation, a builder line), and never overrides a modelled setting. Applied in:
  - `SdkAttributeSync`: an existing `Sdk` whose name isn't one of the `.NET Settings` SDK options (`Uno.Sdk`, `Microsoft.Build.NoTargets/3.7.0`) is never rewritten. A representable one always follows the model, so `MSTest.Sdk` modelled as `Microsoft.NET.Sdk` _is_ rewritten. Rejected: a free-text or `(unspecified)` SDK option (the user chose an explicit `MSTest.Sdk` option instead).
  - `TargetFrameworksSync`: see the invariant below. Rejected for now: modelling platform TFMs.
  - `AppSettingsTemplate.UpdateExistingFile`: same no-op/format-preserving contract as `LaunchSettingsMerger`, via the shared `JsonFileFormatting`.
  - `SlnxMerger.NormalizePath`: `./src/X/X.csproj` and `src/X/X.csproj` are the same entry. `CSharpProjectNETModel.GetRelativeLocation()` keeps its `.` seed, because it also feeds `ProjectConfig`'s output path, and the classic `.sln` template emits `.\` deliberately. Only the `.slnx` side normalises. An existing `./`-prefixed entry is matched and kept as written, not rewritten, since rewriting it would be exactly the churn being removed.

- **`Generate AppSettings File` / `Generate LaunchSettings File` registers a host project's template in one of two modes rather than not at all.** For Web, Worker and Blazor WASM projects, flag off means _hands-off_: the template is still registered, `CanRunTemplate()` is true only when the file exists, and `RunTemplate()` returns it unchanged. A registered template whose output equals the file on disk is what stops the Software Factory both rewriting it and proposing to delete it. Not registering at all would leave a previously generated file looking orphaned. Hands-off also keeps claiming `AppSettingRegistrationRequest`s (`MarkHandled`) and drops them, with one SF info line, so they can't fall through to another project's file. Hands-off covers the file's `.csproj` items too: the template sets the module-internal `FileAddedData.LeaveProjectItemsUnchangedKey` file metadata and the project sync then neither adds nor removes the file's items. Rejected: just omitting the item-type metadata in hands-off mode. The sync reads "no metadata" as "remove the item", so a Worker switched from managed to hands-off lost its `<Content Include>` and stopped copying `appsettings.json`. Keeping the managed metadata instead would add `Content` items to a brownfield Worker. A plain `Microsoft.NET.Sdk` project keeps the old rule (registered only when on), because a hands-off template there would swallow settings that class libraries rely on flowing to their host. The legacy `ASP.NET Core Web Application` element stays unconditional.

- **Existing host projects keep their behaviour through migrations; after that the flags are the user's.** `MigrationHelper.ApplyGenerateSettingsDefaults` sets both flags to true on every Web, Worker and Blazor WASM project, from the `4.1.11-pre.0` version migration (existing apps) and `OnInstallMigration` (apps installing the module, e.g. seeded from an architecture template). Nothing infers defaults in the designer afterwards: a host project added later starts with the stored default (off), and the user ticks the flags. Rejected: a `.NET Settings` On Changed script with an element-metadata marker to default the flags whenever the SDK became a host SDK. It was removed as an unconventional way to manage a setting's value, and it flipped marker-less projects (e.g. apps already on 4.1.11-pre.0) back to on at their first `.NET Settings` edit.

- **The Worker `Program.cs` adapts to an existing file's builder line and run call only.** `ExistingProgramShape` reads the file (through `ExecutionContext.FileSystem`, because `TryGetExistingFileContent` needs `FileMetadata`, which isn't configured until after the constructor). When it finds exactly one `builder` declaration from `WebApplication.CreateBuilder` or `Host.CreateApplicationBuilder`, one `var app = builder.Build();` and one `app.Run();` / `await app.RunAsync();`, the template re-emits those verbatim, so Merge mode adds nothing that duplicates them. `RunAsync` makes a generated `Main` `async Task`. Any other shape is `Unrecognised`: the file is generated `OnceOff` (left untouched) with a warning, because merging into an unknown shape is how duplicate `Run` calls happen. Statement style (top-level vs `Main`) is _never_ detected: it stays with the modelled `Use top-level statements`, and brownfield setup sets that to match the file. Rejected: detecting it from the file, because on-disk detection must never override a modelled setting.

- **A top-level `Program.cs` only gets `using <project namespace>;` when a generated type in the same project is declared in that namespace or under it.** The using stands in for the enclosing namespace a `Main` method's class would have. A brownfield project's code can live under a different root than its name (eShop's `OrderProcessor` project uses `eShop.OrderProcessor.*`), and an unconditional `using OrderProcessor;` failed to compile with CS0246. The check runs in an `OnBuild` callback, once every template is registered. Hand-written types aren't visible to it, which only drops a using that no generated statement needs. Rejected: never adding it, which could break greenfield top-level Workers whose generated statements reference root-namespace types by name. `Intent.AspNetCore`'s `ProgramTemplate` still adds the using unconditionally.

- **`Generate Program File` is the Worker template's on/off switch, and off means hands-off, not unregistered.** It's on `.NET Settings`, shown only for `Microsoft.NET.Sdk.Worker` (the only SDK `ServiceWorkerProgramTemplateRegistration` registers for). That template is a hand-written `ITemplateRegistration`, not a modelled File Template, so it has no Template Output to place or remove in the Codebase Structure designer and this flag is the only control. Off: the template is still registered, `CanRunTemplate()` is true only when `Program.cs` exists, and the file is `OnceOff` (the same mechanism as an `Unrecognised` shape), so it's never created or rewritten and never proposed for deletion. Staying registered also keeps `IProgramTemplate` / `IAppStartupTemplate` lookups by other modules (Windows Service hosting, Quartz, messaging hosted services...) from failing; what they add is dropped, with one SF info line per project. Serilog isn't one of them: its startup configuration skips projects that aren't `Microsoft.NET.Sdk.Web`, and the Worker template doesn't carry the `App.Program` role its program-structure step looks for. The `Logging:EventLog:*` appsettings are skipped too, as they configure logging that only the generated file sets up.

- **Nothing is added to a project on a hands-off template's account: no packages, assembly, framework or project references, its own or what other modules attach to it.** All three dependency collectors read every registered template on the output target without checking `CanRunTemplate()`: `NugetDependencyResolutionFactoryExtensions` (NuGet and assembly references, at `BeforeTemplateExecution`), `FrameworkDependencyResolutionFactoryExtensions` and `ProjectDependencyResolutionFactoryExtensions` (both at `AfterTemplateExecution`). So each one filters with `ExceptHandsOff()` (`Templates/HandsOffTemplates.cs`), which drops any template implementing the module-internal `IHandsOffTemplate` whose `IsHandsOff` is true. `ServiceWorkerProgramTemplate` implements it from `Generate Program File`. That covers every attacher and timing at once: packages added in another module's constructor or `AfterTemplateRegistration` (e.g. `Intent.WindowsServiceHost`'s `Microsoft.Extensions.Hosting.WindowsServices`, `DependencyInjection` and `Configuration.Binder`), and template dependencies recorded by `GetTypeName` in `OnBuild`. The template therefore requests `Microsoft.Extensions.Hosting` unconditionally; the filter is the one mechanism. Hands-off also sets `FileAddedData.LeaveProjectItemsUnchangedKey`, like the AppSettings/LaunchSettings hands-off templates.
  - Why: a hands-off `Program.cs` belongs to a brownfield project that already references what it uses. An earlier draft only stopped the template's own Hosting, which also stopped it masking `DependencyInjection` and `Configuration.Binder` through NuGet consolidation, so the project gained two packages instead of losing one.
  - Not every package that appeared alongside is the Program template's. In a Worker that also hosts `Intent.Application.DependencyInjection`'s `DependencyInjection.cs`, that template requests `DependencyInjection`, `Configuration.Abstractions` and `Configuration.Binder` itself, so a hands-off Worker still gets `DependencyInjection` and `Configuration.Binder` (Abstractions consolidates under Binder). They're that file's own requests, so the filter rightly leaves them. Previously `Hosting` (on, or attached via `Hosting.WindowsServices`) absorbed them by consolidation, which is why they never showed.
  - Accepted cost: in a brownfield Worker that already references `Microsoft.Extensions.Hosting`, those become redundant direct references, possibly at a newer version than the project's own Hosting (`NugetPackages` maps net8 to 10.0.9). The NuGet installer prunes transitive packages only against what is _requested_ in the run, not against what is already installed. That holds for any generated file in any brownfield project, not just hands-off Workers. Rejected: passing a hands-off template's requests to the installer as prune-only hints. It changes shared install behaviour for every project to remove a redundant but working reference.
  - Accepted: a module that parks a package on the Program template which its other generated file in the same project also uses (e.g. `WindowsBackgroundService.cs` and `BackgroundService`, which reached the project through `Hosting.WindowsServices`) no longer gets it hands-off. A Worker whose own `Program.cs` builds a host already references hosting, and Intent never removes a package already in the `.csproj`.
  - Rejected: overriding `GetNugetDependencies()` / `GetTemplateDependencies()` on the template. It works only because `GetAllNuGetInstalls` reads the virtual method for generic `CSharpTemplateBase<T>` subclasses (a type check in `Intent.Modules.Common.CSharp` that could change), and framework and assembly dependencies aren't virtual at all. Rejected: removing them late, in a lifecycle hook. Every hook late enough (`OnBuild`, `BeforeTemplateExecution` on the template) only runs when `CanRunTemplate()` is true, so it misses the no-`Program.cs` case. Rejected: guarding each `AddNugetDependency` in the template (an earlier draft); it can't reach what other modules attach.
  - `Intent.RoslynWeaver.Attributes` isn't requested by this module at all: `Intent.OutputManager.RoslynWeaver` adds it to any project with a template whose `FileMetadata.CodeGenType` is `RoslynWeaver`, whether or not it runs, and the filter doesn't reach it. Hands-off, `GetTemplateFileConfig()` therefore returns a copy of the `CSharpFile` config that reports `Basic` (`GetFileConfig`). That's safe because a hands-off file is never written: absent, it doesn't run, and present, it's `OnceOff`. Rejected: fixing the RoslynWeaver module to skip templates that can't run. It's another repository, and with `Program.cs` present the template does run (as `OnceOff`), so it wouldn't help that case.
  - A new hands-off template elsewhere in this module only needs to implement `IHandsOffTemplate` to get the same treatment.

- **`Generate Program File` defaults to on, and a missing value also means on, so no migration is needed.** The AppSettings/LaunchSettings flags default off because they also apply to plain `Microsoft.NET.Sdk` class libraries; this one is only visible on Worker projects, which always got `Program.cs`. A project saved before the property existed has no value for it, so the template reads it with `GetProperty("Generate Program File", true)` (`ServiceWorkerProgramTemplate.IsHandsOff`), and only an explicit `false` is hands-off. The generated `GenerateProgramFile()` accessor isn't used, because it reads a missing value as `false`, which would silently make existing Workers hands-off. Rejected: a version migration plus `OnInstallMigration` writing `true` for Workers lacking the value. It only runs once, so a Worker merged in later from a branch still on an older module version (after the migration had run) would be missing the value and stop getting `Program.cs`.

- **The Worker template is in Merge mode (`IntentManagedMerge()`) by default.** Previously generated files get a one-line `Mode.Fully` → `Mode.Merge` change. Accepted consequences: uninstalling a module removes its generated _statements_ (RoslynWeaver 4.7.0+) but can leave its `using` lines.

- **The Worker's `Logging:EventLog:*` settings go through `AppSettingsTemplate.AddSetting`, not `ApplyAppSetting`.** An `AppSettingRegistrationRequest` without a role is claimed by _every_ host project's appsettings template, so those settings leaked into all of them. `AddSetting` targets the Worker project's own base (no runtime environment) instance, found with `FindTemplateInstances` from the `AddClass` callback, by which point every template is registered.

- **Every `.csproj` item sort goes through `XmlItemSorter`, which sorts units, not elements.** A unit is an element plus its leading comments (all comments since the previous element) and its same-line trailing comments. The whitespace between units stays put, so layout doesn't change, and an already-ordered container is left untouched (`false`). It serves `SdkSchemeProcessor`, `NetFrameworkPackageReferencesSchemeProcessor` and `VisualStudioProjectTemplateBase.SyncUsings`. Before this, the SDK sort moved only MSBuild `ProjectElement`s, bunching comments at the top of the group on every run. The .NET Framework sort did the same through `XElement.Elements()`. `SyncUsings` used `RemoveAll()`, which deleted comments and the `ItemGroup`'s attributes.

- **The SDK sort runs on `project.RawXml`, not through `ProjectRootElement`.** MSBuild's construction model only exposes elements, so it can't move a comment. Package add, remove and version edits still go through MSBuild. Only the final sort re-parses the XML with `PreserveWhitespace`. If anything moved, the sort writes the result back with the XML declaration and the original file's newline style. Otherwise it returns `RawXml` unchanged.

- **`AddItem` places a new item next to an existing sibling, which can land it between that sibling and its comment.** A new item can't have comments of its own. So `SdkSchemeProcessor` passes the items added in this run to `XmlItemSorter.SortChildren` (`added`). The sorter detaches them, appends them after the last existing unit with that unit's indent, and sorts them like the rest. That also covers a group that holds other items and so isn't sorted: it gets the same placement with an unchanged order. If the result is text-identical to MSBuild's placement, it reports no change. Rejected: repairing each new item where `AddItem` put it (the first version, `MoveOutsideComments`). Several packages installed in one run all go next to the same sibling, so only the last of them was next to the comment and got moved, and the one before it took the comment over. Module installs usually add several packages at once.

- **Removing a package keeps the comment above it, and an `ItemGroup` that still holds comments isn't removed** (`HasComments` in the SDK processor, the `XComment` check in the .NET Framework one). User-written text is never deleted.

## Invariants & Constraints

- **Sort keys use the default (culture-sensitive) string comparison, as `OrderBy` did before.** Changing to ordinal would sort upper case before lower case (`xunit` after every `Microsoft.*`) and reorder existing files on the next run.

- **Same-line trailing comments only stay on their line where whitespace is preserved.** That is the SDK `PackageReference` path. The .NET Framework processor and the `.csproj` template's settings sync (which includes `<Using>`) parse without whitespace and re-indent the whole file whenever they change anything. There, a same-line comment still moves with its element but lands on its own line beneath it. The unit is found from line info (`LoadOptions.SetLineInfo`), assuming a multi-line element closes on the line after its last child. Making those paths preserve whitespace would change how every rewrite of those files is formatted, so it was deferred.

- **`TargetFrameworksSync` only rewrites a single, unconditional, plain-moniker value whose set differs from the model.** Multiple `TargetFramework(s)` elements, a `Condition` on the element or its `PropertyGroup`, or a `$(` reference: untouched. Equal as a set, raw or after reducing `net10.0-android` to `net10.0`: untouched, so order (the first TFM is the IDE's default target) and platform suffixes survive. Platform-suffixed values with a different base set: untouched, with a warning, because rewriting them would mean guessing per-platform version suffixes (`windows10.0.19041.0`). So changing a MAUI project's framework in the model is a manual `.csproj` edit.

- **`AppSettingsTemplate` consults `.editorconfig` only for a brand-new file.** An existing file's indentation and newlines are detected from the file itself. Only the `[*]` section and sections whose glob matches the file apply; previously every `indent_size` in the file applied and the last one won, so eShop's `[*.{cs,...}] indent_size = 4` re-indented its JSON.

- **The project sync never leaves a file's `Remove` item behind when it drops that file's re-include.** `CoreProjectSyncProcessor` removes a file's item when its template requests no item settings. A same-type `Remove` + `Include` pair is the shape written for `RemoveItemType`, so both go together (and an emptied `ItemGroup` with them), restoring the SDK's default globbing. Previously only the `Include` went, which excluded the file entirely. A `Remove` with no matching re-include is a deliberate exclusion by the developer and is kept.

- **`HasLaunchSettings` now requires `Generate LaunchSettings File` for every SDK.** The `3.9.2-pre.0` migration's call to `ApplyLaunchSettingsStereotype` therefore skips host projects for an app upgrading from before it, since the flags aren't set yet at that point. The `4.1.11-pre.0` migration repeats the call after setting them. Note that `ApplyLaunchSettingsStereotype` only saves the package when `setValue` is true.

- **This flag makes floating versions legal to NuGet; it does not change how this module resolves versions.** `SdkSchemeProcessor` (see `FactoryExtensions/NuGet/SchemeProcessors/SdkSchemeProcessor.cs`) still rewrites a `PackageVersion` entry to a pinned version whenever an installed module requests that same package, because `VersionInfo.Version` reads a floating range's `MinVersion` and compares it against the requested version like any other pin. A floating entry only survives untouched when no installed module requests that package. The one way to also protect a module-requested package's float is the _Dependency Version Overwrite Behavior_ module setting (from `Intent.ModuleBuilder`) set to `Never` — its `Never` branch only writes a version when the `PackageVersion` entry is entirely absent.

- **`ApplyFloatingVersionsProperty()` must stay idempotent.** It looks for an existing `CentralPackageFloatingVersionsEnabled` property (case-insensitive) before adding one, and re-sets its value rather than appending a duplicate `<PropertyGroup>` element. A second Software Factory run against the same file must not accumulate elements.

- **Stereotype property definitions have no ordering API.** `IStereotypePropertyDefinitionApi` (see `core.context.types.d.ts`) exposes no `setOrder`/`moveTo` — a new property added via `def.addProperty(...)` is always appended after every existing property. When adding `Central Package Floating Versions Enabled`, it therefore landed after `Solution File Format` rather than immediately next to `Manage Package Versions Centrally` as originally intended; there was no way to reorder it without deleting and recreating the surrounding properties (which would change their ids and risk existing applications' persisted values). Accepted as a cosmetic deviation — the two CPM properties are still adjacent in the stereotype's own description text and in `docs/README.md`, just not in designer property-pane order.

- **When there is nothing to add, `LaunchSettingsMerger.Merge` must return the original string.** It compares the merged tree with the original (`JToken.DeepEquals`) and only re-serializes on a real change. The "no diff" guarantee depends on this; never re-serialize unconditionally. When a change does need writing, the indent character and width, newline style, and leading/trailing whitespace are taken from the existing file. JSON comments are lost on a write, since `JObject` can't hold them inside objects.

- **Every read of an existing `launchSettings.json` goes through `LaunchSettingsMerger.Parse`, never `LaunchSettings.FromJson`.** That includes `BeforeTemplateExecution()`, which reads the `applicationUrl` and `iisExpress` ports. `Parse` turns off date parsing and parses floats as decimals, so date-like strings and values such as `1.50` survive a rewrite exactly as written.

- **`GetDefaultLaunchSettings()` is only called when no file exists.** It is passed to the merger as a `Func`, because `ReplacePorts()` mutates the registered `Profile` instances.

## Module Interactions

- **`Intent.ModuleBuilder`** — its _Dependency Version Overwrite Behavior_ module setting interacts with the limitation above: setting it to `Never` is the only way to also preserve a module-requested package's float, since this module's own NuGet resolution otherwise always wins when a module requests the same package.

- **`Intent.AspNetCore.Swashbuckle` / `Intent.AspNetCore.Scalar`** — publish `DefaultLaunchUrlPathRequest` with `swagger` / `scalar/v1`. A module that publishes a new default path must also have it added to `LaunchSettingsMerger.IntentManagedLaunchUrlPaths`, otherwise a later swap away from it won't update existing `launchUrl` values.

- **`Intent.AspNetCore` (when _Enable HTTPS Redirect_ is off) and `Intent.Dapr.AspNetCore`** publish `LaunchProfileHttpPortRequired`. **`Intent.AspNetCore.Docker`, `Intent.Aws.Lambda.Functions` and `Intent.Blazor`** publish `LaunchProfileRegistrationRequest`. Their profiles are appended to an existing file only when it lacks a profile with that name.

- **`Intent.Modelers.CodebaseStructure`** — `CSharpProjectNETModel` and `SolutionFolderModel` implement `IAllowsCustomFileClassificationModel` from `Intent.Modules.Modelers.CodebaseStructure.Api`, which arrived in 1.1.0, so the `.imodspec` floor stays at 1.1.0 (the metadata-only install). The `.csproj` `PackageReference` is 1.1.2 on purpose, not to match. The `intentarchitect-feed` DevOps feed that CI restores from holds its own `1.1.0`, an early build without that namespace, which shadows nuget.org's `1.1.0` and failed the CI build with CS0234/CS0246. The feed's 1.1.1 and 1.1.2 are complete, and their dependencies match 1.1.0's. Don't lower the reference to 1.1.0 while that feed copy exists. Rejected: 1.2.0, which needs `Intent.Architect.Persistence` 3.7.4 against this project's 3.7.0 (an NU1605 downgrade).
