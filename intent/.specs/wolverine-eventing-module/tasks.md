# Implementation Plan — Wolverine Eventing Module

Translated from the design's **Realization plan** table and its **Modelling order and build order** graph. Three
things about this plan are unusual and deliberate, all inherited from the design:

- **Waves 1 and 2 are a hard gate.** They contain no module artefact at all. R17.5 and R17.6 make green Reference
  Solution tests the precondition for building anything, and R16.5 makes the Reference Solution the thing that never
  bends. If a wave-2 test cannot be made green, the Reference Solution is revised and re-verified — module work does
  not start around it.
- **`[model]` means the Module Builder designer**, never a Domain or Services model of a business application. R1.1
  forbids introducing a designer or a message element type, so the Services designer is read-only everywhere except
  the Reference Solution pair (T0.2) and the Test Applications, which model their own messages as ordinary consumers.
- **`[code]` means a template partial body or a factory-extension override body.** The Module Builder generates every
  file shell — template registration classes, `[IntentManaged(Mode.Fully)]` partials, `Api/*StereotypeExtensions.cs`
  accessors, `NugetPackages.cs` — and those are never hand-edited. Within a wave the sequence is model change,
  Software Factory run against the module application, then bodies.

- [ ] T4. Publishing, sending, consuming, and provider filtering
  - [ ] T4.1 [model] (satisfies: R5.1) — Model the Consumer template
    - C# File Builder template `IntegrationEventConsumer`, **one instance per subscribed message**, model type Integration Event Handler, role `Infrastructure.Eventing.Consumer`. Mirrors the existing `IntegrationEventConsumer` in `Intent.Modules.Eventing.MassTransit`

  - [ ] T4.2 [code] (satisfies: R3.1, R3.2, R3.3, R3.4, R3.5, R3.6, R3.7) — Write publish-rule generation and destination resolution
    - R3.1: `PublishMessage<T>().To…` per Integration Event, fan-out semantics, explicit — **never** `UseConventionalRouting()`, whose per-message exchange-and-queue pair would make two subscribing applications compute the same queue name and become competing consumers
    - R3.2 / R3.4: kebab-cased message type name when no override; an override used **verbatim**, not kebab-cased or otherwise transformed
    - **Unset and empty are different, and this is load-bearing.** Test for the `Destination` property being **absent** before testing for whitespace: absent means the convention applies and the stereotype's only effect was provider designation (composite mode), whereas a value deliberately typed and then blanked must trip R3.5. Getting this backwards either breaks composite mode or silently swallows a mistake
    - R3.5 / R3.6: `ElementException` carrying the offending element — empty-after-trim stops generation and never substitutes the convention name; over 250 characters stops generation naming the limit. No per-broker character rules; the broker rejects those at runtime
    - R3.7: two events resolving to one destination generate without complaint
  - [ ] T4.3 [code] (satisfies: R4.1, R4.2, R4.3, R4.4, R4.5, R4.6, R4.7) — Write send-rule generation for Integration Commands
    - R4.1: explicit send rules with point-to-point semantics, so exactly one consumer receives each command
    - R4.2 / R4.4: kebab-cased command type name by convention; an override read from the **element** and used verbatim on both the sending and the subscribing side, resolved from the single place it is declared. Reading it from a send association end would let two senders disagree about where one command goes
    - R4.5 / R4.6: the same absent-before-whitespace ordering and the same two `ElementException` validations as T4.2
    - R4.7: commands sharing a queue generate without error — that is how ordering between related commands is achieved
  - [ ] T4.4 [code] (satisfies: R3.1, R5.1) — Write listener generation and the subscriber-queue convention
    - `ListenTo…` per subscription. An event subscriber's queue is `{application-name}-{message-name}` kebab-cased, **not overridable** — the application segment is what keeps fan-out working and Wolverine's own convention cannot include it. An Integration Command's listening queue **is** the owner-declared destination, so it needs nothing
    - Note the accepted limitation to carry into T8.4's documentation: with Broker Topology `externally-owned` a subscriber can only consume from a queue matching this convention. If the platform team names subscriber queues itself, the application starts cleanly and receives nothing — the failure is **silent**, which is why the docs must state it
    - Accepted trade to document: the convention uses the short type name, so two applications with identically-named events in different packages resolve to the same destination
  - [ ] T4.5 [code] (satisfies: R5.1, R5.2, R5.3, R5.4, R5.5, R5.6, R5.7, R1.5) — Write the Consumer body and preserve handler bodies
    - R5.1: receive from the transport, resolve the matching `IIntegrationEventHandler<T>`, invoke with the message and a cancellation token
    - R5.6: let exceptions propagate to the configured Error Handling Policy — never swallow them. R5.2: no business logic in the Consumer
    - R5.3: existing `IIntegrationEventHandler<T>` method bodies stay **byte-for-byte** unchanged on regeneration. R5.4: a missing handler gets a generated class throwing `NotImplementedException` in a mode that preserves the developer's body on later runs

### Why the waves fall here

- **Waves 1–2 come before every module wave** because R17.5, R17.6 and R16.5 say so. They also settle five design assumptions (a1, a2, a8, a9, a11) whose answers change what waves 4–7 build — a2 in particular decides whether the Consumer template needs an explicit registration block.
- **Wave 2 carries the design's "Wave 0b"** (T1.3) rather than a later wave, for the reason the design gives: it answers *is the transport shape uniform?* before wave 4 writes the branch. Discovering it late means templates already written against the RabbitMQ shape.
- **Wave 3 is the shared module before its consumers.** There is no Domain → Services → UI ordering question in this feature, because no application designer is mutated. The ordering that matters is that `Intent.Wolverine.Common`'s contribution point exists before the eventing module contributes to it (T2.10) and before the CQRS module is rewritten onto it (T2.8) — which is why R8 sits here rather than beside the coexistence tests it serves.
- **Waves 4–7 each end with their own generate-and-diff task** (T3.7, T4.7, T5.7, T6.7) rather than deferring all verification to wave 8. A module wave whose output is never generated is a wave that proved nothing — and a green module build proves nothing about NuGet resolution, provider filtering or code-management modes.
- **Wave 8 is the parity phase**, where the direction of correction flips and never flips back. It cannot run earlier than T1.5's Baseline capture, and its no-change results are verified rather than accepted (R16.8).
- **Waves are split on `[code]` volume, not aggregate count** — each holds 5–7 implementation points, since implementation dispatches one coding agent per wave. Wave 3's eleven tasks are mostly `[module]`/`[model]`; its code volume is five.
